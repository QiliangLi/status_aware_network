## 1. TensorCast：这是目前归档里**最贴近你这句话**的工作

8 月 10 日的日报已经把它总结成：

> “TensorCast把权重和KV变成统一服务，让路由与放置可以一起编程。”

日报中进一步指出，它把 KV 生命周期从推理引擎中拆出来，让“**路由与 KV 放置由同一运行层联合决策**”。

我又回到论文里核了一下，它说得比日报摘要还要直接。论文明确提出，一个分布式推理系统需要同时：

- balance instance load；
- preserve KV cache locality；
- migrate request states across instances。

因此必须把 **tensor placement / migration / materialization 与 application-level scheduling 决策联合起来**。([Anonymous View](https://rt.http3.lol/index.php?q=aHR0cHM6Ly9hcnhpdi5vcmcvaHRtbC8yNjA4LjA2MDA3djEjUzYuRjc&utm_source=chatgpt.com))

而且它真的实现了一个 programmable request router。这个 router 周期性观察 instance state，在：

**计算负载均衡**

和

**KV cache locality**

之间联合做决定。

例如：

```text
Instance A
GPU load = 很高
Session X 的 KV = 在 A

Instance B
GPU load = 很低
Session X 的 KV = 不在 B
```

普通 load-aware scheduler：

```text
request X → B
           ↓
        KV miss / remote fetch
```

普通 cache-aware scheduler：

```text
request X → A
           ↓
       保住 KV hit
       但 A 已经过载
```

TensorCast 做的是：

```text
观察：
  compute load(A/B)
  + KV state/location

       ↓ joint policy

迁移 Session X + KV：A → B

       ↓

后续 request X → B
```

这已经不是：

> “计算 scheduler 决定 KV 怎么放”

而是：

> **“KV 在哪里、能否迁移、cache locality 如何”和计算负载一起决定 request 应该去哪里。**

这与你说的“**存储侧状态感知反过来影响计算侧整体调度**”几乎重合。

而且结果并不是只有架构描述。论文的联合策略相对于 load-aware + Mooncake，在高并发多轮 workload 中 median TTFT 最多降低 **93.2%**；论文也观察到联合策略能更好地维持 cache hit rate。([Anonymous View](https://rt.http3.lol/index.php?q=aHR0cHM6Ly9hcnhpdi5vcmcvaHRtbC8yNjA4LjA2MDA3djEjUzYuRjc&utm_source=chatgpt.com))

所以我会把 **TensorCast 直接列为这个方向的第一篇重点文献**。

## 2. Kairos：更有意思，因为它让 **KV 状态直接改变计算位置**

Kairos 是另一种形态，而且从你的研究问题来看可能比单纯 cache-aware routing 更有启发。

日报里已经总结得很明确：

> “排队和KV传输可能占P95 TTFT的77%到98%。Kairos选择绕过传输，把部分Prefill放到Decode节点就地执行。”

最终 P95 TTFT 最多下降 81%。

这里正常的 PD 架构是：

```text
Request
   ↓
Prefill GPU
   ↓
生成 KV
   ↓
搬 KV
   ↓
Decode GPU
```

传统 scheduler 主要观察：

```text
Prefill queue
Decode GPU load
SLO
```

然后决定 P/D 节点。

但是 Kairos 发现：

```text
Prefill计算本身
      只占P95 TTFT一小部分

真正大头
  = queue + KV transfer
```

于是它直接改变**计算侧调度**：

```text
如果：

Prefill queue 很长
+
KV transfer 很贵
+
Decode GPU 还有余量
+
不会破坏 Decode TBT SLO

那么：

      不要
Prefill → transfer KV → Decode

      而是

直接把 Prefill
调度到 Decode GPU 上
```

更关键的是，Kairos 判断一个 Decode 节点是否可以接 Prefill 时，模型里直接用了：

**当前 decode batch size + 当前 KV-cache occupancy + 新增 prefill chunk size**。([Academus](https://academ.us/article/2607.02043/?utm_source=chatgpt.com))

所以：

> **KV-cache occupancy 已经成为计算调度的输入变量。**

这个非常接近你说的“状态感知”。

不过我要给它一个边界：

**Kairos 感知的是 GPU serving runtime 内的 KV occupancy 和 KV transfer 开销，而不是一个独立 KV storage system 的实时状态。**

所以如果你们说的“存储侧”特指：

- LMCache；
- CPU DRAM KV pool；
- SSD KV tier；
- remote KV store；
- 跨节点/跨域 KV Cache；

那 Kairos 是**同一思想的近邻工作**，而不是完全命中。

## 3. AAFLOW+：存储/网络状态甚至决定“还要不要算”

AAFLOW+ 在 8 月 10 日和 17 日两期都出现过。

日报里的总结很关键：

> “AAFLOW+把KV当作分布式对象，按链路条件选择传输还是重算。”

它会根据 KV 大小、带宽、时延比较：

```text
已有 KV
   │
   ├─ transfer KV ─────────→ 使用
   │
   └─ local recompute ─────→ 重新 Prefill
```

调度器实际上是在比较：

```text
Cost(KV transfer)
vs.
Cost(Prefill recomputation)
```

10Gbps 条件下，日报记录的 8 个场景里甚至有 **5 个重算更便宜**。

原论文也是明确把 KV cache 做成 distributed first-class object，并提供 transfer / materialization / fork / composition / eviction 等算子。([arXiv](https://arxiv.org/abs/2607.10987?utm_source=chatgpt.com))

所以它其实对应一个非常值得借鉴的思路：

> **存储状态不仅可以决定“算在哪里”，还可以决定“要不要算”。**

换成普通推理场景就是：

```text
Request R
      ↓
发现已有 Prefix KV

                  ┌→ remote fetch
KV residency ─────┤
BW / RTT ─────────┤→ local recompute
queue depth ──────┤
GPU idle ─────────┤→ migrate request
                  └→ prefetch + wait
```

这就是你说的“双向影响”。

## 4. PTStore：更偏“先把存储布局做好”，还没有形成完整计算调度闭环

8 月 11 日调研的 PTStore 把 hot KV prefix 类比 CDN 内容，在多个节点/GPU 上复制。

日报里已经明确写了一句很有意思的话：

> **“它证明了状态感知的KV放置值得验证。”** 

PTStore 这么做的一个重要原因，就是某些 popular prefix 所在服务器会因为大量请求产生 load imbalance。它通过复制热 tensor：

```text
hot KV prefix
      ↓
只在 Node A
      ↓
request 都去 A
      ↓
A 热点

变成：

A    B    C
KV   KV   KV
 \   |   /
  requests
```

论文报告长文 QA workload 相比不聚合跨节点/GPU内存的基线效率提高约 5-6 倍。([arXiv](https://arxiv.org/abs/2607.22648?utm_source=chatgpt.com))

但是它主要解决：

> **如何根据 workload 热度改变 KV placement。**

还不是：

> **实时读取存储状态，然后动态改变 compute scheduler。**

所以我会把它视作你们方向里的**状态供给层**，而不是 scheduler 本身。

# 目前已有工作的真正空缺，也很明显

如果把你说的“存储状态”严格理解成**独立 KVCache 数据层**，我目前在这些日报中还没有看到一套成熟系统完整做到：

```text
KV Storage Control Plane
│
├── prefix / block residency
├── GPU / CPU / SSD tier
├── per-node cache pressure
├── hit probability
├── eviction risk
├── storage queue depth
├── read bandwidth
├── KV transfer BW / RTT
├── hotness
└── replica availability
          │
          ▼
Global Inference Scheduler
          │
          ├── request routing
          ├── P / D node selection
          ├── Prefill deflection
          ├── recompute vs fetch
          ├── request migration
          ├── KV migration
          └── scale / placement
```

**TensorCast已经走到这个框架的大约 70-80% 了，但它的论文策略目前仍比较简单：主要是 cache locality + instance load 的联合 balance。**

它还没有充分回答：

> “如果存储层有十几个状态变量，计算侧究竟怎样做一个**全局最优/近似最优的联合调度策略**？”

这反而很可能就是你现在这句话里真正想研究的东西。

比如 scheduler 的 objective 不应该再只是：

$$
\min TTFT/TPOT \quad \text{s.t. GPU capacity}
$$

而变成类似：

$$
\min
\{
T_{queue}
+
T_{compute}
+
T_{KV-access}
+
T_{KV-transfer}
+
T_{recompute}
\}
$$

其中每个 candidate compute node $i$ 对一个 request $r$ 都有：

```text
GPU queue_i
GPU capacity_i

KV locality(r,i)
KV tier(r,i)
KV hit_probability(r,i)
KV read_queue_i
KV bandwidth_i
KV transfer_cost(src,i)
eviction_risk(r,i)
```

然后计算：

```text
Route to A + local KV hit
vs
Route to B + remote KV fetch
vs
Route to C + KV migration
vs
Route to D + recompute Prefill
```

**这才是“存储侧状态反向影响计算侧整体调度”的完整版本。**

所以我的结论是：

**有，而且不是边缘相关。TensorCast 已经非常直接地命中了这个问题；Kairos 和 AAFLOW+则分别证明了 KV occupancy / KV transfer cost 可以改变计算放置乃至“传输还是重算”的决策。**

但如果你的问题进一步限定为：

> **“独立 KVCache storage system 将实时存储状态反馈给全局 inference scheduler，并联合优化 request routing + P/D placement + fetch/recompute/migration”**

那么从目前这 8 期日报看，**还没有看到一篇把这个问题完整做透的工作**。这个限定之后，反而已经比较像一个可以继续做 gap analysis 的具体研究方向了。

### Cascade 的核心闭环

Cascade 不只是做“SLO-aware scheduling”。它定义了一个 per-request **latency budget**：

$$
Budget = SLO - PredictedRemainingServiceTime
$$

关键在于，这个 `PredictedRemainingServiceTime` 不是只看计算量，而是显式依赖：

- request context length；
- **prefix KV cache hit profile / KV state 在哪一层**；
- 当前 serving instance 的计算负载。

论文明确说，它根据 request characteristics、**KV-cache state** 和 current system load 持续更新 latency budget，然后用这个 budget 协调 **request scheduling 和 KV-cache management**。([arXiv](https://arxiv.org/abs/2608.06557))

所以真正的路径是：

```text
KV Cache 状态
   │
   ├─ HBM hit?
   ├─ DRAM hit?
   ├─ NVMe hit?
   ├─ prefix 命中多少?
   └─ restore 需要多久?
          │
          ▼
预测该请求的 TTFT / remaining service time
          │
          ▼
计算 remaining latency budget
          │
          ▼
改变计算侧调度优先级
   │
   ├─ Tier-1 / Tier-2 queue
   ├─ 谁先执行
   ├─ batch 中优先放谁
   └─ 哪个 request 可以承担额外等待
```

与此同时，同一个 budget 又反过去控制 KV：

```text
Latency Budget
      │
      ├─ fetch KV from DRAM/NVMe
      ├─ prefetch
      ├─ retain in HBM
      └─ recompute prefix
```

这其实已经形成了：

> **KV state → compute scheduling → KV management**

的闭环。论文甚至直接把优化问题表述成 **jointly co-design request scheduling policy σ 和 prefix retrieval policy φ**。([arXiv](https://arxiv.org/abs/2608.06557))

### 一个特别符合你问题的例子

```text

预计执行：3s

Request B
prefix KV：NVMe

```

Cascade 会知道：

> B 的 KV 在深层存储，恢复本身就要吃掉大量 latency budget。

所以 B 已经非常紧迫，scheduler 会把 **B 提前执行**。

这正是：

> **“因为 KVCache 当前所处的存储状态不同，所以计算请求的优先级发生变化。”**

这一点比 Kairos 还更直接符合你原来那句话。

论文的 TTFT estimator 具体就用了 **context length + prefix KV hit profile across the memory pool + active serving load** 来预测请求时延。([arXiv](https://arxiv.org/abs/2608.06557))

如果你所谓的“**计算侧整体调度**”强调的是 cluster-level：

- 请求应该去哪个 GPU / instance；
- Prefill 应该去哪；
- Decode 应该去哪；
- 是否迁移 request；
- 是否把计算挪到 KV 所在节点；

# 1. 先把问题真正定义清楚

正常情况下，我们会认为：

```text
有 KV → 读 KV
没 KV → Prefill 重算
```

但一旦 KVCache 被放到 CPU、SSD、远端 KV Store、Mooncake/LMCache 这种共享存储之后，这个判断就不成立了。

例如：

```text

Prefix = 32K tokens

KV 在远端存储
Storage 当前：
    有效读取带宽 = 20 GB/s
    大量请求排队
    预计 KV ready = 400 ms

GPU 当前：
    Prefill 比较空闲
    重算 Prefix = 180 ms
```

此时：

```text
Cache Hit
≠
应该 Fetch

反而应该：

Cache Hit
→ 发现 Storage Hot
→ 放弃部分/全部 Fetch
→ GPU Recomputation
```

也就是说，**KVCache 是否存在只是第一维，KVCache 当前是否“值得取”才是第二维。**

真正的问题应该从：

> KV-aware scheduling：KV 在哪里？

升级为：

> **KV service-cost-aware scheduling：现在取这份 KV 到底要付出多少时间和资源？**

我不建议最终系统以：

```text

```

作为主要反馈信号。

因为“带宽 95%”不能直接告诉计算侧该做什么。

真正影响请求的是：

$$
T_{\text{fetch}}
=
T_{\text{queue}}
+
T_{\text{transfer}}
+
T_{\text{promotion}}
+
T_{\text{overhead}}
$$

比如：

```text
NVMe
 ↓
DRAM
 ↓
GPU HBM
```

任何一段都可能堵：

```text
NVMe read
PCIe
Network/RDMA
CPU DRAM
CPU→GPU
LMCache queue
Prefetch queue
```

所以所谓 **storage pressure** 更准确地应该定义为：

> **当前 KV 存储路径对新增请求能够提供的边际服务能力。**

也就是说，计算侧真正需要知道的是：

> “如果我现在提交 8 GB KV Fetch，请告诉我什么时候能完成。”

而不是：

> “你现在带宽利用率是多少？”

这两个接口层级差很多。

```text
“感知到 storage cost 后怎么算/取？”

TensorCast
解决：
“Storage 与 Compute 之间应该有什么抽象层？”
```

但 TensorCast 目前主要暴露：

```text
KV在哪里
replica在哪里
worker load怎么样
```

而你真正需要继续补的是：

```text
Storage现在堵不堵？
现在读这份KV预计多久？
如果再加这一笔IO会怎样？
```

所以 TensorCast 更接近你的**架构基础**，而不是最终 policy。

# 7. Kairos 则告诉我们：上层调度可以怎么响应

Kairos 是第三块拼图。

它发现 PD 分离后：

> Prefill queue + KV transfer 可能远比 Prefill compute 本身贵。

于是它不是继续优化 KV transfer，而是说：

```text
既然搬 KV 很贵

那我为什么一定要：

P GPU
 ↓
Prefill
 ↓
KV transfer
 ↓
D GPU

我可以：

D GPU
 ↓
chunked Prefill
 ↓
直接 Decode
```

Kairos 的决策模型里显式计算：

$$
T_{KV-transfer} =
\frac{KVBytes}{Bandwidth}
$$

并且节点每 100ms 向 dispatcher 汇报状态；dispatcher 决定是否进行 Prefill deflection。([Academus](https://academ.us/article/2607.02043/))

所以 Kairos 给你的启发是：

> **Storage pressure 不一定只能触发 recomputation，还可以改变 compute placement。**

这非常重要。

---

# 8. AAFLOW+ 则把最核心的二选一说得最干净

AAFLOW+ 本质上比较：

$$
T_{\text{transfer}}
=
\frac{\text{KV bytes}}{\text{bandwidth}}
+
latency
$$

和：

$$
T_{\text{recompute}}
=
T_{\text{prefill}}
$$

然后：

```text
Transfer faster → Fetch KV
Recompute faster → Recompute
```

它甚至发现低带宽下有不少场景重算更划算。([ResearchGate](https://www.researchgate.net/publication/409442923_AAFLOW_Stateful_Operator_Abstraction_with_Zero-Copy_Distributed_KV_Cache_Orchestration_for_Multi-Agent_Workflows))

但 AAFLOW+ 最大的问题也很明显：

**它更多是基于 bandwidth sweep + analytical cost model，而不是一个在线 storage backpressure control system。**

所以它提供的是你的：

> **decision primitive**

不是完整系统。

# 10. 那么 Storage 到底应该给 Compute 提供什么接口？

这里我认为是整个问题最重要的设计点。

**不要简单定义 `get_storage_bandwidth()`。**

至少应该有三种接口语义。

### 第一类：粗粒度 Pressure State

这是给 Dynamo / Motor 这种 global scheduler 用的。

例如：

```text
StoragePressure {
    tier: "remote_kv_0",

    read_bw_effective: 75 GB/s,
    read_bw_available: 18 GB/s,

    inflight_reads: 146,
    inflight_bytes: 320 GB,

    queue_delay_p50: 12 ms,
    queue_delay_p95: 85 ms,

    service_latency_p95: 140 ms,

    capacity_usage: 0.82,
    eviction_pressure: 0.65,

    pressure_level: HOT,

    timestamp: ...,
    confidence: 0.93
}
```

这里最值得注意的是：

**`available_bw` 比 `utilization` 有用，`queue_delay` 又比 available_bw 更有用。**

---

# 11. 第二个接口反而最重要：Per-request Cost Quote

这是我认为最值得形成独立 abstraction 的地方。

Global scheduler / vLLM 不应该自己根据 storage metrics 推算。

它直接问：

```text
EstimateKVFetch(
    prefix_hash,
    target_gpu,
    deadline
)
```

Storage 返回：

```text
KVFetchQuote {
    hit_tokens: 24576,

    source:
        remote_store_3,

    bytes:
        6.2 GB,

    predicted_ready_time_p50:
        110 ms,

    predicted_ready_time_p95:
        280 ms,

    queue_delay:
        90 ms,

    effective_bandwidth:
        33 GB/s,

    bottleneck:
        "storage_read",

    confidence:
        0.89
}
```

这样 compute scheduler 根本不需要知道：

> 你下面是 SSD、RDMA、Mooncake、S3 还是 CXL。

它只需要比较：

$$
T_{fetch}=280ms
$$

和：

$$
T_{recompute}=170ms
$$

然后：

```text
170 < 280
→ recompute
```

**这比暴露 storage bandwidth 本身干净得多。**

我甚至觉得这个东西可以叫：

> **KV Retrieval Cost Oracle**

这是整个跨层设计里非常核心的 abstraction。

---

# 12. 第三类是 Event / Backpressure Interface

不能让 Dynamo 每个 request 都不停 polling `/metrics`。

Storage 应该主动推：

```text
NORMAL
   ↓
WARM
   ↓
HOT
   ↓
CRITICAL
```

例如：

```text
KVPressureEvent {
    backend: remote_store_3,
    level: HOT,
    reason: READ_QUEUE,
    estimated_bw_available: 12 GB/s,
    p95_fetch_latency: 240 ms
}
```

这样 global scheduler 可以快速改变 policy：

```text
NORMAL
→ cache-first

WARM
→ cost-aware

HOT
→ recompute-preferred

CRITICAL
→ admission control / reroute
```

而且一定要有 hysteresis，例如：

```text
进入 HOT：
BW available < 20 GB/s 持续 200ms

退出 HOT：
BW available > 30 GB/s 持续 1s
```

否则会出现：

```text
Storage堵
→ 所有人开始recompute
→ GPU堵

Storage变闲
→ 所有人又开始fetch
→ Storage堵

...
```

形成控制振荡。

这个反而是一个很典型、也很有研究价值的 systems 问题。

# 16. 我会把 Compute 侧动作分成两层

这一步非常关键，否则 Dynamo 和 vLLM 会职责打架。

| 层 | Storage Hot 后应该做什么 |
|---|---|
| **Global Scheduler：Dynamo / Motor** | Route 到另一 instance、选择其他 KV replica、重新选择 P/D pairing、Prefill deflection、admission/throttle、KV migration |
| **Inference Engine：vLLM / SGLang** | Fetch vs Recomputation、chunked prefill、partial recompute、调整 KV fetch 并发、降低 prefetch 优先级 |

原则应该是：

> **能通过改变 request placement 解决的，先由 global scheduler 解决；placement 已确定后，再由 engine 决定 fetch/recompute。**

否则很容易互相打架。

# 17. 关于“部分重算”，这里有一个需要特别注意的技术细节

不能简单理解成：

```text
100 个 KV blocks
挑任意 30 个不读
单独重算这 30 个
```

Transformer 的计算有前缀依赖。

更安全、实现难度最低的方式是：

```text
32K prefix

前 16K：
HBM / CPU 能快速拿到
        ↓
reuse

后 16K：
remote storage太慢
        ↓
recompute suffix
```

即：

> **复用能够及时取得的最长 prefix，然后从这个 checkpoint 开始重新 Prefill 剩余 suffix。**

例如：

```text
tokens
0────────────────32K

0────8K       HBM
8K──16K       DRAM
16K────────32K Remote Storage HOT

最终：

0────16K  Fetch/Reuse
16K───32K Recompute
```

这样逻辑非常干净。

更激进的：

> 任意非连续 KV block 混合 fetch + recompute

当然也能研究，但会涉及 CacheBlend 一类非前缀 KV 复用机制和 attention correctness/融合问题，第一版没有必要把问题搞这么复杂。

# 18. 最终 scheduler 的决策其实可以非常清楚

对于 Request $r$，候选计算节点 $i$：

$$
T_{\text{fetch}}(r,i)
=
Q_{storage}
+
\frac{KVBytes}{B_{eff}}
+
T_{promotion}
$$

$$
T_{\text{recompute}}(r,i)
=
Q_{GPU}
+
T_{prefill}(tokens)
$$

还可以有：

$$
T_{\text{reroute}}(r,j)
$$

$$
T_{\text{migrate}}(r,i\rightarrow j)
$$

于是问题变成：

$$
a^*
=
\arg\min_{a \in
\{fetch,recompute,reroute,migrate,wait\}}
T_a
$$

同时满足：

$$
TTFT < SLO
$$

这已经是最简单版本。

但真正做系统论文时最好进一步考虑**资源机会成本**：

$$
C_{fetch}
=
T_{fetch}
+
\lambda_s \cdot KVBytes
$$

$$
C_{recompute}
=
T_{recompute}
+
\lambda_g \cdot FLOPs
$$

这里：

- $\lambda_s$ 随 storage congestion 增大；
- $\lambda_g$ 随 GPU congestion 增大。

这样就会自然出现：

```text
Storage空，GPU忙
→ Fetch

Storage忙，GPU空
→ Recompute

Storage A忙
→ Route Storage B

P忙，D空
→ Kairos-style deflection
```

这才是我认为这个问题最漂亮的表达。

# 19. 因此，我现在会把“已有论文覆盖情况”重新总结成这样

**Cascade 是最接近最终 policy 的。** 它已经证明了实时 KV tier/transfer cost、SLO budget、request scheduling 和 recomputation 可以联合考虑，并显式考虑了有效运行带宽。([arXiv](https://arxiv.org/abs/2608.06557))

**TensorCast 最接近你需要的跨层 abstraction。** 它已经把 tensor/KV 状态从 engine 里抽出来，以 Signal + Plan 的方式支持 routing、migration 等跨组件 policy。([alphaXiv](https://www.alphaxiv.org/abs/2608.06007))

**Kairos 最接近 global scheduler 的动作空间。** 它证明 KV transfer 太贵时，完全可以改变 compute placement，而不是被动等 KV。([Academus](https://academ.us/article/2607.02043/))

**AAFLOW+ 最接近核心 decision primitive。** 即在线选择“搬 KV 还是重新计算”。([ResearchGate](https://www.researchgate.net/publication/409442923_AAFLOW_Stateful_Operator_Abstraction_with_Zero-Copy_Distributed_KV_Cache_Orchestration_for_Multi-Agent_Workflows))

而 **Dynamo + LMCache 的当前实现已经提供了做原型的大部分 plumbing**：KV events、分层 cache routing、L2 throughput、inflight load、prefetch、move 等都已经存在。缺的是把这些信息收敛为一个统一的 **Storage Cost / Pressure Signal**，然后真正放进 scheduler 的 cost function。([NVIDIA Dynamo 文档](https://docs.dynamo.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/kv-aware-routing))

```text
Request rate
```


发生 crossover。

```text

SLO Goodput
GPU Utilization

Storage Queue
```

# 4. Storage 怎么模拟？这个最重要

千万不要写：

$$
T_{fetch}=KVBytes/BW
$$

这模拟不出你想研究的问题。

你真正需要的是：

$$
T_{fetch}
=
T_{queue}
+
\frac{KVBytes}{B_{effective}}
+
T_{base}
$$

而且 **Storage 总带宽固定**。

例如：

```text
Storage capacity = 100 GB/s
```

然后人为加入 background traffic：

```text
0~10s:

Background load = 20 GB/s
Available = 80 GB/s

10~12s:

突然有 KV restoration incast

Background + foreground = 130 GB/s
Available capacity 不够
Queue快速增加

12~20s:

恢复正常
```

这和直接设置：

```text
Storage BW = 20 GB/s
```

完全不同。

**你研究的是动态 pressure，不是慢 Storage。**

# 5. Storage 最好模拟成共享带宽，而不是单请求 FCFS

例如三个请求同时 Fetch：

```text
Total = 100 GB/s

A: 10GB
B: 20GB
C: 10GB
```

不要假设：

```text
A读完
→ B读
→ C读
```

更合理的简单模型是 Processor Sharing：

```text
A ──┐
B ──┼── 共享 100GB/s
C ──┘
```

三条都活跃时暂时各：

$$
100/3 \; GB/s
$$

有一个完成后：

$$
100/2
$$

这样就已经能很好地模拟 storage contention。

如果觉得写动态 processor-sharing 麻烦，SimPy 里面自己维护：

```text
active_transfers
remaining_bytes
last_update_time
```

每次发生：

- 新请求加入；
- 一个请求完成；

重新计算每个 active transfer 的带宽即可。

## P1：Static Cost-Aware

# 8. P2：Dynamic Storage-Aware

这是第一个你的 Policy。

Storage 每隔例如 50ms 提供：

```text

inflight_bytes
queue_depth
effective_bw
```

于是：

$$
\hat T_{fetch}^{dynamic}
=
T_{queue}
+
KVBytes/B_{effective}
$$

然后 Engine 比较：

$$
\hat T_{fetch}^{dynamic}
\quad vs \quad
\hat T_{recompute}
$$

例如：

```text

Static:
10 / 100GB/s
= 100ms

所以 Fetch

但是当前 Storage：

effective BW = 20GB/s
queue delay = 150ms

Dynamic:

150 + 10/20
= 650ms

GPU recompute = 220ms

→ Recompute
```

**这就是第一版系统的全部创新逻辑。**

先不要搞复杂。

# 9. P3：Storage-Aware Routing

然后把同样的信息放到 Global Scheduler。

例如：

```text
                    Request
                       │
        ┌──────────────┴─────────────┐

Worker A                           Worker B

KV hit = 32K                     KV hit = 0
GPU queue = 30ms                 GPU queue = 30ms

Storage A:
expected fetch = 500ms

                                 Recompute
                                 = 200ms
```

普通 KV-aware：

```text
→ Worker A
```

Storage-aware：

```text
→ Worker B
→ Recompute
```

这时候 routing cost 可以简单写：

$$
Cost(i)
=
\min
\{
T_{fetch}(i),
T_{recompute}(i)
\}
$$

选：

$$
i^*=\arg\min_i Cost(i)
$$

这已经是非常干净的 global scheduler。

目前 Dynamo 的 KV-aware router 本来就联合使用 prefix overlap 与 projected active load 做 worker 选择；worker 通过 KV creation/release events 更新 router 的 KV 状态。([docs.dynamo.nvidia.com](https://docs.dynamo.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/kv-aware-routing?utm_source=chatgpt.com))

所以未来往真实 Dynamo 上落，本质上就是：

```text
已有：

KV overlap
+
Compute load

增加：

Storage service cost
```
