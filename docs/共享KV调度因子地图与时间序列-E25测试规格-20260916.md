## 1. 测试思路：三层各防一种错

| 层 | 编号前缀 | 防什么错 | 方法核心 |
|---|---|---|---|
| 桶聚合 | BU01–BU12 | 数据算错：区间切分丢/重、守恒破坏、口径混用 | 手算金标夹具（含设计文档 §5.5 两例）+ 构造 run 的恒等式 |
| 因子地图 | FM01–FM08 | 实验跑错：目标/因子/复用/CRN 口径不对 | 小规模真实 run 的字段与配置断言 |
| 图表一致 | FG01–FG05 | 图骗人：图与数据不同源、发布覆盖旧图 | 从落盘数据重算图值、文件名集合断言 |

原则沿用规格 §11.3：每个测试对应**语义不变量或独立解析值**，不接受"函数返回了它自己生成的字段"式断言。随机夹具一律固定种子。

## 2. 桶聚合测试（BU01–BU12）

夹具构造器：`make_tiny_engine(specs, B, ...)` 直接组装 `CqEngine` 跑小规模请求（n≤3、L≤2、小有理数 V/c），不经 e25 矩阵。区段求交函数单独可测（纯函数）。

| ID | 输入 / 夹具 | 硬断言 |
|---|---|---|
| BU01 区间切分 | 纯函数：区间 `[1.4, 3.1)`，Δ=0.5（设计文档 §5.5 例 1） | 各桶分账恰为 0.1/0.5/0.5/0.5/0.1，合计 1.7；端点重合按左闭右开（`[1.5,2.0)` 属左桶含义：1.5 是桶 3 的左端点） |
| BU02 端点与零长 | 区间 `[0.5, 0.5)`（零长）、区间恰为一整桶 `[0.5, 1.0)`、区间跨溢出边界 `[T_anchor−0.1, T_anchor+0.2)` | 零长区间贡献为 0 不产生行；整桶区间恰好一个桶得全长；跨界段在桶 199 与溢出桶各得 0.1/0.2 |
| BU03 三态守恒 | 任意 tiny run（含排空） | `Σ桶(compute_s+stall_s+idle_s) == m × T_end`（1e-9）；与 `WorkerState.compute_s/stall_s/idle_s` 之和逐项相等 |
| BU04 字节守恒 | 同上 | `Σ桶 served_gb == storage.actual_integral_gb`；`Σ桶 requested_gb == storage.requested_integral_gb` |
| BU05 容量闭式 | B(t)=`((0,4),(1,2))`，T_end=3 | 逐桶 capacity 为解析值：桶含 [0,1) 段按 4、其后按 2 积分；总计 `4×1+2×2=8`；该计算**不读** storage 累计器（独立复算） |
| BU06 溢出桶 | 人造 T_end = 1.3×T_anchor 的 run（如放慢策略或缩短锚） | 溢出桶宽度 = T_end−T_anchor；三态守恒含溢出桶后仍成立；`meta.overflow_used=true`；`width_s` 用实际宽度而非 Δ |
| BU07 锚定一致 | 同格点跑 fcfs 与另一策略 | 两份 ts 的 `meta.T_anchor_s / delta_s / K` 完全相等；`T_anchor == ceil_0.1s(1.1 × T_end(fcfs))`（重算核对）；fcfs 两次运行 T_end 一致（确定性前提，复用 U29 机制） |
| BU08 队列时间加权 | 1 请求 t=0 到达、t=0.5 派发、t=1 完成；Δ=0.25（设计文档 §5.5 例 2 的变体） | `queue_mean` 逐桶为时间加权值（手算金标）；断言 `mean(queue_mean) ≠ 事件数平均`（防口径退化）；`queue_max` 为桶内峰值 |
| BU09 累计口径 | tiny run | 最后一桶 `cum_arrived == n_requests`、`cum_done == n_done`；两累计序列单调不减 |
| BU10 空与零值 | 全 h=0（无读取流）请求；空 specs | 无流 run：`served_gb` 全 0、`capacity_gb` 按 B 正常积分、util=0.0（非 null）；空 specs 不产生 ts 文件且不抛异常 |
| BU11 零影响开关 | 同一 tiny run，聚合器开/关各跑一次 | 两次运行的请求/批/事件规范日志哈希相同（聚合是纯观察者）；关闭时 e19–e24 路径行为与现状逐位一致 |
| BU12 ts 落盘格式 | 任一 tiny run 落盘后回读 | JSON 合法、无 NaN/Infinity（出现即解析失败）；行数 = K +（溢出桶被使用?1:0）；字段名与设计文档 §5.4 逐一对应；gzip 可回读 |

**守恒是每 run 的运行时义务**：BU03/BU04 在 e25 正式矩阵中由聚合器内置校验（失败标 invalid），测试保证校验器本身正确（用一个故意篡改字段的 ts 文件断言校验器会拒绝）。

## 3. 因子地图测试（FM01–FM08）

用 `MooncakeSource` 的真实窗口（窗口 0，必要时截 `duration_cap`）跑小规模矩阵片段；断言落在 `e25_records.json` 行与 `ts/` 目录上。

| ID | 输入 | 硬断言 |
|---|---|---|
| FM01 四目标齐全 | FW 基线一格点（1 文件 × 1 窗口 × 8 策略） | θ∈{M,S,T,R} 记录各 8 条共 32 条；全体完成时 `makespan_M` 非 null 且 ≥ max(F)；有未完成时为 null 且 `makespan_M_lower` 非 null |
| FW 模式 M 语义 | 同上 | `makespan_M == max(请求行 F_s)`（从 requests 级数据独立重算） |
| FM02 OL drain 口径 | OL 基线一格点 | 记录含 `drain_M`（= makespan_M_lower）且无 `makespan_M` 非 null 字段混入；OL 记录带 `device_*_main/drain` 拆分且 `main+drain == 全程字段`（1e-9） |
| FM03 CRN 配对 | 同格点 8 策略 | 全部行 `trace_hash` 相同；`storage_served_gb` 策略间相等（读取守恒，沿用 T09 思路）；`cell_id` 相同 |
| FM04 单因子隔离 | line_B 的 B=20 一行 | 与基线行逐字段 diff，仅 `scenario/B/T_anchor/delta_s/ts_path` 等随 B 派生字段不同；`alpha/cap_block/profile_id/rho` 等其余因子字段相同；`factor_line=="line_B"` |
| FM05 跨 θ 复用 | FW 基线简单策略（如 cq_spt） | θ=M/S/T/R 四行指向**同一** `ts_path`，四行 summary 中 θ 无关字段（F、批数、设备秒）逐项相等；`cq_mpc` 的四行 `ts_path` 互不相同 |
| FM06 profile 线 | line_profile 的 N_sat=128 与 no_speedup 各一小格（构造短 u 请求夹具） | N_sat=128：存在批 `G_batch>1.0+1e-9`；no_speedup：所有批 `G_batch==1`（1e-9）（复用 U03 口径）；`profile_id` 正确写入 cell_id 与记录 |
| FM07 能力块 | line_cap 的 A 块一格 | 所有 `batches` 成员数==1（禁止组批生效）；B 块所有批成员同象限（按训练中位数四象限规则复算）；C 块无此限制 |
| FM08 窗口映射与跳过 | seeds 解释与空窗口 | CLI `--seeds 2` 映射窗口 {0,4}（记录 `window` 字段）；有效请求 <16 的窗口被跳过且写入 progress 备注而非静默缺失 |

## 4. 图表一致性测试（FG01–FG05）

数据源唯一性是硬约束：图脚本只准读 `e25_records.json` 与 `ts/*.json.gz`，禁止重跑仿真取数。

| ID | 检查对象 | 硬断言 |
|---|---|---|
| FG01 图 A 同源 | 基线 FW records + 图 A 数据缓存 | 图中每策略每指标的粗横线 == 该策略窗口中位数（从 records 重算，1e-9）；点的个数 == 窗口数 × 文件数 |
| FG02 图 D 归一 | 任一 ts 文件 | 逐桶三占比之和：常规桶 ==1（1e-9）；策略快于锚的空尾桶为 null 且图上留白不画 0；溢出桶按实际宽度归一 |
| FG03 图 E 参考线 | B(t) 阶梯 | 图中阶梯断点时刻与 `meta.b_schedule` 一致；逐桶 `served_gb/width_s` 的最大值不超过该桶内 B 的最大值 + 1e-9 |
| FG04 图 F 与 summary | 峰值一致性 | `max(queue_max over 桶) == summary.max_backlog`（新增字段；若 summary 无此字段则本测试强制其新增，不得删检） |
| FG05 发布隔离 | `--publish-figures` | 发布后 `docs/figures/` 仅新增 `cq_fig_e25_*`；e19–e24 既有正式图（`cq_fig_e19_*`…`cq_fig_e24_*`）的修改时间与哈希不变（文件名集合 + mtime 断言） |

## 6. 冒烟区分度验收（进入全量前的门槛）

沿用规格 §9.8 的区分度思想，E25 的检查项：

| 检查 | 通过条件 | 不满足时的处置 |
|---|---|---|
| SLO 区间 | 三文件中至少两个文件在基线或 B=20/ρ=0.9 格点上，简单强基线 SLO 满足率 ∈ [20%, 95%] | 允许一次扩展 `B∈{5,10}` 或 `ρ∈{0.1,0.2,1.3}`，扩展格点入 manifest，不删初始负面格点 |
| 通道确认 | line_profile 的 N_sat=128 小格上存在 `G_batch>1` 的批（组批通道确实打开） | 若真实 trace 全批仍 N≥128·16（η 触顶），改用四类机制组混合请求作 line_profile 的第二夹具并在文档记录 |
| 时间序列非退化 | 至少一个格点的 ts 中 STALL 占比 > 0 且利用率曲线非常数（存在结构可看） | 全平则说明该格点无 I/O 竞争，换 B=20/ρ=0.9 格点；全部格点皆平时如实报告"该 trace 下无时间结构差异" |
| 图可读性人工检查 | 图 A–F 各一张在报告中能独立回答设计文档 §6 "判读要点"列的问题 | 人工审阅，不通过则修图不修数 |

冒烟阶段不产生研究结论；smoke 图仅以 FCFS 为参照并标注"冒烟"。

## 8. 通俗版解读

这套测试就是给"考场录像机"和"全科成绩单"各上一道质检：

- **BU 组**查录像机本身：一段 1.7 秒的等待切成五份，加起来必须还是 1.7 秒，一分不能丢、一分不能多；录像开机与否不能改变考试过程本身。
- **FM 组**查成绩单的登记：四个科目的分都要有；只拧一根难度旋钮时，其他旋钮的读数不许悄悄变；同一份考卷（同一 trace）所有学生的用纸量必须一样。
- **FG 组**查成绩单印刷：图上画的每一笔都得能从登记簿里原样查出来；新发的图表不许弄脏以前任何一张旧图。
