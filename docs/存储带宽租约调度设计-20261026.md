## 术语

- **计算路由**：决定"这个请求发给哪个推理实例"的部件。按实例的计算负载选目标。
- **存储准入**：决定"这个请求的读取现在能不能开始、以多大份额占哪块盘"的部件。
- **预定（Reserve）**：实例向调度器发出的异步带宽申请，发生在请求进入实例等待队列时。
- **租约（Lease）**：调度器批准预定后下发的授权凭证，带额度（每盘份额）与 TTL（预计读完成时间 + 裕量）。
- **释放上报**：实例在请求**最后一层读完成**时（不等计算完成）发出的归还消息。
- **两项账本**：调度器为每块盘记的账 = 在跑租约份额（未到末层）+ 未决预定中期限紧迫份额。
- **d（需求速率）**：请求运行期间持续占用的读带宽，= 总读量 ÷ 独占完成时间。
- **末层**：请求的最后一个计算层。末层期间不再读任何数据。

## 0. 直读版：提案哪里对、哪里必须改

提案里有三个部件是对的、直接保留：①**每盘带宽从存储侧接口取定值**（如每盘 30 GB/s），比从总带宽推导好；②**调度器集中记账**做存储准入的中心点；③**下发时携带存储信息字段**。

两个结构性问题必须改：

1. **"实例申请 → 批准后才执行"的同步申请制**。它把一次往返延迟放进了请求执行的热路径；更糟的是账本会系统性虚高——从批准到实例真正开始读之间存在通信窗口，这段时间账本记了占用、物理上却没读。提案声称"占用准确、不受排队和通信影响"，恰好相反：**拉取式（申请-批准）记账的误差窗口就是通信延迟本身**。第一轮 DV 实验实测过这个口径（issued 记账）：负载升高时保守代价单调放大（中央等待 133→317ms）。改法：申请改异步预定、批准发租约、末层读毕即上报释放（详见 §3）。
2. **"重读"用布尔字段标记**。这会重新踩回分类死板的问题（75%/3.75 无设计依据——已被上一轮实验证明可整体删除）。改法：不带"是否重读"标志，带**数值字段**（需求速率、每盘份额、期限、预计读完成时刻），准入判定全程用数值，不出现任何阈值分类。

另有一个缺口：计算均衡选出的实例，存储上可能正好是热点——对齐簇场景（对抗二轮 P4 实验）计算侧毫无异常、存储侧整类请求全灭。所以计算路由与存储准入必须**两级串联**，不能只靠计算路由。

## 1. 提案复述（六要素）

1. 调度器用 DeepInfer 的计算负载均衡策略把请求发到推理实例；
2. 重读请求在下发字段中打标记；
3. Router 先获取每个盘的总带宽；
4. 实例执行到重读时，向调度器申请带宽；
5. 申请通过后才执行读取；
6. 调度器在分配后更新自己记账的各盘占用。

## 2. 逐条批判（每条挂实验证据）

**C1 同步申请把通信延迟变成占用误差，且卡在热路径。** 申请-批准是阻塞式往返：实例在等批准期间不能开读。账本误差窗口 = 批准到达与实际开读之间的通信时滞——记的是"已批准"，物理上是"未在读"。这正是第一轮在 DV 工具上实测的 issued 口径：负载越高、滞留越长、虚高越多，保守代价单调放大（中央等待 133→317ms，A 类首字时延反超直接提交）。提案的立论（"占用准确、无排队与通信影响"）方向反了：**推（实例上报实际在读）的误差随上报周期有界；拉（先申请后执行）的误差直接含往返延迟。**

**C2 释放时机未定义——若等请求完成才释放，波量化损失复发。** 每请求一次授权、请求结束回收，则释放对齐"完成"而非"最后一层读毕"。对抗一轮 G4 实验：末层 6ms 空泡 + 唤醒下限造成批间空档，到达率落在有效容量与物理容量之间时达标率 0.572 对 0.921。修复版已验证：末层开算即从账本剔除，可回收约 12~14% 有效吞吐。

**C3 布尔标记重建分类问题。** "是否重读"二值字段需要一条阈值线，而阈值线已被证明无设计依据且可整体删除（nolabel 实验：删分类后母工况逐位等价、全档案免疫且多数反超、G2 悬崖形态结构性消失）。数值字段（需求速率/每盘份额/期限/预计读毕）让判定连续化，同一机制覆盖全部请求。

**C4 计算均衡 ≠ 存储均衡。** 对抗二轮 P4（三盘对齐簇）：计算侧负载完全正常，存储侧一类请求全灭（总带宽未满、单盘已爆）。计算路由只看 worker 维度；盘维度必须由存储准入兜住。两级串联：计算路由选实例 → 存储账本决定放行时机。

**C5 单点与失败路径缺失。** ①高频申请把调度器变成串行化瓶颈（32 实例 × 秒级百次申请）；②授权泄漏：请求被抢占/失败后授权未回收，账本永久虚占；③消息丢失：释放消息丢了账本回不来。需要租约 TTL（到期自动回收）与周期对账（用存储侧实际交付速率校准账本）。记账模型还必须与真实分配器同构——E26f 的 local 崩塌教训：感知模型与真实分配不同构时，公平分配器反而惩罚乐观估计（73.1%→48.6%）。

**C6 实例内行为未设计——申请顺序=执行顺序会造出加载位垄断。** 对抗二轮 B2 实验：慢加载大读占住实例资源，紧期限小簇排在其后，单层语义 57.1%、带实例内保护的 100%。实例侧需要：等待队列按宽裕程度排、同时在加载的重读数有上限、已读完的优先进计算位。这三条与调度器侧准入正交，缺一不可。

**C7 "总带宽"与"可用带宽"是两个接口。** 每盘定值（30 GB/s）是物理总量；若盘被其他租户共享，准入需要的是**当前可用**。若接口给的是定值，参考带宽过期类 bug（对抗一轮 G6，0.321 对 1.000）在盘维度根除；若可变，读取要防抖（连续低观测用中位数确认，W2/W5 结论）。

## 3. 完善方案：预定—租约—上报（Reserve–Lease–Report）

保留提案的三个部件（盘带宽接口、集中记账、下发字段），把"同步申请制"改成三段异步协议，实例内补三条规则，路由改两级串联。

**字段（数值，无布尔标记）**：下发请求携带 `d`（需求速率）、`盘份额表`（该请求块分布到各盘的字节占比，公开哈希可算）、`期限`、`预计读完成时刻`。

**R1 预定（异步，进等待队列即发）**：实例收到请求、放入等待队列的同时向调度器发预定（不阻塞任何执行）。调度器不批时实例照常运行已就绪请求——预定挂起不占计算位（否则复现 B2 的加载位垄断）。

**R2 租约（批准凭证，带 TTL）**：调度器按两项账本判定，容量有余即批；容量满且紧迫则 hold 到容量释放节奏（错峰批准——批准时刻对齐"最早在跑租约的末层读毕时刻"）。租约额度 = 该请求每盘份额；TTL = 预计读完成 + 通信裕量。实例持有效租约才发起读取。

**R3 上报（两路）**：①释放：请求末层读毕即上报（不等计算完成），调度器账本即刻减除、触发下一个 hold 中的租约；②在读集合：实例每步上报当前在读流与剩余字节，供调度器对账与唤醒估计。TTL 兜底消息丢失；周期对账（存储侧每盘实际交付 vs 账本）兜系统性漂移。

**两项账本与放行判定**：

```
账本[盘] = Σ 在跑租约份额(未到末层)  +  Σ 未决预定中期限紧迫(期限−现在<Δ)的份额
放行 ⇔ 每盘: 账本[盘] + 候选份额[盘] ≤ 盘带宽[盘](接口定值) × 容差
          且 候选自身与在跑者的"拉伸后期望完成时刻"不超各自期限
```

第二项（紧迫排队）是二轮后补实验钉死的：一步期限算术只看在跑者时，对齐簇仍死（第 4 条放行时在跑的都来得及、伤害落在排队的第 5、6 条）；加入第二项后 P1（身后无紧迫同伙，应放）与 P4（身后一排紧迫同伙，应拒）可同时判对。Δ 锚定 = P95(单请求自然读时间)。

**实例内三条规则**：等待队列按宽裕程度排；同时在加载的重读数 ≤ 全局额度÷实例数；已读完的请求优先进计算位。

**两级路由**：计算路由（DeepInfer LB，黑盒——开源版未含，生产策略未公开）先选实例；存储准入器再决定放行时机。反压：某实例未决预定数超阈值 → 调度器暂停向它派新的重读预定（判据用"未决预定数"，不用等待队列深度——后者会被轻读污染，一轮 G10~G13 实测过误触）。

### 3.1 两个追问的回答：异步误差的单侧性，与开销核算（准入位置精化）

**追问一：改成异步后，记账还准吗？不准的话够用吗？**

关键性质：**本协议的误差是单侧的，且偏向安全方向。**

- 准入（危险方向）发生在调度器本地：账本在批准那一刻落账，用的是调度器自己的状态——这个方向**零延迟、零误差**。物理超订只能来自准入，而准入总额被账本钳住 ≤ 容量×容差。
- 释放（安全方向）是异步的：末层读毕的上报未到达期间，账本**多记**（保守）——后果是浪费一点容量，永远不会超订。浪费上界 = 释放消息延迟 × 释放速率。
- 敏感度有实验锚：对抗一轮 G4 测出系统对"记账滞后"的敏感尺度约 **5~10ms**（末层空泡 6ms + 唤醒下限 5ms 的损失就在这个量级翻车：0.572 对 0.921）。事件驱动的释放（末层边界引擎自己知道，消息延迟 0.1~1ms）比敏感尺度低一个量级；周期性全量上报只用于对账，不参与放行判定。10% 容差带再兜一层——对抗实验全程带着 10% 容差（故意允许的超订）仍然全胜，说明系统根本不要求精确账本，要求的是**不系统性超订 + 浪费有界**。

结论：不需要准确，需要的是误差方向正确 + 浪费上界 ≪ 敏感尺度，两者按构造成立。

**追问二：没有重读标记，每个请求都申请带宽，开销受得了吗？**

先算最坏情况（真的每请求三消息）：到达率 600/秒 × 3 条 ≈ 1.8k 条/秒小消息；现代 RPC 单点吞吐 10 万条/秒量级；每次账本检查是几十次浮点运算（≤32 在跑 + 未决清单）。**吞吐完全不是瓶颈。** 真正的代价是两个：冷启动往返（空系统上第一条请求要等批准才开读）和批准-开读窗口的账实错位。

更好的做法是让"每请求申请"整个消失——**准入并到路由器**：

```
 精化路径（准入位置 = 路由器；实例侧零申请动作）

 路由器(计算路由信号 + 每盘两项账本,同点持有)
   │
   ├─ 快路径(绝大多数请求): 账本放得下 → 下发消息自带租约
   │    └─ 实例收到即持额度开读, 零额外往返, 冷启动零 RTT
   │
   └─ 慢路径(容量满的少数): 请求留在路由器 hold 队列
        ├─ 到容量释放节奏 → 下发(自带租约)          ← 错峰批准
        └─ hold 队列即"中央等待"——对抗实验反复验证:
            负载下用中央等待换错峰, 总达标率更高(DV 六格全胜)

 实例侧控制消息只剩:
   ① 末层读毕释放上报(每读请求 1 条, 事件驱动)
   ② 周期在读集合(对账用)
   ③ 反压信号(未决/积压超阈)
 每请求控制消息 ≈ 1 条。
```

注意快路径的"放得下就自动批"**不是分类**：判定仍是数值的（每盘账本 + 候选份额 ≤ 容量×容差），批与不批只是协议路径选择，语义与慢路径完全一致——没有引入任何阈值线。小读请求自然走快路径，不是因为被打了"轻"标签，而是因为它的份额数值小、几乎总是放得下（账上放不下时挡它恰好是物理正确的，见前述两难分析）。

hold 队列位置在路由器（中央等待）是实验支持的取舍：中央等待随负载上升（133→317ms）但换来错峰，总达标率更高；实例内只剩排序与加载位规则（B2 的教训），无准入。

### 图 3：每盘账本构成与租约状态机

```
 每盘账本[d]（调度器持有，每次预定/释放/上报时更新）

   ┌── 第一项：在跑租约份额 ──────────────────────────────┐
   │   Σ 持有效租约且未进末层的流: d_i × 盘份额_i[d]          │
   │   (末层读毕上报 → 移出; TTL 到期 → 移出)                │
   └────────────────────────────────────────────────────┘
   ┌── 第二项：未决预定中期限紧迫份额 ─────────────────────┐
   │   Σ 已预定未批准且 期限−现在 < Δ 的流: d_j × 盘份额_j[d] │
   │   (预定被批准 → 移入第一项; 被拒绝/撤销 → 移出)          │
   └────────────────────────────────────────────────────┘

 放行判定: 账本[d] + 候选份额[d] ≤ 盘带宽[d](接口定值)×容差
           且 拉伸后期望完成 ≤ 各自期限 (候选+在跑者逐个检查)

 租约状态机:  预定 ──批准──▶ 有效 ──末层读毕上报──▶ 已释放
               │              │                        ▲
               │              └── TTL 到期 ────────────┘(兜底回收)
               └── 拒绝/撤销(请求失败·实例反压) ──▶ 关闭
```

## 5. 设计决定 ↔ 实验证据映射

| 设计决定 | 依据（实验编号） |
|---|---|
| 末层读毕即释放（不等完成） | G4 饱和窗口（0.572→0.921）；一轮 DV issued 保守代价（133→317ms） |
| 数值字段替代重读标记 | nolabel 实验（分类可删；G2 悬崖消失；W6 关闭） |
| 两级路由（计算+存储） | P4 三盘对齐簇（计算无恙、存储一类全灭） |
| 两项账本（在跑+紧迫排队） | feas 配对实验（一步算术在 P4 失手 1.000→0.667；根因=在跑×排队耦合） |
| 每盘账本而非总账 | P4 击杀（66.7% vs 盘感知 100%，+58pp） |
| 盘带宽用接口定值 | G6 参考带宽过期（0.321 vs 1.000）——定值接口根除该类 |
| 预定挂起不占计算位 + 实例内三条规则 | B2 加载位垄断（57.1% vs 100%） |
| 反压判据用未决预定数 | G10~G13 队列深度被轻读污染误触（中央等待 5~8s） |
| 记账与真实分配同构 + 周期对账 | E26f local 崩塌（73.1→48.6，模型失配被公平分配惩罚） |
| 容差与校准的具体值 | G5（1.1 容差）、W5/W2（中位数防抖、上修迟滞） |

## 6. 风险与验证计划

1. **协议开销未测**：预定/租约/上报三路消息的频率与体积需在 DV 工具上实测（对照：一轮 G8 结论——WAIT 闹钟密度已是基线 11 倍时决策成本仍可忽略，但跨进程消息不是同进程闹钟）。
2. **TTL 与对账周期是新的攻击面**：第三轮对抗增加协议层剧本——释放消息丢失（TTL 兜底窗口内的双重占用）、对账漂移（账本与实际交付的系统性偏差）、预定风暴（反压阈值前的突发）。
3. **计算路由黑盒**：DeepInfer 开源版不含跨副本 LB（见脚注），本设计假定其输出仅含目标实例；若其策略内部也读存储信号，需防双重准入的相互干扰。
4. **验证载体**：DV 工具（真框架）按 `docs/DV实验规格-TFS两层必要性-20261026.md` 扩充租约臂；cq 参考引擎可先模拟协议时序（上报周期/TTL 参数化）。
