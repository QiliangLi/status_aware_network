**研究问题可以收敛为，在所有命中 KV 都必须从共享存储加载的条件下，存储压力如何改变一个请求的实际 prefill 服务时间，以及这个变化应该怎样影响选 worker 和请求执行顺序。**

请求先排队，获得执行准入后才开始读取第 1 层 KV。随后，计算第 l 层时可以加载第 l+1 层。调度层和引擎层消费同一套服务时间估计，分别决定请求分配和执行先后。取算切换、动态选副本和等待期预取均不进入主线。

## 1. 本次修正了什么，以及为什么

用户提出的约束有道理。上一版围绕等待请求提前取回、数据就绪队列和预取提前量展开分析，偏离了本轮希望研究的场景，也引入了不必要的接收缓冲与 HBM 驻留问题。

不过，禁止等待期预取和逐层加载是两个需要分别明确的设定。前者限制读取何时开始，后者规定执行开始后怎样搬运。逐层加载本身并不自动带来 overlap；本研究再固定一种可实现的流水方式，让相邻层的加载与计算重叠。

| 上一版前提或结论 | 本次修改 | 修改原因 |
|---|---|---|
| 请求排队期间可以先取回 KV，再等待 GPU | waiting 中只保留请求与目录元数据，不发起 KV 数据读取 | 避免等待队列提前占用数据缓冲或 HBM |
| 用 `max(取回时间, GPU 排队时间) + 计算时间` 预测首 token | 改为 `执行准入前等待 + 准入后的逐层流水服务时间` | 本请求在排队期间还没有开始加载，不能用排队时间隐藏它的读取 |
| 引擎重点比较已就绪请求，存储代价通常已经付出 | 引擎比较尚未开始加载的候选请求 | 选中请求就启动它的加载与计算，存储状态直接改变待执行服务时间 |
| 将读取提交顺序和 prefill 准入顺序作为两条独立主线 | 二者在主模型中由同一次执行准入决定 | 无需再设计一套针对等待请求的预取控制器 |
| 寻找未来数据到达与 GPU 空档的匹配 | 预测各 worker 已承接工作的完成时间，以及新请求启动后的流水耗时 | 数据到达由执行启动触发，不能当作排队期间独立发生的事件 |

本次保留有限 HBM 的容量检查，但将模型结构折成固定参数，避免把缓存布局优化扩展为另一个研究问题。旧实验的观察保留，适用边界在第 8 节说明。

## 2. 执行模型先固定，防止策略偷偷增加能力

### 2.1 请求的生命周期

```mermaid
flowchart LR
    A[请求到达并选择 worker] --> W[waiting 仅存元数据]
    W --> D[引擎选择下一请求或执行批]
    D --> M[检查执行名额并预留有限 HBM]
    M --> X[启动执行并加载第 1 层 KV]
    X --> P[逐层计算并加载下一层]
    P --> F[首 token]
    F --> R[decode 使用本请求的 HBM KV]
    R --> E[请求结束并释放容量]
    S[存储可观测状态] -. 预计流水服务时间 .-> D
    S -. worker 完成时间估计 .-> A
```

“开始执行”在本文中指请求真正被选入当前执行任务，执行资源和容量已经落实，并开始第 1 层读取。它早于第一个 GPU 计算 kernel。不能把执行开始定义成“GPU 已经计算”，否则第一层 KV 何时读取会产生循环依赖。

也不能把所有 waiting 请求改名为 active，就同时发起读取。执行并发上限固定，并且只对真正启动的请求或执行批允许读取。

| 维度 | 共同设定 |
|---|---|
| 目录与 KV 来源 | 所有 worker 查询同一目录，命中前缀只能从共享存储加载 |
| 读取动作 | 命中即取，无主动重算；未命中后缀正常计算 |
| 副本与放置 | 单副本或固定选源规则，无动态复制、迁移和去重 |
| waiting | 不加载 KV，不占请求 KV 的 HBM，仅保留元数据 |
| 请求内加载 | 按模型层顺序，最多提前到当前计算层的下一层 |
| 请求内计算 | 第 l 层计算依赖该层 KV 和上一层的计算输出 |
| HBM | 执行启动前预留，容量不足留在 waiting，规则对全部策略相同 |
| 暂停与抢占 | 首轮无抢占；若加入 chunk 间暂停，已启动请求保留 active 身份及容量，不能重新当作未启动的 waiting |
| decode | 固定执行纪律，保留时间与 HBM 消耗，不优化其顺序 |

### 2.2 层间 overlap 有依据，但需要边界

缓存前缀在每一层的 KV 已经存在于共享存储中，因此加载第 l+1 层的缓存 KV 不依赖本次后缀在第 l 层算出的激活。第 l+1 层的后缀计算仍需等上一层计算完成。这允许一边计算当前层，一边读取下一层。

Mooncake 原文第 5.2 节明确描述了这样的执行方式，在每层 attention 前等待该层 KV 加载完成，并触发下一层异步加载。这支持本研究的流水设定。Mooncake 同时包含 P/D 分离和 KV 写出，本文只借用加载与计算的依赖关系，不直接继承其显存释放结论。[Mooncake 逐层 prefill](https://arxiv.org/html/2407.00079v4#S5.SS2)

LMCache 的 layerwise 文档也提供了逐层加载与计算交错的机制参照；该页面标注为已弃用的 in-process 模式，不能据此声称当前所有集成都默认具备相同行为。[LMCache Layerwise KV Transfer](https://docs.lmcache.ai/kv_cache_optimizations/layerwise.html)

实际 overlap 还需要异步传输、正确的依赖同步和可并行的硬件资源。传输与计算即使并发，也可能争用 HBM 带宽等资源。初始解析模型假设二者可有效并行，再用无 overlap 和并发降速做敏感性检查，不能直接把理想流水收益当成硬件收益。[CUDA 异步执行说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)

### 2.3 按层加载不等于整个请求只占一两层 KV

如果 decode 仍在该 worker 上执行，并且之后不再反复访问共享存储，已经加载的前缀 KV 以及新生成的后缀 KV 要保留给 decode。计算完一层后就释放该层 KV，会引入后续重读、迁移或写出，超出本轮设定。

因此，最多提前一层限制的是加载领先程度。请求结束前的 KV 总驻留量仍与模型和上下文相关。这部分可以用固定参数表达，无需模拟每个 tensor 的分配过程。

令每层每 token 的本地 KV 大小为固定参数 $\kappa_l$，单位 GB/token，则

$$
B_{i,l}=H_i\kappa_l,\qquad
M_i^{reserve}=(H_i+U_i+O_i^{max})\sum_{l=1}^{L}\kappa_l.
$$

$H_i$ 是命中前缀长度，$U_i$ 是后缀长度，$O_i^{max}$ 是所有策略均可见的输出上限。容量按峰值保守预留，实际数据随执行逐层填入。

$$
\sum_{i\in active\ prefill\ \cup\ decode}M_i^{reserve}
+M_{scratch}^{fixed}\le M_{KV}^{available}.
$$

$M_{KV}^{available}$ 已扣除权重及其他固定占用；$M_{scratch}^{fixed}$ 只计额外临时空间，最终 KV 页已在请求预留中，不能重复计账。直接搬入最终 KV 页的模型可不另设 staging 空间。

本仓库 [ModelConfig](../sim/config.py) 已把普通 K/V 表示的大小折成 `2 × 层数 × KV头数 × head_dim × 元素字节数`。本轮固定一种模型和并行部署，把它换算到实际受限的每个 GPU；若采用不同 KV 表示或压缩方式，直接更换经过核实的 $\kappa_l$。无需同时研究模型结构选择。

**这样，HBM 仍然有限，但它主要是一条执行准入不等式。** 第一轮可选择所有请求都能单独放下、且候选间容量约束不改变排序的场景来分析时间机制；随后再检查有限并发和容量紧张时的稳健性。

## 3. 核心时间公式应当怎样写

### 3.1 先把排队与执行分开

令请求到达时刻为 $a_i$，实际执行启动时刻为 $u_i$，首 token 时刻为 $F_i$。

$$
TTFT_i=(u_i-a_i)+(F_i-u_i)=Q_i+T_i^{pipe}.
$$

$Q_i$ 包含执行名额、前序请求、HBM 和共同 decode 纪律带来的准入前等待。$T_i^{pipe}$ 包含启动后逐层加载、计算、同步及首 token 输出开销。

**本请求的存储加载没有与自己的 $Q_i$ 重叠。** 启动后的层间加载和计算可以重叠；其他 worker 的传输也可以同时发生。这两类重叠必须分清。

### 3.2 一层提前的递推模型

先考虑一个执行中的 prefill 请求，不与其他 prefill 交错，忽略 decode 插入。以 $u_i$ 为时间原点。

- $x_l$ 表示第 l 层从发起读取到 KV 可供计算使用的耗时，含实际排队与传输。
- $c_l$ 表示该层的后缀计算耗时。模型把该层计算整体放在其 KV 就绪后，未进一步拆分 attention 前后的 kernel。
- $A_l,R_l,S_l,Z_l$ 分别为该层读取开始、读取结束、计算开始、计算结束的时刻。

共同的执行规则为

$$
A_1=0,\quad R_1=x_1,\quad S_1=R_1,\quad Z_1=S_1+c_1;
$$

$$
A_l=S_{l-1},\quad R_l=A_l+x_l,\quad
S_l=\max(R_l,Z_{l-1}),\quad Z_l=S_l+c_l\quad(l\ge2).
$$

第 l 层的读取在第 l−1 层开始计算时发起。这个规则明确限制了领先程度，不允许读取线程把后面所有层提前搬完。

```text
先加载第 1 层
随后同时推进两件事
    计算第 1 层    加载第 2 层
等第 1 层计算与第 2 层加载都结束
    计算第 2 层    加载第 3 层
逐层继续，最后完成第 L 层计算
```

不含固定首 token 输出开销 $h_i$ 时，递推展开为

$$
T_i^{pipe}=x_1+\sum_{l=2}^{L}\max(x_l,c_{l-1})+c_L.
$$

若各层近似同质，$x_l=x_i$、$c_l=c_i$，则

$$
\boxed{T_i^{pipe}=x_i+(L-1)\max(x_i,c_i)+c_i.}
$$

使用时再统一加上 $h_i$。这比直接写 `max(总加载, 总计算)` 多保留了流水启动和结束的开销，也比“整段加载后再算”更符合逐层 overlap。

### 3.3 存储状态如何改变未隐藏等待

将流水时间减去 GPU 实际计算时间，得到这个简化模型中的加载等待

$$
S_i^{exposed}=T_i^{pipe}-\sum_{l=1}^{L}c_l
=x_1+\sum_{l=2}^{L}\max(0,x_l-c_{l-1}).
$$

- 当每层加载快于前一层计算，后续大部分读取被隐藏，主要支付第 1 层启动等待。
- 加载慢于计算时，每层都会出现等 KV 的间隙，存储压力被放大为多次可见停顿。

同质模型给出两个区间

$$
T_i^{pipe}=\begin{cases}
x_i+Lc_i,&x_i\le c_i,\\
Lx_i+c_i,&x_i>c_i.
\end{cases}
$$

因而 $x_i/c_i$ 是比“整个存储集群忙不忙”更有解释力的变量。请求可能有很长的命中前缀，加载量大、后缀计算却少，于是几乎没有计算可以隐藏加载。另一个请求的后缀计算较多，反而能隐藏大部分存储时间。

### 3.4 公式的适用范围

$x_l$ 随其他 worker 的读取和背景负载而变化。仿真执行时应把每层读取真正提交给共享资源，按事件完成；预测器只使用可观测状态，不能预先知道实际完成时刻。不能把单个请求的带宽报价复制给全部并发请求，就当作每人独占该带宽。

若加入 decode 或 prefill batch，实际递推还需等待计算资源可用；$T_i^{pipe}$ 不再由以上闭式完整描述。先用单请求、单执行槽模型校验解析关系，再扩展为固定 batch/chunk 纪律，所有策略共享该纪律。解析模型只是一组机制基准，不宣称复现 vLLM 或 SGLang 的完整调度器。

chunk 沿 token 维度划分，layer 沿模型深度划分，二者不能互相替代。同一请求下一 chunk 会再次经过所有层，但已驻留的命中 KV 不应再加载一次。若采用 chunked prefill，必须保留这条工作量守恒规则。

## 4. 存储侧需要提供什么信息

现在两层需要的是**请求开始执行时，每层加载预计花多久，以及其中多少时间无法被计算隐藏**。主线不再预测等待请求提前取回后的就绪时刻。

| 信息 | 谁提供 | 如何使用 |
|---|---|---|
| 请求每层读取量 $B_{i,l}$ | 目录、请求长度和固定模型参数 | 决定本次实际加载工作量 |
| 源节点、共享 fabric、目标入口的可观测负载 | 存储与传输接口 | 估计每层读取排队和服务时间 |
| 预计层加载时间 $\widehat x_{i,l}$ | 共同加载成本预测器 | 代入流水递推，得到服务时间与未隐藏等待 |
| 层计算 profile $\widehat c_{i,l}$ | 计算侧 | 估计可隐藏多少加载，必须包含上下文长度影响 |
| 已承接请求、当前执行进度、HBM 预留 | worker | 估计新请求何时能够启动执行 |
| 状态时间戳与共享瓶颈标识 | 观测接口 | 判断估计是否过期、候选是否在竞争同一资源 |

最小教学估计可写为 $\widehat x_{i,l}=\widehat q+\ell+B_{i,l}/\widehat b$，但必须说明这里的 $\widehat b$ 是服务带宽还是包含排队的端到端有效吞吐，避免重复加排队。

现有 [AccessCostQuery](../sim/quote.py) 和 [StorageObservable](../sim/storage.py) 可以作为接口起点，不能将一次整请求 `quote` 简单除以层数。每层提交可能有固定开销，且提交时间不同。反过来，也不能把整请求只支付一次的连接建立开销重复收取 L 次。模型应分别声明请求级与层级固定成本。

路由时请求还在排队，当前快照不保证在实际启动时仍有效。可采用相同的短期预测或状态保持近似；队列越长，这个误差越应被报告。引擎在真正选择下一请求时重新估计，但不为估计而提前加载数据。

## 5. 调度层怎样选 worker

主决策式是

$$
w^*=\arg\min_{w\in eligible(i)}
\left[\widehat Q_w(i,t)+\widehat T_i^{pipe}(w,t+\widehat Q_w)\right].
$$

可行性包含模型兼容与请求能否最终放下。worker 当前容量不足可以形成等待；不能把“暂时没有空位”和“这个请求永远放不下”混为一谈。

$\widehat Q_w$ 应按照共同的引擎顺序，估计当前活动请求和排在本请求之前的已分配请求还需占用多久。它同时受计算和加载影响。在单 prefill 执行槽、固定 FCFS、容量不额外阻塞的简化场景中

$$
\widehat Q_w\approx\widehat T_{active,w}^{remaining}
+\sum_{j\text{排在前面}}\widehat T_j^{pipe}.
$$

不能只累加前序请求的 GPU 计算量。一个长时间等 KV 的活动请求虽然 GPU 忙碌比例不高，仍可能占着有限执行名额和 HBM。

| 存储状态进入路由的方式 | 何时可能有收益 | 必须有的对照 |
|---|---|---|
| 不同 worker 接收路径不同 | 新请求在某台 worker 上的层加载明显更慢 | 同一预测器的静态、历史和实时输入 |
| 前序请求组成不同 | 即使路径相同，存储压力也可能使某台 worker 的长命中队列耗时变长 | 两组都完整记录 waiting，避免把补记账当作接口收益 |
| 所有候选具有相同服务成本与前序工作 | 存储项共同变化，通常不改变 worker 排名 | 严格对称的无增量控制 |

全局目录对称只消除了本地命中差异，不保证队列中各类请求的流水成本相同。另一方面，所有请求必经的共同 fabric 饱和时，换 worker 不能创造新容量。路由若仍改善 TTFT，需要由等待分布、共享竞争或执行利用情况解释。

原系统的负载评分继续保留为基线。秒制增强式与 KV block 分数不能直接相加；静态、历史、实时三组使用相同的服务时间模型和动作空间，只替换存储估计来源。

## 6. 引擎怎样决定 prefill 执行顺序

### 6.1 排序现在发生在任何加载之前

当一个执行名额释放，引擎在满足共同准入规则的 waiting 请求中选下一项。被选中的请求随后才加载第 1 层 KV，并开始逐层执行。因此，**存储状态直接改变排序要比较的未来服务时间**。

| 排序方案 | 主要排序键 | 对照意义 |
|---|---|---|
| FCFS | 到达时间 $a_i$ | 默认到达序参照 |
| LPM | 命中长度 $-H_i$ | 检查长命中是否确实意味着更快服务 |
| 外生 priority | 预先给定的优先级 | 保留业务优先级维度 |
| 计算时间优先 | $\sum_l\widehat c_{i,l}$ | 测出只看 GPU 工作能解释多少收益 |
| 流水服务时间优先 | $\widehat T_i^{pipe}$ | 把未隐藏加载计入执行成本，分别使用历史与实时估计 |
| EDF | 绝对截止期 $d_i=a_i+S_i$ | 分离通用期限调度的作用 |
| 最小余量优先 | $d_i-t-\widehat T_i^{pipe}$ | 比较立即执行后还剩多少期限余量 |

这里的 $S_i$ 是 TTFT 目标。最小余量规则只是候选启发式，不保证最大 goodput。负余量请求可能已经无法达标，如果永远压在可达标请求之前，会损害总达标数；所有策略先保持相同的不丢弃和老化保护规则，同时报告长请求饥饿与最差类别表现。

### 6.2 一个无需等待期预取的优先级反转例子

以下是人为设定的四层模型，每层相同，无 decode、无额外首 token 开销，两个请求都能放入 HBM。一个 worker 同时只启动一个 prefill；后一个请求在前一个出首 token 后才开始加载自己的第 1 层。

| 请求 | 特征 | 每层计算 $c$ | 存储快时每层加载 $x$ | 存储慢时每层加载 $x$ |
|---|---|---|---|---|
| A | 长命中、短后缀 | 0.010 秒 | 0.005 秒 | 0.040 秒 |
| B | 短命中、长后缀 | 0.020 秒 | 0.001 秒 | 0.008 秒 |

存储变慢在这里表现为两类读取时间均变为原来的 8 倍。代入同一流水式

| 请求 | 存储快时的服务时间 | 存储慢时的服务时间 |
|---|---|---|
| A | $0.005+3×0.010+0.010=0.045$ 秒 | $0.040+3×0.040+0.010=0.170$ 秒 |
| B | $0.001+3×0.020+0.020=0.081$ 秒 | $0.008+3×0.020+0.020=0.088$ 秒 |

存储快时 A 服务更短。存储慢时 A 在层间持续等待 KV，B 的读取仍大部分被计算隐藏，于是 B 服务更短。LPM 和纯计算时间优先仍会选 A，使用当前流水成本的排序会改选 B。

令两请求同时到达，A 的 TTFT 目标为 0.30 秒，B 为 0.10 秒。存储慢时的结果为

| 执行顺序 | A 的首 token | B 的首 token | 达标请求数 |
|---|---|---|---|
| A 然后 B | 0.170 秒 | 0.258 秒 | 1 |
| B 然后 A | 0.258 秒 | 0.088 秒 | 2 |

两种顺序的读取量、GPU 计算量、最后完工时刻完全相同，GPU 总计算都为 $4×(0.010+0.020)=0.120$ 秒。排序通过把等待分给不同请求改善达标数，无需增加 GPU 利用率，也没有为等待请求预取。

这只是存在性算例。动态共享竞争、不同 deadline 和 batching 会改变结果；它不证明流水服务时间最短优先在一般系统中最优。

### 6.3 层内流水属于所有策略共有的执行能力

所有基线和增强策略都使用相同的逐层加载、相同的一层提前限制以及相同 HBM 容量。不能给基线整段阻塞加载、给增强组层间 overlap，然后把差值归因于存储感知排序。

验证顺序建议从单执行槽开始，先将排序效果手算清楚，再扩展到固定大小的执行批。批启动时被选中的成员才能开始加载；未入批请求仍在 waiting。批内的层同步和 GPU 计算模型对各策略一致，不能把每个请求的单独服务时间直接相加当作精确 batch 时间。

运行中的层就绪检查是数据正确性的条件；是否让其他已启动请求或 decode 在某层等待时推进，是另一项共同引擎能力，应显式声明。这里不再把“未加载的 waiting 请求先变成 ready”作为排序前提。

## 7. 指标与实验应当如何解释

| 机制 | 可能改善的指标 | 不保证改善的指标 | 解释证据 |
|---|---|---|---|
| 避开某 worker 的拥堵路径 | TTFT、未隐藏加载等待 | 总物理带宽 | 逐层加载时间、worker 选择分歧 |
| 按流水工作量均衡队列 | TTFT 尾部、worker 忙闲不均 | 共同存储瓶颈的容量上限 | 前序队列的预计及实际服务时间 |
| 改变 prefill 执行顺序 | 部分类别 TTFT、SLO 达标数 | 总 GPU 忙碌时间、完工时长 | 执行次序、首 token 时间、谁承担更多等待 |
| 层间 overlap | 流水服务时间、等 KV 空档 | 物理 GPU 算力 | 相邻层时间线，加载与计算实际交集 |
| HBM 准入限制 | 容量安全 | 单独降低 TTFT | 预留峰值、准入阻塞时间 |

单执行槽、固定服务时间、同一批请求全部处理完的情形中，重排通常不改变服务时间总和。多 worker 动态竞争或 batching 下，顺序会改变资源争用和批组成，利用率才可能进一步变化。不能把 GPU 利用率上升设成排序有效的必要条件。

在逐层执行中，请求处于 active 不表示 GPU 始终在计算。等待 KV 的时间要单独记；只要传输线程活跃就把整段算成 GPU busy，会掩盖研究目标。

首报 TTFT 达标率与分位数，并保留 TTFT/TPOT 联合 serving goodput。decode 顺序虽然固定，prefill 仍可能延长迭代时间，故 TPOT/ITL 继续作为保护指标。资源统计统一窗口；已等待但未出首 token 的请求进入超时和未完成统计。

主实验每个机制都做静态、历史、实时三档预测。普通 EDF 或短作业排序相对 FCFS 的收益，只能证明排序本身有效；实时输入相对同算法、充分调优的历史预测的额外收益，才支持新增存储状态接口。

## 8. 原基线与 G0/G1/G2 如何衔接

### 8.1 保留原基线的决策角色，统一新的执行能力

沿用 [公式级梳理](调度与执行顺序默认策略公式级梳理-20260908.md) 和 [五工作映射](五工作的Scheduler-Engine修改与主流默认实现-20260904.md) 的分类。下表是本场景的实验映射，不宣称完整复现各产品。未在本次逐项复核的具体版本行为，正式实现前仍需查原文。

| 方案族 | 在本场景保留什么 | 需要控制的差异 |
|---|---|---|
| Dynamo、SGLang Router、MindIE Motor | 原有负载或缓存亲和路由评分 | 全局命中相同不代表各自负载定义相同；不要都写成同一个 `gpu_wait` 后再声称验证等价 |
| Preble、Llumnix、TensorCast | 既有实例分配与公平调度角色 | 迁移、复制、放置变化不进入本轮 |
| Mooncake | 传输、排队、prefill 共同参与决策的近邻参照 | 本文只采用共同的逐层加载能力，固定副本与取算动作 |
| Kairos、DistServe | 原映射中的 P/D 约束与资源配置参照 | 固定 worker 部署和执行能力，避免从偏转或扩容获得额外收益 |
| vLLM、SGLang | FCFS、外生 priority、可选 LPM 等顺序基线 | 全部在执行启动后加载，全部共享层间 overlap；LPM 不标成 SGLang 当前默认 |
| TensorRT-LLM | 保守容量准入这一维度 | 容量规则与排序键分开，具体版本默认值待核实 |
| Sarathi-Serve、FastServe | 原映射中的 chunk 和计算调度参照 | chunk、抢占与 batch 能力只能作为共同配置或另做消融 |
| Cascade | 顺序与恢复策略分开建模的角色 | 主线只改变顺序和估计来源，固定 fetch |
| AAFLOW+、Cache Flow | 原映射中的取算选择、部分恢复角色 | 放入扩展，不能用于证明固定 fetch 的路由或排序收益 |

上一轮已核验的基线修正继续保留。Dynamo 同时有 prefill、decode 等负载项；SGLang 官方参数表的 `schedule-policy` 为 FCFS，LPM 为可选项；vLLM 也有 FCFS/priority 配置。本文的统一加载时机是实验设定，不声称这些系统默认都禁止等待期加载。[Dynamo 成本模型](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/modular-components/router/routing-concepts)；[SGLang 参数表](https://docs.sglang.io/docs/advanced_features/server_arguments)；[vLLM 调度配置](https://docs.vllm.ai/en/latest/api/vllm/config/scheduler/)

Mooncake 原文已讨论分布式 KV 复用与发送端拥塞，并采用逐层流水，不能把它收窄成只处理 P/D 传输，也不能把层间 overlap 本身当作本研究新贡献。本研究要验证的是固定共享存储场景中，状态反馈对两层决策的具体增量。[Mooncake 原文](https://arxiv.org/html/2407.00079v4)

### 8.2 旧实验不能直接回答修订后的问题

[现有 M1 引擎](../sim/m1.py) 在到达时启动整段 `_fetch()`，完成后才允许 prefill 准入；它没有逐层加载与计算事件。这与本次执行流程不同。

| 旧观察或实现 | 本次应如何解释或处理 |
|---|---|
| G1 动态取算的改善或退化 | 仍是旧动作空间下的结果，不能外推为固定 fetch 的顺序收益 |
| G2 多种排序打平 | 只说明旧“先取回再排计算”的执行规则和负载下未测出增量，不预测新规则下也打平 |
| D1a 与 D2b 相同 | 未隔离 worker、副本、取算三个动作，不能用于否定纯 worker 路由 |
| 到达即取、`fetch_done` 才准入、HBM 只在准入时记账 | 需要改为执行启动时预留容量并加载首层，不再维护等待期已取回集合 |
| `wait_est()` 不计 waiting，排序键到达时冻结 | 完整记录已承接工作，并在执行选择时按最新共同快照更新估计 |
| 整段 `curve(N)` 预测与实际 `curve(chunk)` 累加 | 逐层/逐 chunk 的预测与执行要一致，不能机械平分非线性曲线 |
| 多 chunk 资源归因与统计窗口问题 | 保留上一版审计结论，正式新实验前做守恒与窗口复核 |
| attain/goodput 实际同时检查 TTFT 与 TPOT | 修正旧结果报告中“TPOT 不计入达标”的说明，另报 TTFT 单项达标 |

上一版把排队与取回直接相加视作当前旧实现的问题，是基于它到达即取的实际行为。**新模型禁止等待期加载后，准入前排队与准入后服务相加是正确的。** 但服务内部应使用层间流水，不能再把整段加载和整段计算直接串联。

原报告与正式图保持原样。本次只修改研究文档，不重跑、改写旧结果，也不宣称当前代码已符合新设计。

## 9. 下一轮实验怎样避免盲试

### 9.1 先验证执行模型，再比较策略

| 顺序 | 实验问题 | 关键对照或不变量 |
|---|---|---|
| 1 | 禁止等待期加载是否落实 | 所有层读取满足 $A_{i,l}\ge u_i$；waiting 的 KV 数据占用为零 |
| 2 | 层间依赖与容量是否正确 | 计算不早于该层读取及前层计算完成；最多提前一层；HBM 预留始终安全 |
| 3 | 流水时间是否符合手算 | 单层退化为加载加计算；同质多层吻合闭式；快存储和慢存储两区间都检查 |
| 4 | 统计是否守恒 | 每请求加载字节等于 $\sum_l B_{i,l}$；后续 chunk 不重复加载；GPU 等数据不算 busy |
| 5 | 并发共享是否真实 | 多 worker 层读取竞争同一存储/fabric，实际服务不超过资源容量 |

先固定单模型参数、单副本、无主动重算。单请求解析验证可暂时关闭 decode；系统级比较恢复共同 decode 纪律，并保留其 HBM 和执行干扰。两种实验的简化边界要分别标明。

### 9.2 用请求的加载/计算比来组织策略实验

| 实验问题 | 固定什么 | 改变什么 | 允许出现的否定结果 |
|---|---|---|---|
| 存储压力会不会改变执行优先级 | 单 worker、同样 HBM、同样层间 overlap | 请求 H/U 组合、背景带宽，使 $x/c$ 跨过 1 | 各请求排名始终相同，新增状态没有排序增量 |
| 排序能否改善 TTFT/SLO | 固定路由、fetch、副本、并发和 batch 规则 | FCFS/LPM/计算优先/历史流水优先/实时流水优先/期限规则 | 无多候选竞争时打平；总体改善但长请求受损 |
| 选 worker 能否受益 | 固定引擎顺序，全部记录相同 waiting 工作 | 路径拥堵或各 worker 前序请求组成 | 严格对称候选时无增量，共同瓶颈容量不增加 |
| 状态放在哪层更有用 | 相同执行能力、记账和动作空间 | Router 历史/反馈 × Engine 历史/反馈 | 两层信息重复，交互为零或负 |
| 估计是否及时 | 已有决策分歧的场景 | 状态年龄相对层耗时及排队时长、估计误差 | 路由时信息在启动前过期，历史预测已足够 |
| 结论是否依赖理想流水 | 固定决策信息与读取量 | 无 overlap、一层 overlap，以及固定的并发降速模型 | 理想收益在实际资源争用下消失 |

不再保留等待期预取、就绪时间对齐、独立读取提交队列的主实验。若后续增加这些能力，需要另行扩展研究范围。

冒烟除瓶颈与 SLO 天花板外，还要记录多候选决策比例、排序或 worker 选择分歧率、每层未隐藏等待及 HBM 阻塞时间。若新旧决策相同，先判断该场景有无信息增量，无需继续靠扩大种子数期待不同结论。

### 9.3 保留可检验的收益边界

本轮最值得检验的机制链为

```text
共享存储状态变化
  → 不同请求的层加载时间变化
  → 加载/计算比例与未隐藏等待发生变化
  → 请求服务时间或 worker 队列完成时间的排名变化
  → 分配或执行先后改变
  → TTFT、类别达标和资源等待分布改变
```

低压力时大部分层加载被计算隐藏，实时反馈可能只改善很小的启动开销。高压力时不同请求的读取代价都上升，但只有排名或截止风险发生差异，排序才可能受益。存储饱和时重排仍可改变谁先达标，不会凭空增加带宽。

正式设计先冻结场景、主指标、候选保护规则和估计器参数。沿用 [纲领 v1.1](共享KV压力感知调度-研究推导与仿真实验纲领-v1.1-20260907.md) 的 CRN、多种子配对及验收约束，至少 10 个种子。相对充分调优的历史基线，容量改善 5% 或主尾延迟改善 10% 的既有实用门槛继续适用，同时保护有效吞吐、decode 和类别服务。类组非劣按原样本门槛及 1 个百分点容许幅度用区间判断。

本次改变了执行模型，正式运行前必须冻结修订后的实验设计，不能把旧 G1/G2 参数和结果直接当成新模型的验收。实现后按仓库流程完成单元测试、冒烟、全量实验，再新增嵌图结果文档。

## 10. 给汇报使用的通俗解释

每台 worker 像一间厨房。排队的订单只登记，不提前把食材搬进厨房。轮到一份订单、操作位置和存放空间都确认以后，才开始领取它的材料。

一道菜分几步做。做第 1 步时领取第 2 步的材料，做第 2 步时领取第 3 步的材料。配送快于烹饪时，大部分等待被藏住；配送慢时，每一步都可能停下来等。已经领进来的材料仍有存放成本，所以接单执行前需要确认整份订单放得下。

派单时要估计每间厨房已接的订单还要忙多久。决定先做哪一单时，要比较这单实际占用多久以及客人还能等多久。只看需要动手的时间，会漏掉每一步等材料的停顿。

| 研究层次 | 一句话说明 |
|---|---|
| worker 选择 | 按包含等 KV 的实际工作量分配请求 |
| prefill 顺序 | 比较加载与计算重叠后，谁先执行更有利于及时完成 |
| GPU 指标 | 区分真正在算和已经开始执行但仍在等数据 |
| HBM 约束 | 排队不提前搬数据，开工前确认容量，执行中按层填入 |
