## 0. 一页总表（每方案一行核心公式）

| 方案 | 层 | 核心决策式 |
|---|---|---|
| Dynamo `kv_router` | 调度 | `cost = scale·max(0, prefill块 − Σ_tier credit_tier·命中) + decode块`，argmin；**分层 = 静态 credit 折扣** |
| SGLang Router `cache_aware` | 调度 | 命中领先 > max(abs_threshold, rel_threshold·len) ? 粘缓存 : 最低负载 |
| MindIE Motor | 调度 | 分发到负载最低的 P/D 实例 |
| Preble | 调度 | `argmin(L+M+P)`；等待队列按缓存未命中率分组、组 g 得 2^(g−1) 个名额比例轮询 |
| Mooncake Conductor | 调度 | `TTFT > T_transfer + T_queue + T_prefill` 才选远端命中；T_transfer 显式含发送节点拥塞 |
| Kairos | 调度 | `T_KV传输 vs 排队+本地prefill` 比较 + D 侧 TBT 准入约束 |
| Llumnix | 调度 | 派发到剩余负载最小实例 + 周期性迁移再平衡 |
| DistServe | 调度（离线） | 在 (P 副本数, D 副本数, 并行度) 空间仿真搜索，最大化每 GPU goodput |
| vLLM | 引擎 | FCFS/priority 排 waiting；每步**先 decode 全量**、剩余 token 预算切 prefill；KV 池水位触发抢占（默认 recompute） |
| SGLang | 引擎 | `lpm` 按前缀命中长度降序（含 in-batch 去重、队列>128 降级 FCFS）；KV 不足时 retract（保留进度） |
| TensorRT-LLM | 引擎 | 准入不等式：`free_KV ≥ ctx+max_out`（GUARANTEED_NO_EVICT，默认）vs `≥ ctx`（MAX_UTILIZATION） |
| Sarathi-Serve | 引擎 | `chunk = min(B − D, 队首剩余 prefill tokens)`，FCFS admission + decode 优先（vLLM V1 原型） |
| FastServe | 引擎 | skip-join MLFQ：按估计剩余计算量直接跳插优先级，token 粒度可抢占 |
| Cascade | 引擎 | `Budget = SLO − γ·½(L_act+L_max)`，升序执行；调度 σ 与 KV 恢复 φ 联合 max Goodput |
| AAFLOW+ | 引擎 | 逐请求 `min(T_transfer, T_recompute)` |

**共同画像**：调度层公式的负载项全是**计算侧**量（KV blocks、token 速率、排队时长），介质差异至多以静态折扣出现；引擎层公式的输入只有**到达时间 / 前缀长度 / token 预算 / KV 池水位**。唯二例外——Mooncake（传输拥塞进决策，但只服务 P/D 传输与副本选择）与 Cascade（有效带宽进决策，但只在单实例内）——与本仓库方向（共享存储集群压力同时反馈 D1 与 D2）仍然错位。

## 1. 预备区分：静态命中折扣 vs 动态取出耗时

这是理解"分层被怎么考虑"的关键。两种建模方式：

- **Dynamo（静态记账）**：知道某段前缀 KV 命中在哪个介质（GPU 显存 / 主机内存 / 磁盘 / 共享缓存），但这只体现为一个**固定折价系数**（tier credit，配置项常数）——"disk 命中算 x 个 block 的功劳"。介质差异被压缩为"这个命中能抵扣多少 KV block 的 prefill 计算量"，**不随介质当前带宽 / 队列 / 拥塞变化**。它回答"命中身份值多少分"，不回答"现在取它要多久"。
- **Cascade（动态成本）**：恢复时间用"**负载下的有效带宽**（effective bandwidth under load）"估计——同样的 CPU DRAM 命中，存储忙时估算的恢复时间更长，长过重算时间就改重算。这才叫消费介质侧实时状态（但仅单实例内）。
- 佐证"传感器在、没人用"：LMCache 已公开 L1↔L2 端到端有效吞吐（submit→complete，含排队 + 网络 + 盘 I/O）、inflight 等指标（见五工作文档 §3.3），默认只用于监控。

## 2. 调度层：请求往哪发——打分公式

### 2.1 NVIDIA Dynamo `kv_router`（默认模式）

来源：[Routing Concepts（官方 KB）](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/routing-concepts)、[Router Guide](https://docs.nvidia.com/dynamo/v-0-9-1/components/router/router-guide)。

**输入**：worker 通过 KV 事件（`BlockStored` / `BlockRemoved`）上报每个 prefix block 所在层；router 维护全表。**输出**：选**成本最小**的 worker。每个候选 worker 的成本（货币单位 = KV block）：

```text
raw_prefill_blocks      = active_prefill_blocks + incoming_prompt_blocks
                          （该 worker 已在跑的 prefill 工作量 + 本请求未命中的 prompt 块数）
overlap_credit_blocks   = device_credit + host_credit + disk_credit + shared_cache_credit
                          （本请求在该 worker 各层命中的块数 × 各层折价系数）★分层在这里★
adjusted_prefill_blocks = max(0, raw_prefill_blocks − overlap_credit_blocks)   （折扣后下限为 0）

potential_decode_blocks = active_decode_blocks + incoming_active_blocks
active_request_blocks   = decode_active_request_weight × active_requests      （默认权重 0，可选开）

cost = prefill_load_scale × adjusted_prefill_blocks
     + potential_decode_blocks
     + active_request_blocks
```

要点：

1. **统一货币是 KV block**：命中越多 → prefill 工作量被抵扣越多 → 成本越低。不是"分数相加"而是"**活儿抵扣**"模型：`cost ≈ 这个 worker 为这个请求还要算多少 + 它已背了多少 decode 负担`。
2. **分层 = credit 折价**：device（GPU）/ host（内存）/ disk / shared-cache 四类命中给不同 credit（数值为配置项，官方 KB 未列默认常数——以 [Configuration and Tuning](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/routing-concepts) 所引配置文档为准，**待核实具体默认值**）。另有 `overlap_score_credit_decay`：缓存富但 prefill 已过载的 worker，其 device credit 打折——但该"动态"由**计算侧负载**驱动，仍与存储介质侧带宽无关。
3. **负载项精细化（可选项）**：默认 prefill 按输入 token 全额计价直到首 token；`--router-prefill-load-model aic` 时改用 AIConfigurator 的 prefill 时长预测、以最老 active prefill 为时间锚点做衰减。decode 侧默认按 active KV blocks 计；可开 output block 估算（有期望输出长度时按进度给分数权重）。
4. **选择与兜底**：先按 allow-list / exact pin / DP-rank / taint / busy-threshold 过载状态过滤，再对 cost 取 argmin（`router_temperature > 0` 时对归一化 cost 做 softmax 采样防 herd）。无 KV 事件时退化为 round-robin / random。

### 2.2 SGLang Router `cache_aware`（默认策略）

来源：[SGLang v0.4 博客（算法描述）](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/)、[sglang-router（PyPI，参数文档）](https://pypi.org/project/sglang-router/)、[DP Router 指南](https://sgl-project.github.io/advanced_features/dp_dpa_smg_guide.html)。

router 为每个 worker 维护一棵**近似 radix tree**（随路由过的请求惰性更新）：

```text
对每个 worker：hit_i  = 近似树与本请求的最长匹配前缀
              load_i = 归一化负载（inflight + 队列估计，映射到 [0,1]）
两个候选：
  A = 命中最长的 worker（cache affinity）
  B = 负载最低的 worker（least-loaded / power-of-two 抽样选出）
若 hit_A 对 hit_B 的领先 ≤ max(cache_aware_balance_abs_threshold,
                                cache_aware_balance_rel_threshold × prompt_len) → 发给 B（负载优先）
否则                                                                  → 发给 A（局部性优先）
```

即**双阈值滞后切换**：命中优势明显就粘缓存，否则保均衡。`power_of_two` 策略 = 随机抽 2 个 worker 取负载低者（低开销近似 least-loaded）。

### 2.3 MindIE Motor

来源：[MindIE Motor 简介（昇腾官方文档）](https://www.hiascend.com/document/detail/zh/mindie/300/mindiemotor/motordev/user_guide/introduction.md)。

一句话：把请求分发到**负载最低**的 Prefill/Decode 实例（纯负载均衡，无 KV 局部性感知）。`recompute_enabled` 是 engine 返回 `stop_reason=recomputed` 后的**失败重试**语义，不是调度动作（五工作文档 §2.2 已核实）。

### 2.4 论文侧

**Preble（arXiv:2407.00023，[原文](https://arxiv.org/html/2407.00023v2)）**——分布式全局前缀树 GLB + 两级公式（Algorithm 1 / Algorithm 3 摘录）：

```text
实例选择（E2 算法）:  对每个实例算 LoadCost = L + M + P，取最小
  L = (active_input_tokens + pending_input_tokens) / input_token_rate     # 算力积压
  M = active_memory + pending_memory − available_memory                   # 内存积压
  P = (avg_active_output_tokens + pending_output_tokens) / output_token_rate  # 输出积压
（前缀命中通过抵扣 pending_input_tokens 进入 L——与 Dynamo 同思想）

等待队列优先级（本地 queue，比例轮询防饿死）:
  按缓存未命中率把请求分进 P 个组: g = ⌈R_p × P⌉   （未命中率越高组号越大）
  每轮组 g 分到 2^(g−1) 个调度名额 → 命中差（被 LPM 类策略亏待）的请求获得指数级补偿
（GLB 树的更新由各实例周期性上报缓存未命中率 >10% 触发）
```

**Mooncake Conductor（arXiv:2407.00079，[原文](https://arxiv.org/html/2407.00079v4)）**——论文 §4.2 Algorithm 1 摘录（**唯一显式把 KV 传输拥塞写进决策**的主流工作）：

```text
for 每个预填充实例 p:
    prefix_len = 本请求在 p 上已缓存的匹配长度
    T_queue    = p 的预填充排队时间（指数加权平均: T = α·T_prev + (1−α)·T_cur）
    if best_prefix_len / prefix_len < kvcache_balancing_threshold:   # 本地命中已够好
        T_prefill = EstimatePrefillExecutionTime(len(tokens), prefix_len)
        if TTFT_SLO > T_queue + T_prefill: 选 p
    else:                                                            # 别处命中明显更长
        T_transfer = EstimateKVCacheTransferTime(p ← best_instance, best_prefix_len − prefix_len)
        T_prefill  = EstimatePrefillExecutionTime(len(tokens), best_prefix_len)
        if TTFT_SLO > T_transfer + T_queue + T_prefill: 选 p
D 实例按负载均衡选
若预测 TTFT/TBT 超 SLO → 提前拒绝（HTTP 429）      # SLO 驱动的过载保护
若 best_prefix_len / p.prefix_len > 阈值 → 把热点 KV 从最佳实例迁到 p   # 负载/命中再平衡
```

论文原话强调 `T_transfer` 的预测难点："不仅由数据量决定，还取决于**当前网络状态，尤其是发送节点是否拥塞**"。与本仓库方向最接近，但其拥塞项只为 P↔D 传输与副本选择服务，没有把共享存储集群压力反馈到 engine 的执行顺序 / 取算权衡。

**Kairos（arXiv:2607.02043，五工作文档 §4.2 已核实）**：dispatcher 每 100ms 收节点状态；deflection 判据 = 比较 `T_KV-transfer = KVBytes/Bandwidth` 与"P 侧排队 + 本地 prefill 时间"；D 侧准入条件 = `decode batch size + KV occupancy + 新增 prefill chunk` 仍满足 TBT SLO。

**Llumnix（OSDI'24，[论文页](https://www.usenix.org/conference/osdi24/presentation/sun-biao)）**：新请求派发给"预测剩余负载最小"（running + queued 的剩余 token 总量）的实例；运行中定期在负载最高/最低实例间**迁移请求 + KV**（按迁移成本与请求优先级挑选），另有 consolidation 模式把请求收拢以释放实例。（机制级描述，论文未给单一闭合公式。）

**DistServe（OSDI'24，[论文](https://arxiv.org/html/2401.09670v3)）**：离线放置搜索——给定 SLO，在 (P 副本数, D 副本数, 各自并行度) 空间里仿真搜索，**最大化每 GPU goodput**（同时满足 TTFT/TBOT 的吞吐）。不做事中逐请求路由。

**TensorCast（arXiv:2608.06007，五工作文档 §4.1 已核实）**：计算负载 ↔ KV locality 联合打分路由 + 请求/KV 迁移动作。

## 3. 引擎层：请求按什么顺序执行

### 3.1 调度步骨架（Orca 迭代级调度）

Orca（arXiv:2206.11198，[论文](https://arxiv.org/abs/2206.11198)）确立**迭代级调度**（continuous batching）：引擎每个 decode 迭代结束都重新决策批里放谁。所有现代引擎共用骨架：

```text
每个 engine step:
  ① 处理 running 列表：为其中每个请求的下一步 decode 分配 KV block
     └─ 分配失败（KV 池不足）→ 抢占（vLLM: preemption / SGLang: retraction）
  ② 处理 waiting 队列：按调度策略排序，逐个 admission 进 running（prefill 开始）
     └─ token budget 用完就停，剩下的等下一步
"顺序"由两件事决定：②里 waiting 的排序策略（fcfs/lpm/priority…）
                    ①里 budget 在 decode/prefill 间的分配方式
```

### 3.2 vLLM（V1）

来源：[SchedulerConfig 文档](https://docs.vllm.ai/en/latest/api/vllm/config/scheduler/)、[Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/)、[V1 chunked prefill 调度讨论](https://discuss.vllm.ai/t/v1-chunked-prefill-scheduling-policy-how-prefill-would-be-scheduled/146)。

**`fcfs`（默认）的含义**：waiting 队列按**到达序**排队，admission 从队首逐个取；**running 内部不重排**——进了 running 的 decode 请求每步固定推进 1 token，除非被抢占。FCFS 只管"新请求进批的顺序"。

**`priority` 的含义**：waiting 队列改按请求自带的 priority 值排序，**值小的先调度，同值按到达时间**（文档原文："lower value means earlier handling; time of arrival deciding any ties"）。priority 是调用方显式传的数字——没有任何自动的 SLO / 紧迫度推断（这正是 Cascade 批评并替换的点）。

**chunked prefill 与 FCFS 的配合**（文档原文："In V1, chunked prefill is enabled by default whenever possible. With chunked prefill enabled, the scheduling policy **prioritizes decode requests**. It batches **all pending decode requests** to the batch before scheduling prefills"）：

```text
每步 token budget = max_num_batched_tokens（如 2048）
① 先放 running 里全部 pending decode：每个请求 1 token
② 剩余预算给 waiting 队首的 prefill：
     若队首 prompt 剩余 tokens ≤ 剩余预算 → 整个进批
     若超出 → 只切出"剩余预算"大小的一块，本步算这块，
              剩余部分下步继续切（同一请求可连续多步占队首）
③ 队列内部顺序始终是 FCFS（或 priority）排序，budget 决定"切到谁为止"
```

数值例子：budget=2048，running 有 500 个 decode（占 500 token）→ 剩 1548；队首 prompt 4000 tokens → 本步 prefill 1548，下步再 1548，再下步 904，三步完成；期间新到的 prefill 请求都排在后面。

**"优先 decode"的具体含义**：不是重排队列，而是**预算分配顺序**——decode 先拿满，prefill 只吃剩余。效果：新到的长 prefill 永远挤占不了正在 decode 的请求的迭代节奏，TBT 稳定（Sarathi-Serve 无停顿思想，vLLM V1 直接采纳）。相关参数：`long_prefill_token_threshold`（超过该值的超长 prompt 被特殊处理/推迟细切，默认 0 关闭）；`scheduler_reserve_full_isl=True`（admission 前校验全 ISL 装得进 KV，防过准入抖动）。

**"显存压力触发抢占"的具体含义**：running 的 decode 每步要 +1 token 的 KV block；当 KV 池不足以让所有 running 请求继续（且已低于 `watermark` 预留水位）时，scheduler 从 running **末尾（最近加入的请求）**开始抢占：释放其全部 KV、放回 waiting。两种模式——**recompute**（默认：`num_computed_tokens` 清零，回来时从头重算，白算的部分作废）与 **swap**（V0 可选：KV 换出到 CPU 内存，重入时换回；V1 重构后以 recompute 为主）。触发器**只有 HBM/KV 池水位**，与外部存储压力无关。

### 3.3 SGLang 引擎内 `--schedule-policy`

来源：[`schedule_policy.py` 源码（main 分支，2026-09-07 核查）](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_policy.py)、[Server Arguments](https://sgl-project.github.io/advanced_features/server_arguments.html)。

排序都作用于 waiting 队列：

| 策略 | 排序键（源码逻辑） |
|---|---|
| `fcfs`（默认） | `wait_queue_entry_time` 升序，不重排 |
| `lpm` | 对每个等待请求在 radix tree 上 `match_prefix` 得 `num_matched_prefix_tokens`，**按命中长度降序**（cache-aware）。两个附加逻辑：**(a) in-batch 去重**——树匹配 ≤32 token（`IN_BATCH_PREFIX_CACHING_CHECK_THRESHOLD`）的请求再对"模拟等待队列树"匹配，若与其他等待请求共享前缀达到去重阈值则赋 `float("inf")` 排最后（同一前缀只算一次，避免重复 prefill）；**(b) 队列过长降级**——`waiting_queue > 128` 时退回 FCFS（前缀匹配开销过大）。radix cache 关闭时同样降级 FCFS |
| `dfs-weight` | 调 `tree_cache.dfs_weight_order()`，按 radix tree 深度/共享度加权排序（权重计算在 `radix_cache.py`；面向 multi-chat 多轮对话场景） |
| `random` | `random.shuffle(waiting_queue)` |
| `lof` | longest output first（`max_new_tokens` 降序 tiebreak） |
| `priority` | 排序键前置 `priority` 字段；方向可配 `schedule_low_priority_values_first`（默认小值先） |
| `routing-key` | 与 running 批中同 routing_key 的"热"请求优先（DP 亲和，`(0, -count, key)` 键） |

**SGLang 的"抢占" = retraction**（[调度器架构文档](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/03-scheduler.md)）：decode 阶段 KV 池不足以让所有 running 请求 +1 token 时，`retract_decode()` 把部分 running 请求**退回 waiting（保留已算 KV，回来不重算前缀）**，同时把 `new_token_ratio`（每请求期望生成 token 数估计，受 `--schedule-conservativeness` 控制）调保守。与 vLLM 的区别：SGLang 保留进度只重排队，vLLM 默认丢弃进度重算。

### 3.4 TensorRT-LLM（第三种哲学：不重排，只控准入）

来源：[Useful Runtime Options（官方调优指南）](https://nvidia.github.io/TensorRT-LLM/performance/performance-tuning-guide/useful-runtime-flags.html)、[SqueezeBits 对比分析](https://blog.squeezebits.com/vllm-vs-tensorrtllm-4-which-scheduler-wins--33083)。

顺序仍是到达序，差异在 admission 不等式：

- **GUARANTEED_NO_EVICT（默认）**：`free_KV ≥ context + max_new_tokens 的最大需求` 才准进批 → 任何运行中请求**保证全程不被逐出**。代价：按最坏输出长度预留，利用率低。
- **MAX_UTILIZATION**：`free_KV ≥ 当前 context 需求` 即准进 → 尽量塞满，输出超预期时可能逐出。
- 新版 Executor 另有动态 KV 分配的 `kMAX_UTILIZATION` 变体（塞满且不逐出）。

### 3.5 论文侧

**Sarathi-Serve（OSDI'24，[论文](https://arxiv.org/html/2403.02310v1)）**——vLLM V1 调度器的原型：

```text
每迭代 token 预算 B：
  batch = {全部 running decode}（各 1 token）
  c = min(B − #decode_tokens, 队首请求剩余 prefill tokens)   # prefill chunk 大小
  admission 顺序 = FCFS；chunk 尺寸对齐 tile quantum 使每迭代计算量均匀
⇒ 每迭代耗时 ≈ 常数 ⇒ TBT 有上界（无停顿/stall-free），长 prefill 不阻塞 decode
```

**FastServe（arXiv:2305.05920，[论文](https://arxiv.org/abs/2305.05920)）**：skip-join MLFQ——N 级优先队列，长请求逐级降级、新短请求可在 **token 粒度抢占**长请求；skip-join 指输入长度已知时按估计剩余计算量**直接跳插**到对应优先级（SJF 思想），无需从最低级排起。

**Cascade（arXiv:2608.06557，五工作文档 §4.3 已核实）**——唯一用 SLO 预算替换 FCFS 的工作：

```text
Budget_i = SLO_i − Lr_i
Lr = ½(L_actual + L_max) × γ   （γ>1 guardband；L 由离线训练的 TTFT estimator 预测，
                                 特征 = context length + 跨 tier 命中 profile + 当前负载）
执行顺序 = Budget 升序（最紧迫先）；Tier-1（快超时）/ Tier-2 两级队列
恢复策略 φ（per-request：从哪个 tier 取 / prefetch / retain in HBM / recompute）与 σ 联合：
  max Goodput over (σ, φ)；恢复耗时按"负载下有效带宽"估 → 取太慢就重算
```

**AAFLOW+（arXiv:2607.10987）**：逐请求 `T_transfer = KVBytes/BW + latency` vs `T_recompute = T_prefill`，取小者（BW 为配置/扫描值，非实时）。

**Cache Flow（arXiv:2604.25080）**：恢复拆 token × layer × GPU 三维片段，每片段独立选 fetch 或 recompute，I/O 与 GPU 计算重叠，最小化恢复 makespan。

## 4. 对本仓库方向的含义

把 §0 总表最后一层含义说透：

1. **D1 与 D2 的默认公式里都没有存储侧实时变量**。Dynamo 的分层 credit 是"命中身份"的静态折价；SGLang lpm 只消费前缀长度；vLLM/SGLang/TRT-LLM 的顺序键只有到达时间/优先级数字/前缀长度/水位。
2. Mooncake（传输拥塞 → T_transfer）与 Cascade（有效带宽 → 恢复耗时 φ）证明了"取出耗时"进决策式是可行且有收益的，但前者限于 P/D 传输场景、后者限于单实例内。
3. 因此纲领 v1.1 的定位不变且被本轮公式级核查**加强**：把共享 KV 存储集群级压力（队列深度、有效带宽、incast）作为一等反馈信号，同时改写 D1（路由打分式）与 D2（排序键/取算权衡）两处公式，仍是空白。落地时可参照：Dynamo 的 cost 单位（KV block）与 LMCache 的有效吞吐指标天然同构，可直接把"命中折扣"升级为"按当前实测有效带宽折算的取出耗时"。
