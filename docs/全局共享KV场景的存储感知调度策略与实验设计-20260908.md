## 0. TL;DR

1. **一致性判决：总体一致，需三点锚定。** 纲领 v1.1 的核心命题（存储侧运行状态反馈 → 路由与恢复/顺序的联合决策）、信息阶梯 I0–I4、History 强基线与统计/验收规则，与"存储状态影响调度层选 worker、引擎层定执行顺序"的研究意图一致；v2 代码已具备全局可见目录与共享存储拓扑。但需把本文 §2 的**场景锚定 S-G** 冻结为第一阶段主场景（当前代码默认 `local_cache_gb=12`，本地缓存维度尚未移出），把 **D2 执行顺序策略族**显式纳入基线与增强体系（纲领只把它定为"共同引擎纪律"），并依赖尚未建成的 **M1 引擎**（decode + waiting 队列 + HBM）。
2. **场景锚定的关键推论：** 在"所有 worker 全局可见、本地无缓存不对称"的 S-G 场景下，Dynamo 式 prefix-overlap 打分对所有 worker 相同 → **主流 D1 路由基线全部退化为纯负载均衡**（RR / least-loaded）。存储状态进入 D1 的合法通道只剩三条：worker×源×动作联合决策、源/副本选择、非对称路径。这是本文所有 D1 增强策略的设计依据，也是 G3 负控制的验证对象。
3. **策略族：** D1 三个增强（动态取出成本路由 D1a、压力感知源选择 D1b、存储压力偏转 D1c）+ D2 五个增强（就绪时间排序 D2a、动态取算 D2b、SLO 预算排序 D2c、取回准入门控 D2d、排队期预取 D2e），全部只消费 `StorageObservable`/`quote` 可观测视图（信息边界铁律），且每个增强都能写成一个基线公式的**单项替换**，保证归因干净。
4. **实验设计：** G0（M1+R0 前置）→ G1（信息阶梯 × 策略族，四象限压力）→ G2（混合负载 × D2 族）→ G3（Router×Engine 2×2 与对称性负控制）→ G4（接口时效 d/τ）→ G5（并发闭环与门控）。统计与验收全部沿用纲领 §10/§11.2。

## 1. 一致性核对：现行研究思路 vs 本文场景

用户场景的两条硬设定：**(a) 所有 KVCache 默认从存储侧捞（worker 不维护跨请求的本地 KV 缓存，命中一律经共享存储取回）；(b) 所有 worker 能看到全局所有 KVCache（目录全局可见，无位置信息不对称）。** 研究问题 = 在此场景下，把存储侧状态加入调度层"选 worker"（D1）与引擎层"执行顺序"（D2）的决策公式，能否改善 GPU 利用率、存储带宽利用率、SLO 达标与 TTFT。

### 1.1 一致的部分（不需要改）

| 项 | 证据 |
|---|---|
| 核心命题 = 存储状态反馈 → D1 路由 + D2/D4 恢复与顺序的联合决策 | 纲领 v1.1 §1.1 命题原文即"存储侧提供的、计算侧难以及时推断的运行状态……帮助系统更合理地分配读取与计算工作" |
| 信息阶梯与强基线方法论（I0–I4、History-Cost、History-Oracle 诊断） | 纲领 §6.2、§8.2；`StorageObservable`（util/bw/queue/quote 四信号 + EMA/噪声/陈旧）与 `quote.AccessCostQuery`（含压力档位 NORMAL/WARM/HOT/CRITICAL 滞回）已实现 |
| 全局可见目录 | `MetadataDirectory`（`sim/topology.py:114`）对全部 worker 暴露同一副本表；"所有 worker 看到所有 KV"已满足 |
| 场景可配置 | `TopoConfig.local_cache_gb` 设 0 即关闭本地缓存（`LocalKVCache.insert` 对 cap≤0 直接跳过），"默认从存储捞"技术上已可表达 |
| 共同引擎纪律 = vLLM 式 chunked prefill + decode 优先 | 纲领 §5.2 已定，与公式级梳理的 vLLM V1 行为一致 |
| 指标体系 | 纲领 §4 的 goodput/λ*/类别达标率/资源利用率口径覆盖用户点名的四个指标（§7 对齐口径） |
| 推进状态 | M0/R0 已完成（解析一致、守恒、阈值交叉全过），符合纲领 §12.1 顺序 |

### 1.2 需要锚定的三点差异

| # | 差异 | 现状 | 本文处理 |
|---|---|---|---|
| D-1 | 纲领保留 worker 本地 HBM 缓存维度：`L(w)` 字段（§2.1）、Locality+Load 基线（§8.2）、R7 内生缓存；代码默认 `local_cache_gb=12` | 本地缓存不对称是旧 v2 实验（E5–E9）的重要维度 | §2 冻结 **S-G 场景**：第一阶段 `local_cache_gb=0`、副本放置冻结、无写回；`L(w)` 恒 0，locality 维度整体移出主实验、降级为 R7 扩展。旧 E5–E9 结论按纲领 §9 档位表处理（多数"重跑"） |

## 2. 场景锚定 S-G（第一阶段主场景，冻结）

在纲领第一阶段部署假设（同构 worker、共置 PD、固定副本、无主动复制/预取/迁移）之上，追加/收紧以下设定：

```text
S-G-1  拓扑：W 个同构 worker（GPU 池 + 有限 HBM）× K 个存储节点（mem/ssd 两 tier）
       + 单一共享 fabric；路径延迟 path_lat[w][k] 静态已知（可配置对称/非对称）。
S-G-2  KV 来源：全局共享存储是唯一持久 KV 来源。目录全局可见（每个 worker 知道
       每个前缀块的 (node, tier) 副本集合）；副本放置冻结（预装只读共享前缀集）。
S-G-3  本地缓存：worker 无跨请求本地缓存复用（local_cache_gb=0）。活动请求 KV
       在 HBM 中只服务于本请求执行；本地写回/淘汰/命中留到 R7 扩展，不入第一阶段。
S-G-4  默认动作：命中 → fetch（源可多选）；未命中或策略选择 → recompute（全量
       prefill）。第一阶段动作空间 = {fetch(源), recompute}；partial+overlap 属
       R6，实现后按纲领 §5.5 加入。
S-G-5  引擎（M1）：迭代级调度；共同纪律 = chunked prefill + decode 优先
       （纲领 §5.2 主配置）；waiting 队列排序策略是被比较的实验维度（§3.2/§4.2）。
S-G-6  信息边界（铁律）：非 Oracle 策略只读 StorageObservable / quote（I2/I3/I4）
       与 GPU 可观测视图；存储内部队列/带宽/背景真值仅 Oracle 诊断可读。GPU 侧
       估计所有策略对称（含相同误差过程），SLO 预算类策略只用 O_hat 不用真值 O。
```

**S-G 与"主流部署"的关系。** S-G 对应"共享 KV 数据层作为唯一缓存层"的部署形态（LMCache 共享 L2 / Mooncake 全局池一类），而不是 vLLM 默认的 worker 本地 APC。它使位置信息对称化，从而把研究焦点从"locality 路由"移到"**取出成本与时序**"——这正是存储状态反馈能起作用的地方。

## 3. 基线映射：公式级梳理 → S-G 场景下的具体形态

基线的原则：**每个基线 = 公式级梳理中的一个真实默认方案，在 S-G 下取其退化/直译形态**；所有基线共享相同 trace、目录、引擎执行能力与失败处理（纲领 §8.1）。

### 3.1 D1 路由基线（选 worker + 选源）

| 基线名 | 源方案（公式） | S-G 下的形态 | 退化说明 |
|---|---|---|---|
| **B-RR** | Dynamo 无事件兜底 / Motor RR | `w = i mod W`；源 = 静态偏好（mem 优先 + 最近路径） | 最弱参照 |
| **B-LL** | Motor"负载最低" / SGLang `cache_aware` 退化 | `w = argmin gpu_wait(w)`；源同上 | SGLang cache_aware 的双阈值切换在全局可见下命中项恒等 → 恒选 least-loaded |
| **B-DynKV** | Dynamo `kv_router` 成本式（§2.1 公式） | overlap 项对全部 worker 相同（全局可见）→ 成本式中 prefill 抵扣为常数，**退化为 B-LL + 静态 tier credit 源选择**（现有 `DefaultServing2` 即此形态：mem 优先、近路径优先） | **关键推论**：主流 D1 默认在 S-G 下不消费任何动态存储状态；"低层命中价值更低"只剩静态 tier 偏好 |
| **B-Moon-S** | Mooncake Conductor（§2.4 公式），估计取静态带宽 | `选 w,s：TTFT_est = T_queue(静态) + T_transfer(nominal) + T_prefill` | J+I0（Static-Cost）的 Mooncake 形态 |
| **B-Hist** | 纲领 History-Cost（J+I1） | 同 B-Moon-S，但 T_transfer 由按 (路径,大小) 的 EWMA 历史估计 + 自身在途记账 | **核心强基线**：证明新增接口必要性必须赢它 |
| 诊断 | History-Oracle / True-State / OracleV2 | 纲领 §8.2 原样保留 | 估计器上界与真值上界诊断 |

### 3.2 D2 引擎执行顺序基线（waiting 队列排序 + admission + 取算）

依赖 M1 引擎（chunked prefill + decode 优先为共同纪律，以下只变排序/取算）：

| 基线名 | 源方案 | S-G 下的形态 |
|---|---|---|
| **E-FCFS** | vLLM V1 默认 | waiting 按到达序 admission；token 预算内队首优先、超长切块；命中即取（到达即提交 fetch，取回完成才能进 running） |
| **E-LPM** | SGLang `lpm` | waiting 按 `num_matched_prefix_tokens` 降序（命中长度 worker 无关但仍决定顺序）；命中即取 |
| **E-Prio** | vLLM `priority` / SGLang `priority` | waiting 按外生 priority 值升序（小值先）；对照用，验证排序维度本身的影响 |
| **E-NoEvict** | TRT-LLM `GUARANTEED_NO_EVICT` | admission 不等式 `free_KV ≥ ctx + max_out`（保守预留），顺序 FCFS；检验准入保守度与存储策略的交互 |
| **E-StaticAR** | AAFLOW+ 静态二选一 | 排序 FCFS，但逐请求 `min(T_transfer_nominal, T_recompute)` 决定 fetch/recompute |
| **E-Casc-S** | Cascade（σ+φ），成本取静态 | `Budget = SLO − γ·½(L_act+L_max)` 升序排序；恢复策略用静态带宽成本 |

D3/D4（命中 → 取还是算）不单列：默认全部"命中即取"，`E-StaticAR`/`E-Casc-S`/增强 D2b 是其替代项，保证与公式级梳理的默认画像一致。

### 3.3 基线的组合默认

主对照组 = **B-LL × E-FCFS × 命中即取**（Motor 负载最低 + vLLM 默认引擎 = S-G 下最接近"生产默认栈"的组合）；其余基线用于定位收益来源（排序维度 vs 路由维度 vs 取算维度）。

## 4. 增强策略设计：把存储状态写进 D1/D2 公式

设计约束：**(i)** 每个增强 = 某基线公式的单项替换（归因干净）；**(ii)** 只读 I2/I3/I4 可观测视图（`quote.estimate()` 已提供 `time/pressure/util/confidence` 与分段分解）；**(iii)** 控制面成本按纲领 §6.4 主配置（独立容量分母）计入。

统一记号：请求 `i` 输入 `N_i`、命中 `H_i`、后缀 `U_i=N_i−H_i`、KV 字节 `B_i=KV_bytes(H_i)`；`Ê_path(w,s,B)` = 经 `quote` 的动态取出耗时估计（含源 tier + fabric + 路径延迟）；`T_rec(w,i)=C_w(N_i,0,b)` = 全量重算成本；`T_suf(w,i)=C_w(N_i,H_i,b)` = 命中后剩余 prefill；`gpu_wait(w)` = GPU 可观测排队估计。

### 4.1 D1 增强（路由层）

**D1a 动态取出成本路由（I2/I3）。** 把 B-DynKV 的"静态 tier credit"替换为"动态取出耗时"，worker×源×动作联合 argmin：

```text
cost(w, s, a) = gpu_wait(w) + [a=fetch: Ê_path(w, s, B_i)] + T_suf(w,i)
                [a=recompute: T_rec(w,i)]
选 argmin cost(w, s, a) over w ∈ W, s ∈ replicas(i), a ∈ {fetch, recompute}
```

与 B-DynKV 的唯一差异：`credit_tier·命中块数 → Ê_path`（"命中身份值多少"→"现在取要多久"，即公式级梳理 §1 的静态/动态之分）。与 B-Moon-S 的唯一差异：估计源从静态/历史 → quote 快照。退化检验：quote 退化为 nominal 带宽时应逐位复现 E-StaticAR 的决策（不变量测试）。

**D1b 压力感知源选择 + 防羊群（I2/I3 + 协同）。** 固定 worker（= B-LL），只改源选择：

```text
s* = argmin_s Ê_path(w, s, B_i)
防羊群：Ê 差 < max(abs_τ, rel_τ·Ê_best) 的候选集内随机化（或 top-2 轮转 + 滞回）
```

隔离"源选择"这一条存储状态入口的独立价值（对应 E18 协同思想，参数化自 SGLang router 双阈值的形式）。

**D1c 存储压力偏转（I2/I3）。** Kairos deflection 的存储版：

```text
若 min_{w,s} [gpu_wait(w) + Ê_path(w,s,B_i) + T_suf] > min_w [gpu_wait(w) + T_rec(w)]
→ 该请求改走 recompute（计算换带宽）
```

只改动作选择，不改 worker 选择，用于隔离"取算切换"与"路由"两个入口。

### 4.2 D2 增强（引擎执行顺序层）

**D2a 就绪时间排序（I2/I3）。** 把 E-FCFS 的排序键"到达时间"替换为"预计就绪时间"：

```text
r_i = max(0, Ê_path(w_i, s_i, B_i) − gpu_avail(w_i))     （fetch 请求）
r_i = 0                                                    （recompute/无命中请求）
waiting 按 (r_i, a_i) 升序 admission；命中即取不变
```

直觉：存储队列深时，优先放无需等待 KV 的请求进批，GPU 不为"还没到的数据"空转——这是纲领 §3.2"等待 KV 的请求不应阻塞 ready 请求"的主动化。压力低时 `r_i≈0`，退化为 FCFS（不变量）。

**D2b 动态取算（I2/I3）。** E-StaticAR 的动态版：逐请求

```text
T_fetch_eff = Ê_path(w, s, B_i)（含当前排队与有效带宽）
a_i = fetch    若 T_fetch_eff + T_suf < T_rec
    = recompute 否则
```

与 AAFLOW+ 的差异仅在 BW 从配置值变为实时估计；与 Cascade φ 的差异在无 SLO 项（SLO 版见 D2c）。

**D2c SLO 预算排序（I2/I3 + O_hat）。** Cascade σ 的存储动态版：

```text
Budget_i = SLO_TTFT(i) − L̂r_i
L̂r_i = ½(L_act,i + L_max,i) × γ        （L̂ 输入含 Ê_path 或 T_rec，按候选动作取小者）
waiting 按 Budget 升序（最紧迫先）
```

与 E-Casc-S 的唯一差异：恢复/剩余时间估计里的传输成本从静态带宽 → 动态 quote。O_hat 全策略共享（信息边界 S-G-6）。

**D2d 取回准入门控（I3 + 协同）。** 利用现有压力档位（`quote.pressure()`，NORMAL/WARM/HOT/CRITICAL 滞回）做 incast gate：

```text
每个引擎迭代，允许新提交的 fetch 并发上限：
  c_max(pressure) = {NORMAL: ∞, WARM: 2, HOT: 1, CRITICAL: 0}（起始档位，S0 冻结）
超限请求留在 waiting（按 D2a 排序），recompute/decode 不受限
```

这是 R5 协同的引擎侧最小形态：不承诺资源，只限己方提交速率；对照"无限流 + 同样信息"以分离"信息"与"协同"的贡献。

**D2e 排队期预取（I1/I2）。** 请求进 waiting 即预发 fetch（取回与排队等待重叠），受 D2d 门控与取消语义约束（请求被抢占/重排时取消未完成段，已传字节照计费——纲领 §6.3 承诺对账）。隔离"时序重叠"这一独立收益来源。

### 4.3 组合与交叉

- 主增强组合 = **D1a × D2a/D2b**（先单变量，再组合；组合收益若不大于单变量之和，报告交互为负并归因）。
- 2×2 交叉（纲领 §8.3）：Router {Hist, FB} × Engine {Hist, FB}，动作空间相同，回答"状态应交给谁"。
- 一致性约束：Router 与 Engine 的候选计划、约束和提交协议固定；若 Engine 改写 Router 提议（如 D2b 覆盖 fetch 决策），资源承诺同步更新（影子记账对账）。

## 5. 信息边界与接口对齐

## 6. 实验设计（G 系列，依赖 M1；映射纲领 R 包）

执行规则全部沿用纲领 §10（解析预测 → 开发集冒烟查区分度 → 粗扫描 → 冻结矩阵 → ≥10 种子配对 → 模型变体）；验收沿用 §11.2 默认线。每个 G 包的结果文档带模型状态标签（decode 开、缓存冻结、瓶颈结构）。

### G0（前置）：M1 引擎 + R0 扩展

**交付。** M1 引擎：迭代级调度（chunked prefill + decode 优先）、waiting/running 队列、有限 HBM 容量账本、抢占/回退纪律、排序策略可插拔（§3.2/§4.2 的策略接口）。
**验收。** 纲领 §11.1 不变量中 M1 相关项：资源/工作守恒、依赖与完成顺序、容量安全、极限退化（quote→nominal 复现静态策略决策；`local_cache_gb=0` 下无 local 命中）、确定性；解析一致用 M0 场景回归 + "单 worker 无竞争 = M0 公式"扩展（decode 开启后 T_iter 曲线的解析对照）。
**不通过则不进入 G1+。**

### G1：存储状态进入 D1/D2 的信息增量与策略收益（→ R1+R3 核心）

- **场景。** W∈{2,4}、K=2、单/多副本；纲领 §7.1/§7.2 的 8 类负载起步 + 长尾混合；压力四象限（I/O 紧 GPU 松 / GPU 紧 I/O 松 / 双紧 / 双松）由背景负载 schedule 构造，含平稳/阶跃/交替。
- **对照。** B-RR / B-LL / B-DynKV / B-Moon-S / B-Hist × {E-FCFS}；然后固定 B-Hist×E-FCFS 为参照，单变量加 D1a、D1b、D1c、D2a、D2b、D2d；信息源替换对照（I0/I1/I2/I3/I4 同策略换信号）。
- **必报。** 固定负载：各类 TTFT/TPOT/ITL 分位、类别达标率、goodput；λ*（上、下端）；GPU 忙碌分解（prefill 必要 / 重复重算 / decode）与存储有效吞吐分解（前台 fetch / 背景）；动作分布（fetch/recompute 比例随时序）；History-Oracle 与 True-State 诊断；负收益区域保留。
- **判读。** 增强只赢 B-RR/B-LL 不算数（默认方案在 S-G 下本就不消费存储状态）；必须赢 B-Hist 才构成接口增量（纲领 R1 判读）。D1b 与 D2b 的相对大小回答"源选择 vs 取算切换哪条通道值钱"。

### G2：混合长短负载下 D2 策略族的收益与代价转移（→ R2）

- **场景。** 纲领 §7 全部六组负载设计（8 类、长尾份额、相关性组、突发/热点漂移）；引擎纪律变体（decode 优先 / 配额制 / prefill 优先两档对照）。
- **对照。** E-FCFS / E-LPM / E-Prio / E-NoEvict / E-StaticAR / E-Casc-S × {D2a, D2b, D2c, D2e}；固定 B-Hist 路由。
- **必报。** H×U 动作分布（分短/长输出面）；各类 TTFT/TPOT/ITL/达标率 8 类各一行；每类占用的 GPU/I/O/HBM；E-LPM 的假设检验：**lpm 优先放大命中（大 KV 取回），在存储压力下是否反而恶化 TTFT 尾部**（长命中请求插队 → 大字节 fetch 挤占 fabric）。
- **判读。** TTFT 改善但长输出 ITL/弱势类跌破约束，不算 serving 收益（纲领 R2）；大小分层后收益消失 → 说明原提升来自请求组成。

### G3：Router×Engine 2×2 与对称性负控制（→ R3）

- **场景。** 2×2（Router/Engine × Hist/FB，动作空间相同）+ 决策结构对照（分阶段 vs 联合枚举）；热点分别放置在源 tier / 单 worker 入口路径 / 共享 fabric。
- **必报。** 交互项 `Y11−Y10−Y01+Y00`（带区间）；worker→源流量矩阵；各资源饱和度。
- **负控制（关键）。** **对称拓扑 + 单副本 + 对称 worker**下，D1 增强相对 B-LL 的增益应≈0（无源选择空间、路径同构、worker 同构 → 存储状态无法区分 worker）。若出现显著增益，说明模型里有未声明的非对称性，先修模型再谈结论。fabric 饱和场景是"路由创造不了新容量"的必要负控制（纲领 §11.3）。

### G4：接口时效与最小字段（→ R4）

- **干预。** `d/τ ∈ {0, 0.01, 0.1, 0.5, 1, 2}`（采样间隔扫描）；信号消融（util/bw/queue/quote 单留/单去，已有基础设施）；噪声 σ 与丢包；控制面两档记账（独立 vs 计入 fabric）。
- **必报。** 净收益 vs 状态年龄曲线；字段消融表；决策差距 `m` 与预测误差 `e` 分布（纲领 §3.5 预言检验）。
- **判读。** I4 同步 quote 若支付等待成本后不优于 I2 快照，选快照。

### G5：并发闭环与门控（→ R5）

- **场景。** burst 到达 + 多决策者同时见"同一份快照"；副本对称/非对称；集中提交 vs 分布式无共享 vs 影子承诺。
- **对照。** 无协调 / D2d 门控 / D1b 防羊群 / 影子承诺 + 滞回 / 令牌；单项消融后组合。
- **必报。** 排队字节与 ready 工作时间线、路由份额切换率、峰值与恢复时间、λ* 边界。
- **判读。** "精准估计"与"资源承诺"分离：完美状态 + 无协调仍 herd 时，协同是主要缺口（纲领 R5 判读）。

### 实施顺序与停止条件

```text
M1 引擎 + G0（不变量）→ G1（单变量信息/策略增量）→ G2（混合负载 D2 族）
→ G3（2×2 + 负控制）→ G4（时效/字段）→ G5（闭环/门控）→ 阶段性判决
```
阶段性判决按纲领 §12.2：允许带适用范围的中间判决（如"单瓶颈、decode 开、冻结缓存下 D2b 有/无增量"）；S2 后若 B-Hist 已足够，收敛结论并停止扩展接口主张。R6（partial）与 R7（内生缓存/本地写回）在 G 系列之后按纲领进入条件决定，不在本设计范围内。

## 7. 指标口径对齐（用户四指标 → 纲领定义）

| 用户指标 | 采纳口径 | 防误读约束（纲领 §4.3） |
|---|---|---|
| GPU 利用率 | GPU 忙碌时间比例 + **分解**（必要 prefill / 因策略选择的重算 / decode / 空转等待 KV） | 忙碌度提高≠收益（重算也提高忙碌度）；混合 batch 分摊单列估算 |
| 存储带宽利用率 | 每 tier 与 fabric 的有效服务 GB/s（物理容量分母 + 前台可用容量分母双报） | 集群平均掩盖热点节点；背景与前台拆分 |
| SLO | 类别达标率 `A_c`、`min_c A_c`、goodput、λ*（达标上界/下端报网格精度） | 非劣按类组判定；不能以牺牲弱势类换总体均值 |
| TTFT | 各类 TTFT P50/P95/P99 + 完整 CDF；ITL/TPOT 同报 | P99 报样本量；"TTFT 好、ITL 差"不构成 serving 收益 |

## 8. 边界与待定项

1. **本设计不改代码。** M1 引擎、D2 策略接口、G 系列 CLI 注册（建议 `--exp g0..g5`，沿用 `sim/run.py` choices 机制）是下一步实现工作，按仓库流程（设计→实现+不变量测试→冒烟→正式）推进。
2. **partial（R6）、本地写回/内生缓存（R7）、主动复制/预取驻留（R8）不在 S-G 第一阶段**；D2e 预取是排队期 fetch 提前提交，不引入新数据放置，属排序/时序范畴。
3. **T_iter 曲线形状**（纲领 §5.2）待 M1 标定，G2 必报两档形状 × 长短命中交互；ℓ（传输启动成本）与背景 schedule 结构沿用纲领 §13.2 待标定清单。
4. **旧实验结论的适用范围**：E5–E9/E13–E18 在 `local_cache_gb=12` 下取得，S-G 冻结后其 locality 相关结论不外推；按纲领 §9 档位表，多数须在 M1+S-G 下重跑后才能引用。
5. 用户场景中"所有 worker 看到全局所有 KVCache"若未来放宽为"目录有延迟/有盲区"，属信息边界变化，须按纲领 §6.1 目录观测层重新设计，不在本文范围。
