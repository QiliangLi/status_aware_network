## 1. 这套仿真在研究什么

一句话：**大模型推理服务里，请求命中了前缀缓存时，KV 数据是从存储"取回"还是在 GPU 上"重算"、请求派给哪个计算节点、多个请求怎么组成一批——这些调度决策在存储带宽紧张时怎么做才是对的。**

自包含地展开（五句）：

1. 每个推理请求是一段 prompt。若它的前缀部分之前被算过，对应的 **KV 中间结果**（很大，每个 token 每层数十 KB 量级）可以复用，不必重算。
2. 复用有两条物理途径：**取回**——把 KV 字节从共享存储搬进 GPU，走网络和存储带宽；**重算**——GPU 从头 prefill 这段前缀，烧算力。
3. 两者谁快，取决于当时存储有多挤。取回耗时 ≈ 启动延迟 ℓ + 字节数 B ÷ 当前可用带宽 b；重算能省下的 GPU 时间记为 ΔC。于是有一个干净的分界：

   **取回划算 ⇔ ℓ + B/b < ΔC ⇔ b > B/(ΔC−ℓ)**

   这是全部策略做文章的那条线（仓库里的解析层 M0 严格推导过它，包括 ΔC ≤ ℓ 时取回永远不划算的退化情形）。
4. 麻烦在于 **b 不是常数**：背景流量在波动、并发请求在互抢、同一份数据的不同副本放在快慢不同的地方、预取和复制还会额外占带宽。"压力感知调度"就是让决策对这些波动有反应，而不是按额定带宽一厢情愿。
5. 调度器既不该看到一切（真实系统做不到），也不该什么都看不到（那无从感知）。所以本仓库的方法论核心是一句纪律：**给每个策略规定"能看什么"，然后在相同视野下比较不同策略**（§2.2）。

顺着这条主线，仓库里实际有三台仿真器——**同一个公式，把不同的量变成决策变量**：

| 仿真器 | 把什么变成决策变量 | 回答的问题 | 决策粒度 |
|---|---|---|---|
| **① 取回决策** | b 的波动 | 这一个请求：取回还是重算？派给哪个计算节点？ | 单请求 |
| **② 分布式拓扑** | B 的来源 | 从哪个副本、哪一层存储、取多少比例（F）？派给谁？另外后台要不要搬数据？ | 单请求 + 后台控制 |
| **③ 组批错峰** | 时机与批 | 哪些请求组成一批？现在派发还是等一等（错峰）？ | 一批请求 |

另有四个小工具（解析公式、对拍微仿真、精确最优求解器、迭代级引擎支线），见 §4。

### 术语表（后文直接使用，遇疑回查）

| 术语 | 含义 |
|---|---|
| h / u | 一个请求"命中的前缀 token 数 / 新增 token 数"。h 决定要从存储读多少 KV 字节，u 决定 GPU 要算多少 |
| 命中（hit） | 该请求的前缀在缓存体系中存在可用 KV |
| fetch / recompute / prefill | 取回复用 / 整段重算 / 未命中时的正常计算（与 recompute 同一条执行路径） |
| local | 前缀就在本计算节点的缓存里，只需算 u 部分 |
| partial(F) | 只取回命中 KV 的 F 比例、其余重算；取回与计算并行（仿真器②的动作） |
| TTFT / SLO / goodput | 首 token 延迟 / 完成时限要求 / 单位时间满足 SLO 的完成数（主指标） |
| 流体资源 | 用"速率 × 时间"连续积分来建模的带宽或算力，见 §2.1 |
| 背景负载 bg(t) | 仿真的注入项：分段常数的干扰流量/干扰算力，扮演"别的部门也在用" |
| ground truth / observable | 物理真值 / 策略被允许看的"仪表盘"视图，见 §2.2 |
| Oracle | 被允许读真值、甚至精确推演未来的参照策略，用作性能上界 |
| CRN | 公共随机数：所有策略跑同一条请求轨迹，唯一差异是决策——控制变量法的仿真版 |
| quote | 访问成本查询接口：输入字节数 + 目标位置 → 预计完成时间与压力档位 |
| 批（batch）/ 层 ℓ | 多个请求一起算（批越大，单 token 计算越便宜，见 η）；计算按模型层数 L 分层推进，每层开算前必须把该层 KV 读齐 |
| 错峰（stagger） | 让不同批的读取时间互相错开，避免同时挤占共享带宽 |
| 老化保护 | 等待超过阈值的请求强制优先入批，防止饿死 |

## 2. 三台仿真器共用的底座

![仿真架构总览](figures/fig_arch_overview.png)

**图 1 读法**：入口只有一个命令行（`sim/run.py`）。往下是三台仿真器（右三栏）加一栏解析工具，各自是独立的模块族；全部落在同一层共用底座上（配置单位、请求对象、指标、实验装配、测试）。仿真器①② 共用同一套事件内核与运行装配，③是后造的独立内核。

### 2.1 物理资源：流体近似

存储侧：额定带宽 − 背景负载 = 可用容量，在并发传输之间**均分**（processor sharing）；每次传输有一个很短的启动门控期。计算侧：prefill 耗时由查表曲线给出（token 数 → 秒），每计算节点一条 FCFS 队列，服务速率 = 1 − GPU 背景负载。

推进方式是这套内核的关键：时间只在**解析上必然发生事件的时刻**跳（某个传输完成、门控到期、背景负载断点），两时刻之间用积分一步算完。没有离散步长、没有数值漂移——这是单元测试能拿解析解直接对拍的原因。仿真器③更严格：全程用分数（Fraction）运算，小算例可以和穷举最优**严格相等**。

### 2.2 信息边界："仪表盘"与"透视眼"（方法论核心）

![信息边界双世界](figures/fig_arch_dual_world.png)

**图 2 读法**：左栏是物理真值（只有 Oracle 家族可读），中栏是策略唯一可读的仪表盘，右栏是策略。红色虚线是 Oracle 的特权通道——它绕过仪表盘直读真值，用来标定"如果看得见一切能好到什么程度"。

- **ground truth（真值）**：资源内部队列、真实背景负载，以及"精确推演"接口——不改世界就能算出"假如我现在插入一个传输/任务，何时完成"。
- **observable（仪表盘）**：周期采样（所以陈旧）+ 指数平滑（所以迟钝）+ 乘性噪声（所以有误差）的估计视图；提供四种信号口径（quote / 带宽份额 / 利用率 / 队长）和带滞回的压力档位（NORMAL / WARM / HOT / CRITICAL）。取回成本查询 quote 就建立在其上。
- **边界的实现强度**：仿真器①② 靠对象引用（普通策略拿不到真值对象的引用）；仿真器③ 靠类型系统（可观测快照这个类型物理上不含真值引用）。
- 一条铁律（AGENTS.md §3）：**边界必须匹配研究问题，且对所有被比较的策略一致**。GPU 侧默认真值可见是请求级仿真的既定简化（计算和 GPU 同信任域）；专门研究 GPU 侧估计误差的实验会对称地给 GPU 也装一个仪表盘，不单侧开洞。

### 2.3 可复现装置

CRN：同一种子生成逐字节相同的请求轨迹，策略之间唯一差异是决策。随机数按"种子流水" `rng([seed, 盐, 流号])` 分流——观测噪声、决策抖动、负载各自独立，改一个不牵动其他。仿真器③另有两层保险：全程分数算术，以及 trace/manifest 的规范化 JSON SHA256 哈希（配置变了哈希必变）。

### 2.4 度量

请求级（仿真器①②）：TTFT 分位数（p50/p95/p99）、SLO 达标率、goodput、动作占比（fetch/重算/部分取回/local）、误路由率、quote 估计误差（中位绝对百分比）、副本翻转率。统计窗口统一为去掉预热段后的到达请求。批级（仿真器③）：整批视角的队列等待 / 计算时长 / 批内停等三段分解；未完成请求**右删失**（按到达截止报 TTFT 下界，不假装完成）；时间序列带守恒校验（§4.3）。

## 3. 三台仿真器

每台按同一模板介绍：**建模对象 → 决策空间 → 物理执行 → 策略谱系 → 它专门回答的问题**。三台的策略谱系有个共同手法：按"看得见多少"从少到多排列，两端是"完全不看压力的默认行为"和"看见一切的 Oracle 上界"，中间是本方向的压力感知策略。

### 3.1 仿真器①：取回决策（请求级，一个共享存储）

- **建模对象**：若干 GPU 计算节点，共享一个（或少数几个）KV 存储池。请求按 Poisson 到达，从若干"前缀类"中抽样（类决定前缀长度），按命中率决定 h=前缀长度还是 0；可叠加突发、会话续写、热度漂移三种负载形态。
- **决策空间**：路由（派给哪个计算节点）+ 引擎动作（这个请求 fetch 还是重算）。
- **物理执行**：fetch = 存储传输完成后，把剩余后缀交给 GPU prefill；重算 = 全量 prompt 直接交给 GPU。
- **策略谱系**（信息量递增）：P0 命中即取（完全不看压力）→ P1 按额定带宽静态估计 → P2 读仪表盘动态估计 → P3 路由与动作联合取代价最小 → P4 Oracle 上界。另有轮询 / 最短队列 / KV 感知三条纯路由基线。信号口径（quote/带宽/利用率/队长）可切换，用于回答"哪种信号够用"。
- **专门回答**：压力感知到底有没有收益、需要多准的信息、以及收益离上界多远。

### 3.2 仿真器②：分布式拓扑（请求级 + 数据放置层）

![分布式拓扑](figures/fig_arch_v2_topo.png)

**图 3 读法**：上半是决策层（策略在 worker × 副本 × 动作 × F 的组合里选代价最小的，代价来自 quote 接口），下半是物理层（4 个带本地缓存的计算节点、3 个双层数据节点、一条所有流量都过的共享 fabric）。红色路径是一次取回的三级顺序链路。

- **建模对象**：在①的世界之上加入**放置**——每个计算节点有小容量本地缓存（LRU）；三个存储节点各有内存层 / SSD 层（带宽、容量各异）；一切跨节点流量再共享一条 fabric；元数据目录记录每个前缀类放在哪些（节点， 层），副本可运行时增删。
- **决策空间**：一次**联合决策**：worker × 副本（node, tier）× 动作（local / fetch / partial）× 取回比例 F。代价由 quote 接口给出：路径延迟 + 存储层估计 + fabric 估计。
- **物理执行**：取回走三级顺序链路（路径延迟 → 存储层服务 → fabric 传输）；partial 让取回链路与 GPU 剩余计算并行，完成时间取两者最大；命中完成后把前缀写回本节点缓存。
- **后台控制器**（决策之外的持续数据搬运，同样只读仪表盘）：副本控制器——滞回判定某副本持续高压后复制 / 跨层降级 / 冷类迁移 / 容量淘汰，带冷却时间防抖；预取器——按会话节奏预取（可选压力门控与保护），重算完成后把 KV 异步回写共享存储（"重算逃逸的免费副本修复"）。
- **策略谱系**：先是**真实系统默认行为的映射**——命中即取 + credit 路由（Dynamo + vLLM 式）、locality 路由（TensorCast 式）、静态成本二选一（AAFLOW+ 式）、部分取回（CacheFlow 式）、SLO 预算 + 保守系数（Cascade 式）；然后是本方向的联合决策，及其抗振荡版（上次副本滞回粘住 + 次优副本概率分流 + 在途流量影子项防羊群）；最后是 Oracle 和两个先知上界（未来视线做批量分配、突发时按车道吞吐比例切分的流体最优）。
- **专门回答**：看得见拓扑与压力的联合决策，比各真实系统的默认行为好多少、比"看见一切"差多少；以及数据搬运（复制/预取）什么时候帮倒忙。

### 3.3 仿真器③：组批错峰（批级，精确内核）

![组批错峰引擎](figures/fig_arch_cq_engine.png)

**图 4 读法**：左侧是三个正交状态机（请求从排队到完成、一个批内逐层"读齐—等前层—计算"、计算节点三态记账）；右上是一个时刻内的固定处理顺序（处理到不动点才推进时间）；右下是共享带宽的分配规则与守恒账本。

- **为什么要单独造一台**：①②的决策粒度是"一个请求到达时做什么"。要研究"**哪些请求组成一批、什么时候派发、要不要等带宽**"，就必须把批、层间读取与计算的交错、等待语义建成一等公民，还要能和穷举最优对拍——于是放弃通用事件库，自研事件循环 + 分数算术。
- **建模对象**：所有请求进**一个统一队列**；m 个计算节点；每批受硬约束（条数 ≤ 8、新增 token 总量 ≤ 上限、显存峰值 ≤ 工作区）；计算按 L 层推进——**层 ℓ 开算前必须读齐该层全部成员的 KV**，层 ℓ 一开算就提交 ℓ+1 层的读取（读取流的申请速率和截止时刻可设：错峰在物理上有显形）。共享带宽 FCFS 按申请上限分配，到期没读完的流提升为最高优先级但保持排队序。批越大单 token 计算越便宜（批加速 η），但批大了读取也大——这就是组批的内在权衡。
- **决策空间**：一个"联合动作" = 给当时每个空闲计算节点发一个批（成员列表），或让它等到某个未来时刻（**等待本身是显式动作**）。
- **物理执行**：同一时刻内按固定五步处理（结算完成与到达 → 推进已有批的层 → 发布观测并落实决策 → 到期流提升 → 出现新空闲则再派发），循环到不动点才推进时间。控制器有显式成本：决策可以同刻生效、固定延迟、或按实测 CPU 时间延迟；动作过期或验证失败时回退到保守基线并计数审计。
- **策略谱系**：排序填批族（先到先服务 / 最长前缀优先 / 最短作业 / 最早截止 / 最松弛 / 读写互补配对；统一的填批规则：排序后逐个加，第一个放不进就停）→ 老化保护锚点（等太久的请求强制进批）→ 模型预测控制（枚举候选批与联合动作，在"从仪表盘重建的估计世界"里闭环推演到排空并打分；双预算：CPU 时间 + 推演事件数，超了就回退）→ 精确求解器（§4.2）。
- **真实负载**：三份 Mooncake 生产 trace（会话型 / 工具代理型 / 合成型）导入为 h/u：以"前 20% 请求的块集合构成冻结目录"的假设派生每个请求的首现命中；等时切窗、按目标到达率缩放时间轴（保留同刻突发）；时限 = 到达 + α × 参考服务时间。
- **专门回答**：组批与错峰的收益从哪来；简单排序能吃到多少；显式搜索还能再吃到多少；离穷举最优还差多少。

### 3.4 三台之间的关系

①和② 共用同一套流体内核、请求对象与指标采集，一次运行在装配层分岔（有没有挂拓扑）；③完全独立，自带内核与指标口径（右删失）。三台之间没有代码复用关系，只有方法论传承（CRN、信息边界、策略谱系两端夹逼）。这不是缺陷而是刻意的：每台为自己的研究问题保持最小的复杂度，代价见 §7 架构债。

## 4. 解析与理论工具

1. **解析层（M0）**：§1 那条分界线的严格推导——取回耗时、划算条件、带宽阈值 b\* = B/(ΔC−ℓ)、以及 ΔC ≤ ℓ 时取回永不划算的退化情形。配套一个**对拍微仿真**：单 GPU / 单 I/O、串行 FCFS 的小事件模型，产出甘特区间，验证解析值与仿真值一致（仿真的正确性从最简单的世界开始背书）。
2. **精确求解器（仿真器③的配套）**：小算例上把所有合法派发方案在时间网格上枚举或分支定界，给出每个目标下的最优解与上下界证书。它回答的不是"比基线好多少"而是"**离最优还差多少**"——把启发式策略的成色标出来。
3. **守恒校验**：把每个已完成 run 的带宽账本复算一遍（∫带宽 dt = Σ 服务字节，容量侧解析积分独立于引擎累计器），不平的 run 直接判废、不许进图。时间序列聚合器据此把"画错图"变成"报错"。
4. **迭代级引擎支线**：把 GPU 建模到迭代 / token 预算粒度（每迭代先推全部 decode，剩余预算切 prefill 分块；活动请求按显存峰值全程保守预留；命中即取在到达时发起）。它研究准入与排序策略，与①②并行存在，共享同一存储与观测组件。

## 5. 实验装置：从命令行到结论

![实验流水线](figures/fig_arch_pipeline.png)

**图 5 读法**：第一行是执行链（命令行 → 实验装配出配置网格 × 策略集合 × 种子 → 仿真运行 → 事件内核 → 指标），第二行是产物链（结果表 → 分析绘图 → 入库图片 → 根目录结果文档），左下质量门、右下可复现性手段是两条护栏。

- **入口统一**：`python -m sim.run --exp <实验名> --seeds N --procs P`；每个实验可单独冒烟（短时长、少种子）。
- **并行**：多种子/多配置作业用多进程池分派。
- **质量门**：不变量单元测试全绿才提交（解析解吻合 / 字节守恒 / 确定性 / 策略单调性，147 项）；全量实验前先冒烟并检查**区分度**（策略不能都顶在满分期天花板——那是场景没调出瓶颈的信号）；改动共享代码后用少量种子回归核对结论方向不变。
- **产物纪律**：原始结果不入库（gitignored），图片入库且禁止用小样本重跑覆盖正式图；结果文档放仓库根并嵌图，每图配两三句读法，结尾附贯穿类比的通俗版解读。

## 7. 架构债与已知局限（现状披露，非待办清单）

1. **组批仿真器的预测控制深度被钳制**：多步推演（H>1）未实现，统一按单步执行并记审计计数——引用其结论时应记得它实际是单步。
2. **轨迹缓存无界**：请求轨迹按运行配置缓存在进程内字典，长驻大批量实验的内存单调增长；当前规模未成问题。
3. **指标口径双轨**：请求级（预热窗口统计）与批级（右删失下界）各一套，无共享无换算；共享指标层是历史上真实的风险源（AGENTS.md 已点名）。
4. **两套事件内核不互通**：通用事件库（①②支线用）与自研精确内核（③）并存，流体资源、观测层、指标各写一份。
5. **实测控制器成本不可跨机复现**：决策延迟按实测 CPU 时间注入，机器相关；跨机器对比应改用固定延迟模式。
6. **小残留**：quote 接口一个噪声参数形同虚设（噪声在别处叠加，有注释说明）；一个指标回调为空占位；命令行的部分参数只有批级实验消费。
7. **工作区未提交修改**（基线之上）：一个实验文件与两张图有未提交改动，属进行中的另一项工作，本文未触碰。
