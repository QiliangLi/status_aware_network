# 双机协作机制-20261022

## 0. 背景与需求

- 仓库原先单机（mac）开发；2026-10-22 起 win（DESKTOP-TJL427K）新接入，两台机器分别用 ZCode 开发，经 GitHub 同步。
- 常规节奏：白天一台（9:00–22:00）、夜间另一台（23:00–次日 9:00）；交接点可能有长仿真未跑完，两机短暂甚至较长时间并存。
- **关键前提**（决定机制形态）：所有任务由用户统一下发，用户始终知晓各机在跑什么；需要重叠开发时用户会主动开分支隔离。
- 因此机制目标只有一个：**保证在 main 上工作前有意识地取到最新代码**，不做任何自动协调。

## 1. 最终机制（已落地 AGENTS.md §10）

1. **trunk-based**：日常开发都在 main；临时分支的创建与合入时机由用户显式驱动，合入 main 须用户命令。
2. **单元边界同步铁律**：每个 session 开始、每个逻辑单元开始前与结束后 `git fetch origin`；若 `HEAD..origin/main` 非空，先 `git pull --rebase origin main` 再继续。push 被拒同样先 pull --rebase 再推。
3. 临时分支上同样遵守同步铁律，并在单元结束处 rebase 到最新 `origin/main`，防止分支腐化。
4. 长仿真启动前，其依赖代码必须已 commit+push（记录运行基线，保证可复现）；运行中的仿真基于工作区快照，不受 main 后续更新影响。
5. `results/` 不跨机：谁启动的仿真由谁的下一个 session 收尾（出图+结果文档+推送）；极端情况可同种子重跑（CRN 确定性保证数字一致）。
6. 换机交接前确保无未推送提交（收不了尾的打 `wip(scope):` 提交推上去）。
7. **机器清单**（见 §2 表）：新机器接入时在 AGENTS.md §10 登记一行。

## 4. 被否决的设计（记录以免重提）

- **v1：HANDOFF.md 单文件**（在跑声明区 + 交接日志）：完成靠人肉删条目，迭代多了状态不可信——"记到 handoff 里的任务到底完没完成"无法客观回答。
- **v2：一锁一文件 + 客观完成判定 + 过期接管（4h）**：技术上可行但过度设计——用户是唯一任务下发者、知晓全局状态、重叠时主动开分支，不需要自动协调；固定过期阈值对超长仿真任务也不成立。
- **常驻机器分支**：日常需反复检查 main 是否更新，负担大于收益。
- **GitHub issue / 机器自注册表 / hostname 自动派生**：均为自动协调类机制，在"用户手动调度"的前提下不需要。
