## 1. 首先确定究竟要证明什么

### 1.1 把总问题收敛为一个可检验命题

> 在多 worker 共享 KV 存储、请求长短混合的推理服务中，存储侧提供的、计算侧难以及时推断的运行状态，是否能帮助系统更合理地分配读取与计算工作，在保护持续生成质量和各类请求服务质量的前提下，提高可承载负载，或降低相同负载下的尾延迟与资源成本？

这个命题包含四项必须同时检查的条件。

1. **存在决策空间。** 请求至少有两种可执行方式，如换副本、换 worker、恢复 KV 或重算。若所有请求只能走同一条路径，更多信息未必能改变结果。
2. **存在信息增量。** 新接口必须超越位置目录、计算负载，以及调用方可获得的历史传输耗时和自身在途请求；不能只胜过一个从不更新带宽的弱基线。
3. **改变的是系统资源分配。** 单个请求提前完成，可能使别的请求更晚完成。需要记录收益归谁、成本由谁承担。
4. **收益经得起现实约束。** 必须支付传输、重算、HBM 占用和反馈成本，并考虑 decode、反馈延迟、估计误差和共享瓶颈。

研究的最终产物应该是一张有证据支持的**适用边界图**，以及边界内值得实现的最小机制。某些区域没有收益、甚至有负收益，是这张图的必要组成部分。

### 1.2 不预设所有功能都属于同一个贡献

把候选贡献分成三层，按顺序推进。

| 层次 | 要回答的问题 | 第一批必须具备的动作 | 进入下一层的理由 |
|---|---|---|---|
| 信息价值 | 存储侧反馈是否优于计算侧已有信息？ | 固定可比的 worker/副本选择与完整 fetch/recompute | 已有稳健的信息收益，或者明确定位了缺少的可执行动作 |
| 分配与协同价值 | 多请求共享资源时，如何避免自私决策相互伤害？ | 在相同动作上增加在途记账、限流或排序 | 观测准确后仍有争抢、队列增长或类别受损 |
| 放置与生命周期价值 | 应否提前改变数据位置和驻留状态？ | 复制、预取、迁移、保留与淘汰 | 已证明仅靠前台调度无法消除某种热点或重复搬运 |

部分恢复属于引擎能力扩展，要单独验证，不是证明信息价值的先决条件。第一版不同时引入所有动作，以免无法区分哪个机制有效。

### 1.3 对起点文档的判断作哪些修正

这不是对既有实验的复核。下面只修正后续推理的前提，旧实验的适用范围仍由其原始证据决定。

| 原有表述或倾向 | 本文采用的口径 | 修正原因 |
|---|---|---|
| 命中后一般取回，因此研究动态取回/重算 | 命中给出了一个可选执行路径；研究其机会成本和信息增量 | 取回/重算及预算化恢复已有相关机制，不能把二选一动作本身作为新贡献 |
| 存储状态是计算侧无法知道的信息 | 计算侧可以估计其中一部分；关键在覆盖范围、及时性与估计成本 | 需要强历史观测基线，才能证明增加接口的必要性 |
| 先看资源利用率，再看服务效果 | 保留资源图用于解释；最终成败由服务约束、容量和成本决定 | 重算也会提高 GPU 忙碌度，高利用率本身不构成收益 |
| 动态压力有价值，某个毫秒级反馈周期足够 | 都降为待验证假设，反馈周期用相对时间尺度研究 | 对象大小、突发速度、路由并发和变化周期可能改变结果 |
| 协同主要改善稳定性，没有额外吞吐 | 吞吐、稳定性、尾延迟分别检验 | 特定负载下的启发式结果不能排除其他混合负载中的容量收益 |
| 预取浪费主要由缓存留不住导致 | 分别测试预测错误、完成太晚、驻留失败、取回本来就不值 | 这些机制都能生成相似的低命中或高浪费指标 |

相关工作沿用[既有 D1–D7 映射](五工作的Scheduler-Engine修改与主流默认实现-20260904.md)：全局路由、实例内排队、恢复、prefill/decode、生命周期是不同决策点。但两处边界需要依据原文进一步收紧。

- **Cascade。** 原文 §II-B 涉及多实例与 pooled KV，§IV-C 使用负载下的有效链路带宽并按预算限制恢复量。因此不能称其只面对本地物理存储，也不能把“不感知动态带宽”设为其本质。本文保留其预算调度/恢复的机制归属；是否覆盖本课题的跨路由器承诺与共享瓶颈反馈，须通过算法、接口和实验范围进一步核查，不能用部署示意图直接判断。[论文原文](https://arxiv.org/html/2608.06557v1)
- **CacheFlow。** 原文 §3.3 明确处理批内共享计算/I/O 和逐块更新。本文保留其部分恢复与重叠的机制归属，但不再用“静态单请求优化”概括整篇工作。后续应与其资源分配思想作强对照，而不是仅比较固定恢复比例。[论文原文](https://arxiv.org/html/2604.25080v1)

因此，现阶段可以提出“有待检验的跨层机制”，不能宣称“已有系统都没有这条反馈边”或已经确认论文创新性。

## 2. 先拆开请求，避免从定义上制造结论

### 2.1 “长请求”至少涉及三个不同长度

请求的基础记录应包括以下字段。长度统一为 token 数，时间为秒，数据为十进制 GB。

| 字段 | 含义 | 对系统的主要影响 | 到达时调度器是否知道 |
|---|---|---|---|
| `N` | 完整输入长度 | prefill、attention 上下文和初始 KV 占用 | 知道 |
| `H(w,s)` | 对 worker `w`，通过候选来源/组合 `s` 可得到的合法连续命中前缀长度 | 可以少算多少、可能搬运多少 | 通过有版本和时效的目录估计 |
| `L(w)` | worker 本地 HBM 已可复用的连续前缀长度 | 可免除的远端读取 | 通过统一计算侧视图获知 |
| `U=N-H` | 相对于某个候选命中前缀，仍需计算的后缀 | 必须执行的 prefill | 由候选 `H` 决定，不是跨 worker 恒定属性 |
| `O` | 实际输出长度，包含消耗计算的 reasoning token | decode 工作、持续时间、KV 增长 | 通常未知；仿真器真值可知，在线策略不可读取 |
| `O_hat` | 基于请求类别/历史估计的输出长度或分布 | 路由和容量预测 | 所有可部署策略共享同一估计器 |
| `prefix_id / session_id` | 精确前缀关系与会话关系 | 复用、共享块、热点和后续轮次 | 已出现的信息可知，未来轮次未知 |
| `class / tenant / SLO` | 业务类别、租户与服务目标 | 优先级、时限、公平性 | 知道，且跨策略固定 |

必须有 `0 ≤ L ≤ N`、`0 ≤ H ≤ N`。用于候选成本比较的 `H` 是本地与候选来源合并后的连续覆盖，因此 `H≥L`；来源自身覆盖范围另存为块集合。多个副本中重复的前缀不能累加成更长的命中。不同位置的非连续 KV 块不能不经依赖处理就算作普通前缀命中。

长输入、长命中、长输出应分别命名，禁止在日志或图中只留下 `short/long` 而不注明维度。一个输入短、输出很长的推理请求，可能是 decode 大户；一个输入长、命中长、输出很短的请求，可能主要消耗取回带宽。两者需要的调度动作不一样。

### 2.2 命中率、命中长度和实际复用量不是同一个指标

至少分别记录：

- 请求命中率：有任何合法命中的请求比例。
- token 命中率：可用命中 token 总数除以输入 token 总数。
- 字节命中量：按实际 KV 表示计算的可复用 GB。
- 实际复用量：策略真正使用的本地/远端 KV，而非目录中“存在”的量。
- 重算量：在有可用副本时仍选择计算的部分，与无缓存可用的必要计算分开。

“全部请求都命中 128 token”和“少数请求命中 32K token”可以有相同的某一种命中率，却具有完全不同的压力。以一个命中率参数代表两者，会丢失研究问题。

### 2.3 KV 字节不能独立于模型和长度随意填写

对普通、未压缩的多头或分组查询 attention，可用以下逻辑总量作一致性检查：

```text
KV_bytes_per_token = 2 × 层数 × KV_heads × head_dim × 每元素字节数
KV_GB(h) = h × KV_bytes_per_token / 10^9
```

这里的 2 表示 K 和 V；这是按张量维度计数的公式，不适用于所有模型结构。实际配置还必须说明 KV 是否分片、复制、量化、压缩、按块对齐，以及元数据和转换成本。TP 下按真实 KV 分片方式计算每设备数据，不能无条件把逻辑总量除以 GPU 数量。

纯算例：32 层、8 个 KV head、head_dim 为 128、每元素 2 字节时，每 token 为 131072 字节，4096 token 为约 0.537 GB。这仅验证单位；不能据此指定所有实验的模型。

若 worker 已拥有前 `L` 个 token，完整恢复候选前缀至 `H` 通常只需获取缺少的块。实际字节按块集合去重、对齐后计数，不能一边享受本地命中、一边仍按完整 `H` 收费，或完全免除 HBM 接收占用。

### 2.4 正确的计算成本要包含上下文

定义 `C_w(N,h,b)` 为在 worker `w` 上，前 `h` 个 token 已就绪时，处理到总输入长度 `N` 的计算服务成本；`b` 表示当时的 batching/执行条件。

一般不能直接使用 `C_w(N-h,0,b)` 替代，因为后缀仍要关注已缓存上下文。也不能未经标定就认为 `C_w(N,h,b)=C_w(N,0,b)-C_w(h,0,b)`：kernel 启动、分块和批处理可能让二者不等。

Decode 也不能是固定的“每输出 token 一个常数”。其执行时间应依赖活动 batch、各请求当前上下文和资源条件。prefix reuse 直接免除的是部分 prefill，后续生成仍然执行；系统层面可能通过改变竞争间接影响 decode。[vLLM APC 文档](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

## 3. 从单请求的权衡，推导到多请求的资源分配

### 3.1 第一步：在无竞争条件下确认取与算的交叉边界

先固定 worker、缓存状态和执行方式。记：

```text
R = 从现有本地状态出发，不使用远端 KV 的 prefill 成本
P = 恢复目标前缀后，剩余 prefill 的成本
F = 将缺失 KV 恢复至该 worker 可使用位置的端到端时间
ΔC = R - P
```

在恢复与后续 prefill 串行、无排队的限定模型里：

```text
取回路径 = F + P
重算路径 = R
取回划算 ⇔ F < ΔC
```

关键比较对象是**这次取回实际避免的计算**，不是完整输入的 prefill 成本。将 `F` 与全部 `R` 比较而漏掉 `P`，会系统性高估取回。

进一步假设单个瓶颈、固定启动成本 `ℓ`，则 `F=ℓ+B/b`。当 `ΔC>ℓ` 时，取回所需带宽阈值为：

```text
b* = B / (ΔC - ℓ)
```

若 `ΔC≤ℓ`，在这个限定模型中仅提高带宽也无法让取回胜出。这些公式首先用于微实验和不变量检查，不直接成为完整 serving 的延迟公式。

**一个特别重要的反例。** 假设 KV 大小与命中长度线性相关，避免的计算也严格线性相关，且没有固定开销，那么 `B/ΔC` 与命中长度无关。这时仿真不可能仅凭长短命中得出不同的取回偏好。若希望研究长短差异，必须说明差异来自上下文计算曲线、启动成本、deadline、并发竞争还是容量，而不能只把同一模板放大十倍。

### 3.2 第二步：加入竞争后，不能给两个动作加同一个 GPU 等待时间

恢复时 GPU 可以继续服务其他请求。取回完成后才加入 ready 队列，重算则可以更早进入 GPU 队列；二者遇到的 decode batch 也可能不同。因此不应普遍写成：

```text
共同 GPU 等待 + min(F + P, R)
```

完整模型必须按事件推进。建议把一次请求表示为以下依赖图：

```text
到达 → 目录/状态查询 → 路由与动作提交
                        ├→ 读取/传输 → KV 就绪 ─┐
                        └→ 合法的重算任务 ──────┤
                                               ▼
                                    输入状态完整可用
                                               ↓
                                       剩余 prefill
                                               ↓
                                     首 token → decode → 完成
```

每次 GPU 调度只选依赖已满足的工作；等待 KV 的请求不应无理由阻塞其他 ready 请求。其 HBM 预留和在途缓冲占用仍应显式存在。

### 3.3 第三步：混合请求真正竞争的是稀缺资源的分配权

看一个无排队的小算例。两请求同时到达，各需 1 GB KV，共享 I/O 为 1 GB/s，单 GPU 上重建它们分别需要 0.2 秒和 2 秒。忽略后缀、decode 和传输启动成本，只允许完整取回或完整重算。

| 分配方式 | 执行过程 | 两者全部恢复完成时间 |
|---|---|---:|
| 都取 | I/O 总计 2 GB | 2 秒 |
| 都算 | GPU 总计 2.2 秒 | 2.2 秒 |
| 贵的取、便宜的算 | I/O 做 1 秒，GPU 同时做 0.2 秒 | 1 秒 |
| 便宜的取、贵的算 | I/O 做 1 秒，GPU 同时做 2 秒 | 2 秒 |

这个算例证明了**异质计算代价使分配有价值**，尚未证明需要动态反馈：静态成本策略也能选择第三行。只有当可用带宽、已有承诺或 GPU 工作发生变化，且新信号能及时改变正确分配时，才构成信息价值的证据。

可用 `ΔC/B` 表示“每 GB 取回大致避免多少 GPU 服务时间”，作为解释性特征。不过，最大化这个比值不等于最大化 SLO goodput：一个高比值请求可能没有足够 deadline，一个低比值请求可能马上超时；长输出还可能长期占据 HBM 和 decode batch。

### 3.4 第四步：把对别人的影响纳入假设

读取的外部成本是占用共享 tier、路径、NIC 和缓冲；重算的外部成本是占用 GPU 时间、HBM 带宽及后续 batch 位置。候选动作的分析可写为：

```text
本请求预计完成代价
  + 新增读取给其他请求造成的延迟
  + 新增计算给其他请求造成的延迟
  + HBM 驻留与后续生命周期代价
```

这是一种问题分解，不要求第一版精确估计所有项。第一版先比较逐请求成本决策与只增加“已承诺工作记账”的版本；若仍有系统性伤害，再研究资源价格、预算或队列调度。

排队数不能代替工作量：10 个 0.01 GB 请求和 10 个 1 GB 请求不是同一种存储压力。即使剩余字节相同，不同服务纪律下，新请求的完成时间也可能不同。状态设计必须服务于模型中的具体服务规则。

### 3.5 第五步：信息只有在足以改变动作且来得及时的时候才值钱

先构造两种真实存储状态，使计算侧在请求到达前看到的位置、GPU 状态及已完成访问历史相同，但外部租户刚开始占用不同副本，导致最佳动作不同。若及时存储反馈可以区分这两个世界，就得到了清楚的信息增量实验。

随后延长可观测历史、给基线加入在线学习和自身在途记账。若收益消失，结论应是“历史估计已足够”，而非接口必不可少。

定义决策差距 `m` 为最佳与次佳动作的预测成本之差，定义预测不确定性尺度为 `e`。当 `m` 远大于 `e`，粗粒度信息可能足够；当二者接近，频繁追逐小差异可能导致振荡。需要同时画出成本估计误差、动作误判和实际服务损失，不以预测 MAE 单独判定接口好坏。

### 3.6 第六步：decode 和容量决定收益是否能够持续

远端拥塞时把请求转为重算，可能改善新请求 TTFT，却拖慢已进入 decode 的请求。反过来，取回减少 prefill，可能让更多请求同时进入 decode，进而碰到 HBM 容量或 decode 服务上限。

因此，必须比较完整的三段过程：

```text
恢复/重算如何分配
        ↓
多少请求、在何时进入 decode，占用多少 KV
        ↓
持续生成是否达标，队列是否能长期稳定
```

只用 GPU 背景利用率模拟长输出，无法回答这个问题。背景负载可以做干预，但不能替代真实请求的逐步生成、完成与释放。

## 4. 先定义成功，再选择算法

### 4.1 主服务指标与公平性约束

对请求 `i`，定义到达时间 `a_i`、第 `j` 个输出 token 时间 `t_i,j`、完成时间 `f_i`。

```text
TTFT_i = t_i,1 - a_i
ITL_i,j = t_i,j - t_i,j-1                 （j ≥ 2）
TPOT_i = (f_i - t_i,1) / (O_i - 1)      （O_i > 1）
E2E_i = f_i - a_i
```

`O=1` 时 TPOT/ITL 记为不适用；不能以除零、默认失败或伪造 0 值污染统计。

每个业务类别事前固定 TTFT、TPOT 目标。流式业务还应固定 ITL 超标 token 比例上限或停顿上限，因为平均 TPOT 可以掩盖一次很长的卡顿。离线业务如有 E2E 目标，应另列，不混用交互式的默认 SLA。业务类别和 SLO 在到达时确定，不能依据事后实际输出长度给请求重新分配一个更有利的目标。

定义 `Y_i=1` 表示请求完成且满足该类全部预注册服务目标；否则为 0。主报告包括：

```text
请求 goodput = Σ Y_i / 到达测量窗口长度
合格输出 token goodput = Σ (Y_i × O_i) / 同一窗口长度
类别达标率 A_c = Σ_{i∈c} Y_i / N_c
```

同时报告各类别的数量和 token 份额，不能通过多完成短请求把少数长请求的失败隐藏掉。`min_c A_c`、类别 TTFT/ITL 尾部、等待最久请求及租户达标率为必报项。Jain 指数可以辅助展示，不能替代最低服务水平，因为“大家都失败”也可能看起来很公平。

### 4.2 两种主比较，解决低负载天花板问题

1. **固定到达负载。** 比较 goodput、类别达标率、尾延迟、每个合格请求的资源成本。低负载 goodput 相同很正常，此时主要观察是否增加无谓开销。
2. **固定服务质量。** 扫描共同的到达率，寻找所有预注册类别均达到目标、且队列没有持续增长的最大可承载到达率 `λ*`。这是容量收益，不能用某一时刻的最高完成吞吐替代。

没有业务 SLO 时，先用策略无关的隔离运行参考生成若干严格程度，并标为合成目标。例如以无复用的隔离 prefill 参考设置类别 TTFT 档位，以固定参考 batch 的 decode 测量设置 TPOT 档位；参照配置跨策略冻结。必须展示 SLO 扫描，不能调到新策略刚好达标、基线刚好失败的位置后只报告这一档。

主实验不主动丢弃请求。后续如研究准入/拒绝，所有策略获得同等能力，拒绝与超时计入全部到达的服务失败，并单列拒绝率。不能只在被接纳请求上计算达标率。

### 4.3 资源指标用于解释收益来自哪里

| 资源 | 必须记录 | 防止的误读 |
|---|---|---|
| GPU/计算组 | 忙碌时间、prefill/重复计算/decode 工作、ready 队列、KV 等待、各 worker 差异 | 忙碌度提高就被当成效率提高 |
| HBM | 活动 KV、可回收缓存、在途预留、峰值、逐请求驻留 GB·s | 恢复似乎免费，实际挤掉 decode 或缓存 |
| 每个 tier | 有效服务 GB/s、剩余工作、读写拆分、前后台占用 | 集群平均掩盖热点节点 |
| 网络/NIC/共享链路 | 每方向实际流量、带宽占用、排队、前后台分解 | 副本变多被误认为共享网络容量变多 |
| 状态接口 | 消息率、GB/s、CPU/查询服务时间、状态年龄、超时、预测误差 | 只计信息收益，不计获得信息的成本 |

GPU“忙碌时间比例”是仿真资源占用指标，不等同于硬件 SM 利用率。混合 batch 中不能把整次 kernel 时长同时计给 prefill 和 decode；类别分摊若无法直接测量，应单列为估算。

带宽占用至少同时给出物理容量分母与前台可用容量分母。前台可用容量分母为窗口内可用服务量积分；其为零时记不适用。多资源链路的流量可按每条链路分别计量，但不能把“同一份数据经过三跳”误计成三倍应用读取量。

最终接受的是服务质量约束内的容量或成本改善，而不是让每个资源尽可能接近 100%。

## 5. 仿真世界需要精确到什么程度

### 5.1 用三层模型回答不同问题

| 模型层 | 必须包含 | 能回答什么 | 不能宣称什么 |
|---|---|---|---|
| M0：解析/小规模模型 | 一个 GPU、一个 I/O 资源、少量请求、明确服务纪律 | 阈值、守恒、资源分配反例、精确最优对照 | 完整 serving 收益 |
| M1：机制主模型 | 多 worker、分块 prefill、逐迭代 decode、有限 HBM、共享路径、动态观测 | 信息与动作的因果作用、长短混合下的收益边界 | 尚未标定硬件上的绝对 req/s 或毫秒结果 |
| M2：迁移验证模型 | 实测性能曲线、真实前缀关系/会话、至少一个独立硬件或模型配置 | 排序和边界在目标部署上是否成立 | 未覆盖架构和协议的普遍结论 |

M1 不是先写一个完整推理框架。只实现会改变本课题因果链的要素。若 M0 中无法解释机制，增加拓扑和 trace 只会使解释更困难；若 M1 没有 decode，不能跳到 serving 结论。

### 5.2 计算模型：以执行迭代推进，而不是每请求占一条独立车道

一个 worker 表示固定并行配置的完整模型服务组。第一版各 worker 同构，不混入 GPU 型号选择。

每次计算迭代执行以下过程：

1. 收集已就绪的 decode 请求和可运行 prefill chunk，检查活动 KV 与缓冲容量。
2. 按共同的引擎调度纪律选择 batch。主配置采用 decode 优先、剩余 token 预算放入 prefill chunk；所有策略使用相同预算和分块粒度。
3. 用 `T_iter(prefill_chunks, 各 chunk 的已有上下文, decode_contexts, 配置)` 计算迭代时长。
4. 迭代完成后推进 prefill 进度、产生 token、更新 KV、释放已完成请求、触发下一轮决策。

这一共同调度纪律参照 vLLM 当前文档所描述的 chunked prefill 行为；它是本文选定的可比运行配置，不是对所有版本、所有引擎默认配置的概括。[vLLM 优化文档](https://docs.vllm.ai/en/latest/configuration/optimization/)

`T_iter` 优先来自 profiling 的插值/回归。无实测时，可以采用可解释的合成曲线，但必须同时改变曲线形状和混合 batch 干扰强度做敏感性分析，结果标记为机制级。不能把 prefill/decode 当成两条互不竞争的独立满速通道。不能让预测器与执行器永远调用同一个精确函数后宣称预测问题已经解决。

到达时真实 `O` 放在执行器私有状态中。调度器只看到 `O_hat`、输出上限提示、已经生成的 token 数及由它们更新的条件分布。提示上限不等于实际输出长度。专门的未来已知诊断可以读取 `O`，但必须单独命名。

如研究 PD 分离，应作为 M2 后的独立部署扩展：加入 P→D KV 转移、两个池的调度和各自服务目标，不能通过调低共置模型的干扰系数冒充 PD。

### 5.3 HBM 与缓存：既有容量约束，也有依赖约束

HBM 总账至少分为模型/运行时固定占用、活动请求 KV、可回收缓存、已预留或正在传入的 KV/缓冲。活动请求增长与恢复提交必须经过同一容量检查。

主模型先采用简单且对称的内存纪律：活动 KV 不驱逐；优先淘汰无引用的缓存块；不足则等待容量，不默认给予某个策略抢占能力。已就绪请求的批次准入预留本次迭代增长所需空间。为避免所有活动请求都无法继续增长的死锁，第一版按公开最大输出上限做保守的活动集合可行性检查；随后以统一抢占机制做敏感性实验，评估保守预留损失。真实 `O` 不用于在线预留。

缓存必须以可共享的块/前缀关系表示，而非“某类请求完成后这一类永远命中”。共享块只存一份、引用计数区分多个消费者；释放一个请求不能删除仍被其他请求使用的块。相同模型身份、token 前缀和兼容 KV 表示才允许复用。

对 `H=N` 的完整前缀命中，仍需显式计入生成首 token 所需的最终计算或 logits 重建；除非另外建模结果缓存，不能令首 token 免费产生。该项并入统一首 token 执行模型，微实验中可为所有动作添加同一常数。

主因果实验采用**冻结放置模式**：预装固定的只读共享前缀集，每个 worker 的初始本地缓存状态相同于对应策略的其他运行，禁止完成请求后增加跨请求驻留条目。活动 KV、传输缓冲、decode 增长仍计入容量。它用于隔离调度决策，不代表完整缓存系统。

随后开启**内生缓存模式**：所有策略从相同初始状态开始，按共同写回/淘汰规则演化。此时不同策略得到不同命中率是执行路径的真实后果，不应强行重置为同样命中。两种模式都要报告，分别对应直接作用和包含缓存反馈的总作用。

### 5.4 网络与存储：每一份字节必须走完自己的路径

最小拓扑从 2 个 worker、2 个存储节点、1 个共享瓶颈开始；扩展到 4/8 个 worker 检查规模效应。存储节点可包含 DRAM 与 SSD，但先用单 tier 验证机制，再加入 tier 差异。

```text
存储介质 → 源节点服务/发送口 → 共享链路 → 目标接收口 → HBM 搬运/就绪
```

某些实际部署会合并其中环节。配置需标明每段是物理独立资源、共享资源还是固定延迟。网络信号若来自 NIC/交换机或独立监控器，应标明提供者；不能把存储节点并不掌握的整条 fabric 真值自动算作存储侧可知。

采用分块、可流水的离散事件模型：一个块经过必要阶段后可进入下一阶段，后续块可以在前一阶段继续执行。每个阶段有容量、服务规则和缓冲限制。应固定以下语义：

- 存储服务可用带宽分享或有限并发队列表示；主模型与替代纪律都要说明。
- 网络流在每个共享约束下分配带宽；若采用流级多资源分配，必须显式满足所有经过资源的容量约束。
- 单次请求的不同流共享 NIC，不得每条流都独占完整 NIC 带宽。
- SSD 至少有对象大小/并发影响的服务曲线或替代模型；理想 processor sharing 不用于直接声称真实队头阻塞特性。
- 背景占用可用外生剩余容量 schedule，或显式背景任务表示。对同一背景流二者只能选一种，防止扣减两次。

无竞争、大对象、稳定流水时，时间可接近“启动延迟 + 字节/最慢阶段带宽”；完全串行模型则接近“各阶段时间相加”。这两个限定模型可用于验证，但真实竞争时不得直接用 `min bandwidth` 或简单求和替代事件执行。

所有 fetch、复制、预取、写回、迁移都登记来源、去向、经过的资源和流量类别。复制不是只占目标存储；从 GPU 回写也不是直接把对象瞬移到 DRAM。取消操作只释放未执行部分，已经移动的数据、已做的计算和回滚开销不能删除。

### 5.5 部分恢复：先规定哪些块由谁生成，再谈重叠

“取回 50%，其余重算”不足以定义一个可实现动作。第一种可检验方案为：对需要重建的连续前缀 `[0,H)`，从左至右计算早期块 `[0,k)`，同时获取已有正确 KV 的后部块 `[k,H)`；两边完成后，才能处理依赖完整前缀的后缀。已有本地块可以免除对应工作。

```text
输入前缀     [ 早期块：依赖就绪后重算 ][ 后期块：取回已有 KV ] | 未命中后缀
GPU          → → → → →
I/O                                ← ← ← ← ←
                                   两边状态完整 → 处理后缀
```

在模型身份、位置和前缀完全一致时，取回已有的后部 KV 不要求先完成本地早期块计算；而重算后部 token 需要其前置依赖。若选择“先取早期块、同时重算依赖这些块的后缀”，必须等待相应依赖，不能免费重叠。这个方向选择与 CacheFlow 的 token 级恢复思路相符，但本文只实现其中一个明确子集，不称为完整复现。[CacheFlow §3.1](https://arxiv.org/html/2604.25080v1#S3.SS1)

引擎将每个 KV 块标为本地复用、取回或生成，记录开始/完成事件。每个必需块最终恰有一个可用版本。边界 `k` 必须按块对齐，在线变更需处理已经承诺的工作。

在理想无竞争条件下，可以用 `max(取回时间, 重算时间)` 校验两路重叠；正式模型按依赖、GPU batch、DMA/HBM 干扰和缓冲推进。若收益只存在于零干扰、无限缓冲的理想重叠模型，应报告为待实现潜力。

## 6. 信息接口：证明哪些信息值得跨层传递

### 6.1 信息来源分层，避免把“可观测”写成“全知”

| 信息层 | 内容 | 可部署策略的获取方式 |
|---|---|---|
| 请求已知信息 | 输入、类别、公开输出上限、已出现的 session 历史 | 请求入口 |
| 计算域观测 | 当前 running/ready、活动 decode、HBM、本地缓存、自己已分配的请求 | 共同 GPU observable；不包含真实未来输出 |
| 调用方历史 | 成功/失败/超时的传输、大小、路径、耗时、自己的在途提交 | 所有基线都允许维护；历史信息不是应排除的信号 |
| 目录观测 | 块范围、位置、副本状态、版本 | 带延迟的目录更新 |
| 存储/路径反馈 | 工作量、有效服务能力、共享资源身份、健康与缓冲压力 | 来自实际提供者的 snapshot/quote |
| 执行器私有真值 | 各资源内部事件、尚未公开的变化、真实输出长度 | 仅评估器或明示的诊断策略 |

“当前真值可见”和“知道未来服务需求”应分开。即使计算域允许读取当前精确占用，也不能顺手读取每个活动请求还会生成多少 token。若研究 GPU 预测误差，所有非未来已知策略使用相同误差过程与观测器。

### 6.2 先比较最小信息阶梯

| 信息版本 | 输入 | 用于回答 |
|---|---|---|
| I0 | 静态位置、名义成本、计算域观测 | 没有在线存储感知的起点 |
| I1 | I0 + 调用方按大小/路径学习的历史成本 + 自身在途 | 不新增接口能做到多少 |
| I2 | I1 + 当前服务能力的资源快照 | 新鲜带宽信息有多少增量 |
| I3 | I2 + 在途/排队剩余工作量、共享瓶颈标识 | 字节工作量与跨请求竞争是否必要 |
| I4 | 由 I2/I3 可取得数据生成的请求级端到端 quote | 统一估计服务能否减少上层推断负担 |

每项至少做一次单独移除与从 I1 增量加入。I4 与 I3 使用相同原始信息时，其收益属于估计封装/算法差异；只有引入了额外数据源时才称为信息增量。

资源利用率高可能表示长队列，也可能仅表示恰好持续忙碌。单独 queue count、util 或平均吞吐并不天然充分。候选接口是否足够，以动作和服务损失评估，不能预先规定 quote 一定最好。

LMCache 的公开指标说明提供了吞吐、在途任务和预留内存等可落地线索；其中部分吞吐是 submit→complete 的端到端字节/耗时，含队列和网络，不能再次作为原始介质速率加上一遍排队延迟。它们是接口原型的数据来源候选，不等于已经具有本设计需要的完整信号。[LMCache Metrics](https://docs.lmcache.ai/mp/observability/metrics.html)

### 6.3 Snapshot 与 quote 的最小语义契约

资源快照至少包含 `resource_id、共享范围、采样时刻、版本、有效期、数据来源、单位、服务规则、工作量摘要、容量/健康摘要`。置信区间如未经覆盖率校验，应称“不确定性估计”，不能写成已保证的 P95。

Quote 的输入至少包含候选 worker、缺少的块/GB、来源路径、请求类别和允许动作；输出包含：

```text
预计端到端完成代价及不确定性
所依赖资源与版本
数据采样时刻、生成时刻、到期条件
关键阶段成本或瓶颈解释
是否包含调用方已提交工作、是否包含本次请求
失败/不可用状态
```

必须区分三件事：

1. **估计**不锁定资源。读到一个低价 quote 不保证其他请求不会同时使用它。
2. **提交**才增加实际或影子承诺工作。一次调度评估多个候选，不得给所有候选都增加负载。
3. **完成、取消、失败**释放对应承诺；快照已包含某笔工作后，影子记录要对账，防止重复记账。

采用显式 reservation/令牌服务属于协同动作，要给对照相同能力和成本，不能隐藏在“信息更准确”里。目录失效时执行层必须检查块可用性，对所有策略采用共同的失败回退规则；不能让策略通过一次失败免费知道整个世界的真值。

### 6.4 状态传播成本必须进入时间轴

至少模拟采样间隔、传输延迟与抖动、接收/处理队列、丢失或超时、时钟误差。决策使用的是已经到达的状态，不是把真值标记成旧时间戳。

主比较冻结计算侧观测质量，仅改变存储观测；后续做 GPU 误差 × 存储误差的对称交叉实验。测量噪声按资源和时间过程生成，避免“某策略多调用一次接口就多抽一次随机数”导致 CRN 失效。

过期或低置信时回退到 I1 的保守估计，或者维持当前决策并限制改派。是否等待一次同步 quote 是一个有成本的选择；低时延请求可能不值得发 RPC。

不要预先固定“100–500 ms 足够”。以状态有效年龄 `d` 和压力变化特征时间 `τ` 的比值 `d/τ` 为横轴，再补充实际秒数。还要记录更新间隔内新增工作占可用服务量的比例，用于识别同样年龄、不同到达强度下的失效差异。

## 7. 混合长短负载应该怎样构造

### 7.1 第一组：满足物理约束的输入长度 × 命中长度 × 输出长度

采用绝对命中长度，而非先用百分比。以下是**起始离散档位**，不是生产分布：

| 输入 `N` | 短命中 `H=512` | 长命中 `H=3072` |
|---|---|---|
| 短输入 `4096` | 后缀 `3584` | 后缀 `1024` |
| 长输入 `32768` | 后缀 `32256` | 后缀 `29696` |

每格再交叉短输出 `O=128` 与长输出 `O=2048`，得到 8 类。所有组合满足 `H≤N`。这里的“长命中”只是该正交设计中的较长档位，并非覆盖了真正的大 KV 对象。

这里的 8 类首先是**生成与事后分析分组**，不自动成为调度器可见的业务标签。尤其不能把“短输出组/长输出组”传给在线策略，从而通过标签泄露真实 `O`。在线业务类别与可用提示单独生成；允许存在有噪声的相关性，但准确输出长度只留在执行器和评估器。各分析组使用其到达时已经确定的业务 SLO。

另加两个控制：`H=0` 的未命中，以及合法的近全命中 `H≈N`。近全命中独立成组，不能把短输入配上超过输入长度的“长 KV 命中”。

这组回答“输入/命中/输出的变化和交互如何影响结果”，但 `U=N-H` 也在变化，所以还不能把所有差异单独归因于可恢复 KV 大小。

### 7.2 第二组：命中长度 × 未命中后缀 × 输出长度

为了分开“可选恢复工作”和“必须处理的新输入”，再使用：

```text
H ∈ {512, 16384}
U ∈ {512, 8192}
N = H + U
O ∈ {128, 2048}
```

同样得到 8 类，覆盖长命中与短后缀的情况。它与上一组是互补坐标系，不能把 `N/H/U` 当成三个独立因素同时回归。还应在连续扫描中加入固定 `N` 改 `H`、固定 `H` 改 `U`，确认二点实验没有遗漏交叉区间。

### 7.3 第三组：检查“长尾占少量请求、大量工作”的真实压力

先跑每类独立到达，确定各自隔离成本和饱和方向；再采用以下混合比例：

- 8 类等请求数，用于观察交互，不称为真实业务。
- 短请求占 90%、长请求占 10%，再把长请求占比改为 1%、25%、50%。这里“长”每次明确指定输入、命中或输出维度。
- 按参考策略下的 GPU 服务需求或远端字节需求近似等工作量混合，观察少数大请求的资源影响。

每组报告请求份额、输入/输出 token 份额、潜在远端字节份额、参考 GPU 工作份额。等请求比例不等于等负载。

对每种混合分别做两种比较：

1. 固定同一到达率，看改变业务组成会带来什么总体压力。
2. 根据**共同冻结参考模型**调整到达率，使某项参考负载接近，帮助解释资源结构差异；不能按每个被测策略自己的吞吐重新归一化。

一次调节到达率一般不能同时匹配 GPU、网络和 HBM 三项压力。无法匹配的维度必须列出，不能把“同总 token/s”称为完全等负载。

### 7.4 第四组：只改相关性，不改边际分布

固定同一批合法 `(N,H)` 样本、同一组输出长度和同一组到达时间。分别将 `O` 随机配对、与 `H` 正相关配对、与 `H` 负相关配对，保持输入/命中二元组和输出的边际分布完全一致。

再单独改变热点前缀与请求大小、SLO 类别的对应关系。若关联不同，结果不同，说明平均命中率和平均请求长度不足以描述负载。

改配对后若业务类别规定了输出或 SLO 的条件关系，应保持这些约束或明确标为合成干预。不要创造不可能的请求来追求形式上的正交。

### 7.5 第五组：到达过程、热点与外部竞争

| 过程 | 具体设计 | 排除的替代解释 |
|---|---|---|
| 平稳到达 | Poisson 作为基础，再用等间隔作控制 | 收益是否来自随机排队而非信息 |
| 突发到达 | 相同平均到达率下的短 burst/ON-OFF，改变峰值与持续时间 | 平均负载相同是否仍会羊群 |
| 外部存储压力 | 分段常数 schedule；平稳、阶跃、交替、非周期漂移 | 当前状态是否优于长期平均 |
| 热点漂移 | 固定对象大小分布，切换热门 prefix 集合 | 是否仅在固定热点有效 |
| 请求与压力相关 | 同相/反相/独立，分别报告 | 是否依靠人为挑选“GPU 恰好空闲”的有利窗口 |

需要同时存在请求自身造成的共享竞争和外部租户造成的未知竞争。只用外生背景控制拥塞，会低估策略决策反过来改变压力的闭环效应。

### 7.6 第六组：会话和真实 trace

主容量比较采用开放到达，trace 的到达时刻不随被测策略完成速度改变。后续增加闭合会话：下一轮在上一轮完成后等待预先采样的 think time 到达，前缀随历史增长。

闭合会话下不能同时固定各策略实际到达时间和会话依赖。CRN 应共享会话树、token 内容/长度、think time 和外部扰动；实际到达时间由各策略完成事件产生。报告会话完成率、轮次延迟、总完成轮数，不能直接把它与开放到达的 `λ*` 混为一个容量指标。

真实 trace 必须能恢复前缀身份或 token 关系，或明确标为“长度真实、前缀关系合成”。只有 `(input_tokens, output_tokens)` 的日志不能自动生成真实 cache hit。原始样本到类别和块目录的转换规则、隐去字段与截断规则都应归档。预测模型仅用训练会话拟合，评估会话和热点阶段留出，避免看到未来。

## 8. 对照策略怎么设，才能把贡献归因清楚

### 8.1 信息实验与算法实验必须分开

所有策略共享 trace、硬件、初始目录、GPU 观测、输出预测器、引擎执行能力和失败处理。不同实验只打开需要变化的因素。

第一组采用同一个决策器 `J`：枚举相同可行动作，根据统一 GPU 估计和对应信息版本的访问成本预测选择最低预计 TTFT 的动作；平分时使用固定规则。此时只改变 I0–I4，测信息的因果增量。`J` 是容易解释的起点，不能因为定义了最低 TTFT 就假定它优化完整 SLO。

第二组固定同一信息版本，再比较成本贪心、预算化选择、资源分配、在途协调。此时测算法增量。若一种预算化或协调算法有效，再对它重复关键 I1/I3 对照，检查信息与算法是否存在交互。

### 8.2 主基线清单

| 对照 | 规则与输入 | 作用 |
|---|---|---|
| Fetch-only / Recompute-only | 有合法命中就全部恢复 / 忽略远端并补齐本地缺失计算 | 检查两端极限，不作为唯一对手 |
| Locality+Load | 本地/分层命中收益与当前 prefill/decode 负载联合路由 | 比纯追逐 locality 更强的实践参照 |
| Static-Cost | `J+I0`，名义带宽与离线计算曲线 | 测相对静态信息的收益 |
| History-Cost | `J+I1`，按路径和对象大小更新的传输估计，并记自己的在途 | **证明新增状态接口必要性的核心基线** |
| Feedback-Cost | `J+I2/I3/I4` | 测跨层反馈的增量 |
| Budget+History / Budget+Feedback | 同一预算排序与恢复规则，只替换访问估计信息源 | 防止把 SLO 调度能力误算成存储反馈收益 |
| Coordinated | 在某个已固定的决策器上增加公共承诺记账/令牌/分流 | 测共享竞争的协调增量 |
| True-State Diagnostic | 当前内部资源状态精确，其他已知信息和动作与所比策略相同 | 估计当前状态误差影响，不称全局最优 |

Locality+Load 的机制参照 Dynamo 官方描述的 prefix overlap 与 active prefill/decode load 联合选择；不能用“只挑命中最多的 worker”代表它。[Dynamo KV-Aware Routing](https://docs.dynamo.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/kv-aware-routing)

History-Cost 至少包括按大小/路径的条件估计、EWMA 或滑动窗口、超时样本处理、陈旧度、不确定性及本地已提交工作。调参使用独立开发 trace；稳定带宽下应能收敛到合理成本。对未使用路径的信息缺失，是其真实限制，可增加同等预算的主动探测版本，探测流量和延迟必须计费。

已有文档中的 AAFLOW+-style 仍映射到完整 transfer/recompute 的成本原语；本文的 Static-Cost 是该类思想的受控抽象，不代表论文所有机制，也不复用其性能数字。Cascade-like 保留预算排序与恢复能力；不能删去它的动态成本思想后声称战胜 Cascade。CacheFlow-style 的对照在 R6 中至少包含按恢复价值分配 I/O 的批内版本，且列明未实现的 layer/GPU 维度。[既有机制映射](五工作的Scheduler-Engine修改与主流默认实现-20260904.md)

### 8.3 用交叉消融回答“状态应交给谁”

在相同 worker、副本和恢复动作空间下做 2×2：

| | Engine 使用 History | Engine 使用 Feedback |
|---|---|---|
| Router 使用 History | 基础组合 | 只改实例内恢复选择 |
| Router 使用 Feedback | 只改 worker/副本选择 | 跨层组合 |

Router 与 Engine 的候选计划、约束和提交协议固定。某个格子“看不见反馈”不意味着禁用其换副本或重算能力。若 Router 提议的计划被 Engine 改写，资源承诺必须同步更新。

另外比较“分阶段决策”与“联合枚举”，二者拿到相同信息、具有相同最终合法动作集合，单独评估决策结构。不能把联合枚举只开放给反馈版，再把总收益称为信息价值。

### 8.4 真值策略、未来视线和上界分开命名

当前真值贪心可能因为短视而输给有噪声但更会协调的策略；其性能不是可证明上界。未来已知 list scheduling 也只是启发式，不能用于证明“知道未来没有价值”。

在 M0 的有限到达、小请求集上，枚举路由/取算/合法顺序，或使用能提供最优性证书的求解方法，得到该限定问题的精确最优解。固定粒度和资源规则，报告求解空间及 gap；不要求为完整模型求解不可承受的最优策略。

另可建立静态多类流体松弛作资源可行性诊断。令 `x_c,a` 为类别 `c` 分配给动作 `a` 的速率，`d_c,a,r` 为该动作消耗的资源 `r` 工作量：

```text
Σ_a x_c,a = λ × p_c
Σ_c,a x_c,a × d_c,a,r ≤ capacity_r   对所有资源 r
x_c,a ≥ 0
```

这说明任何稳定分配都必须支付相应资源工作。只有在工作量模型成立、没有漏算成本，而且放松的是约束而非添加限制时，最大 `λ` 才能称为该模型的容量上界。混合 batching 的非线性效率、HBM 时间占用、deadline、缓存演化和依赖均可能超出这个 LP。此时它仅是诊断图，不能挂上完整 serving 的“理论上界”标签。

## 9. 按证据依赖顺序安排实验

使用 `R0–R9` 表示本文的研究实验包，不对应已有 E 编号。实际实现时再分配新的 CLI 实验编号，每个包可拆分多个单实验。每个结果必须同时给出配置、对照、资源证据、服务指标和能支持/不能支持的结论。

### R0：先证明仿真器会算账，也会尊重依赖

**问题。** 阈值、共享资源和执行依赖是否实现正确？

**场景。** 单请求、单 GPU/单 I/O；相同和异质大小的 2–4 请求；无排队、已知 FCFS、理想分享三类解析场景。加入一个长 prefill 与正在 decode 的短流，检查分块与 token 事件。

**对照与干预。** 先测试固定 fetch/recompute 与精确小规模最优；实现部分恢复时再补齐其所有合法边界的 R0 测试。扫带宽跨过第 3 节的交叉点；手工改变一个请求的成本或到达次序。

**必须输出。** 请求/块级甘特图、逐资源工作账本、解析值与仿真值误差表。部分恢复实现后，其两端要与完整恢复和重算一致；第一阶段不以尚未选择实施的扩展能力阻塞核心验证。

**判读。** 阈值不吻合、出现免费重叠、资源超过容量或零成本完整命中，先修模型。R0 不通过，不进入机制跑分。

### R1：存储反馈的信息增量究竟在哪些区域存在

**问题。** Feedback 相对 History 的收益是否真实，是否只是在打败 Static？

**场景。** 先固定单 worker 与共享存储、冻结前缀放置，以完整 fetch/recompute 开始；使用少量异质请求，随后在 M1 中保留真实 decode。加入第 3.5 节的两个计算侧不可区分世界。

**干预。** 扫存储外部占用与计算侧已有请求压力，覆盖两侧空闲、I/O 紧/GPU 松、GPU 紧/I/O 松、两侧都紧。压力既有平稳也有变化；实际队列与服务占用用于核实瓶颈，而不是仅相信配置值。

**对照。** 两端极限、`J+I0`、`J+I1`、`J+I3`、同决策器真值诊断。先用低成本新鲜反馈寻找潜力，再计入现实反馈成本。

**必须输出。** 固定负载的净 goodput/类别达标率差值热图、读取与重算比例、GPU 和 I/O 同轴时间线、容量 `λ*`、History 与 Feedback 的动作分歧。负收益和无差异区域保留在图上。

**判读。** 如果仅胜过 Static，则只能证明静态模型不足。若真值也不能改进，先检查动作、模型和瓶颈空间；不能继续堆接口字段。若两个世界最优动作始终相同，该场景不能证明状态的决策价值。

### R2：长短混合与 decode 会不会改变方向

**问题。** 哪类请求适合消耗 I/O，哪类适合重算，谁承担了新决策的代价？

**场景。** 完整执行第 7.1/7.2 节两组 8 类设计、长尾比例、固定边际的相关性设计。先分别运行各类，再混合。主配置固定缓存放置；用相同引擎分块规则。

**干预。** 扫长输出比例、未命中比例、decode 负载和 HBM 压力；在 R1 中有代表性的有利、边界和不利区域重复。decode 关闭的版本只用于测量建模缺口，不作为最终 headline。

**对照。** History、Feedback、配对的 Budget 版本；再加一个只优化 TTFT 的版本作诊断。所有版本都能读到同一 `O_hat`，另设真实 `O` 已知的诊断以量化预测空间。

**必须输出。** `H×U` 下的动作分布图，按短/长输出分面；每类 TTFT、TPOT、ITL、达标率；该类占用的 GPU/I/O/HBM；固定质量的容量曲线。8 类各自一行，不能只输出一个总体平均。

**判读。** TTFT 改善而长输出 ITL 或某类达标率跌破约束，不能接受为 serving 收益。若大小分层后收益消失，应说明原来的提升来自请求组成。若长命中收益与线性模型完全一致，没有交互，应接受“长度本身不产生新机制”的结论。

### R3：路由、副本与恢复需要联合到什么程度

**问题。** 状态应供给 Router、Engine，还是二者；换位置究竟绕开了哪个资源？

**场景。** 2/4 worker、2 存储节点。同一逻辑前缀具备固定副本；构造本地命中 worker 忙、无本地命中 worker 空闲的冲突。分别把热点放在源 tier、单 worker NIC、共同 fabric。主实验不移动数据。

**干预与对照。** 第 8.3 节 2×2，外加同信息下的分阶段/联合决策；逐项固定 worker、固定副本、固定恢复动作。GPU 与存储压力分别独立/同相/反相变化。

**必须输出。** worker→副本流量矩阵、本地实际复用、各共享资源饱和度、类别服务指标、2×2 的交互项。交互项按同一指标计算 `Y11-Y10-Y01+Y00`，附不确定性，不以柱状图看起来更高代替。

**判读。** 源 tier 热点能因换副本缓解，而所有副本共用的 fabric 瓶颈未必能缓解。后者是必要负控制。若只给 Engine 状态已获得全部收益，就优先实现 Engine 接口，不强求联合控制架构。

### R4：最小接口、时效和成本的边界

**问题。** 哪些字段是必要的，多久更新值得，过期时如何退化？

**场景。** 选择 R1–R3 的稳定、有变化和突发代表点，执行 I1→I4 阶梯。至少加入“相同请求数、不同剩余字节”和“相同利用率、不同已有工作”的状态对。

**干预。** `d/τ` 起始取 `{0, 0.01, 0.1, 0.5, 1, 2}`；0 仅为诊断理想条件。加入偏差、相关噪声、丢包、突发状态服务排队，另做 GPU × storage 预测误差交叉。同步 quote 与异步 snapshot 比较包含 CPU、消息和关键路径成本。

**必须输出。** 净收益随状态年龄变化曲线、字段移除消融、预测误差与决策损失、接口消息率/延迟分布、过期回退动作、区间估计覆盖率。

**判读。** 精准 quote 若支付成本后不如轻量快照，就选择快照。若只在理想零延迟反馈下有效，不能称接口具有工程可行性。通过范围应同时写实际时间、变化尺度和请求规模。

### R5：闭环竞争会不会把好信息变成坏决策

**问题。** 多个决策者同时选择“当前最快”的资源后，会发生什么？协同改善的是容量、尾部还是两者？

**场景。** 多个独立 router 在一次状态更新间隔内接收 burst；副本对称与非对称各一组。分别采用集中即时提交、分布式无共享承诺、分布式有延迟承诺，禁止把同一时间到达都按全局串行真值处理。

**干预与对照。** 固定信息和动作，依次加入影子工作、共享承诺、随机分流、滞回、令牌限制；单项消融后再组合。扫描 router 数、burst 强度、反馈年龄，保持总平均负载相同；另做随 worker 增长而固定每 worker 负载的扩展组。

**必须输出。** 排队字节/ready 工作时间线、路由份额、切换率、峰值、超载后恢复时间、分位延迟、容量边界。稳定性以长时间队列漂移和扰动恢复评估，不只比较短窗口峰值。

**判读。** 完美状态仍可能因未计入同时提交的工作而失效；精准估计与资源承诺是两个问题。若容量不增但尾部改善，可报告稳定性贡献；若容量也增，按证据修正“协同只有稳定性价值”的预设。

### R6：部分恢复的收益来自能力，还是来自信息

**问题。** 引入合法部分恢复后，完整取算决策是否仍足够？信息增量是否还存在？

**场景。** 第 5.5 节块依赖模型，冻结放置；覆盖 `H×U×O`、恢复块粒度、DMA/HBM 干扰与 I/O/GPU 压力。

**对照。** 完整取算、固定切分、按成本搜索切分、按每 GB 避免计算分配 I/O 的批内策略。做“完整/部分”×“History/Feedback”的 2×2；部分组都具备相同重叠能力，再单独关闭重叠作消融。

**必须输出。** 切分边界分布、实际重叠率、浪费/重复工作、关键路径甘特图、TTFT/ITL 与容量；块粒度减半/加倍后检查结论收敛。

**判读。** 若部分恢复收益大而反馈增量小，贡献应落在恢复调度能力；若计入依赖和干扰后收益消失，不能用理想 `max` 公式维持正面结论。

### R7：允许缓存和会话演化后，结论能否保持

**问题。** 前台决策是否只在冻结命中下有效；长期是否导致反复读取、重算或缓存挤占？

**场景。** 开启共同缓存准入/淘汰规则和有限 DRAM/SSD 容量，采用前缀热度漂移、真实前缀关系及闭合会话。初始缓存相同，后续状态由每个策略自己演化。

**干预。** 容量相对活跃工作集比例取 `{0.25, 0.5, 1, 2}` 起步；分别改变重用间隔、对象大小和热点迁移。开启/关闭并发同前缀的重复 fetch 合并，作为所有策略共有的服务能力。

**必须输出。** 目录命中与实际复用、缓存驻留、重复传输、重算后回写、请求/会话指标，冻结与内生模式的差值。容量占用和流量的所有后台成本都计入。

**判读。** 若冻结模式有效但内生模式失效，先定位是驻留、放置、合并还是回写导致，不立即加入预测器。若简单合并已消除热点，应相应缩小共享存储压力机制的适用范围。

### R8：有条件地研究主动存储控制

**进入条件。** R7 显示可归因的放置/驻留问题，且前台调度无法合理解决。否则不实施本实验包。

**问题与单独实验。** 复制测试“是否有独立服务路径可分流”；预取测试“是否来得及并且值得”；驻留测试“是否挤走更有价值的块”。先逐项验证，再做前台反馈 × 存储控制的 2×2。

**比较。** 无控制、简单阈值/热度控制、压力门控；预测版本另加真实历史预测与未来已知诊断。为各部署计入相同总容量、或明确报告额外容量成本。预装全副本若有无限容量或免费初始化，只能称特殊诊断，不能称公平基线或普遍上界。

**必须输出。** 复制/预取启动和完成、前台挤压、后续使用时刻、驻留/淘汰、逐资源净成本、服务指标。预取失败按生命周期事件区分没有使用、使用时尚未完成、已完成但被淘汰，并另估计“命中却不节约关键路径”的情况；不要把不同口径混成一个命中率。

**判读。** 一次复制值得的条件，至少包括剩余热度窗口内的预期净收益足以支付复制与驱逐的机会成本。热点更快消失、共同 fabric 已饱和、预测错误时应出现无收益区。仅在免费复制或未来精确已知时有效，不足以推进部署。

### R9：独立标定与迁移验证

**问题。** 模型形状、参数或负载来源稍变，主要结论是否还成立？

**采集。** 固定模型/并行/量化配置，测 `(N,H,batch)` 的 prefill、不同上下文组合的 decode、混合 batch、KV 搬运和并发 I/O；记录冷热缓存、传输路径和后台流量。采用 profiling 加预测的思路有成熟先例，但仿真器名称不能代替本项目自己的误差验证。[Vidur 论文](https://arxiv.org/abs/2405.05465)

**方法。** 拟合数据与验证数据分离。先验证服务时间，再验证共享资源竞争，最后用小型端到端原型比较策略排序和关键瓶颈。至少一个模型或硬件配置、一个请求/热点分布留出；未测的范围不无提示外推。

**必须输出。** 预测与实测散点、按大小/并发分桶的误差、端到端资源时间线、核心配对实验的方向和幅度。若没有真实设备，提交采集协议与待标定列表，全部结论继续停留在 M1。

**判读。** 参数敏感性保住排序但尚无实测，只能称模型内稳健。实测误差若足以跨越取算决策差距，应先校准，不以更多种子掩盖系统误差。

## 10. 实验执行与统计规则

### 10.1 先找边界，再做有限覆盖，避免失控的全排列

每个实验包按以下顺序执行：

1. **解析预测。** 先写下预期瓶颈、动作交叉位置、可能的负结果，以及观察到什么会否定推导。
2. **独立开发集冒烟。** 以 1–2 个种子、120–200 秒作为起点，检查到达、缓存路径、decode 进度、资源守恒和服务区分度。长会话/长周期不够时延长时长，不能为适应冒烟时长把长请求截短后当正式负载。
3. **粗扫描。** 找到低负载、接近容量、明显过载，以及动作交叉区域。开发集初步获得参考容量后，可用 `{0.5, 0.8, 1.0, 1.2} × 参考 λ*` 附近作探测；正式配置直接存具体到达率，参考无稳定容量时改用物理需求尺度。
4. **冻结正式矩阵。** 保留无收益、边界和有收益点，冻结参数、种子和主指标。不能只保留新策略赢的格子。
5. **正式多种子运行。** 起始至少 10 个独立 trace 种子；根据配对差值不确定性增加到 20 或 30，规则事前确定。边界附近加密，远离边界的同质区域不必盲目重复。
6. **误差与模型变体。** 在代表点改变 GPU 曲线、存储服务纪律、路径流水、块粒度和缓存规则。最后才运行更广的组合或真实 trace。

上面的秒数、种子数都是起始预算，不能替代足够的样本量与状态变化次数。正式动态实验建议至少经历 20 个主要压力周期；非周期漂移使用多个独立完整漂移序列。

### 10.2 CRN 固定外生世界，不固定策略造成的后果

同种子共享请求的基础特征、开放到达时间、初始目录、背景过程和资源噪声轨迹。随机流按用途分离，并以请求/资源/时间键关联，避免策略多发一次请求就错位整个随机序列。

路由后的缓存、队列、并发、完成时间由各策略独立演化；这些是需要测量的后果，不能为了“公平”强制相同。也不能拿基线生成的拥塞时间线让所有策略重放，从而切断反馈闭环。

两类因果问题分开处理：

- **整段配对运行**比较策略的总效果，包含对未来队列与缓存的影响。
- **同一时刻状态分叉的小规模反事实**比较单次动作代价。评估器复制状态并分别推进，分叉信息不提供给在线策略；不把这个局部差值当成整个运行的总收益。

真实 `O` 与未来到达只在明确的未来已知诊断中暴露。开发 trace、预测器训练 trace 和正式评估 trace 必须分离。

### 10.3 用到达窗口统计，避免“没完成就不计入”

预热窗口、测量窗口和收尾窗口分开。测量队列包含在测量窗口到达的所有请求；它们之后完成也仍属于原到达队列，goodput 分母为测量窗口长度。

停止到达后继续执行到该队列全部完成或达到预注册最长随访时间。随访结束仍未完成的请求按未达标计入主指标，单列数量和已等待时间；不能只对已完成样本报告一个看似优秀的 P99。若未完成比例使目标分位数不可识别，应报告分位数下界/不可估计及原因。

这类到达队列 goodput 不等于可持续吞吐。容量实验另外在持续到达段检查未完成数和剩余工作的漂移，延长窗口复检边界；停止到达后的清空能力不能证明到达期间稳定。资源成本按同一 cohort 的全部执行归属统计，含收尾阶段；资源利用率则单列持续测量窗口与清空窗口，避免分母混用。

正式报告同时列预热结束的缓存与队列状态。内生缓存既报告共同冷启动过程，也报告足够预热后的稳态；不能让某个策略免费得到预先优化的热缓存。

### 10.4 汇总单位是独立种子/会话组，不是把所有请求当独立样本

每个种子内先计算各策略差值，再报告配对差值中位数与 95% 置信区间；可采用对种子重采样的 bootstrap。会话或长时相关 trace 按独立会话组/时间块处理相关性，具体重采样单位写入报告。不能对同一突发内数千请求做独立 bootstrap 伪造精度。

P99 要报告每类样本量。建议正式关键格子每类累计至少 10000 个请求作为起点，同时检查种子间变动；达不到时优先报告 P95、完整 CDF、超标率及 P99 不确定性。不要把各类 P99 的平均数称为总体 P99，也不要把所有 token 混在一起掩盖少数严重停顿的请求。

负载扫描得到的 `λ*` 应报告满足约束的下端和不满足约束的上端，注明网格精度。若置信区间跨过达标阈值，就增加样本或将边界标为未确定，不能假定中点已经是精确容量。

### 10.5 每个实验必须留下一份可复现证据包

至少包括以下内容：

| 产物 | 必填内容 |
|---|---|
| 实验清单 | 设计版本、假设编号、配置、主指标、负控制、验收条件 |
| 运行清单 | commit、完整命令、种子、依赖版本、trace/配置哈希、模型与硬件标定来源 |
| 逐请求记录 | 类别、N/H/U/O、到达/首 token/完成、SLO、决策、读取/重算、失败与未完成状态 |
| 逐决策记录 | 候选计划、当时实际可见输入、快照版本/年龄、预测成本、选择理由、提交与取消 |
| 逐资源记录 | 队列/工作量、服务量、活动流、HBM 与缓冲、前台/后台分类 |
| 汇总与图 | 每类服务质量、资源解释、配对差值、置信区间、局限和替代解释 |

记录全部 token 时间过大时，可以流式累计 ITL 直方图和每请求停顿统计，但要为审计保留代表 trace。采样规则跨策略一致，并保持尾部事件可追溯。

结果文档放仓库根，图存 `docs/figures/` 并用相对链接嵌入。每个实验至少一张服务结果图和一张资源/时间线解释图；解析实验用甘特图与误差表。正文先给带条件的判决，再展示资源如何变化和服务是否改善。本文是设计文件，不放未经运行的“示意结果曲线”冒充实验数据。

## 11. 验收标准与必须允许出现的否定结论

### 11.1 实现正确性是硬门槛

新机制实现时必须新增以下适用的不变量测试；测试不能只复述策略代码选择了什么。

| 不变量 | 必须验证的性质 |
|---|---|
| 单位与字节 | KV 张量计数、分片/块对齐一致，GB 与 Gb/s 转换正确 |
| 资源守恒 | 各资源累计服务不超过可用容量积分；取消不抹掉已消耗服务 |
| 工作守恒 | 必要 KV 块均由有效复用、取回或计算产生；无凭空出现、漏算或意外重复 |
| 容量安全 | 活动、共享、可驱逐和预留块不重计、不超配；拒绝准入后仍能推进已有工作 |
| 依赖与完成 | 无前置状态就绪不得执行对应后缀；首 token、decode、释放顺序正确 |
| 极限与退化 | 无远端命中时不取回；部分恢复两端退化正确；关反馈开销为零时配置可复现 |
| 解析一致 | 单请求阈值、已知排队场景、两请求算例与手算一致 |
| 单调性范围 | 固定动作、固定负载、无策略切换的简单模型中，提高瓶颈容量不应延长服务；不要求复杂闭环策略全局单调 |
| 信息隔离 | 改动尚未公开的未来输出或未来压力，不应改变同一已知历史下的在线决策 |
| 承诺对账 | 候选查询无副作用；提交、取消、完成和快照合并不漏记/双计 |
| 确定性 | 同配置、种子和事件顺序产生相同日志；同时间事件按事前规则处理 |

更改共享执行/指标组件时，按仓库规范运行全量测试和既有 v1 回归。回归用于防止破坏既有行为，不能代替上述新问题的验收。少种子冒烟不得覆盖正式入库图。

### 11.2 机制 go/no-go：先写阈值，后看结果

若还没有业务给出的最小实用收益，建议采用以下**默认研究验收线**，正式运行前可根据部署成本修改并留痕：

- 在两个事前指定、具有不同干扰结构的主场景族中，相对 History 强基线，容量 `λ*` 中位数至少提高 5%，配对差值区间下端大于 0；**或者**固定负载下主尾延迟至少降低 10%，同时不降低有效吞吐和类别服务约束。
- 以上收益已经包含反馈、决策和新增数据动作成本。各预注册类别达标率下降不超过 1 个百分点，且满足各类绝对最低目标；用配对差值的单侧区间检查非劣，不能只看中位数。
- 至少经过一种模型结构变体与一种分布变化后仍有解释一致的收益；“只有某个精确参数点赢”不满足稳健性要求。
- 低负载、无远端访问和共同瓶颈不可绕开的控制场景允许没有收益；默认要求新增机制在低负载的 P95 延迟退化不超过 5%，否则必须限制其启用范围并解释原因。

5%、10%、1 个百分点均是项目决策线，不是文献事实或自然定律。效果达不到这些线，不等于统计上不存在；应明确区分“有小幅作用”和“值得增加系统复杂度”。若基线已让所有请求达标，不使用不可改善的 goodput 比较强行作 no-go，改看容量、延迟和成本。

### 11.3 观察到不同结果时，研究应如何继续

| 观察 | 目前能下的结论 | 下一步 |
|---|---|---|
| Static 差，History 与 Feedback 相同 | 在线估计有用，新增接口未显示增量 | 优先完善计算侧历史估计，缩小接口主张 |
| Feedback 好，真值更好 | 状态年龄/噪声/模型误差仍有限制 | R4 定位字段与时效，先测净收益 |
| 真值贪心也差，协调后变好 | 主要问题是并发承诺与资源分配 | R5；不继续只提高遥测精度 |
| TTFT 好，ITL 或长类达标率差 | 成本被转移到 decode/弱势类别 | 修改目标或增加共同的保护约束，重跑 R2 |
| 换副本无效，共同 fabric 饱和 | 路由没有创造新容量 | 研究减流量/重算，或改变实际拓扑；不虚增副本带宽 |
| 部分恢复有效，动态信息无增量 | 引擎能力是主要收益来源 | 将恢复调度与信息贡献分开陈述 |
| 固定缓存有效，内生缓存无效 | 短期决策被长期生命周期成本抵消 | R7 解释具体成本，再决定是否进入 R8 |
| 仅理想 overlap 或免费复制有效 | 收益依赖不现实条件 | 暂停部署主张，验证执行能力与代价 |
| 真值/未来已知诊断也无收益 | 本场景可能缺少可优化空间，或诊断器太弱 | 用小规模最优和资源可行性检查区分；保留负结果 |
| 少数场景有效，范围清晰 | 条件性机制成立 | 形成启用/回退规则，不宣传普遍优越 |

### 11.4 结论模板

后续每个 headline 用下面的结构表述：

> 在【部署与模型】、【N/H/U/O 组成】、【主要瓶颈】及【状态质量】下，相对【具备何种信息与动作的基线】，加入【唯一主要变化】使【主指标】变化【效应量与区间】；【各类 TTFT/TPOT/ITL】满足【约束】。资源证据显示【因果解释】。在【负控制或边界】下该收益消失/反转，因此结论只覆盖【范围】。

任何不能填出基线能力、收益承担者和失效边界的“总判决”，都需要补实验。

## 12. 实施顺序与每一步的交付物

### 12.1 最小研究闭环

```text
冻结请求/资源/服务定义
          ↓
M0 + R0：解析、依赖、守恒
          ↓
M1：真实竞争的 prefill + decode + HBM + 数据路径
          ↓
R1：History 与 Feedback 是否真的不同
          ↓
R2：混合长短与完整服务约束
          ↓
R3：状态消费位置和共享瓶颈
          ↓
R4：最小信号、时效、净成本
          ↓
R5：并发闭环稳定性
          ↓
第一份机制判决与适用边界
```

R6 的部分恢复是单独动作扩展，R7 的缓存演化是部署结论前的必检项；R8 按问题进入。R9 的小型 profiling 可以在 M1 设计时启动，最终独立迁移验证在核心机制冻结后完成。不要等所有高级功能齐全才允许第一次 no-go。

### 12.2 分阶段交付与停止条件

| 阶段 | 交付物 | 可以进入下一阶段的条件 |
|---|---|---|
| S0 定义冻结 | 字段/单位、依赖图、可见性、SLO、首批矩阵、来源与待标定清单 | 不存在未说明的“长短”、免费动作或未来真值 |
| S1 模型正确 | M0/M1 核心、测试、R0 图与账本 | 不变量通过；GPU/I/O/decode 路径均被实际触发 |
| S2 信息与混合负载 | R1/R2 图表、配对统计、逐类收益和伤害 | 对强基线有可解释结果；负结果也完成归因 |
| S3 跨层与时效 | R3/R4/R5、字段/消费方/更新规则建议 | 净收益、稳定性和退化行为清楚 |
| S4 扩展检验 | R6（若研究该动作）、R7，必要时 R8 | 动作收益与信息收益分开；内生缓存下仍可解释 |

如果 S2 显示 History 足够，应将阶段结论写完整，停止把“必须新增存储反馈接口”当作目标。若 S3 只需要实例内轻量反馈，应以最小可行机制结束本轮，而非继续扩展全局控制器。

每个阶段按仓库流程执行：先补具体设计，再实现与不变量测试，冒烟检查区分度，正式实验，根目录结果文档嵌图，最后提交推送。配置采用 frozen dataclass、背景负载使用 schedule；新实验注册 CLI 并可独立冒烟。这些是实施约束，不要求在本次设计文档任务中提前修改仿真代码。

## 14. 通俗理解：把整个系统想成共用仓库的多间厨房

### 14.1 先把“长短”说成人能理解的东西

有几间厨房共用一个半成品仓库。厨房里已经打开的半成品就像本地 KV，仓库里的半成品就像远端 KV。厨师可以去取，也可以重新做。货梯和走廊由所有厨房共用。

一张订单包含三件不同的事。

**输入长度**像开工前需要完成的备菜工作。**命中长度**像已经有人做好的、可以复用的那部分备菜。**输出长度**像开席后还要连续上多少轮菜。备菜很多但半成品齐全，不一定费很多厨师时间；备菜不多但要连上几十轮菜，也可能长期占住厨房。

因此，不能只把订单分成“大单、小单”。要问准备多少、现成多少、还要上多久。实验里的两组 8 类，就是把这几件事拆开搭配，看看谁在抢什么资源。

### 14.2 仓库里有，不等于现在取最合适

两份半成品一样重，一份重新做只需两分钟，另一份要二十分钟。货梯一次只能运一份，优先运第二份、第一份在厨房重做，可能让两桌客人都更早吃上。

但这个例子还没证明一定要安装仓库实时看板。一个了解重量和制作时间的老调度员也可能安排正确。新看板必须在货梯突然被别人占用、某条路堵住等情况下，比厨房自己积累的送货记录更及时地帮助决策，才值得增加。

这就是为什么必须用“会学习历史的基线”比较，而不能只找一个永远相信货梯空闲的对手。

### 14.3 第一口快了，还要看后面的菜是否断档

发现货梯拥堵后，让厨师把所有半成品重新做，可能让新桌第一道菜快一些，却把正在用餐的客人后续菜肴全部拖慢。

TTFT 是多久吃到第一口，ITL 是两道菜之间等多久，整个请求完成是这一桌是否顺利吃完。厨房忙得不可开交，只说明厨师忙；如果大家都在重复切菜、后续菜迟迟不上，不能说服务变好了。

所以每轮实验都要同时看新桌、老桌、大单、小单。不能为了多报几桌“小单完成”，让少数大桌一直等到打烊。

### 14.4 为什么要分步骤做实验

先固定仓库里放什么、放在哪里，才能看清调度是否安排得更好。然后再允许半成品被吃掉、补货、挪位置，检查这个安排长期会不会出问题。最后才研究提前备货、复制到别的仓库，以及保留哪些半成品。

如果一开始同时换厨师、扩仓库、加货梯、改菜单，最后即使服务变快，也很难知道究竟哪件事有用。

各实验可以用一句话理解：

| 实验 | 厨房里的问题 |
|---|---|
| R0 | 先确认账算对了，不能凭空多出厨师、半成品或货梯容量。 |
| R1 | 实时仓库消息是否比厨房自己的送货经验更有用？ |
| R2 | 备菜多少、现成多少、连续上菜多久混在一起后，是否有人被牺牲？ |
| R3 | 换厨房、换仓库、改为现做，哪种动作能真正绕开堵点？ |
| R4 | 看板要报什么、多快更新，才抵得上维护它的成本？ |
| R5 | 所有厨房同时冲向“最空的货梯”时，是否需要共同排号？ |
| R6 | 一部分现做、一部分去取，实际能否同时推进而不互相等？ |
| R7 | 长期接单、消耗和补货之后，前面的好安排还能否成立？ |
| R8 | 提前备货和另开副本仓库，是否真的比占用的空间与运力更值？ |
| R9 | 纸上的厨房规律，放进实际厨房还能不能对得上？ |

### 14.5 最后应该得到什么答案

理想的研究结果不是一句“看仓库状态一定更好”。它应该能告诉实际部署者：什么订单组合、什么堵点下值得看；信息可以旧到什么程度；应该由谁决定；何时去取、何时现做；哪些情况下应退回简单办法。

若发现厨房自己的经验已经足够，或者所有路都堵在同一部货梯上，文档也应该明确说没有必要增加复杂机制。能可靠地分清这些情况，才是这套仿真的价值。
