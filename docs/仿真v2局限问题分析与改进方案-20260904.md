## 问题①：参数为占位标定，结论缺绝对可信度

### 问题定位

`GpuConfig.prefill_table`、各 tier 带宽（60/25/40/15 GB/s）、fabric（120 GB/s）、`path_lat` 全部为编造占位值。E5–E9 的结论是机制层面的相对比较，绝对数字（如"P99 = 8.3 s"）不可外推。

### 分析

标定的关键是每个模型假设都要有对应的实测对象，且要**带着证伪意图去标定**——尤其流体模型的两条强假设：

1. processor sharing（并发 N 路取回时带宽均分）；
2. reserved-capacity GPU 背景（rate = 1 − bg）。

真实 NVMe 并非纯 PS：并发升到设备队列深度后吞吐走平（K 路上限），此时单流不再降速。若实测如此，现有模型需要加 `max_active` 参数（最多 K 个活跃传输均分带宽，其余整队等待）——这是唯一的模型改动预案。

### 方案（三层标定，全部有现成工具）

| 标定对象 | 方法 | 填入 |
|---|---|---|
| GPU prefill 曲线 | 目标 GPU 上跑 `vllm bench serve` 类脚本，4K–64K token 网格测延迟；再注入后台负载验证 reserved-capacity 模型 | `GpuConfig.prefill_table` |
| 存储 tier | 部署 NVMe 后端 LMCache，可控并发×可控大小打取回负载；读它公开的 **L1↔L2 端到端吞吐（submit→complete）与 inflight loads** 反推 | 各 `StorageConfig.b_total / t_base`（及可能的 `max_active`） |
| fabric / 路径 | 节点间 RDMA 吞吐 + 延迟实测；若与业务流量共享则把监控占用写成 `bg_schedule` | `TopoConfig.fabric / path_lat` |

### 验证实验

- 用一段生产/回放 trace 在标定后的仿真里重跑，对比真实 TTFT 分布。
- 复测 quote 估计误差（E6 的 `quote_mape` 口径）。

### 验收标准

- 仿真 TTFT P50/P95/P99 相对实测误差 < 15%；
- quote 中位误差仍 < 10%；
- 若引入 `max_active`，需附一条"并发-吞吐曲线：模型 vs 实测"的拟合图。

## 问题②：预取未实现；本地缓存为被动 LRU，无跨 worker 协同

### 问题定位

Q4 的"预取"在 v2 中只有"完成即写本地缓存"的被动形式。本地缓存各 worker 独立 LRU：同一类被多份缓存（浪费 HBM）、覆盖的类数少（命中率受限）。

### 分析

预取的正确形态必须是**压力门控**的：E7/E8 已证明存储拥塞时额外流量有害，无脑预取会撞上同一堵墙。因此"压力门控预取 vs 无脑预取"本身就是一个值得报告的对照——预期无脑预取在拥塞区**变差**，复刻 E7 的"静态信息陷阱"叙事。

### 方案

**预取（两个机制，均长在现有部件上）：**

1. **会话续写预取**：多轮会话第 k 轮完成后，预测第 k+1 轮复用同一前缀；仅当 quote 压力 ≤ WARM 时，用空闲带宽把该前缀提前拉进本地缓存。
2. **重算后回写**：worker 重算跳过取货后完整 KV 已在本地——异步回写到某个存储节点（复用 `_ctrl_loop` 的 `_do_replicate` 内部传输机制）。等价于把"重算逃逸"变成免费副本，自动修复被跳过的取回。

**本地缓存协同放置：**

- 类 → 偏好 worker 的一致性哈希，路由时轻微偏向持有者（保持 load 平衡权重）；
- 基于滚动热度的准入（冷类不进缓存，防止污染）。

### 验证实验（E10）

- 负载：多轮会话生成器（轮数几何分布、轮间隔分布），关闭存储侧复制以隔离变量。
- 策略：no-prefetch / always-prefetch / **pressure-gated-prefetch** / oracle。
- 指标：goodput、本地命中率、**浪费预取字节**（预取了但未使用即被淘汰）、存储负载增量、缓存冗余率（同类被几份缓存持有）vs 覆盖类数。

### 验收标准

- pressure-gated 预取相对 no-prefetch 在会话型负载下 goodput 提升 ≥5%，且拥塞区不劣化（always-prefetch 预期劣化，作为反例呈现）；
- 协同放置后缓存冗余率显著下降且总命中率不降。

## 问题③：E9 oracle 出现"P99 更高但 SLO 率更高"的矛盾形态

### 问题定位

E9 中 oracle 的 burst 窗口 SLO 率最高（0.794）但 P99/P95 反而最高（19.7 s / 14.4 s，高于 greedy 的 8.3 s / 5.5 s）。这一形态若不解释清楚，会被审稿人当作结果不可信的证据。

### 分析（待验证假设）

**oracle 是"完美信息下的逐请求贪心"，不是全局最优。** 它逐单决策时使用 `hypothetical_*` 精确预测当前队列，但看不到同一 burst 里尚未提交的后续请求：

- 它可能为多单选择 GPU 重算（单看每单最优），150 × 0.211 s / 4 worker ≈ 8 s 起步的**车队效应**推高尾部；
- 而 greedy 因羊群把流量分到两个副本的存储队列上，存储队列是带宽型排队，尾部形态不同。

若成立，这反而是**加分结论**：即使信息完美，逐请求局部最优仍非全局最优——协同（准入整形 / 全局分配）具有独立于信息新鲜度的价值，强化 Q5 的 claim。

### 方案

1. **诊断实验（先做）**：输出 oracle 在 burst 窗口内的逐请求动作分布、按动作分解的 TTFT 分布，验证"GPU 重算车队"假设。
2. **clairvoyant 上界**：对 burst 整体解一个离线分配问题（150 单 × 少量候选动作，贪心或 LP 松弛均可），作为真正的全局最优参照。
3. 若 clairvoyant 明显优于现 oracle：把 E9 的上界替换为 clairvoyant，并在结果文档中新增"逐请求贪心（即便完美信息）vs 全局分配"的差距一栏。

### 验证实验（E9b）

复用 E9 场景，新增两列：oracle-action-breakdown 诊断图；clairvoyant 上界。指标：SLO 率、P99、按动作的 TTFT 分解。

### 验收标准

- 给出矛盾的确定性解释（假设证实或推翻，二选一，不允许悬置）；
- 若证实，E9 结论升级为"协同价值 = 信息价值 + 分配价值"两层。

## 问题④：复制仅 mem→mem 同层；容量压力只统计不使用

### 问题定位

`_ctrl_loop` 的目标层固定为源同层；节点 `cap_gb` 与 `capacity_pressure()` 已统计但未驱动任何决策——无跨层降级、无容量淘汰，节点容量事实上无限。

### 方案（三块，全部扩展现有控制器）

1. **跨层降级**：目标层不再固定——对 (node, mem) 与 (node, ssd) 各调一次 quote，选便宜的；mem 拥堵而 ssd 空闲时降层复制。
2. **迁移 vs 复制区分**：滚动热度高的类**复制**（留双份，提可用性）；热度低的类**迁移**（复制 + 淘汰源，回收 mem 容量给热类）。
3. **容量淘汰联动**：`capacity_pressure(n)` 超阈值时淘汰该节点上滚动需求率最低的类，**前置检查目录确认该类在别处仍有副本**（避免孤儿化导致被迫全量重算）。

### 验证实验（E11）

- 负载：节点 `cap_gb` 压到仅够存数个前缀；类数多、Zipf 热度随时间漂移（制造"放置必须跟随热度"的压力）。
- 策略：静态放置 / **压力+容量感知分层（含迁移与淘汰）** / clairvoyant 放置。
- 指标：goodput、副本分布跟随热度的时滞、孤儿事件数、淘汰次数、mem 层容量占用曲线。

### 验收标准

- 分层控制器在容量受限场景下相对静态放置 goodput 提升 ≥5%；
- 孤儿事件为 0（正确性硬约束）；
- 热度漂移后副本分布收敛时滞有量化数字。

## 问题⑤：GPU 侧真值可见，无预测误差层

### 问题定位

策略读 GPU 侧用的是 `GpuPool.remaining_service()` / `drain_est()`——**真值精度**的队列与速率信息。真实系统中计算时间预测是有误差的（Cascade 之所以用带 guardband 的 TTFT estimator，正因如此）。当前设计对存储侧结论**无偏**（所有对比策略拿到同样的 GPU 信息），但带来两个问题：

1. **与 Cascade 类基线的绝对可比性缺失**：Cascade 的核心就是"SLO 预算 × 有误差的恢复时间预测"；我们的 joint2 拿真值 GPU + 有误差的存储 quote，是一场不对等的比较。审稿人问"你和 Cascade 比呢"时，现有基线集（文档 §3 映射表）里恰恰缺 `cascade2`。
2. 收益稳健性未刻画：GPU 估计本身有噪声/陈旧时，joint2 的联合决策收益还剩多少，没有数据。

### 分析

修法与存储侧**对称**，不做单侧开洞（AGENTS.md §3 已固化为原则）：

- 新增 `GpuObservable`（与 `StorageObservable` 同构）：按 interval 采样、EMA、乘性噪声；`drain_est`/`remaining_service` 的策略入口全部改走该视图；Oracle 保留真值。
- `cascade2` 基线 = budget 优先级调度（SLO − 保守估计剩余服务时间，guardband `Lr = ½(L_actual+L_max)×γ`）+ request 级动态 KV 恢复决策，但**无跨副本/跨 worker 全局视野**——即调研对话修正后的 Cascade 边界（request-level optimization）。

### 方案

1. **GpuObservable 层**：复用 `ObsConfig` 的 interval/EMA/noise 语义，独立可调（GPU 与存储的陈旧度可以不同）；`PolicyCtx` 挂 GPU 视图，v1 策略保持真值不受影响（向后兼容开关）。
2. **cascade2 基线**：按上一条定义实现，进 `V2POLICIES` 与基线映射表（文档 §3 补一行）。
3. **E12 实验**（两个面板）：
   - **稳健性扫描**：GPU 估计噪声 σ ∈ {0, 0.1, 0.3} × 陈旧度 {0, 50, 200 ms}，看 joint2 相对 static2/default2 的收益保留率；
   - **对等比较**：cascade2 vs joint2（两者都读带误差的 GPU + 存储 quote，差异只在"request 级预算调度 vs 全局联合调度"）——这正是调研对话末尾建议的"Cascade-like vs Cascade + 共享存储压力反馈"对照。

### 验收标准

- cascade2 加入后，joint2 在共享存储拥塞场景下优势仍显著（≥5% goodput），且优势随存储压力上升而扩大（印证"request 级 → 集群级"的 gap 论证）；
- GPU 噪声 σ=0.3 / 陈旧 200 ms 时，joint2 相对基线的收益保留 ≥70%（否则说明联合决策对 GPU 估计误差过敏，需在方案中引入保守项）；
- v1 策略行为回归不变（真值开关默认开启）。

## 优先级与量级

| 顺序 | 事项 | 对应问题 | 理由 | 量级 |
|---:|---|---|---|---|
| 1 | E9 oracle 矛盾诊断 + clairvoyant 上界 | ③ | 半天可完成；消除一个论文级风险，且大概率反转为加分结论 | 0.5 天 |
| 2 | GpuObservable + cascade2 基线 + E12 | ⑤ | "Cascade 已经做了"是本方向最大质疑；对等比较（双方都有预测误差）直接回应之 | 1–1.5 天 |
| 3 | 压力门控预取 + 缓存协同放置（E10） | ② | 机制缺失中最大的一块；与 E7/E8 叙事闭环 | 2–3 天 |
| 4 | 跨层降级 + 容量淘汰联动（E11） | ④ | 站在现成控制器上扩展 | 1–2 天 |
| 5 | 真实标定 | ① | 最影响可信度但依赖硬件；标定脚本脚手架可与 3/4 并行；GPU 侧预测误差参数（问题⑤）随标定一并填入 | 硬件相关 |

依赖关系：④ 的"迁移 vs 复制按热度区分"复用 ② 的滚动热度统计；③ 独立；② 的 GpuObservable 是 ⑤ 的 E12 前置；① 独立但建议在 ②③④⑤ 定稿后统一复跑一遍全部实验出终版数字。
