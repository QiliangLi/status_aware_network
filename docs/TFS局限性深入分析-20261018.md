# TFS 的局限:逐条分析与影响评估(简化技术中文版)

| 项目 | 约定 |
|---|---|
| 创建日 | 2026-10-18(同日按用户指示改写为简化技术中文版) |
| 对象 | `sim/cq/policies.py` 的 `TFS`(`cq_tfs`) |
| 依据 | E26f 实验记录(《实验结果-E26f-零读第三类实验-20261011.md》§9)与本文附带的复算方法 |
| 用途 | 划清两件事的边界:已验证的实验结论;未验证的部署判断 |

## 术语

- **TFS**:本仓库的规则式调度器。每轮决策只做排序和计数,不推演。
- **读取压力 d**:每层读取量 ÷ 每层计算时长。数值越大,请求越占带宽。
- **重流**:读取压力不低于门槛的请求。E26f 里是 A 类。
- **轻流**:读取压力低于门槛的请求。E26f 里是 B 类和零读的 C 类。
- **门槛**:全体已到请求读取压力的 P75(第 75 百分位数)。
- **配额 C**:允许同时在跑的重流条数上限。C = ⌊带宽上限 ÷ 门槛⌋。E26f 里 C = 4。
- **末层**:一条请求的最后一个计算层。末层计算期间,该请求不再读取任何数据。
- **空泡**:重流占着配额、但不占带宽的那段时间。
- **E26f**:验证 TFS 的实验。结论:TFS 拿到 MPC 相对 FCFS 收益的 95.3% 与 91.3%。
- **MPC**:推演式调度器。TFS 的对比基线。

## 共同条件

- E26f 实验有五个条件:每批一条(n_max=1);请求类别离散;计算时长公式精确;期限 = 4 × T0;到达构成恒定。
- 九条局限在这五个条件下全部不触发。
- 因此每条局限写两栏影响:
  1. **对实验结论的影响**:是否动摇「捕获 95%/91%」等已得数字。
  2. **对真实部署的影响**:把 TFS 搬到真实系统时的风险。
- 验证状态分三档:**已验证**(有检查方法与结果)、**未验证**(有机理推演,没有实验)、**未确认**(缺证据,写明确认方法)。

## 1. L1:不考虑批(batch size)

**问题**:TFS 只派单条请求。读取压力、配额、时间预算、豁免全部按单条定义。真实推理服务把多条请求拼成一批执行。

**为什么 E26f 测不出**:实验规定每批一条。全部策略在同条件下比较。

**量化**(已验证:用标定画像复算,方法见文末):

| 拼批方式 | 每层计算 | 节省 |
|---|---|---|
| 8 条 A 拼一批 | 44.48 ms(单条累计 48.16 ms) | 7.6% |
| 8 条 B 拼一批 | — | 0.15% |
| 8 条小请求(h=512,u=128)拼一批 | 1.99 ms(单条累计 7.34 ms) | 73% |

**解释**:A 的每层计算 85% 花在注意力项。拼批摊薄不了注意力。短序列的线性项可以摊薄,所以小请求收益大。

**影响**:
- 对实验结论:零。
- 对真实部署:高。真实系统普遍拼批;短序列负载下拼批是最大的单根杠杆。TFS 的规则必须先改成批粒度,旧结论才适用。

**改法方向**:按批定义读取压力(批读取量 ÷ 批计算时长)、配额、时间预算。必须先写设计文档,再实验。

## 2. L2:带宽占用缺少实时视角

### 2a. 配额数的是 NPU,不是带宽

**问题**:配额计「这个 NPU 挂着一条重流」的全程。一条 A 的末层计算(6.02 ms)期间不读任何数据,但仍占配额。

**量化**(已验证:复算):
- A 占 NPU 49.6 ms,占带宽 43.6 ms。
- 每条 A 留 6.02 ms 空泡,占槽位时间的 12.1%。
- 重流吞吐上限因此损失 13.8%。

**影响**:
- 对实验结论:零。数字是实测,已包含这个效应。它属于「为什么还差 MPC 一点」的解释项(见第 4 节)。
- 对真实部署:中。

**改法**:配额只数「仍有未完成读取」的重流。判定用公开信息:已完成层数 < 7。

### 2b. 轻流没有闸

**问题**:轻流恒可派。多条轻流可以自己把带宽挤满。TFS 不数轻流,挤满了也不知道。

**量化**(已验证:复算):
- 本工况 B 平均并发 22.4 条,带宽需求 30.2 GB/s,占上限 25%。
- B 到达率 ×3 即 91 GB/s;×4 即饱和。

**影响**:
- 对实验结论:零。
- 对真实部署:中。轻流主导的负载下没有保护。

**改法方向**:给轻流设第二道更高的闸,或达到阈值后轻流也 WAIT。未设计,未验证。

### 2c. 闹钟对齐的是「批完成」,不是「带宽释放」

**问题**:WAIT 的唤醒时刻取最早重批的完成时刻。带宽释放比完成早一个末层(6.02 ms)。空泡出现时,等待者还睡着。

**影响**:与 2a 合并计。**改法**:与 2a 同一处修。

## 3. 其他七条局限

### 3.1. L3:门槛的三个毛病

1. **切口任意**。门槛上下的两条请求,读取压力只差一点,待遇差一道闸。
2. **门槛不直接锚定容量**。它回答「谁相对重」,再由配额公式接回容量。直接的替代是绝对阈值(如 带宽 ÷ NPU 数)。未探索。
3. **门槛锚定累计到达记录,不跟当前队列**。曾经跟过队列:A 完成离队后,配额在 4 和 89 之间来回跳(20260930 修复记录)。修法是锚定累计分布。代价:对当前队列不敏感。

**影响**:对实验结论:零(类别离散,门槛恰好切在类边界)。对真实部署:中。真实 trace 的读取压力连续分布,切口问题会暴露。未验证。

### 3.2. L4:老化豁免从未点火

**问题**:E26 全系列豁免时限为零。豁免分支从未触发。两个后果:
1. 阈值怎么设,没有设计过。
2. 设了之后有什么副作用,没有数据。

**影响**:对实验结论:零。对真实部署:中。期限越来越紧的轻流持续插队时,没有饥饿保底。

### 3.3. L5:计算时长靠公式,真实系统只能靠估计

TFS 每一步都要回答一个问题:这条请求每层算多久?记这个时长为 c。

- 读取压力 d = 每层读取量 ÷ c。
- 配额 = ⌊带宽上限 ÷ 门槛⌋,而门槛来自 d。
- WAIT 的闹钟也用 c 估计「最早的重流什么时候完成」。

仿真里 c 是精确的:公式直接算出来。真实系统里没人提前知道一条请求要算多久,只能估。估计就有误差。

误差为什么危险?因为配额是整数,一档一档地跳。用一条 A 走一遍:

1. 真实 c = 6.02 ms。d = 29.2 GB/s。配额 = ⌊120 ÷ 29.2⌋ = **4**。4 条 A 共占 116.7 GB/s,刚好贴住上限。✓
2. 把 c 估小 20%(以为只要 4.8 ms)。d̂ = 36.5。配额 = ⌊120 ÷ 36.5⌋ = **3**。只放 3 条 A,实际只占 87.5 GB/s。**浪费了四分之一带宽。**
3. 把 c 估大 20%(以为要 7.2 ms)。d̂ = 24.3。配额 = ⌊120 ÷ 24.3⌋ = **5**。放 5 条 A,实际占了 145.9 GB/s。**超过上限 22%。**

结论:估计偏一档,容量错 ±25%。

**改法方向**:估计一律往保守侧取(宁可用不满,不得超订);或者配额不数整数条数,按 d 加权记账。未实施,未验证。

### 3.4. L6:「等久的人自然排最前」只在特定期限规则下自动成立

先看 E26f 里为什么饿不死。用数字走一遍:

1. E26f 的期限 = 到达时刻 + 4 × T0。
2. 一条新到的 C,时间预算恒为 3 × 48.2 = 144.5 ms。不管什么时候到,预算都是这个数。
3. 一条等待中的 A,预算从 148.9 ms 开始,每等 1 ms 就少 1 ms。
4. A 等过 5 ms 后,预算低于任何新到的请求。它排到队首。下一个空出的配额位就是它的。

所以轻流源源不断地到达,也只能让 A 晚几十毫秒,不能让 A 永远等。

这个证明用到一个前提:**每一类新到请求的预算是一个固定的正数**(3 × T0)。

前提什么时候破?期限不再跟 T0 挂钩、想给多紧就给多紧的时候。比如一条新到的请求预算 50 ms,老 A 预算 80 ms——新请求插到 A 前面,合理(它更急)。但如果每条新到的都比上一条更紧,老 A 前面永远有人,永远轮不上。这就是饿死。

保底机制是老化豁免:等够久了强制派一次。它没有启用(见 3.2),阈值也没有设计过。

**影响**:对实验结论:零。对真实部署:取决于期限怎么给。按 T0 比例给期限的系统自动安全;期限可以任意紧的系统有饿死风险。未验证。

### 3.5. L7:只管一种资源;NPU 进度在仿真里免费可见

两条:

1. **只管存储带宽这一种共享资源。** NPU 算力只通过「32 个工人、一人一活」间接体现。算力需求远超带宽承载(比如计算下限是存储的两倍以上)的工况没有测过。
2. **TFS 判断「哪条重流还在读」,要读 NPU 的进度(算到第几层)。** 仿真里这个数字是真值,免费可见(既定简化)。真实系统里要靠引擎上报,上报有延迟和误差。误差又叠加进 3.3 的估计问题。

### 3.6. L8:TFS 被叫醒的次数是 FCFS 的 11 倍

WAIT 会设闹钟。每个闹钟到点,就是一次新的决策。实测同一条负载:

- FCFS 决策 345 次。
- TFS 决策 3807 次,是前者的 11 倍。

仿真里无所谓:每次决策 0.11 ms,总共不到半秒。真实系统里有两个隐患:

1. 很多进程抢一个中央调度器,决策本身要排队。
2. 闹钟不精确。定时差 5 ms,等于给每个配额位再加一个空泡(见 2a)。

### 3.7. L9:门槛跟着「历史全部到达」走,不跟「现在谁在排队」

门槛 = 全部已到请求 d 值的 P75。它是一辈子的累计账,不是当前队列的快照。两个边角:

1. **刚开机**:只有几条请求,门槛由这几条随便定,不稳定。
2. **负载突变**:新来一批完全不同的请求后,门槛要等新样本攒够才挪过去,中间有一段错配。

E26f 三类各三分之一、从头到尾不变,两个边角都不出现。

## 4. TFS 比 MPC 差的那几个点,是谁的账

先看账单。实测:

- 总满足率:TFS 比 MPC 低 1.4 个点(存储瓶颈格点)、3.9 个点(计算瓶颈格点)。
- A 类存活率:低 4.2 个点、11.6 个点。

在实验条件下,L1(批)、L5(c 估计)、L6(期限形状)都不出现,先排除。剩下两个候选:

1. **空泡(2a + 2c)**。MPC 推演时看得见「那条 A 快读完了,带宽马上空出来」,于是提前派下一条。TFS 看不见,傻等它完全结束。空泡占槽位 12%,量级和残差对得上。未验证。
2. **洪峰时刻的联合调度**。MPC 在少数决策点同时调整多个 NPU 的派发顺序。TFS 一次只看一个 NPU。这部分是「用规则换速度」的固定差价,修不掉。

怎么确认第 1 条?做一个小改版 `tfs_bw`(配额数「还在读的」,闹钟对准「最后一次读完成」),同实验重跑。几秒钟的事。A 存活率若追平 MPC,空泡就是主因,结案。

**结论**:九条局限加在一起,相对 MPC 的影响有上界:不超过 4 个点。

## 5. 先修哪个

1. **`tfs_bw` 小改版(推荐先做)**:配额只数还在读的重流,闹钟对准带宽释放时刻。设计已写好,重跑 4 个 run,秒级。做完即可确认或排除空泡这个主因。
2. **批粒度改造**:按批定义 d、配额、时间预算。工作量大,必须先写设计文档再动。
3. **c 估计取保守侧**:宁可少派,不得超订。中等工作量。
4. **豁免参数化**:设计豁免时限,补「期限越来越紧」的对抗工况。中等工作量。
5. **其余记录在案**:轻流软闸、绝对门槛、冷启动。遇到对应工况再动。

## 6. 本文自身的限制

- 量化数字来自标定画像与 E26f 记录。复算方法见附录。
- 标「未验证」的条目是机理推演,不是实验结论。
- 对比基线是 MPC,不是理论最优。TFS 与最优的差距未界定。
- 真实系统(批处理形态、定时器精度、估计误差形态)的论断未联网核实。部署前按 `AGENTS.md` §1 补调研。
