## 术语

- **TFS**：本仓库的规则式调度器。三个动作：分诊、填空、错峰。每轮决策只做排序与计数，不推演。
- **TFS-G**：本设计提出的 Dynamo 层 TFS。管全局准入与全局账本。
- **TFS-E**：本设计提出的 vLLM 层 TFS。管实例内队列序与加载并发。
- **重流**：读取压力不低于门槛的请求。E26f 里是 A 类。
- **轻流**：读取压力低于门槛、仍读数据的请求。E26f 里是 B 类。
- **零读类**：不读数据、只计算的请求。E26f 里是 C 类。
- **读取压力 d**：每层读取量 ÷ 每层计算时长。数值越大，请求越占带宽。
- **门槛**：全体已到请求 d 值的 P75。
- **配额 C**：允许同时在跑的重流条数上限。C = ⌊带宽上限 ÷ 门槛⌋。
- **账本**：调度器对「带宽被谁占用」的计数。两种口径：issued（下发即计数）与 active（真正在读才计数）。
- **在途预算**：已下发、尚未开读的重流条数的上限。防账本修正后的洪峰直灌。
- **中央等待**：请求在 Dynamo 准入前排队的时间。
- **直接提交**：请求到达即下发的基线策略。
- **DV 工具**：外部仿真工具。真实 Dynamo + vLLM 框架，计算为 mock。TFS 在其 Dynamo 层做请求级准入。
- **E26f**：本仓库验证 TFS 的实验系列。存储轨道三臂：母实验（FCFS 分配）、单池 max-min、盘维度。

## 1. 问题定义

三组新证据改变了对 TFS 的认识：

1. DV 工具的多级速率对照证明：batch 不为 1 时 TFS 仍然全胜，但获胜方式与 batch=1 的 cq 线不同——下发慢、在飞读取快。
2. E26f 存储轨道三臂证明：带宽聚合还是打散到盘，调度结论不动。
3. 两者合起来引出两个未回答的问题：
   - **问题一**：TFS 的「够」是对负载族的，还是对当前负载的？重读请求变多时，TFS 会退化吗？更细粒度的存储状态还能再买到收益吗？
   - **问题二**：TFS 现在整体在 Dynamo 层。真实系统是两层：调度层（Dynamo）与引擎层（vLLM）。TFS 怎么拆？

## 2. 三组证据确立了什么

### 2.1 速率对照：batch 不为 1 时，TFS 换了一种获胜方式

已验证的事实（DV 工具，每格 360 条，24 次运行）：

| 事实 | 数字 | 出处 |
|---|---|---|
| TFS 总 SLO 六格全胜（2 工况 × 3 倍率） | cA：66.4/48.3/43.9% 对 37.2/24.7/19.4%；cB：70.3/49.2/41.9% 对 42.2/26.4/23.1% | 速率对照 §1 |
| batch 确实不为 1 | TFS 平均 batch 1.09~1.54；直接提交 1.87~2.60 | 速率对照 §2 |
| TFS 的 IO 等待近乎消失 | 1.3~3.6%，直接提交 7.7~24.5% | 速率对照 §3 |
| TFS 的实际带宽更高 | 平均 88.5~110.9 GB/s，直接提交 55.4~93.4 | 速率对照 §4 |
| 保守的代价随倍率上升 | 中央等待：cA 133.1→184.7→224.6ms；cB 135.7→238.2→317.2ms | 速率对照 §5 |
| 反例一：A 类可以先输 | cB 2 倍档 A 类 TTFT：TFS 1023.0ms > 直接提交 940.9ms | 速率对照 §0 |
| 反例二：单 seed 可以平 | cA seed417 1 倍档：直接提交 66.9% > TFS 66.4% | 速率对照 §0 |

**账本高估的机理**（用户提出，本文按证据定级）：

1. TFS 在 Dynamo 层下发读请求后，即认为该请求占用了存储带宽（issued 口径）。
2. batch 不为 1 时，请求先在 vLLM 的 waiting 队列排队。读取未开始，带宽实际空闲。
3. 因此账本高估占用。高估使 TFS 下发更保守。

**自洽抵消**：保守下发使在飞读取变少。每条在飞读取分得更多带宽，完成更快。下发慢的坏处被在飞快部分抵消。

**验证状态**：

- 现象已验证：IO 等待 1.3~3.6%、实际带宽贴上限（速率对照 §3/§4）。
- 机理未验证：DV 工具未记录「已下发未开读」的滞留请求数，高估量没有直接测量。确认方法见 §5 指标 H2。
- 外部旁证（不是 DV 的测量）：vLLM 官方 RFC [#62532](https://github.com/vllm-project/vllm/issues/62532) 实测，异步 KV 拉取的墙钟 **80% 以上是调度排队延迟**，传输只占零头——拉取总时延 1.0~1.8s，线路传输仅 208~283ms。请求经过三个队列：`waiting` → `kv_holding_waiting` → `running`。这证明「下发 ≠ 开读」在真实 vLLM 里量级可观。

**抵消为什么不可依赖**：抵消量随工况漂移，无人控制它。cB 2 倍档中央等待 317.2ms，A 类 TTFT 已超过直接提交（§2.1 反例一）。保守的代价正在吃期限。

### 2.2 存储物理：聚合还是打散，调度结论不动

| 口径 | TFS 捕获率（对 MPC） | mpcS−FCFS 总 SLO 差距 | 出处 |
|---|---|---|---|
| 母实验（FCFS 分配，batch=1） | cA 91.8% / cB 95.2% | +29.4 / +44.7pp | 盘维度文档 §5 |
| 单池 max-min（batch=1） | cA ≈100% / cB 88.3% | +28.1 / +45.3pp | max-min 重跑 §0/§4 |
| 盘维度（3 盘 × 40GB/s） | cA 93.4% / cB 100% | **+35.8 / +49.7pp** | 盘维度文档 §1/§4 |

**读法**：三臂同负载同 seed（CRN）。换分配规则、换盘拓扑，五臂排序逐位不变。存储物理变差时，调度的相对收益反而扩大。

两条附带的硬数字：

1. **盘倾斜的代价无人吃到**：fcfs 臂 B 类 SLO 中位 96.7%→71.7%，总带宽利用率 −7.3pp（功守恒破坏）。MPC 与 TFS 都不感知盘，这 7.3pp 留在桌上（盘维度文档 §4-H3）。
2. **local 崩塌的方法学教训**：local 的评分假设每流独得 min(q, B̂)。该假设在 FCFS 分配下近似成立，在 max-min 下系统性乐观。local 在 cB 从 73.1% 跌到 48.6%（max-min 重跑 §6.2）。结论：**调度器的感知模型必须与真实分配器同构，否则更细的感知反而放大误差**。

| 维度 | 已验证范围 | 未验证方向 |
|---|---|---|

## 3. 问题一：TFS 够了吗

### 3.1 结论的准确表述

**已验证**：在「d 分诊结构存在、期限 ∝ T0、c 精确已知、重读占比 1/3、batch ≤ 1.5」的负载族内，TFS 捕获 MPC 收益 88~100%，且对存储层物理（分配规则、盘拓扑）不敏感。

**未验证**：换负载不退化。当前证据不得外推到重读占比升高、d 连续分布、c 带估计误差的工况。

因此答案分两半：对**已测负载族**，TFS 够了（收益捕获近满、成本零推演）；对**负载族之外**，存在明确的退化路径，且大部分已量化到数字。

### 3.2 退化路径清单

| 路径 | 触发工况 | 机理 | 预期 | 状态 |
|---|---|---|---|---|
| R1 重读占比升高 | A 类占比升高，或前缀命中率下降 | 门槛切口失准 + 配额相对变紧 + 高估量随 waiting 滞留增大 | 退化，量级未测 | 未验证（§5 工况含扫描） |
| R2 轻流洪峰 | B 到达率 ×3~×4 | 轻流恒可派、无闸；×3 即 91GB/s，×4 饱和 | 带宽打满，无保护 | 已验证（复算，局限性 §2b） |
| R3 c 估计误差 | 真实系统无精确 c | c 偏 ±20% → 配额跳档 3/4/5 → 实际占用 87.5/116.7/145.9 GB/s | 容量错 −27%~+22% | 已验证（复算，局限性 §3.3） |
| R4 期限任意紧 | 期限不与 T0 挂钩 | 「等久自然排前」的前提失效；老化豁免从未点火 | 饿死风险 | 未验证（局限性 §3.2/§3.4） |
| R5 盘倾斜长尾 | 真实 trace 块分布散布 | 策略不感知盘，倾斜被承受 | B 长尾 + 吞吐 −7.3pp | 已验证（盘维度 §4，量化的是盲区不是能力上限） |
| R6 冷启动与突变 | 开机、负载切换 | 门槛锚定累计到达记录 | 短期错配 | 未验证（局限性 §3.7） |

**读法**：R2/R3/R5 有数字，是真实风险；R1 是用户点名的工况，恰是 §5 扫描的对象；R4/R6 依赖期限与运营形态，留给 E29 及后续。

### 3.3 更细粒度的存储状态：候选清单与代价

| 候选状态 | 修正的盲区 | 预期收益 | 失配风险 |
|---|---|---|---|
| ① 账本 issued → active | 空泡 12.1%（cq）；DV 的下发保守 | 重流吞吐上限 +13.8%（cq 口径）；中央等待下降（DV） | 下发变激进 → 引擎层排队加深 → **必须与两层拆分同做**（§4） |
| ② 盘维度占用入报价 | 盘维度 −7.3pp 与 B 长尾 | 未测；上限是 7.3pp 的一部分 | local 教训：感知模型必须与逐盘 waterfill 同构，乐观评分反噬 |
| ③ 门槛改当前队列快照 | 切口任意；冷启动错配 | 未测 | 20260930 振荡史：曾随离队在 4↔89 跳 |
| ④ 轻流软闸 | 轻流洪峰无保护 | 未测 | 闸值无设计数据 |
| ⑤ d 加权记账替代整数配额 | c 误差跳档 | 未测 | 失去整数配额的简单性 |

**优先级判断**：

1. ①是前提。DV 现状最疼的点是保守代价（中央等待随倍率单调上升）；修正它必须先把引擎层的控制权建出来，即问题二。
2. ②有量化靶子（7.3pp、B 长尾 14%），但先要过一个同构性测试：感知模型预测的每盘速率与真实逐盘 waterfill 对拍。local 的教训直接适用。
3. ③④⑤ 等 E29 用真实 trace 检验 L3/L5/L9 之后再动。E29 的连续 d 分布正是门槛与加权记账的第一次真实考场。

### 3.4 与 E29 的衔接

E29（真实 trace 集群定标）会让 L3/L5/R6 首次接受连续分布检验。本文不并入 E29 矩阵；重读占比扫描放在 DV 工具侧（§5）。

## 4. 问题二：两层拆分设计

### 4.1 两层的真实结构（外部系统，已核实来源）

| 层 | 组件 | 事实 | 来源 |
|---|---|---|---|
| Dynamo | SelectionService 等 | 请求选路、KV 感知路由；DV 工具的 TFS 在此层做请求级准入 | [Dynamo 仓库](https://github.com/ai-dynamo/dynamo)（`components/core/src/selection_service.rs`）、[官方文档](https://docs.nvidia.com/dynamo/v1.3.0/getting-started/introduction) |
| vLLM V1 | Scheduler | 双队列 `waiting`/`running`；异步 KV 拉取下再分出 `kv_holding_waiting`，共三段 | [vLLM API 文档](https://docs.vllm.ai/en/stable/api/vllm/v1/core/sched/scheduler)、RFC [#62532](https://github.com/vllm-project/vllm/issues/62532) |

关键事实：**上层下发 ≠ 下层开读**。RFC #62532 实测，拉取墙钟 80% 以上是调度排队延迟（1.0~1.8s 中传输仅 208~283ms）。scheduler 会跳过 HIT_PENDING 的请求、先收更晚的冷请求——引擎层的排序行为直接决定「下发到开读」的滞留时长。

### 4.2 拆分原则：三律各归其层

| TFS 动作 | 归属 | 理由 |
|---|---|---|
| 分诊（d、门槛、C） | TFS-G | d 分布是全局量，只有上层看得全 |
| 填空（轻/零流不阻塞） | G 与 E 各守一道 | G 保证准入不拦；E 保证批内不被未就绪重流挡住 |
| 错峰（配额） | 拆两半 | G 持全局 active 账本；E 持实例内加载并发上限。同一物理约束的两半控制权 |
| 账本 | G 持有，E 喂数据 | 修正 issued 失真，又不让上层瞎猜 |
| 唤醒（WAIT 闹钟） | G | 用「最早 active 完成估计」替代「最早下发完成」 |

### 4.3 TFS-G：Dynamo 层规则表

| 序 | 规则 | 与现状 TFS 的差异 |
|---|---|---|
| G0 分诊 | d、门槛 P75、配额 C，口径同现状 | 不变 |
| G1 填空 | 轻/零流恒可派，slack 升序 | 不变 |
| G2 守门 | 重流仅当 Σactive 重流 + 在途条数 ≤ C + inflight_bound | 计数从 issued 改为 active + 在途预算 |
| G3 锚点让位 | 老化豁免仅当无等待中的轻/零流 | 不变 |
| G4 错峰 | WAIT 至最早 active 完成估计（剩余字节 ÷ 近期实际速率） | 唤醒口径改 |
| G5 反压 | 实例 waiting 深度超阈值 → 该实例停收重流，直到回落 | 新增 |

### 4.4 TFS-E：vLLM 层规则表

| 序 | 规则 | 依据 |
|---|---|---|
| E1 队列序 | `waiting` 按 slack 升序，替代 FIFO | RFC #62532 的队首提升同思想；填空律的批内兑现 |
| E2 加载并发 | 每实例同时在加载的重流字节 ≤ 该实例份额；条数与字节双口径 | 错峰的实例内一半；字节口径弱化 c 估计误差 |
| E3 就绪优先 | 已就绪的请求优先进 `running`；未就绪重流不得阻塞轻/零流 | RFC #62532 机制 1B（decode → 就绪 kv_holding → 冷 prefill 三遍调度）同型 |
| E4 上报 | 每步上报：正在加载集合、各剩余字节、waiting 深度 | G 的账本与反压的数据来源 |

与 RFC #62532 的关系：E1/E3 与其提议的调度侧修复同型。差异有二。其一，RFC 以到达序为默认，TFS-E 以 slack 序。其二，RFC 是单层修复，TFS-E 与 TFS-G 构成跨层闭环。

### 4.5 为什么安全：两半控制权

1. 账本修正后下发更激进，风险由 E2 兜住：实例内加载并发上限保证物理带宽不打爆。
2. 上报延迟或丢失，风险由 inflight_bound 与周期校准兜住：账本漂移有上界。
3. c 估计误差（R3）由 E2 的字节口径弱化：按字节记账不随估计值跳整数档。
4. 抵消从偶然变设计：现状的「保守下发 → 在飞更快」是无人控制的均衡；两层化把它拆成两个显式旋钮（全局 active 账本、实例内加载并发），各自可调可测。

### 4.6 与 tfs_bw 小改版的关系

`docs/TFS局限性深入分析-20261018.md` §5 推荐的 tfs_bw（配额只数还在读的、闹钟对准带宽释放）是两层拆分在 batch=1 世界的投影：batch=1 时下发即开读，issued ≈ active，账本修正只剩空泡一项。两件事共享「active 账本」这一核心口径，验证载体不同（cq 线 4 个 run 秒级；DV 侧见 §5）。

## 5. 验证方案（预注册；载体为 DV 工具）

### 5.1 臂（5 个）

| 臂 | 内容 |
|---|---|
| B1 直接提交 | 基线 |
| B2 TFS 单层 | 现状（issued 账本） |
| B3 TFS 两层 | TFS-G + TFS-E |
| B4 消融 G-only | 只改账本（active + 反压），引擎原生 |
| B5 消融 E-only | 只改引擎（E1~E3），G 维持 issued |

### 5.2 工况

- 到达率：3 档（1 / 1.5 / 2 倍，沿用速率对照网格）。
- **重读占比**：{1/3（现状）, 1/2, 2/3}——提高 A 类占比实现。此扫描同时回答问题一的 R1 路径。
- 固定 seed 展示 + 多 seed 中位数判读，沿用速率对照的口径。

### 5.3 指标

总 SLO、分类 TTFT、**中央等待**（保守度的直接量）、**waiting 深度时序**、**issued − active 账本差**（把 §2.1 的机理推演变成实测）、IO 等待、带宽曲线。

### 5.4 预注册假设

| 假设 | 内容 | 判定口径 |
|---|---|---|

## 7. 通俗版解读

把两层想成**医院的预检台和诊室**：

- **预检台（Dynamo，TFS-G）**看得见全院的病人构成，决定放谁进门。现在的 TFS 预检台有个错觉：化验单一发出去，就当人家已经在抽血了。其实单子压在诊室的抽血队列里（vLLM 的 waiting 队列）。于是预检台以为管道满了，少发单——在抽血的病人反而每人分到更粗的管子，抽得快。歪打正着，但这个平衡没人管：病人来得越猛，预检台压单越狠（中央等待 133→317ms），最急的病人开始吃亏。
- **两层化**做一件事：预检台只数「真的在抽血的」（active 账本），同时给每个诊室一条规矩「同时抽血的人数有上限」（TFS-E 的加载并发）。预检台敢多发单了，因为诊室自己兜得住；诊室里先来后到改成分诊急缓（slack 序），血已经抽完的优先进诊室看病（就绪优先）。
- **问题一的答案**也是这个故事的后半段：现在的 TFS 在「病人构成不变」的医院里够用了（换分水规矩、换窗口布局都不掉分）；但病人里「要抽血的」占比翻倍时，压单的错觉会被放大——这正是下一轮实验要扫的档位。
