## 1. 语义变更:改了什么、为什么

### 1.1 现行口径(frozen_history_catalog,规格 §5.5)

- 取每份 trace 时间最早的 **20% 请求**,把它们的前 512-token 完整块插入一棵**前缀 trie**,构成"缓存目录";
- 之后(训练/评价段)每条请求从首块沿自己的 hash 序列在 trie 上走,**走到第一个不在树上的块停止**,得连续命中块数 k;
- h = min(512·k, input_length−1),u = input_length−h;
- 目录**运行期间不增不减**,三个文件目录互相隔离。

设计意图:命中机会对所有策略完全相同,防止"完成快的策略动态制造命中"把缓存机制混进调度收益。

### 1.2 新口径(first-seen,全局首现判定)

- 按 (timestamp, source_line) 稳定顺序**全局扫一遍** trace,维护一个"已见 hash 集合";
- 每条请求:某块 hash **在它之前的任何请求中出现过** → 该块视为命中;**全局第一次出现** → 未命中;
- 扫完一条请求后,才把它自己的完整块加入"已见集合"(同一条请求内部的重复块**不互相可见**);
- 命中长度 h 与 u 同样按"至少留 1 个 token 现场计算"保护:h = min(命中 token 数, input_length−1);
- 每条请求的 h **一次性预计算**,作为新字段写入增强 trace 文件;仿真导入时直接读字段,不再做 trie 查询。

两者本质区别:**目录的构成与增长方式**。旧口径 = "只有最早的 20% 请求贡献缓存,之后冻结";新口径 = "全部历史请求按时间顺序滚动贡献缓存,越晚的请求可命中的越多"。新口径更接近真实系统里"用过的前缀都会被缓存"的动态行为;它对调度对比仍然公平——因为命中长度是**预先离线算好、写死在 trace 字段里**的,与任何策略的运行行为无关。

## 2. 四个必须先拍板的决策点

新口径的用户描述存在四处歧义,本文档给出推荐;**实施前请用户确认**。

| # | 决策点 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| D1 | 命中是否要求**从头连续** | A. 连续前缀:从首块开始连续检查,遇到第一个未命中块即停,h = 512×连续块数<br>B. 稀疏累计:每个块独立判定,h = 所有"已出现过"块的 token 总和(可跳着) | **A(连续)** | prefill 的 KV cache 是前缀性的:第 i 个块的 KV 依赖前面所有块,稀疏命中无法直接用于标准 attention。B 需要另一种系统抽象(分块缓存+重算),超出本模型边界 |
| D2 | 同一请求内部的重复块是否互相可见 | A. 不可见(整条请求处理完后才入集合)<br>B. 可见(块逐个入集合) | **A(不可见)** | 同内容块在不同位置的 KV 含位置编码,不能跨位置复用;且 B 会让"输入自身重复"的请求获得物理上无法解释的命中 |
| D3 | 尾块(不满 512 的最后一块)是否参与判定 | A. 参与<br>B. 不参与 | **A(参与,用户裁定)** | 用户观点成立且经数据检验证实:hash_id 是块内容的指纹,内容不同(含长度不同)指纹必不同——三份 trace 全量扫描中,"同一 hash 既以完整块又以尾块出现"的冲突为 **0** 次、"同一 hash 以两种不同长度尾块出现"的冲突为 **0** 次。因此完全按请求显示的 hash_ids 判定即可,尾块有自己的指纹,无歧义。尾块命中时该请求记全命中(h = input−1,u = 1) |
| D4 | 三段式时间切分(20%/20%/60%)是否保留 | A. 保留:最早 20% 弃置(不参与打分),中间 20% 训练,后 60% 评价<br>B. 弃置段并入训练(0/40/60)<br>C. 全量打分(不切分) | **A(保留,待确认)** | 三段式的目的见 §2.1:是**调参与打分的分离**,不是让各方案跑不同数据子集——所有方案都在评价段的全部 15 个窗口上配对比较。保留弃置段的理由:它是全 trace 最早的流量,面对的历史几乎为零、首现未命中占主导,统计特性与后段差异大。若选 C(用户直觉的"跑完整 trace"),技术上无障碍,但 B\*/gate 等参数将在打分同一份数据上选定,报告须声明该方法论弱点 |

下文按 **D1=连续 / D2=不可见 / D3=参与 / D5=first_seen 默认** 展开,D4 待确认(暂按 A);若 D4 选其他组合,仅影响数据装载与结果可比性,不影响命中语义与修改清单。

### 2.1 D4 补充说明:三段式到底在防什么

三段式**不是**"每个方案只跑一部分数据"——每个方案都会跑评价段的全部 15 个窗口,所有方案在**同样的窗口**上做配对比较。切分解决的是另一个问题:实验里有一批"必须先看数据才能定"的参数——B\*(从 7 个简单基线里选最强者当参照)、老化保护阈值、MPC 的改善门槛等。如果这些参数在**最终打分用的同一份数据**上挑选,就是"先看考卷再复习":赢了也分不清是策略真好还是参数恰好贴合了这份考卷。所以纪律是:训练段(中间 20%)上定参数 → 冻结 → 评价段(后 60%)打分,打分数据在调参时一次没被看过。最早的 20% 在旧口径里另有用途(建冻结目录);新口径不需要建目录,它的去留就是 D4。

## 3. 精确定义与预处理算法

### 3.1 伪代码(方案 A/A/A)

```text
seen = 空集合                       # 已见 hash(来自之前请求的全部块,含尾块)
for row in rows 按 (timestamp, source_line) 升序:
    n_full = floor(row.input_length / 512)
    k = 0
    for i in 0 .. len(hash_ids)-1:  # 完整块与尾块都参与判定(D3=A)
        if row.hash_ids[i] in seen: k += 1
        else: break                 # 连续前缀:首个未命中即停(D1=连续)
    hit = 512*k
    if k > n_full:                  # 尾块也命中 → 全命中,留 1 token
        hit = row.input_length - 1
    row.hit_tokens = min(hit, row.input_length - 1)      # 至少留 1 token
    row.u_tokens   = row.input_length - row.hit_tokens
    row.full_hit_adjusted = (hit >= row.input_length - 1)
    seen ∪= row.hash_ids            # 本请求全部块入集合(处理后,D2=请求内不可见)
输出:增强 trace(每行新增 3 个字段)
```

### 3.2 产物文件与格式

- **原始三份文件一律不改**(它们是官方发布、SHA256 验收的输入);
- 新增派生文件:`mooncake_trace/derived/<原名>.hit.jsonl`,每行 = 原行全部字段 + `"hit_tokens": int, "u_tokens": int, "full_hit_adjusted": bool`;
- 同目录生成 `derived/derive_report.json`:输入文件 SHA256、行数、输出 SHA256、按段统计(弃置/训练/评价各自的请求命中比例、token 命中比例、h/u 分位数)——作为**新口径的验收指纹**;
- `derived/` 不入库(mooncake_trace 整体不入库的既定纪律),由预处理脚本可重现生成;`derive_report.json` 的关键数字抄录进本文档附录与 manifest。

### 3.3 新口径验收指纹(实测,2026-09-15)

按方案 A/A/A 对三份 trace 全量扫描的结果(与旧口径对照,详见第 6 节):

| 文件 | token 命中比例(新) | 请求 h>0 比例(新,弃置段之后) | u 中位数(旧→新) | 全命中行数(u=1) |
|---|---:|---:|---:|---:|
| conversation | **0.374** | 1.000 | 5408 → **2010** | 100 |
| toolagent | **0.571** | 1.000 | 861 → **681** | 221 |
| synthetic | **0.651** | 0.531 | 2458 → **348** | 203 |

D3 数据检验(支持"参与"无歧义):三份 trace 各 18.3 万/18.3 万/4.4 万个不同 hash 中,"同一 hash 既以完整块又以尾块角色出现"= 0;"同一 hash 以不同长度尾块出现"= 0——hash_id 为内容指纹的假设自洽。

实现完成后,预处理脚本输出必须与上表逐位一致(差异仅允许来自决策点组合的不同)。

## 6. 研究影响预警(必须重跑,新旧不可混)

用第 3.1 节算法实测三份 trace(弃置段之后),关键量变化:

| 量 | 变化 | 连锁影响 |
|---|---|---|
| token 命中比例 | 12.8%→37.3% / 40.8%→57.0% / 28.9%→65.0% | 读取量 V=κ·h·32 整体上升,共享带宽压力**加大** |
| u 中位数 | 5408→2010 / 861→681 / 2458→373 | 短 u 请求占比上升 |
| u 均值 | 仍为数千(p95 一至三万) | 批内 N=Σu 大概率仍 > N_sat=512,**E21 的 G≈1 结论方向上可能保持**,但必须重跑验证——短 u 批的出现可能让部分格点 G>1 |
| λ0 | 重算(变小:V↑) | 所有 ρ 格点的绝对负载变化,主矩阵须整体重跑 |
| T0/SLO | T0 = 读取↑ + 计算↓ 的净效应,deadline 全体移动 | E21/E23 的满足率绝对值与旧口径不可比 |

结论:**E19–E24 的全部冒烟数字在新口径下作废并重跑**;正式报告只引用与所声明口径一致的数据。两套口径允许并存为对照面板(frozen = "静态目录"下界情景,first_seen = "全历史滚动缓存"情景),这本身是一个有价值的敏感性维度。
