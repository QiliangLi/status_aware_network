# 存储带宽分配策略替换设计：max-min fair（水土填充）

- 日期：2026-10-16
- 状态：**设计待评审（未实现）**
- 来源：跨仓库移植。源设计文档 `dynamo_vllm_simulation/docs/存储带宽分配策略设计-maxmin-20261009.md`（该侧已于 2026-10-10 实现于 `dynamo_vllm_cpu_sim/sim/storage.py`）；本设计把其 **max-min fair 带宽分配策略**移植进本仓库 v1/v2 主线的 `SharedKVStorage`，替换现行**等分（processor sharing）**速率规则。
- 关联：`sim/storage.py`（现行实现）、`sim/config.py`、`sim/engine2.py`、`sim/policies2.py`（Oracle/估计公式）、`sim/worker.py` / `sim/m1.py` / `sim/prefetch.py`（submit 调用点）。

## 1. 问题定义

现行 `SharedKVStorage`（`sim/storage.py:44`）的带宽分配规则是**处理器等分**：就绪传输集合（过了 `t_base` 门控）按 `rate = cap(t) / N` 均分动态容量，与传输自身的消费节奏无关。问题：

1. 等分不考虑"请求要这么快没用"——消费端（GPU prefill）吸收 KV 的速率有上限，超出部分对该请求的端到端无边际收益（重叠工况下），却被等分规则照样分走，挤占了高需求请求；
2. 无法表达需求异质性的公平语义（A/B 双类需求不同时，等分既非按需也非按价值）。

目标：把速率规则替换为**带需求上限的 max-min fair（水土填充）**——每个传输携带需求 `d`（速率诉求），容量供过于求时按需分 + 剩余均分，供不应求时迭代水土填充到不动点。该策略在 dynamo 侧已定义、实现并验收，本设计做跨仓库移植与本仓库语义融合（动态背景负载、双世界信息边界、v2 串行取回链路）。

## 3. 核心性质：同质需求下与现行策略严格等价（替换的安全网）

**命题**：所有活跃传输需求相同（= d）时，waterfill 分配恒等于 `cap / N`：

- Σd ≤ C 时：`alloc = d + (C − N·d)/N = C/N`；
- Σd > C 时：首轮 `share = C/N < d`，无超额者，各得 `C/N`。

而现行 PS 的速率就是 `cap/N`。**推论**：

1. 现役全部实验配置（本仓库尚无需求覆盖机制，所有请求推导需求同值）在替换后**时间线不变**——既有结论文档与入库图**无需重跑**（与源设计 §2"历史基线须重跑"的处境不同，根源是那边改了 Path 放置语义、这边没改）；
2. 两策略的行为差异**只出现在显式配置异质需求的场合**——本次替换改变的是模型的可表达性（按需求公平），不是存量行为；
3. 因此 `bw_policy` 默认值可以直接切到 `max_min_fair`（用户意图"换成"），`ps_share` 保留为对照/回归选项，翻转零风险。

实现上用**同质快路径**（§4.2）保证浮点层面与 PS 逐位一致，使回归对拍可以精确断言。

## 4. 策略形式化

### 4.1 需求 d 的定义与推导

沿用源设计 §3.1 的推导（逐层重叠的追赶节奏，聚合模型下层数相消）：

```
d = kv_gb_per_token / prefill_s_per_token
```

- `prefill_s_per_token = curve(REF) / REF`，REF 取 `prefill_table` 末点（默认 65536 tokens → 0.410 s → **6.256e-6 s/token**）；
- 默认参数下 `d_ref = 0.00032768 GB/token ÷ 6.256e-6 s/token ≈ 52.4 GB/s`；
- REF 不取请求自身长度查表（那会让需求与请求类耦合），对齐源设计"同配置同值 + 覆盖字段制造异质"的口径。

**语义与建模选择的如实记录**：d 表示消费端吸收 KV 的速率，"超过 d 的分配对端到端无边际收益"在**重叠工况**（v2 `partial` 动作，取回链路与剩余 prefill 并行）下严格成立。本仓库 v1 `fetch` 与 v2 非 partial fetch 是**串行**（fetch 完才开始 prefill，`sim/worker.py:17-23`），此时超额分配仍会缩短 TTFT，"d 上限无收益"不严格成立——这是对齐源设计的建模选择，其对低需求类的代价由 E28-H1 量化（§9），不在此预判。

**需求是请求属性，非全局常量**：`Request.demand_gbps` 在 build 时按类注入；per-class 覆盖经 `WorkloadConfig.cls_demand_scale`（§5），供异质需求实验。

**数值 sanity（默认参数的争抢度）**：v1 池 b_total=100 → 单请求 d/C = 52%；v2 ssd 池 30 → d > C（单请求即饱和，waterfill 自然给满 C，不预截断，与源 §7 同一处置）；fabric 120 → 3 并发 Σd ≈ 157 > 120 进入填充区。默认工况已处高争抢区间，E28 无需另造过载配方（E25"存储过载配方"的教训是不重造，此处默认即高争抢）。

**信息边界**：d 由模型/负载配置推导，不是存储内部状态（队列/带宽/背景负载/`hypothetical_*` 之外的新增可见量），所有策略合法可见，不违反信息边界铁律。

### 4.2 waterfill 算法（照搬 dynamo 已实现版本 + 同质快路径）

模块级纯函数，放 `sim/storage.py`：

```python
def waterfill(capacity: float, demands: list[float]) -> list[float]:
    """带需求上限的 max-min fair 分配，迭代到不动点；O(n log n)。"""
    n = len(demands)
    if n == 0:
        return []
    d0 = demands[0]
    if all(d == d0 for d in demands):        # 同质快路径：数学上恒为 C/n，
        return [capacity / n] * n            # 单独分支保证与 ps_share 逐位一致（§3）
    total = sum(demands)
    if total <= capacity:                    # 供过于求：按需分 + 剩余均分
        bonus = (capacity - total) / n
        return [d + bonus for d in demands]
    alloc = [0.0] * n                        # 供不应求：升序一轮扫描即不动点
    cap = capacity
    for i in sorted(range(n), key=lambda i: demands[i]):
        share = cap / n
        alloc[i] = min(demands[i], share)
        cap -= alloc[i]
        n -= 1
    return alloc
```

性质（继承源设计 §3.3，单测覆盖）：不动点（无人超过自身需求除非全部满足）、N=1 得整个 C、均匀需求退化 C/N、确定性（排序无平局随机）。

### 4.3 动态容量与事件循环

流体推进结构不变，**切分点集合不变**：完成点、gate 开通点、bg 断点、submit 点（分配在相邻事件间恒定——需求集合与容量均不变，推进精确无近似）。`advance_to` / `_next_event_time` / `hypothetical_fetch_time` 三处的速率计算替换：

| | 现行（ps_share） | 新（max_min_fair） |
|---|---|---|
| 就绪集速率 | `rate = cap / len(ready)` | `allocs = waterfill(cap, [tr.demand for tr in ready])` |
| 最早完成 | `last_t + min(remaining)/rate` | `min_i(last_t + remaining_i / allocs[i])` |
| `hypothetical_fetch_time` | 克隆活跃集 + 插入项，逐步等分模拟 | 同结构，速率换 waterfill（用活跃传输**真值需求**）；签名增 `demand` 参数（缺省推导值），`sim/policies/oracle.py:12` 与 `sim/policies2.py:445`（`_hyp_fetch`）调用处透传 |

`cap ≤ 0`（背景负载吃满）的处理沿用现行：跳到下一个 bg 断点。

### 4.4 数值例子（本仓库默认参数）

v1 单池 C=100，两类并发：A 类（32k tokens，11.4 GB）需求 1.0×=52.4、C 类（8k tokens，2.7 GB）覆盖 0.25×=13.1。Σd=65.5 ≤ 100 → A 得 52.4+17.5=**69.9**，C 得 13.1+17.5=**28.6**（等分则为各 50：A 被 50 卡住消费节奏、C 拿了用不完的 50）。第三请求加入后 Σd=117.9 > 100 → 填充区迭代。串行链路下这意味着 C 类 fetch 从 2.7/50=54 ms 拖到 2.7/28.6=94 ms、A 类从 11.4/50=228 ms 提前到 163 ms——重排的零和性与工况依赖性正是 E28 的研究对象。

## 5. 配置接口

`StorageConfig` / `WorkloadConfig` 新增字段（全部带默认值，**老配置零改动**）：

```python
@dataclass(frozen=True)
class StorageConfig:
    b_total: float = 100.0
    t_base: float = 0.005
    bg_schedule: tuple = ((0.0, 0.0),)
    bw_policy: str = "max_min_fair"   # max_min_fair（新默认）| ps_share（旧等分，对照/回归用）

@dataclass(frozen=True)
class WorkloadConfig:
    ...
    demand_scale: float = 1.0         # 全局需求缩放（敏感性实验）
    cls_demand_scale: tuple = ()      # ((cls, scale), ...) 按类覆盖，制造异质需求
```

`Request` 新增 `demand_gbps: float = 0.0`（0 = 未设置，装配处填推导值）。

规则：

- `bw_policy` ∉ {"max_min_fair", "ps_share"} → 装配处 `ValueError`；
- **默认值切到 `max_min_fair` 是本次"替换"的落点**；由 §3 等价性，存量配置行为不变。如评审认为应保守，改回一行默认值即可，无其他牵连；
- `ps_share` 下出现 demand **忽略不报错**（同一份配置双策略对照，沿源设计 §5 惯例）；`max_min_fair` 下 `submit` 必须带正 demand（断言）；
- 需求表在装配处构建一次：`cls_demand_gbps(spec) -> {cls: d_ref × demand_scale × cls_scale}`，`build_request` 注入；
- `demand_scale` / `cls_demand_scale` 只改需求不改计算与字节口径（做需求敏感性时不动 `kv_gb_per_token` / `prefill_table`，与源设计"优先用 trace 覆盖而非改全局系数"同理）。

## 6. 信息边界影响

- **观测层零改动**（`StorageObservable` / `quote.AccessCostQuery`）：bw 信号 `share = cap/qdepth` 在均匀需求假设下与 waterfill **精确一致**（§3 同一数学事实），quote/util/queue 公式同构。异质需求下成为同质近似——偏差方向：过估低需求请求的份额、欠估高需求请求的；观测层看不到他者需求，这是合法信息约束而非实现缺陷。若 E28 显示该偏差影响策略排序，再立项 demand-aware 估计（超出本次范围，挂起）；
- **Oracle 精确重写**（§4.3），信息优势语义不变（仍唯一可访问真值需求与未来背景负载）；
- **既有策略无结构性影响**：`static_fetch_t`（nominal）、shadow 项（`nbytes/b_total` 服务时间近似）维持公式（本就是同质假设近似）；E26f 的 GuardedEDFBW / TFS 读 quote，公式未动，其结论在 §3 等价性下继续成立。

## 9. 实验设计：E28（新实验，实现后执行）

- 文件 `sim/experiments/e28_maxmin.py`，注册 `sim/run.py` CLI；可单实验冒烟（`--exp e28 --seeds 2 --duration 200`）。
- **研究问题**：需求异质时，max-min 相对等分在什么工况兑现收益、代价落在谁身上？
- 场景矩阵（CRN 同种子同 trace）：
  - a) v1 串行 fetch：`cls_demand_scale` 制造异质（如 C 类 0.25×、D 类 1.0×，扫 {同质, 2×, 4×} 档）× {ps_share, max_min_fair} × λ 扫描（争抢度轴）；
  - b) v2 partial（overlap）同上维度；
  - c) 同质基线（H3 的实证，sanity 而非新结论）。
- 指标：分类 TTFT P50/P95、SLO 满足率（总/分类）、fetch 链路时长分布、goodput；多种子取中位数。
- 假设：
  - **H1（串行重排）**：a) 中 max_min 使低需求类 TTFT 恶化、高需求类改善，总 SLO 变化方向取决于各类 SLO 余量分布——串行下带宽重排近零和（总字节守恒）；
  - **H2（overlap 兑现）**：b) 中低需求类不受损（其完成时间以重叠的计算为地板）、高需求类受益 → 总 SLO ↑。预期 max-min 的收益只在 overlap 工况兑现——与 E26 分诊区"mpc−local 差距只在分诊区兑现"的历史模式同构；
  - **H3**：同质下两策略一致（§3 实证）。
- 结果文档：仓库根 `实验结果-E28-YYYYMMDD.md`，图 `docs/figures/fig_e28_*.png`，结构按 AGENTS.md §6（元信息表 → 总判决 → 分实验表+图+读法 → 衔接 → 局限 → 通俗版）。

## 10. 范围排除与已知语义损失（如实记录）

1. **cq 线不替换**：`sim/cq`（E20–E27 精确搜索 / MPC / TFS）有独立的 `StorageSim`（FCFS 按申请上限分配），不共用 `SharedKVStorage`。如需对齐另立设计文档，本次不动。
2. **fabric 结构差异**：源设计是"盘内 waterfill + 全局链路比例压缩"（并联缩放）；本仓库 v2 是 tier→fabric **串行两跳**，各自独立 waterfill。串行下端到端"需求满足保证"不成立（类比源 §3.5 已知语义损失），且请求先占 tier 后占 fabric、两段速率可不同。保留本仓库串行模型（三级顺序是 v2 既定结构，`sim/engine2.py` 头注），改并联超出本次范围。
3. **串行 fetch 下 d 上限语义是建模选择**（§4.1），代价量化交给 E28-H1，不在本设计中隐藏。
4. **观测层同质近似偏差**（§6）：异质需求下 quote/bw 估计有偏，方向已记录，修复挂起。
5. **不引入 disks×paths 硬件拓扑与 `path_Bps`**：本仓库研究对象是调度/决策策略，v1 backend 池、v2 (node, tier) 池已是分配域抽象；引入盘/通道拓扑会改写全部既有实验语义且与 v2 节点层级抽象冲突。源设计的 Path 语义修订（放置只定 ASU、发 IO 时指派）在"无 Path 概念"的本仓库无从谈起，也就无需移植。
