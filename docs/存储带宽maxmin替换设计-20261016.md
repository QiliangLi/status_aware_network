## 1. 问题定义

现行 `SharedKVStorage`（`sim/storage.py:44`）把一个存储资源（v1 每 backend、v2 每 (node, tier) 与 fabric）建模为**单一带宽池**：速率规则为处理器等分（就绪传输按 `cap(t)/N` 均分），放置无盘维度——一次取回是池上的一个整体传输。两处与真实系统不符：

1. **放置**：真实系统的 KVCache 以**一致性哈希**分布在存储节点的各个盘上；一次取回的前缀 KV 散在多块盘上，逐块（IO 级）并发读取，完成由最慢盘决定。
2. **速率规则**：等分不考虑"请求要这么快没用"——消费端（GPU prefill）吸收 KV 的速率有上限，超出部分对该请求的端到端无边际收益（重叠工况下），却被等分规则照样分走，挤占了高需求请求；也无法表达需求异质的公平语义。

**物理与参数化锚点（三/四次修订）**：单个盘的上限带宽 **40 GB/s**（`disk_bps`，与源实现 `disk_Bps` 同值）是物理基元；**池总带宽 `b_total` 是主配置**（沿用现行所有实验口径——v1 默认 100、v2 fabric 120、E26/E27 存储 B=120 等），**盘数不是配置项，而是派生量**：

```
disks = max(1, ceil(b_total / disk_bps))     盘容量 = b_total / disks ≤ disk_bps
```

总带宽 120 GB/s 的存储资源派生 **3 块盘 × 40**；总 100 → 3 盘 × 33.3；总 60 → 2 盘 × 30；总 ≤ 40 → 1 盘。向上取整保证单盘带宽不超过 40 上限（四舍五入会在如 90→2×45 时超限，不采用）。

目标：替换为源设计的组合模型——**块经一致性哈希放置到池内各盘（盘数按上式派生），每盘独立做带需求上限的 max-min fair 水土填充，逐块 IO 为分配主体**。该策略在 dynamo 侧已定义、实现并验收；本设计做跨仓库移植与本仓库语义融合（动态背景负载、双世界信息边界、v2 串行取回链路）。

## 3. 新旧模型关系与存量基线策略

两策略的关系（`bw_policy` 配置项，二选一）：

- **`ps_share`（现行模型逐字保留）**：单池聚合 + 等分 + 无盘无块。不引入任何新语义——它是**旧口径的回归锚点与 A/B 对照臂**，复现全部既有结果；
- **`max_min_fair`（新默认，本次替换的落点）**：派生盘数 + 块放置 + 逐块 IO + 盘内 waterfill。对齐源实现语义，无中间形态（不设"多盘但聚合"的折中模式）。

**与旧行为的差异 = 替换本身**，来源有三（即使需求同质）：

1. **哈希倾斜长尾**：请求各盘块数 ~ 多项式分布，完成由最慢盘决定。量级（D=3、期望近似）：C 类 16 块最慢盘期望占比约 0.43（均值 0.33 的约 1.3 倍），D 类 128 块约 0.37（约 1.1 倍）——块数少的类受倾斜伤害更大；
2. **逐块公平语义**：均匀需求下，同盘上所有块 IO 的完成时间相等、**与请求大小无关**（每块 `块字节/单块速率`，两种容量情形皆然）；而现行 PS 的完成时间正比于字节数。小类不再"因为小而早完成"；
3. **速率规则**：异质需求下 waterfill 按需封顶（§4.3/§4.5）。

内部性质（单测用，非基线保证）：同质需求下盘内 waterfill 退化为逐块等分（数学事实：Σd ≤ C 时 `d+(C−Σd)/N = C/N`；Σd > C 时首轮无超额者）——用于 waterfill 向量断言与实现正确性检查。

**存量基线策略（如实记录）**：

- 已入库图与结论文档对应 `ps_share` 语义，**不重算、不覆盖**（AGENTS.md §7 图保护规则）；
- 默认切 `max_min_fair` 后，主线实验**重跑时数字会变**——这是替换的预期后果而非回归事故；后续新实验在新模型下出数；
- 需要旧口径复现或新旧对照时，显式配 `ps_share`；
- 实现提交时的回归协议：v1 四件套（e1a/e1b/e2/e3/e4）双臂跑——`ps_share` 臂应与既有结果一致（回归锚），`max_min_fair` 臂记录为新基线；
- 若评审认为默认应保守（`ps_share` 缺省、新模型 opt-in），改一行默认值即可，无其他牵连。

## 4. 策略形式化

### 4.1 需求 d 的定义与推导

沿用源设计 §3.1（逐层重叠的追赶节奏，聚合模型下层数相消）：

```
d = kv_gb_per_token / prefill_s_per_token
```

- `prefill_s_per_token = curve(REF) / REF`，REF 取 `prefill_table` 末点（默认 65536 tokens → 0.410 s → **6.256e-6 s/token**）；
- 默认参数下 `d_ref = 0.00032768 ÷ 6.256e-6 ≈ 52.4 GB/s`；
- REF 不取请求自身长度查表（那会让需求与请求类耦合），对齐源设计"同配置同值 + 覆盖字段制造异质"；
- **d 是逐 IO 属性**（源实现对每块 Read 携带 demand）：一个请求多块时每块各携 d，请求在某盘的聚合诉求 = 块数 × d。

**语义与建模选择的如实记录**：d 表示消费端吸收 KV 的速率，"超过 d 无边际收益"在**重叠工况**（v2 `partial`）下严格成立。本仓库 v1 `fetch` 与 v2 非 partial fetch 是**串行**（fetch 完才开始 prefill，`sim/worker.py:17-23`），此时超额分配仍缩短 TTFT——这是对齐源设计的建模选择，代价由 E28-H1 量化。逐 IO 粒度还带来"多块请求聚合诉求 ∝ 块数"的语义（单请求独占时其全部块吃满各盘容量，与源 §3.3 "N=1 分得整个 C" 的推广一致）。默认推导值 d_ref=52.4 可能**大于单盘容量**（如 v1 池 100 → 3 盘 × 33.3）——单请求独占一盘时逐块等分自然吃满盘容量、需求线不约束（与源 §7 "d > 盘容量允许、不预截断"同一处置）。

**信息边界**：d 由模型/负载配置推导、放置由 (池, cls, 块号) 确定函数给出——都不是存储内部状态（队列/带宽/背景负载/`hypothetical_*` 之外的新增可见量），所有策略合法可见，不违反铁律。

### 4.2 块放置与盘维度（二次修订引入；三/四次修订锚定参数化）

- **块定义**：`block_tokens` 个 token 的 KV（字节 = `block_tokens × kv_gb_per_token`），默认 512——对齐 Mooncake trace 的 512-token 块口径（§9 trace 维度可换 64）。类 T tokens → `n_b = ceil(T / block_tokens)` 块，末块部分字节；默认类目（8k/16k/32k/64k）均为 512 整倍。
- **盘数派生（四次修订核心）**：`disks = max(1, ceil(b_total / disk_bps))`，`disk_bps = 40 GB/s` 缺省。**没有 `disks` 配置项**——总带宽是配置，盘数是派生：120→3、100→3（33.3/盘）、80→2、60→2（30/盘）、40→1、≤40→1。对齐（整除）时单盘恰为 40；不对齐时单盘 = 总/盘数，向上取整保证 **单盘 ≤ 40 上限**。
- **放置规则（HRW / 最高随机权重一致性哈希）**：
  ```
  disk(pool, cls, idx) = argmax_{d ∈ [0, disks)} sha256(f"{pool}:{cls}:{idx}:{d}")
  ```
  - 确定性、无随机数 → CRN 不受影响；同输入同落点；
  - **一致性**：增删盘只重映射少数块（HRW 性质），与 `LocalKVCache` coord 模式的 crc32 偏好哈希（`sim/topology.py:31`）同族；
  - 哈希含池标识：同一类的不同副本（不同 node/tier）倾斜模式解耦；
  - 与源实现 `disk_of`（sha256 取 max）同一构造，仅键空间不同。
- **取回分解**：请求在 (node, tier) 池取回 T′ tokens（全量 fetch 为类 tokens，partial 为 `fetch_tokens`，**均取前缀块** 0..n_b′−1）→ 按放置聚成每盘 `(块数 K_d, 字节 b_d)` → 生成 `(请求, 盘)` 组。partial 的前缀块对齐保证不同副本服务的同一请求块集合一致。
- **IO 粒度与公平**：组内 K_d 块 = K_d 个独立 IO、各携需求 d，参与该盘 waterfill（与源实现 `submit` 逐块建 `Read` 语义一致）。同组块同尺寸、同时刻、同需求 → **同时完成**，事件数 ≈ 组数（实现按组存储、分配时按块数展开，语义等价于字面逐块对象，单测对拍）。
- **完成语义**：rid 在池上全部组完成（含最慢盘长尾）→ tier 侧完成 → fabric **聚合**传输（单 claim、demand d、无盘维度——网络链路不是盘）。不做逐块流水（块级流式穿越 fabric 超出本次范围，见 §10.6）。
- **盘容量**：`cap_d(t) = b_total/disks − bg(t)/disks`（= `(b_total − bg(t))/disks`，背景负载是池级聚合量，平摊到各盘）。

### 4.3 waterfill 算法（照搬 dynamo 已实现版本）

模块级纯函数，放 `sim/storage.py`：

```python
def waterfill(capacity: float, demands: list[float]) -> list[float]:
    """带需求上限的 max-min fair 分配，迭代到不动点；O(n log n)。"""
    n = len(demands)
    if n == 0:
        return []
    total = sum(demands)
    if total <= capacity:                    # 供过于求：按需分 + 剩余均分
        bonus = (capacity - total) / n
        return [d + bonus for d in demands]
    alloc = [0.0] * n                        # 供不应求：升序一轮扫描即不动点
    cap = capacity
    for i in sorted(range(n), key=lambda i: demands[i]):
        share = cap / n
        alloc[i] = min(demands[i], share)
        cap -= alloc[i]
        n -= 1
    return alloc
```

性质（继承源设计 §3.3，单测覆盖）：不动点、单 IO 得整个盘容量、均匀需求退化 `cap/N`、确定性。（均匀需求两情形皆退化 `cap/N` 的证明见 §3 内部性质。）

### 4.4 动态容量与事件循环

流体推进结构不变，**切分点集合不变**：完成点、gate 开通点、bg 断点、submit 点（相邻事件间各盘的需求集合与容量恒定，分配恒定，推进精确无近似）。变化：

| | 现行（ps_share 单池） | 新（max_min_fair 逐盘） |
|---|---|---|
| 分配单元 | 池上就绪传输集合 | 每盘就绪块 IO 集合（按组展开） |
| 速率 | `rate = cap / len(ready)` | `allocs = waterfill(cap_d(t), [d × 组展开])` |
| 最早完成 | `last_t + min(remaining)/rate` | 每盘 `min_i(last_t + remaining_i/allocs_i)`，全局取 min |
| `hypothetical_fetch_time` | 克隆活跃集 + 插入项，逐步等分模拟 | 同结构，按盘模拟 waterfill（用真值需求与放置）；签名增 `demand`、`plan` 参数，`sim/policies/oracle.py:12` 与 `sim/policies2.py:445` 透传 |

`cap ≤ 0`（背景负载吃满）沿用现行：跳到下一个 bg 断点（对每盘等价，因平摊）。

### 4.5 数值例子

**速率规则差异（单盘内）**：两类块 IO 并发于同一盘（容量 33.3，v1 池 100 派生 3 盘）：A 类需求 1.0×=52.4、C 类覆盖 0.25×=13.1。Σd=65.5 > 33.3 → 填充区：均分 16.7 < 52.4、> 13.1 → C 类块定格 13.1，剩余 20.2 给 A 类块 = **[13.1, 20.2]**（等分则各 16.7：A 被卡住消费节奏、C 拿了用不完的 16.7）。总带宽 120 的池（3×40）同理放大。

**盘维度差异（v1 池 100 → 3 盘 × 33.3）**：A 类（64 块）与 C 类（16 块）同池，哈希后 A 每盘约 21 块、C 每盘约 5 块（有倾斜）。逐块公平下同盘块 IO 同时完成：C 类不再因小而早完成；C 类的完成还受自身最慢盘拖累（16 块 D=3 时期望最慢盘约 7 块，均值 5.3）。

**默认争抢度 sanity**：v1 池 100（3 盘）→ λ_hit≈3.5/s × 11.14 GB ≈ 39 GB/s offered，中等争抢，E28 用 λ 扫描抬升；v2 默认节点（mem 60→2 盘 / 40→1 盘、ssd 25/15→1 盘）派生盘数自动生效；fabric 120 聚合无盘。逐块需求 d=52.4 大于多数单盘容量：单请求独占盘时吃满盘，需求线不约束（§4.1）。

## 5. 配置接口

`StorageConfig` / `WorkloadConfig` 新增字段（全部带默认值，**老配置零改动**）：

```python
@dataclass(frozen=True)
class StorageConfig:
    b_total: float = 100.0        # 池总带宽（主配置；现行口径不变）
    t_base: float = 0.005
    bg_schedule: tuple = ((0.0, 0.0),)
    bw_policy: str = "max_min_fair"   # max_min_fair（新默认）| ps_share（旧模型，回归锚/对照臂）
    disk_bps: float = 40.0            # 单盘上限带宽（物理基元，源实现 disk_Bps 同值）
    block_tokens: int = 512           # 块粒度（token 数），放置与分解用

    @property
    def disks(self) -> int:           # 盘数是派生量，不是配置项（四次修订）
        return max(1, math.ceil(self.b_total / self.disk_bps))

@dataclass(frozen=True)
class WorkloadConfig:
    ...
    demand_scale: float = 1.0         # 全局需求缩放（敏感性实验）
    cls_demand_scale: tuple = ()      # ((cls, scale), ...) 按类覆盖，制造异质需求
```

`Request` 新增 `demand_gbps: float = 0.0`（0 = 未设置，装配处填推导值）。

规则：

- `bw_policy` ∉ {"max_min_fair", "ps_share"}、`disk_bps` ≤ 0、`block_tokens` ≤ 0 → 装配处 `ValueError`；
- **盘数一律派生**（`ceil(b_total/disk_bps)`），无对齐校验、无报错分支——任何 `b_total` 都合法；单盘带宽 = `b_total/disks ≤ disk_bps`（向上取整保证）；
- **默认 `max_min_fair` 是"替换"的落点，代价是主线重跑数字会变**（§3 存量基线策略，含保守替代方案）；`ps_share` 语义固定为现行单池聚合等分（无盘无块），用于旧口径复现与 A/B；
- fabric 池无盘维度（网络链路，聚合单 claim 参与 waterfill）；盘分解只用于存储资源池（v1 backend 池、v2 (node,tier) 池）；
- `max_min_fair` 下存储池 submit 必须携带块计划（防静默聚合退化，见 §7 接口）；`ps_share` 下 demand / disk_bps / block_tokens **忽略不报错**（同一份配置双策略对照，沿源设计 §5 惯例）；
- 需求表在装配处构建一次：`cls_demand_gbps(spec) -> {cls: d_ref × demand_scale × cls_scale}`，`build_request` 注入；
- `demand_scale` / `cls_demand_scale` 只改需求不改计算与字节口径（做需求敏感性不动 `kv_gb_per_token` / `prefill_table`，与源设计"优先用覆盖而非改全局系数"同理）；
- 做盘拓扑敏感性时调 `disk_bps`（如 b_total=120 下 `disk_bps` ∈ {120, 60, 40} → 1/2/3 盘，总带宽不动）——这是总带宽固定下改变盘数的合法途径（E28 归因用，§9）。

## 6. 信息边界影响

- **观测层零改动**（`StorageObservable` / `quote.AccessCostQuery`）：bw 信号 `share = cap/qdepth` 在均匀需求假设下与盘内 waterfill 的逐块等分一致（§3 内部性质），quote/util/queue 公式同构。异质需求下成为同质近似——偏差方向：过估低需求请求、欠估高需求请求；多盘下 qdepth 语义变为池上活跃 `(请求,盘)` 组数（ps_share 下即请求数，不变）。观测层看不到他者需求与各盘倾斜，这是合法信息约束而非缺陷。若 E28 显示偏差影响策略排序，再立项 demand-/placement-aware 估计（超出本次范围，挂起）；
- **Oracle 精确重写**（§4.4），信息优势语义不变（仍唯一可访问真值需求、真值放置下的盘内竞争与未来背景负载）；
- **既有策略无结构性影响**：`static_fetch_t`（nominal）、shadow 项（`nbytes/b_total`）维持公式；E26f 的 GuardedEDFBW / TFS 读 quote，公式未动——其结论属 `ps_share` 口径（§3），新模型下的表现由 E28 重新评估。

## 9. 实验设计：E28（新实验，实现后执行）

- 文件 `sim/experiments/e28_maxmin.py`，注册 `sim/run.py` CLI；可单实验冒烟（`--exp e28 --seeds 2 --duration 200`）。
- **研究问题**：需求异质与盘维度放置下，max-min 相对等分在什么工况兑现收益、代价落在谁身上？
- 场景矩阵（CRN 同种子同 trace）：
  - a) v1 串行 fetch：`cls_demand_scale` 异质（如 C 类 0.25×、D 类 1.0×，扫 {同质, 2×, 4×}）× {ps_share, max_min_fair} × λ 扫描（争抢度轴）；
  - b) v2 partial（overlap）同上维度；
  - c) **盘拓扑轴（归因用，总带宽固定）**：`b_total=120` 下 `disk_bps` ∈ {120, 40} → 1 盘 / 3 盘（盘数是派生量，总带宽固定下经 `disk_bps` 改变盘数，§5）——隔离放置/长尾效应与速率规则效应；
  - d) **块粒度轴**：`block_tokens` ∈ {512, 64}（放置粒度，对齐 Mooncake/AgentX 两套块口径）。
- 指标：分类 TTFT P50/P95、SLO 满足率（总/分类）、fetch 链路时长分布（含最慢盘占比）、goodput；多种子取中位数。
- 假设：
  - **H1（串行重排）**：a) 中 max_min 使低需求类 TTFT 恶化、高需求类改善，总 SLO 方向取决于各类 SLO 余量——串行下带宽重排近零和（总字节守恒）；
  - **H2（overlap 兑现）**：b) 中低需求类不受损（完成以重叠计算为地板）、高需求类受益 → 总 SLO ↑。预期收益只在 overlap 工况兑现——与 E26 分诊区"差距只在分诊区兑现"的历史模式同构；
  - **H3（盘拓扑独立效应）**：c) 中同总带宽下 3 盘相对 1 盘改变分类 TTFT 分布——小类受最慢盘长尾拖累、逐块公平拉平同盘完成时间；该效应与速率规则正交；
  - **H4（块粒度）**：d) 中小块（64）加剧逐块公平的拉平效应并降低单请求倾斜方差（块多更均匀），对大类有利、对小类的长尾略有缓解。

## 10. 范围排除与已知语义损失（如实记录）

1. **cq 线不替换**：`sim/cq`（E20–E27 精确搜索 / MPC / TFS）有独立的 `StorageSim`（FCFS 按申请上限分配，其 B=120 GB/s 即本设计派生 3 盘的同一口径），不共用 `SharedKVStorage`。如需对齐另立设计文档，本次不动。
2. **fabric 结构差异**：源设计是"盘内 waterfill + 全局链路比例压缩"（并联缩放）；本仓库 v2 是 tier→fabric **串行两跳**，fabric 为聚合池（无盘维度）。串行下端到端"需求满足保证"不成立（类比源 §3.5 已知语义损失），且请求先占 tier 后占 fabric、两段速率可不同。保留本仓库串行模型（三级顺序是 v2 既定结构，`sim/engine2.py` 头注），改并联超出本次范围。
3. **块级流式穿越 fabric 不做**：tier 各盘组完成时间不同，理想流式应让先完成的块提前进 fabric；本设计保持"tier 全部完成 → fabric 聚合传输"的现行串行结构（§4.2），长尾盘因此串联延迟而非流水掩盖——保守方向，记为已知损失。
4. **串行 fetch 下 d 上限语义是建模选择**（§4.1），代价量化交给 E28-H1。
5. **观测层同质近似偏差**（§6）：异质需求与多盘倾斜下 quote/bw 估计有偏，方向已记录，修复挂起。
6. **不引入 Path 通道层**：`paths_per_disk`/`path_Bps`/选路策略（源设计 P0/P1 挂载点）与本仓库研究对象（调度/决策策略）无关；无排队语义本仓库天然满足。
7. **无 `disks` 配置项、无聚合折中模式**（四次修订）：盘数只经 `b_total`/`disk_bps` 派生；需要"总带宽固定下改变盘数"时调 `disk_bps`（§5）。不设"多盘但请求聚合"的中间形态——那是旧行为，由 `ps_share` 臂承担。
