## 1. 问题定义

MPC(推演式)在 E26 系列持续胜出,但代价是每格点 1~1.9h 墙钟(E26f 实测,MPC_PAR=6 后)与决策点的推演引擎依赖;FCFS/EDF 秒级但收益差 30~45pp。问题:**MPC 的收益有多少来自可以被显式规则表达的结构,多少来自推演本身的"看远"?** 若前者占主导,则可得到一个在线可部署(无推演、O(n log n)/决策)的调度器,并反过来检验我们对收益机理的理解是否完备——规则版失灵之处,就是推演不可替代之处。

## 2. 收益场景与规律(证据链)

### 2.1 收益在哪里出现(场景)

| 场景 | MPC 收益(代表数字) | 出处 |
|---|---|---|
| S1 带宽分诊区:重流聚合需求>B、d 异构 | mpcS−FCFS 总 SLO +32.2pp(D1fA,3 seed 中位) | E26f §4 |
| S2 簇到达:同刻 k 条紧期限重流 | E26e k16:mpcS 60.0 vs FCFS 48.8;mpc 簇发 ≤5/簇 vs FCFS 峰 16 | E26e 终态 |
| S3 零读/轻类存在 | C-SLO:mpcS 100% vs FCFS 30%(D1fA)/43%(D1fB) | E26f §2 |
| S4 计算饱和(轻度) | mpcS−FCFS **不收窄反扩大**:+44.7pp(D1fB)>+32.2pp(D1fA);FCFS 连宽期限 B 都排队死(B 40%) | E26f §4 |
| 反面:连续平缓工况 | D1 连续工况下规则式 CPA 落败、收益消失 | E27;E26c |

### 2.2 规律(每条注出处;TFS 规则的直接依据)

- **L1 d-分诊律**:调度的有效分诊变量是 **d=V/c**(每层读取/每层计算,全公开),不是类别标签也不是纯 deadline;带宽约束只对重流(d≥d_heavy=P75)计费,轻流不计(20260929 朴素 ΣV/c 试点证伪→修正为只对重流计费)。
- **L2 填空律**:零读/轻类的死亡**纯由排队时间驱动**(其服务不占带宽、占 worker 短);有空闲 worker 即派,理论存活率 100%(E26f:mpcS 全 seed C=100%;FCFS C=30%,死于 FIFO 排队)。
- **L3 错峰律**:同刻 k 条重流齐派→瞬时超订→全体 IO 等拉长→紧期限类成批死亡;重流派发应对齐**配额释放节奏**(下一重批完成时刻),而非到达节奏(E26e mpc ≤5/簇≈配额 C=4;E26f cA mpcS 需求超订 75%<实际饱和 86%=压平扎堆申请)。
- **L4 守门律**:单维排序必崩——纯期限序饿死宽期限类(E26f cA:EDF 的 B 仅 28%),纯 FCFS 在计算饱和下把宽期限类排队死(cB:B 40%);紧期限洪峰需**并发上限**,宽期限类需**老化保底**(GuardedEDF 锚点先例)。
- **L5 瓶颈自适应律**:计算饱和下"留白等带宽"仍划算——守门防的是后续排队死,而非带宽本身(E26f cB makespan 2.16s<FCFS 2.73s;带宽不紧张时配额自然不 binding,bw_sat cB 73%)。
- **L6 保守账本律**:对带宽的**乐观外推**(local 独立评分)在洪峰期诱发过度派发,反把填空类挤死(local C 中位 84%、rep2 53% vs mpc 100%);保守计数(在跑重批账本)永不乐观。MPC 对 base 的有效偏离极少且集中:E26f cA mpcS dev 仅 8~22/1348~1954 决策(<2%),全部落在簇洪峰时刻。
- **L7 代价律**:上述规律全部可用公开快照的 O(n log n) 规则表达;MPC 的 1~1.9h/格点 换来的正是这 <2% 偏离的搜索。

### 2.3 外部先例(定位,非依据)

- [Sarathi-Serve(OSDI'24)](https://www.usenix.org/conference/osdi24/presentation/agrawal) 的 chunked-prefill+stall-free:把重计算拆片与轻工作交错避免互相停顿——与 TFS"重流错峰+轻流填空"同思想家族,但资源维度不同(他们拆计算保 decode,我们拆带宽保紧期限类);[SARATHI(arXiv:2308.16369)](https://arxiv.org/abs/2308.16369)。
- [Cerebrium token-load-aware routing](https://cerebrium.ai/resources/token-load-aware-routing-llm-serving)(队列深度感知路由)与 [Databricks 推理性能工程](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices)(内存带宽是比峰值算力更好的速度预测子)为相邻证据。
- "d 分类 + 带宽并发准入"这一具体组合**未见公开先例**(2026-10-14 检索;待核实——后续调研补)。

## 3. 算法设计:TFS(Triage-Fill-Stagger),pid `cq_tfs`

### 3.1 设计原则

零推演:不建 forecast 世界、不评分候选、不做带宽外推;每决策点只读公开快照(`StorageObservable`/`quote.AccessCostQuery` 同边界,GPU 侧沿用 v1 既定真值可见简化),复杂度 O(n log n)(排序)。结构上**包含 GuardedEDFBW 的骨架**(quota/wake/重流计费口径原样复用 `bw_demand`),差异集中在洪峰时刻的仲裁序——恰好是 mpcS 偏离的集中点(L6/L7)。

### 3.2 规则表(与 §2.2 律的对应)

每决策点,对每个空闲 worker 依次尝试,直到派满或无:

| 序 | 规则 | 依据 |
|---|---|---|
| R0 分诊 | `bw_demand` 口径:d_i=V_i/c_i(公开画像公式浮点重算)、d_heavy=hist P75、C=⌊b_ref/d_heavy⌋、heavy_run=在跑重批数(账本) | L1 |
| R1 填空 | 轻/零流(d<d_heavy)恒可派;**worker 稀缺时**(等待的轻/零流数 > 空闲 worker 数)轻流按 **slack_i=deadline_i−now−T0_i 升序**(短服务紧期限先完成),非稀缺时按 deadline 序(此时两序等价——派得完) | L2 |
| R2 守门 | 重流仅当 heavy_run<C;重流内部按 **(slack, deadline)** 序(宽 slack 让位) | L4 |
| R3 锚点让位 | 老化锚点豁免配额**仅当无等待中的轻/零流**(防饿死不牺牲填空——base 的无条件豁免在 E26f 造成簇发峰 16) | L2+L4 |
| R4 错峰 | 配额满时该 worker WAIT 至配额释放时刻(`bw_demand` 的 wake 口径:最早重批完成/最早流完成) | L3+L6 |

参数:无新增自由度(d_heavy/C/wake 沿用 base 口径);slack 用公开 T0。

### 3.3 伪码

```python
class TFS(SimplePolicy):                      # pid "cq_tfs"
    def decide(self, snap, scn):
        d, d_heavy, C, heavy_run, wake = bw_demand(snap, self._hist)
        slack = {r.rid: float(r.deadline_s) - float(snap.now) - float(r.T0_s)
                 for r in snap.requests if r.rid in snap.queued}
        light = sorted((r for r in snap.requests if r.rid in snap.queued
                        and d[r.rid] < d_heavy),
                       key=lambda r: (slack[r.rid], r.deadline_s, r.rid))
        heavy = sorted((r for r in snap.requests if r.rid in snap.queued
                        and d[r.rid] >= d_heavy),
                       key=lambda r: (slack[r.rid], r.deadline_s, r.rid))
        anchors = self._aged_anchors(snap, scn)
        scarce = len(light) > len(snap.idle_workers)     # R1 稀缺判定
        acts, used, acc = [], set(), heavy_run
        for wid in sorted(snap.idle_workers):
            pick = None
            if scarce and light:                          # R1:slack 序填空
                pick = next((r.rid for r in light if r.rid not in used), None)
            if pick is None:                              # R2:重流守门
                for r in heavy:
                    if r.rid in used or acc >= C:
                        break if acc >= C else None       # 见下——重流可派则取
                    pick = r.rid; break
            if pick is None and not light:                # R3:锚点让位后豁免
                for a in anchors:
                    if a in snap.queued and a not in used:
                        pick = a; break
            if pick is None:                              # R4:错峰 WAIT
                acts.append(Action("WAIT", wid, (), wake)); continue
            acts.append(Action("DISPATCH", wid, (pick,)))
            used.add(pick)
            if d[pick] >= d_heavy:
                acc += 1
        return JointAction(tuple(acts))
```

(实现时重流段写清楚:按序取第一个未用的且 acc<C 的重流;伪码行文从简。)

### 3.4 与既有策略的关系

| | FCFS/EDF | GuardedEDFBW(base) | **TFS** | local/mpc |
|---|---|---|---|---|
| 仲裁 | 到达序/期限序 | 期限序 | **slack 序+稀缺切换** | 推演评分 |
| 重流约束 | 无 | 配额 C | 配额 C | base 配额+搜索偏离 |
| 填空类保护 | 无 | 轻流恒可派 | 轻流恒可派+**稀缺 slack 序** | 同左+推演修正 |
| 老化豁免 | — | 无条件 | **让位于填空类** | 同 base |
| 带宽预测 | 无 | 无(账本) | 无(账本) | 有(推演/独立评分) |
| 决策成本 | O(n log n) | O(n log n) | O(n log n) | 1~1.9h/格点 |

## 4. 实验设计(E26g)

### 4.1 臂(6)与格点(3)

臂:`fcfs / edf / base(cq_bwedf=GuardedEDFBW 单独成臂) / tfs(cq_tfs) / localS_v2.1 / mpcS_v2.1`。base 单独成臂以分解"底座贡献(base−fcfs)"与"规则增量(tfs−base)"。

格点(全为已有工况,负载零新自由度,CRN 同 seed 复用):
- **D1c_k16**(E26e,双类无 C,seed=408):纯错峰收益环境;
- **D1fA_k16**(E26f,三类存储瓶颈,seed=416):错峰+填空;
- **D1fB_k16**(E26f,三类计算瓶颈,seed=424):守门+瓶颈自适应。

矩阵 3×6=18 runs;mpcS 三格点已有结果可直接复用(E26e k16/E26f 两格点,同 seed 同负载——**须核对 records 字段口径一致后引用,不重跑**);实际新跑 ≈3 格点 × 5 臂 = 15 runs,其中 MPC 类仅 localS×3(tfs/base 秒级)。

### 4.2 预注册假设

- **H1(主)**:三格点上 `tfs 总SLO ≥ fcfs + 0.8×(mpcS−fcfs)`(捕获 MPC 收益 ≥80%)。
- **H2(填空律)**:D1f 两格点 tfs 的 C-SLO=100%。
- **H3(代价)**:tfs 单 run wall_s < 10×fcfs(预期同数量级)。
- **H4(规则增量)**:tfs−base ≥ 0 于三格点(允许打平——若 <0 说明某规则在该工况有害,消融定位)。
- **H5(消融,若 H1 未达)**:去 slack 序 / 去锚点让位二臂定位失灵规则;若全消融后仍差 >20% 收益,结论转为"推演不可替代部分主要由 X 构成"。
- 备用:若 H1 在 D1fB 失败而 D1c/D1fA 达标,按 §2.2-L5 检查 compute-guard 变体(带宽未饱和时配额放宽)——作为新自由度须单独预注册说明。

## 5. 局限

- 规律蒸馏自 E26 系(单带宽资源、batch=1、GPU 真值可见的 v1 简化);对批调度(n_max>1)、多 backend、GPU 侧观测受限工况的泛化未验证。
- slack=T0 感知仲裁与既有 `cq_slack` 的关系未对照(TFS 的 slack 仅在重流配额与稀缺轻流内生效,语义不同;对照属可选补臂)。
- H1 的 80% 阈值是工程意义约定(非理论推导);若实测落在 60~80%,结论表述为"规则捕获大部分但非全部",须列出差额来源分析。
- mpcS 结果跨实验复用须核对 records 字段一致性;D1c_k16 的 E26e 记录无 C 字段(双类工况,tfs 同口径)。
- E27 的教训(连续工况规则落败)意味着 TFS 的适用域=分诊区;在线部署的负载监测(何时在分诊区)是 TFS 之外的系统问题,本文不解决。
