①系统与画像：看懂例子需要的四个事实2 分钟

1.1 一个请求 = 已缓存前缀 h + 新算部分 u，逐层"先读后算"

每个请求到达时带着两个数：h 个 token 的 KV 已在存储里（可复用），还要新算 u 个 token。 计算是逐层的：第 ℓ 层先读齐本层所有 KV Block，才能开始算；算本层的同时提交下一层的读取（只提前一层 lookahead）。 末层算完 = 首 token 返回（TTFT 的终点）。读不齐就得停 —— 这个状态叫 STALL。

式(11)·层依赖 Cβℓ = max(Rβℓ, Zβ,ℓ−1, Eβℓ) ，  Zβℓ = Cβℓ + cβℓ   R=本层读齐时刻  Z=本层算完  c=本层纯计算时长  E=写缓冲可预留时刻

本页的例子都取 L=1 层（单层就够讲清机制），此时公式坍缩成一句话：首 token = 读齐时刻 + 计算时长。

1.2 四类请求：分类只看 h 和 u 是否过线

分类 χi = ( 1[hi > 80000], 1[ui > 512] ) ，  0 记 S、1 记 L，第一维=命中、第二维=未命中

阈值：h=80000（等号属 S）、u=512（等号属 S）。拖到 80000 两侧看类别翻转。

SS 短命中 · 短未命中
χ = (1[40000>80000], 1[128>512]) = (0,0) → SS
每层读 ≈ κ·h = 4.096e-6 × 40000 = 0.164 GB  |  每层写 ≈ κ·u = 0.0005 GB

κ=4.096×10⁻⁶ GB/token/层（synthetic-v1 起点值）。读写是分开的两个量：LS 读多写少，SL 读少写多。

SS（h≤80K, u≤512）
新 token 少；但 h 逼近 80K 时仍有大读取——别把 SS 当零成本
LS（h>80K, u≤512）
典型"读多算少"：κℓh 的读取主导，attention 随 h 增长
SL（h≤80K, u>512）
典型"算多写多"：新 KV 写回与新计算都重
LL（h>80K, u>512）
读、attention、写回三头都重
混合批不改成员类别。一个批里 SS 成员的 I/O 永远走 SS 组、LL 成员走 LL 组——不能按"批里最长者"把所有人升成 LL，也不能让短成员替长成员占 SS 份额。

中央等待队列 + 调度器（S 层）组批、选空闲实例、决定启动时刻（可有限延迟=错峰）。请求一直留在中央队列，领取时才绑定实例。
▼ 领取：批成员 + 启动时刻   ▲ 盘负载观测（版本化）
NPU 实例 × m（P 层）同构实例，每实例同时只有一个完整 prefill 批；为已释放的 I/O 在目标盘、本类别组内选一条 Path。
▼ Block I/O 按 (盘, 类别组, Path) 入队   ▲ 选路报价与版本

组基础带宽 20/12/4/4 GB/s（SS/LS/SL/LL），来自配置而非硬件差别；每条 Path 的基础速率 r 分别为 5/24、1/8、1/8、1/8 GB/s。同实例末层算完才出首 token；新算出的 KV 还要写回存储，与读取竞争同一个 40 GB/s。
→系统就绪。接下来把现有默认规则摆上台面——B0 带宽规则里藏着一个可疑的等式：权利居然跟着"开了几条 Path"走。

→份额会随 Path 数漂移，是第一处可疑。第二处在 NPU 每次提交 I/O 的那个动作上：选哪条 Path。

7.1 控制闭环：中央不碰队列细节，存储不改批成员

中央调度器 · S 层（S0→S1）
组批、领取顺序、启动时刻（立即 / 关键事件后 / 有限 δ 延迟=错峰）。候选批含 singleton、同类批、读算互补、盘负载互补、含最老请求批；对同时空闲的实例做互不重叠的联合选择。
决策时机：实例空闲 / 关键 I/O 完成 / 有限周期
▼ 下发：批成员 + 启动时刻（原子领取，版本校验）
▲ 上报：DiskGroupObservation——各盘各组服务量、活跃数、估计容量、版本
NPU 数据面 · P 层（P0→P1）
为每个已释放 I/O 在目标盘、本类别组内选 Path：P1 先用式(17) 筛 2–4 条，再在估计状态中重放入队到完成；配合版本号与客户端账本防惊群。
决策时机：每个 I/O 提交时
▼ 下发：Block I/O → (盘, 组, Path) 入队，FIFO 不许加塞
▲ 上报：PathObservation——未完成数、剩余字节、速率区间
ASU 存储 · B 层（B0→B1）
快速工作守恒分配：队头完成/新入队立刻回收空闲容量；B1 按式(18) 组保底+权重水位，组内再按请求权重水位分到各队头。每 Path 队头串行、FIFO，不可抢占。
决策时机：队头变化即时 / 组权重 ~5ms 更新
▼ 需求反馈：ServiceHint——每个请求的消费时刻（下一层预计开算时间）、最终 deadline、权重。它是"需求信号"不是硬资源预留。
共同信息边界
三层共享请求 ID、类别、层消费时刻、deadline、配置版本。普通策略只见导出观测（版本化、带交付延迟），拿不到存储内部真值队列；Oracle 基线另设。对每个候选动作，在"估计状态"里重放到窗口结束、统一排空，按四目标打分——CPU 与通信开销计入真实时间。

J_T = Σ(Fi−ai)/n
平均 TTFT
J_R = Σ(Fi−ai)/Ti⁰/n
平均归一化 TTFT（T⁰=同拓扑独占重放的基线）

④ 的表格正好给出这四个目标在同一例子上的取值——B 在 J_S/J_T/J_R 全胜且 J_M 不劣；C 只赢 STALL 卡秒（不在这四个目标里）。不同目标可能选出不同方案，所以每次实验只优化一个 J。

诚实边界。这套设计尚未实现，也未取得实验增益：所有带宽/时间数字都是解析算例；单 Path 独占 40 GB/s 是理想化模型，首轮必须硬件标定；优化不能把热盘数据改读到冷盘；"多开 Path / 更大批 / 更高利用率"都不是应强行通过的单调性断言。Go/no-go 预注册：至少两个未参与调参的独立场景中，相对最强同能力简单基线净改善 ≥5%（时延）或 ≥5 个百分点（SLO），配对 95% 区间不跨零。

⑨通俗版：仓库、窗口与加工台一图流类比

  • 每个 ASU 是一座总出货速度 40 的仓库，里面 256 个取货窗口（Path），每个窗口各排一条队。货放在哪座仓库由货号（hashID）决定，不能因为旁边仓库清闲就去那里取同一件货。
  • B0 的问题是：多开窗口 = 多分余量。订单量没变，只是一类订单多开了几个窗口，另一类就被挤慢——并发数偷走了业务优先级（②）。
  • "队伍人数少"不一定快：前面一个人搬四吨，可能比四个人各搬一小箱等更久。选窗口要看前面剩多少货（③）。
  • 中央调度器是安排加工台领料的人：决定哪些订单一起加工、何时来取料。有时先让小订单取完、大订单晚 0.025 秒开始取，小订单就按时交付而大订单一分钟都没多等（④）。但仓库不挤时，故意等待只有成本。
  • 两座仓库总出货够 ≠ 每座都够：8 吨货全压在一座，总量再宽也要排队（⑤）。
  • B1 给每类订单保底速度 + 按需借余量，跟你开了几个窗口无关（⑥）。
  • 新做出的 KV 还要送回仓库：回货区（写暂存池）满了同样堵加工台——只优化取货是不够的。
  • 最终裁判是订单完成时间与按时交付率，不是窗口开得多、设备看起来忙。
