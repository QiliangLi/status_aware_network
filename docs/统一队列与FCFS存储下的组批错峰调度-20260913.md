# 统一队列与 FCFS 存储下的组批错峰调度

| 项目 | 定义 |
|---|---|
| 研究问题 | 如何选择 batch 的成员、大小与启动时刻，使多个推理实例更好地共享存储带宽 |
| 请求队列 | 调度器维护统一队列，实例没有待执行请求队列 |
| 执行方式 | 空闲实例领取一批，执行完后再领取下一批 |
| KV 读取 | 全局可见、命中即从共享存储读取，排队时不预取，执行时逐层加载 |
| 存储服务 | 按读取提交顺序先满足申请速率，剩余带宽继续分给后续读取 |
| 优化目标 | 分别最小化全部完成时间、最大化 SLO 满足率、最小化平均及归一化 TTFT |
| 解释指标 | 全局 NPU Compute、STALL、Idle 与存储带宽利用率 |
| 文档性质 | 独立的问题分析、形式化模型、复杂度论证及算法设计；算例不代表实测性能 |
| 单位 | 秒、十进制 GB、GB/s |

## 1. 问题边界与系统架构

**调度器通过决定“哪些请求一起执行、何时交给空闲实例”，改变各层读取进入 FCFS 存储服务的顺序与速率需求。** 存储分配规则固定以后，全局优化集中到 batch 的形成和启动节奏。

```text
请求到达 → 调度器统一队列
                 ↓ 空闲实例领取一个 batch
          读取第一层 KV → 计算第一层
                 ↓ 当前层计算与下一层读取重叠
          完成本批 prefill，产生首 token
                 ↓ 实例再次请求领取 batch

各实例已提交的逐层读取 → 同一个 FCFS 按需分配器 → 共享存储带宽
```

统一队列可以重排候选请求。存储 FCFS 约束的是读取的提交顺序，并不要求调度器按请求到达顺序组批。调度器可以暂缓满足某个空闲实例的领取请求，期间请求继续留在统一队列，没有被预先派发，也没有开始加载。

### 1.1 所有比较共同遵守的假设

| 约束 | 本文采用的设定 |
|---|---|
| 模型与资源 | 固定模型、固定实例数与每实例 prefill 资源份额；主模型采用同构实例 |
| KV 可见性 | 所有实例查询同一全局目录，不依赖跨请求的 worker 本地缓存优势 |
| KV 放置与选源 | 单副本或共同固定选源规则，不优化复制、选副本和缓存迁移 |
| 读取与计算 | 命中的前缀从存储加载，计算尚未覆盖的后缀，不主动用重算替代读取 |
| 执行前 | 统一队列只保留请求和元数据，不发起该请求的 KV 数据读取 |
| 活动批 | 每实例同时执行一个完整 prefill 批，完成后再领下一批；活动批不迁移、不重排成员 |
| 层间流水 | 计算第 $\ell$ 层时最多提前加载第 $\ell+1$ 层，不加载下一批 |
| 有限容量 | 所有策略共用容量检查和最大批预算；需要保留的 KV 不能因当前层算完就假设立即释放 |
| 请求服务 | 主实验不拒绝、不丢弃请求，过期请求仍须执行；共同的老化或最长等待规则另行明确 |
| 信息边界 | 在线调度只用已到达请求、计算画像和存储可观测反馈；未来 trace 与存储内部真值只用于离线或 Oracle 对照 |

这里的“一个完整 prefill 批”明确规定本层读取齐备才启动本层批计算，成员在最后一层完成后一起产出首 token。这是基础执行模型。chunked prefill 会改变重新组批和 KV 保留边界，应作为独立扩展，不能混入基础组批比较。

分析到首 token 为止，吞吐均称为 prefill 请求吞吐。decode 的影响只可作为各策略共同的固定资源预算，不模拟逐 token decode 或其 KV 生命周期。按层等待本层 KV、触发下一层加载可参考 Mooncake 的 Layer-wise Prefill，但本文的统一队列、领取方式和存储 FCFS 均是明确的研究设定。[Mooncake，§5.2](https://arxiv.org/html/2407.00079v4#S5.SS2)

### 1.2 决策范围为什么收缩

统一队列取消了“先派发到实例队列、再改派”的需要。所有尚未执行的请求都可以在下次领取时重新选择实例与同批成员。因此，本模型不再把 re-schedule 列为优化动作。

存储层也不再根据 SLO 或计算紧迫性改变服务优先级。调度器只能通过合法的组批、排序和延迟启动影响未来提交顺序，不能在预测中偷偷重排已经提交的读取。此前允许优化存储分配策略的结论，不能直接转用于这个固定 FCFS 模型。

## 2. batch 为什么可能提高计算效率

### 2.1 先区分请求数、后缀长度与前缀长度

设请求 $i$ 的缓存命中前缀长为 $H_i$，待计算后缀长为 $U_i$。对于一个批 $\mathcal B$，至少记录

$$
n_{\mathcal B}=|\mathcal B|,\qquad
T_{\mathcal B}=\sum_{i\in\mathcal B}U_i,\qquad
P_{\mathcal B}=\sum_{i\in\mathcal B}\left(U_iH_i+\frac{U_i(U_i+1)}2\right).
$$

$T_{\mathcal B}$ 是本轮要计算的 token 数。$P_{\mathcal B}$ 是标准因果注意力中 query 与可见 key 配对数量的近似工作量，实际 FLOPs 还需乘以模型相关系数。

固定模型第 $\ell$ 层每 token 的 KV 大小为 $\kappa_\ell$，则

$$
v_{i\ell}=H_i\kappa_\ell,\qquad
V_{\mathcal B\ell}=\sum_{i\in\mathcal B}v_{i\ell}.
$$

“长请求”可能指长命中前缀，也可能指长待算后缀。前者直接增大存储读取，后者增大线性层与注意力计算。两者需要分开，不能仅按总输入长度估计 batch 成本。

| batch 变化 | 对计算的主要影响 | 对共享存储的直接影响 |
|---|---|---|
| 请求数增加，后缀总 token 也增加 | 小矩阵可能变得更易并行，计算总工作也增加 | 加入请求的命中 KV 需要读取 |
| 请求数增加，后缀总 token 保持不变 | 线性层主要矩阵规模可能接近，序列管理与注意力形状变化 | 取决于新增请求的前缀总量 |
| 单请求后缀已经很长 | 单个请求可能已能充分使用计算单元，继续组批收益有限 | 仍需额外读取同批请求的 KV |
| 前缀很长、后缀很短 | 新 token 不多，注意力仍需访问长上下文 | 读取量大，未必有足够计算掩盖 I/O |
| 长短序列混合 | 取决于 packed、padding 和注意力内核的实现 | 改变批读取量、申请速率与提交节奏 |

### 2.2 线性层、注意力与固定开销的作用不同

线性层可以把多个请求的 token 合并为更大的矩阵乘法。在小规模时，更大的矩阵通常能增加并行工作、摊薄权重读取和内核启动开销。规模继续增大以后，吞吐会接近硬件或内核上限，总耗时则继续随工作量增加。NVIDIA 的矩阵乘法与全连接层指南说明了矩阵维度、算术强度和分块效率的关系，具体阈值不能直接移植到某个 NPU 模型。[NVIDIA 矩阵乘法指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)，[全连接层性能指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-fully-connected/index.html)

prefill 本身就包含多个 token。SARATHI 的特定模型和硬件实验中，prefill 在请求 batch 为 1 时已经能够充分使用计算资源，继续增加请求数时每 token 耗时变化很小。因此，不能将小 batch 的 decode 收益直接当作 prefill 组批的收益。[SARATHI，§3.1 与图 3](https://www.microsoft.com/en-us/research/uploads/prod/2023/09/sarathi_preprint.pdf)

注意力的请求之间不存在交叉注意力，长请求的上下文不能帮短请求省去自身所需的 attention 工作。多个短请求与一个相同总 token 数的长请求，注意力工作量也可能不同。在没有缓存前缀的简单例子中，一个 1024-token 后缀的配对数为 524800，四个 256-token 后缀总计为 131584；线性层 token 总量相同，注意力工作相差近四倍。

如果实现采用 padding，混合长短可能把短序列填充到较长形状并引入无效工作。采用 packed 或变长内核时，不应再按“所有请求补齐到最长”计费，但仍需考虑内核形状与批同步。使用哪一种布局必须固定并通过 profile 体现。

### 2.3 用计算画像代替固定 batch 加速倍数

定义第 $\ell$ 层批计算时间

$$
c_{\mathcal B\ell}=g_\ell\bigl(\{(H_i,U_i)\mid i\in\mathcal B\},\text{固定硬件与内核配置}\bigr).
$$

一种解释性分解是

$$
c_{\mathcal B\ell}\approx
\tau_\ell+
\frac{F^{\mathrm{linear}}_\ell(T_{\mathcal B})}{\Pi^{\mathrm{linear}}_\ell(\mathcal B)}+
\frac{F^{\mathrm{attn}}_\ell(P_{\mathcal B})}{\Pi^{\mathrm{attn}}_\ell(\mathcal B)}+
T^{\mathrm{other}}_{\mathcal B\ell}.
$$

这里的有效吞吐 $\Pi$ 需由测量得到，包含内存访问和内核效率的影响，不直接使用峰值算力。此式帮助选择 profile 输入，不替代测量，也不能将各项已经包含的开销再次重复相加。

批计算收益可表示为

$$
\eta_{\mathcal B}=
\frac{\sum_{i\in\mathcal B}\sum_\ell c_{\{i\}\ell}}
{\sum_\ell c_{\mathcal B\ell}}.
$$

$\eta>1$ 表示合批减少总 NPU 计算秒数。它不表示每个请求更早完成，也不保证利用率时间占比上升。正式仿真至少应覆盖接近无收益、明显受益，以及混合形状带来额外开销的画像。

### 2.4 batch 应该怎么设

“设置 batch”包含两类不同决策。

| 离线固定的能力上限 | 在线实际选择 |
|---|---|
| 最大请求数 $N_{\max}$ | 本批具体成员及请求数 |
| 待算 token 预算 $T_{\max}$ | 是否只取少数请求或填满预算 |
| 共同的 KV 与工作区容量约束 | 选择哪种长短、读算结构 |
| 完整 prefill 或固定 chunk 执行方式 | 现在发批，或暂缓到一个后续时刻 |

基础可行性条件包括

$$
|\mathcal B|\le N_{\max},\qquad
\sum_{i\in\mathcal B}U_i\le T_{\max},\qquad
\operatorname{MemoryFeasible}(\mathcal B)=1.
$$

若完整请求的后缀超出 token 预算，需要预先规定可容纳最大支持请求的预算，或明确加入 chunk 能力，不能悄悄将该请求丢掉。

离线先扫描后缀 token 总量、前缀长度和混合比例，找到计算吞吐逐渐饱和的区域，再结合容量确定上限。在线从统一队列选合法候选批，比较计算收益、组批等待和全局 I/O 后果。空闲实例不必每次都取最大批，也不应默认等到满批才启动。

实际引擎中，token 预算本就是独立的配置维度。vLLM 文档讨论 `max_num_batched_tokens` 对执行行为和性能的影响；本文借鉴这个区分，不复用其包含其他阶段的默认调度逻辑或具体推荐数值。[vLLM 性能配置](https://docs.vllm.ai/en/latest/configuration/optimization/)

## 3. FCFS 按需分配必须怎样定义

### 3.1 三个量不能混用

| 量 | 含义 |
|---|---|
| 读取量 $V_f$ | 该次读取最终必须传输的 GB 数 |
| 申请速率 $q_f$ | 读取方向存储申请的 GB/s，是服务分配的输入 |
| 实际速率 $b_f(t)$ | FCFS 在当时分给该读取的 GB/s |

另有一个分析量，即为了在计算消费前就绪所需的速率。它用于判断是否会等待，不能自动当成实际分配结果。

FCFS 顺序按读取提交时间和固定平局序号排列。设时刻 $t$ 未完成的读取依次为 $f_1,\ldots,f_k$，可用共享带宽为 $\beta(t)$，则

$$
b_{f_j}(t)=\min\left(q_{f_j},\left[\beta(t)-\sum_{h<j}b_{f_h}(t)\right]_+\right).
$$

这允许多个读取同时传输。例如 $\beta=4$，按顺序的申请为 1、2、3 GB/s，则实际分配为 1、2、1 GB/s。队首申请 4 GB/s 时，后续读取暂时分不到带宽，这是同一规则的特例。

当前模型以“一个 batch 的一层读取”为一个服务申请单位。对象或请求粒度的 FCFS 会改变提交次序和队头阻塞，需要单独作为服务粒度敏感性实验。不能只写 FCFS 而省略单位。

### 3.2 申请速率从哪里来

FCFS 分配规则本身不能确定 $q_f$。为了得到可复现的完整模型，本文补充一条所有策略共用的申请规则。设实例入口速率上限为 $P_w$，则

$$
q_{\mathcal B1}=P_w,\qquad
q_{\mathcal B\ell}=\min\left(P_w,\frac{V_{\mathcal B\ell}}{c_{\mathcal B,\ell-1}}\right),\quad \ell\ge2.
$$

第一层没有前一层计算可供隐藏，按入口上限申请。后续层按“希望在当前层计算期间读完”的窗口申请，申请值在本次读取完成前固定。计算时间为零的退化情况按入口上限处理。

**这条申请规则是将“按需”具体化的建模选择，不是 FCFS 的必然含义。** 它不作为调度器任意可调的限速变量。若早期没有分到足够速率，本次读取可能迟到；模型没有免费补偿，不能假设它仍在原截止时刻完成。

必须用“所有层始终按 $P_w$ 申请”做敏感性对照。两种规则都符合 FCFS 按需分配，但混合组批能否真的降低申请速率，结论会不同。若真实系统支持随剩余数据与消费时限更新申请，也应另行固定更新规则和开销，再比较调度，不能只给新策略这一能力。

### 3.3 FCFS 下，全局干扰怎样产生

新提交的读取排在已有读取之后，在申请值不变时，不会降低排在它前面的读取已获得的速率。但它可能排在其他实例尚未发出的下一层读取之前，进而拖慢后者。错峰主要改变这些未来的先后关系。

调度器提前发出一个大批，可能使它的后续读取成为其他批的队头阻塞；推迟该批也可能浪费本来可以利用的剩余带宽。预测必须重算后续各层的提交与完成事件，不能只检查当前队列长度。

该服务规则在申请总量达到可用容量时尽力用满带宽。申请总量低于容量时，带宽利用率可以低于 100%，即便仍有数据未读完。提高申请速率会改变模型，不应通过预取下一批或静默超额服务来填满带宽。

## 4. 长短请求合批，会降低带宽诉求并损害短请求 SLO 吗

这个判断需要分别检查读取量、消费窗口和完成时刻。

### 4.1 读取量不变，所需速率可能下降

不做去重、压缩或重算时，短请求 S 的每层读取量始终是 $v_{S\ell}$。若它独立执行时前一层计算耗时为 $c_S$，与长请求合批后为 $c_{LS}$，则分摊到短请求的窗口需求为

$$
q_S^{\mathrm{need}}=\frac{v_S}{c_S},\qquad
q_{S\mid LS}^{\mathrm{need}}=\frac{v_S}{c_{LS}}.
$$

只有当 $c_{LS}>c_S$ 时，后者才下降。它是批需求的解释性分摊，存储收到的仍是整批申请

$$
q_{LS}=\min\left(P_w,\frac{v_L+v_S}{c_{LS}}\right).
$$

例如每层 $v_L=4$、$v_S=1$ GB，单独计算分别为 2、1 s，合批计算为 2.25 s。短请求的窗口需求从 1 降到约 0.444 GB/s，整批申请约 2.222 GB/s。读量仍为 5 GB，第一层仍按入口上限申请。

若以两个独立请求同时处于对应计算窗口为参照，其需求总和为 3 GB/s；但实际独立执行的窗口不一定同时出现，所以不能直接把这个差值当作全局节省的带宽。

还存在相反的效应。同一个批计算得更快，$c_{\mathcal B}$ 更小，按窗口及时取数所需的速率反而更高。更高的 batch 计算效率，可能暴露更多存储等待。

### 4.2 短请求的 SLO 是否下降，取决于完整反事实

设短请求单独执行与合批的完成时刻分别为 $F_S^{\mathrm{sep}}$、$F_S^{\mathrm{mix}}$，则

$$
F_S^{\mathrm{mix}}-F_S^{\mathrm{sep}}
=(u_S^{\mathrm{mix}}-u_S^{\mathrm{sep}})
+(T_{LS}^{\mathrm{exec}}-T_S^{\mathrm{exec}}).
$$

合批可能增加启动读取、批计算和同步等待，也可能因为更早获准执行、减少总计算或改善其他批节奏而减少排队。只有满足

$$
F_S^{\mathrm{sep}}\le d_S<F_S^{\mathrm{mix}}
$$

时，才能说这次合批使短请求从满足 SLO 变成失败。两种方案都在截止时间内时，SLO 满足率不变；合批更早执行时也可能改善短请求结果。

因此，正确的研究假设是，混合组批可能用短请求更长的完成时间换取更平缓的后续层速率需求，其净效果由计算收益、FCFS 次序、排队和 SLO 余量共同决定。

## 5. 完整形式化模型

### 5.1 输入与调度决策

有限请求集合为 $\mathcal I=\{1,\ldots,N\}$，请求参数为到达时间 $a_i$、前后缀长度 $(H_i,U_i)$、绝对截止时间 $d_i$ 和固定参考 TTFT $T_i^0>0$。其他输入包括 $W$ 个实例、层数 $L$、计算画像 $g_\ell$、容量约束、带宽 $\beta(t)$ 及共同申请规则。

离线求解给定全部输入。在线调度在时刻 $t$ 只能使用已经到达的请求、活动批进度及可观测预测。

一个调度方案 $\sigma$ 由以下对象组成

$$
\sigma=\{(\mathcal B_b,w_b,u_b)\}_{b=1}^{m}.
$$

$\mathcal B_b$ 是第 $b$ 个批的成员，$w_b$ 是执行实例，$u_b$ 是实际领取并开始读取的时刻。$m$ 也由组批决定。所有请求恰好出现一次

$$
\bigcup_b\mathcal B_b=\mathcal I,\qquad
\mathcal B_b\cap\mathcal B_{b'}=\varnothing\ (b\ne b'),\qquad
u_b\ge\max_{i\in\mathcal B_b}a_i.
$$

每个批满足第 2.4 节容量约束。同一实例的活动区间 $[u_b,F_b)$ 两两不重叠。未到 $u_b$ 的请求一律在统一队列，离线计划的未来分配不等于物理上预先派发。

### 5.2 逐层依赖与实际存储服务

定义批 $b$ 第 $\ell$ 层的读取提交、读取完成、计算开始和计算结束为 $A_{b\ell},R_{b\ell},C_{b\ell},Z_{b\ell}$。

$$
A_{b1}=u_b,\qquad Z_{b0}=u_b,
$$

$$
R_{b\ell}=\inf\left\{r\ge A_{b\ell}\ \middle|\
\int_{A_{b\ell}}^r b_{b\ell}(t)\,dt=V_{b\ell}\right\},
$$

$$
C_{b\ell}=\max(R_{b\ell},Z_{b,\ell-1}),\qquad
Z_{b\ell}=C_{b\ell}+c_{b\ell},\qquad
A_{b,\ell+1}=C_{b\ell}.
$$

实际速率 $b_{b\ell}(t)$ 必须满足第 3 节 FCFS 等式，不能只满足 $\sum b\le\beta$ 就被优化器自由选择。批完成及成员首 token 时刻为

$$
F_b=Z_{bL},\qquad F_i=F_b\quad(i\in\mathcal B_b),\qquad T_i=F_i-a_i.
$$

同刻事件需固定处理顺序。本文算例先处理读取和计算完成，再推进已有活动批并提交下一层读取，最后处理空闲实例领取；多个领取按实例编号排序。这个规则属于可复现输入，不能由优化器临时改变平局。

### 5.3 不同目标分别定义

取共同观测起点 $t_0$，有限工作集全部完成时间为

$$
M(\sigma)=\max_iF_i-t_0.
$$

四个主要优化问题共用上述可行域 $\Sigma$，只改变目标

$$
\min_{\sigma\in\Sigma}M(\sigma),
$$

$$
\max_{\sigma\in\Sigma}A(\sigma),\qquad
A(\sigma)=\frac1N\sum_i\mathbf1[F_i\le d_i],
$$

$$
\min_{\sigma\in\Sigma}\bar T(\sigma),\qquad
\bar T(\sigma)=\frac1N\sum_i(F_i-a_i),
$$

$$
\min_{\sigma\in\Sigma}\bar R(\sigma),\qquad
\bar R(\sigma)=\frac1N\sum_i\frac{F_i-a_i}{T_i^0}.
$$

SLO 可采用 $d_i=a_i+s$，或 $d_i=a_i+\alpha T_i^0$。两种定义分开实验。$T_i^0$ 使用单请求独占基准资源、按共同申请和层间规则执行的固定参考时间。一般 batch 画像下它未必是理论下界，应称“参考 TTFT”。如果必须使用理论下界，需要另行证明并固定其定义。

归一化 TTFT 对应调度文献中的 slowdown 或 stretch 思路，但分母必须写清。它按 $1/T_i^0$ 加权时延，不等于平均 TTFT 除以平均参考时间。[Total stretch minimization，§1](https://arxiv.org/html/1404.6502)

有限工作集吞吐为 $N/M$，与平均完成时间不同。持续流量实验还需报告给定 SLO 满足率下的最大稳定到达率；DistServe 与 Sarathi-Serve 都以时延约束下的服务容量评价系统。本文只使用其中的 prefill 时延部分。[DistServe](https://arxiv.org/html/2401.09670v3)，[Sarathi-Serve，§2.3](https://arxiv.org/html/2403.02310v1#S2.SS3)

### 5.4 全局 NPU 与存储指标

令有效计算时间为

$$
K(\sigma)=\sum_b\sum_\ell c_{b\ell}.
$$

在同构单 NPU 实例模型中

$$
U_{\mathrm{cmp}}(\sigma)=\frac{K(\sigma)}{WM(\sigma)}.
$$

每个 NPU 的时间互斥分为 Compute、活动批因 I/O 无法继续的 STALL、没有活动批的 Idle，以及显式计费的控制开销 Other。全局各项之和为 $WM$。等组批与延迟领取计入 Idle，不得移出统计窗口。

若以最大 NPU 计算时间占比为独立目标，可写成

$$
\max_{\sigma\in\Sigma}\frac{K(\sigma)}{WM(\sigma)}.
$$

当组批不改变 $K$ 时，它等价于最小化 $M$。当 batch 提升效率、减少 $K$ 时，它们可能冲突。更慢的计算可能让 NPU 更久处于 Compute，却降低请求吞吐。因此，主实验用 Compute、STALL、Idle 解释请求指标，不以提高忙碌时长代替提高效率。

存储带宽利用率为

$$
U_{\mathrm{io}}(\sigma)=
\frac{\int_{t_0}^{t_0+M}\sum_f b_f(t)\,dt}
{\int_{t_0}^{t_0+M}\beta(t)\,dt}.
$$

所有请求都执行、读取总量固定且 $\beta$ 恒定时，$U_{\mathrm{io}}=V_{\mathrm{total}}/(\beta M)$。它与 $M$ 直接关联，不是一项独立收益。还应记录申请未满足率和每层迟到时间，解释固定 FCFS 是否把带宽服务给了合适的执行阶段。

## 6. 一个动作的全局代价应随目标改变

“全局”规定受影响范围，目标函数规定如何评价。它不专属于 $M$。

在相同已知状态下，比较执行动作后的方案 $\sigma_1$ 与维持参考动作的方案 $\sigma_0$。以下统一定义为收益，正值表示改善。

| 目标 | 动作的全局收益 |
|---|---|
| 最小 $M$ | $\Delta_M=M(\sigma_0)-M(\sigma_1)$ |
| 最大 SLO 满足率 | $\Delta_A=\frac1N\sum_i\bigl(\mathbf1[F_i^1\le d_i]-\mathbf1[F_i^0\le d_i]\bigr)$ |
| 最小平均 TTFT | $\Delta_T=\frac1N\sum_i(F_i^0-F_i^1)$ |
| 最小平均归一化 TTFT | $\Delta_R=\frac1N\sum_i(F_i^0-F_i^1)/T_i^0$ |
| 最大 NPU 计算时间占比 | $\Delta_U=K(\sigma_1)/(WM(\sigma_1))-K(\sigma_0)/(WM(\sigma_0))$ |

这里的求和对象是相同的完整评价请求集，包括本次没有被选中、但因 FCFS 次序变化而受影响的请求。改变 batch 成员时，不能只比较被选中请求的完成时间，也不能给不同动作使用不同的 $N$。

在固定观测窗口 $H$ 内比较 NPU 利用率时，则应使用 $\Delta_U=(K_H^1-K_H^0)/(WH)$。不能把一项策略按固定窗口、另一项按各自排空时间统计。

SLO 目标具有跳变。节省很多秒但没有改变任何请求是否按时，$\Delta_A$ 仍为零；把两个请求救回、却让三个原本按时的请求失败，净收益为 $-1/N$。有预测误差时，可比较预计成功概率之和，但不能将它称为已实现满足率。

在线实现中，两个候选都应使用同一个后续调度规则继续预测，使差值来自当前动作。短预测窗口之外保留统一的剩余工作估计，不能用推迟困难请求到窗口外的方式虚增收益。在线预测无法知道未来到达，因此所得收益是条件预测，不是离线全局最优保证。

## 8. 这个问题是否 NP-hard

### 8.1 结论的适用范围

**上述一般离线优化模型是 NP-hard 的。** 对最小 $M$ 和允许固定 SLO 的最大满足率，可以直接证明强 NP-hard；平均 TTFT 与归一化 TTFT 也能包含已知困难问题。固定计算工作量时，最大 NPU 时间占比继承最小 $M$ 的困难性。

这是对可变请求集、资源规模和计算画像输入的复杂度结论，不等于任意固定模型、两个长度、八个请求的子问题都同样困难。NP-hard 也不等于小规模不能求全局最优，更不等于不存在近似算法。

### 8.2 最小 $M$ 的直接归约

从 3-Partition 出发。给定 $3m$ 个正整数 $p_i$，满足

$$
Q/4<p_i<Q/2,\qquad \sum_i p_i=mQ,
$$

问题是能否分成 $m$ 个三元组，每组和为 $Q$。将它映射为本文的一个受限实例。

| 构造项 | 设定 |
|---|---|
| 请求与实例 | $N=3m$ 个请求、$W=m$ 个同构实例，全部在 0 到达 |
| batch 与层 | 最大 batch 为 1，只有一层 |
| 计算时间 | 请求 $i$ 的计算时间为 $p_i$ |
| 存储 | 带宽及入口上限均为 1，每个请求读取 $\varepsilon=1/(2N)$ GB |
| 判定阈值 | 是否存在 $M\le Q+1/2$ 的方案 |

如果存在三元划分，让每个实例依次领取对应的三个请求。该实例总计算为 $Q$，所有读取的服务总时间仅为 $N\varepsilon=1/2$，因此每个实例由存储造成的累计额外等待不超过 1/2，总完成时间至多 $Q+1/2$。

反过来，若不存在划分，任何请求到实例的分配中，至少有一个实例的整数计算负载达到 $Q+1$，所以 $M\ge Q+1$，无法达到阈值。构造规模为多项式，且没有将 KV 读取设为零。

因此，一般模型即使不组批、只有一层、FCFS 不可调整，也已强 NP-hard。加入层间 overlap 和批选择不会使包含该特例的一般问题更容易。这里的归约是本文推导，3-Partition 与经典机器调度复杂度背景可参考 [Lenstra、Rinnooy Kan 与 Brucker，1977](https://ir.cwi.nl/pub/18051)。

### 8.3 SLO 满足率的困难性

给上述构造的所有请求设置相同截止时间 $d_i=Q+1/2$。能否让满足率达到 100%，恰好等价于能否令 $M\le Q+1/2$。所以允许固定 SLO 的最大满足率问题强 NP-hard。

这证明了本文包含固定阈值情形的一般 SLO 问题。若进一步限定所有请求只能采用同一个 $\alpha$ 的相对阈值 $d_i=a_i+\alpha T_i^0$，上述公共截止时间归约不能直接套用，应另证该受限子问题；不能从其他目标的困难性直接跳到它。

### 8.4 平均与归一化 TTFT 的困难性

考虑单实例、单层、batch=1。经典请求处理时间为 $p_i>0$、到达时间为 $a_i$。选择共同 $0<\delta<\min_i p_i$，令每个请求以 1 GB/s 读取 $\delta$ GB，计算时间为 $p_i-\delta$。

该实例领取一个请求后直到完成才领取下一个，读取与计算合成一个不可抢占的 $p_i$ 长度任务。于是

$$
\min\bar T\quad\Longleftrightarrow\quad
1\mid r_i\mid\sum C_i,
$$

因为 $\sum a_i$ 是固定常数。这是带释放时间的单机非抢占总完成时间问题，已知强 NP-hard。[原始复杂度研究](https://ir.cwi.nl/pub/18051)，[该问题的算法研究与问题定义](https://www.sciencedirect.com/science/article/pii/S0377221722005148)

在同一构造中，无争用参考时间恰好为 $T_i^0=p_i$，因此

$$
\min\bar R\quad\Longleftrightarrow\quad
\min\sum_i\frac{C_i-a_i}{p_i}.
$$

它是单机非抢占 total stretch 问题。Legrand、Su 与 Vivien 的报告第 5.1 节、定理 4 给出了 NP-completeness 证明。因此归一化目标也 NP-hard，不能只用任意加权完成时间的困难性代替证明，因为这里权重被约束为 $1/p_i$。[原文与证明](https://perso.ens-lyon.fr/frederic.vivien/Publications/LIP-2006-19.pdf)

这些构造均保留正的 KV 读取，但只证明一般输入模型。对于固定层数、特定实测画像等更窄的模型，若需要单独的复杂度分类，应另行证明。

### 8.5 存在容易求解的特例

单机、全部同时到达、batch=1、每请求服务时间固定且没有跨请求资源耦合时，短作业优先可最小化平均完成时间。此时归一化目标的权重为 $1/p_i$，交换论证中的排序比值为 $p_i/(1/p_i)=p_i^2$，仍按 $p_i$ 升序。

因此，不能将所有短作业排序问题都称为 NP-hard。困难来自更一般的到达、实例分配、组批与共享服务时序组合。

## 9. 怎样求全局最优，怎样评价近似最优

### 9.1 先区分三个“最优”

| 名称 | 已知信息与保证 |
|---|---|
| 离线全局最优 | 已知完整请求、资源轨迹和确定计算画像，在声明的完整动作空间中求最优 |
| 小窗口精确最优 | 只对当前候选集和预测窗口求最优，保证不覆盖窗口外与未来到达 |
| 在线近似或启发式 | 每次基于已知状态做决策，性能需要理论界或独立实验验证 |

即使计算能力无限，在线策略也无法总是匹配知道未来的离线最优。一个非抢占长批刚启动后可能到达紧急短请求；选择等待又可能面对再无新请求的情形。两个未来在决策时不可区分。

### 9.2 小规模精确求解

对有限请求集，可枚举所有合法 batch 分组、实例分配和启动决策，或将其编码为混合整数规划、约束规划。关键约束应包括

| 约束类别 | 必须表达的内容 |
|---|---|
| 组批 | 每请求恰好属于一个选中批，满足请求数、token 与容量上限 |
| 实例 | 每批只选一个实例，整个活动区间不与该实例其他批重叠 |
| 执行 | 按第 5.2 节表达读取释放、计算依赖和一层 lookahead |
| 存储 | 读取顺序由提交时刻决定，速率必须等于 FCFS 按需分配结果 |
| 时间与 SLO | 原始到达和截止时间不变，明确时刻精度与同刻处理规则 |
| 目标 | 使用第 5.3 节对应函数，SLO 引入按时完成指示变量 |

只写共享带宽容量约束，让求解器随意决定每条流的速率，会求出一个更强存储调度器的最优值，不能作为本模型的可执行最优方案。允许该自由度只能用作松弛下界，并明确标注。

在固定 batch 与事件先后关系下，本文申请值是常数；带宽恒定或分段常数时，各事件间 FCFS 分配也是常数。可通过枚举事件关系、线性化分配中的 min/max，构建精确模型。完整枚举规模会迅速膨胀，求解器需要分支定界与对称性削减。

另一条更容易实现的路线是规定调度时钟精度 $\Delta$、最大时域和离散服务规则，做有限状态搜索或 CP-SAT。枚举必须包括允许的延迟领取，不能只枚举“实例一空闲就立即发批”的非延迟计划。按时间格求得的全局最优只对该离散模型成立，需用更细精度检查稳定性；FCFS 在提交先后翻转时可能发生不连续变化，不能无证明地宣称误差最多一个时间格。

CP-SAT 使用整数约束，返回 `FEASIBLE` 仅表示找到可行解，`OPTIMAL` 才表示求解器证明相应模型最优。输入近似、时间离散和候选裁剪的限制仍然存在。[OR-Tools 官方说明](https://developers.google.com/optimization/cp/cp_solver)

### 9.3 用上下界认证一个解有多接近最优

最小化目标使用下界 $LB$ 与可行解上界 $UB$，报告

$$
\operatorname{gap}=\frac{UB-LB}{LB},\qquad LB>0.
$$

对 SLO 成功数，报告已找到成功数 $K_{\mathrm{feas}}$ 与可证明上界 $K_{\mathrm{upper}}$，差额除以 $N$ 得到满足率的加性差距。最优成功数可能为零，不宜只报乘性比值。

$M$ 的基础下界至少包括总读取服务量和经过正确计算的总计算工作下界。令所有请求单独执行的计算总量为 $K_{\mathrm{single}}$，若可证明任意合法批的计算收益不超过 $\eta_{\max}$，则在 $t_0=0$、恒定带宽下

$$
LB_M\ge\max\left(\frac{V_{\mathrm{total}}}{\beta},
\frac{K_{\mathrm{single}}}{W\eta_{\max}}\right).
$$

不能直接把单请求计算之和除以 $W$ 当作组批模型的下界，因为合批可能减少这些计算秒数。单请求参考 TTFT 同样未必是合法下界。

对平均目标可以使用放松资源竞争和批同步后的优化值作为下界；对 SLO 可以用允许更强存储服务或更多计算并行的松弛模型求成功数上界。所有松弛必须扩大可行域，不能仅换一个未经证明更乐观的估计公式。

### 9.4 一条可证明但很弱的近似界

在全部请求同时到达、同构实例、恒定带宽、$P_w=\beta$、固定读取量、共同申请规则且计算收益有上界 $\eta_{\max}$ 时，可以给出一个保守构造。

只用一个实例，逐请求执行，其余实例保持空闲。独占时，第一层耗时为 $v_1/\beta$，后续读取耗时为 $\max(v_\ell/\beta,c_{\ell-1})$，所以该串行可行方案满足

$$
M_{\mathrm{serial}}\le\frac{V_{\mathrm{total}}}{\beta}+K_{\mathrm{single}}.
$$

结合上一节下界，有

$$
M_{\mathrm{serial}}\le(1+W\eta_{\max})M^*.
$$

这个界可能很松，且随实例数增长，不能据此把串行方案推荐为高性能实现。它说明在明确前提下，确实可以构造有保证的近似算法；实用算法还需要显著更好的表现或更紧的界。该推导不直接覆盖动态到达、背景带宽变化、另一种申请策略，以及另外三个优化目标。

经典纯计算并行机问题的 LPT 算法具有更好的近似界，但其前提没有本文的 batch 收益与共享 FCFS 存储，不能直接移植其保证。[Graham，1969](https://fanchung.ucsd.edu/ron/papers/69_02_multiprocessing.pdf)

### 9.5 推荐的可扩展算法

实践中先实现有限候选的滚动预测，再用局部搜索改进。这里称为启发式，只有与精确界对照后才能报告“接近最优”。

```text
当请求到达、批完成或存储观测更新时
    读取统一队列、活动批状态和 FCFS 可观测状态
    从队列构造有限候选批
        到达序批、短服务批、截止时间批、同类批、读算混合批、单请求批
    对每个空闲实例考虑立即领取及少量延迟领取时刻
    对多个空闲实例联合生成互不重叠的候选批组合
    对每个组合执行相同 FCFS 模型的全局预测
        使用固定后续规则处理未选请求并补上窗口末端的剩余工作
        按选定主目标计算全局收益
    执行最优候选的当前领取动作
    延迟方案中的请求仍留在统一队列，到时重新决策
```

延迟候选可取当前层计算预计结束、某个先提交读取预计完成、下一次调度时钟等时刻。它们是一组搜索候选，不能未经证明声称包含连续时间最优点。控制开销、最大候选数和最大等待需要固定。

候选数量大时用 beam search 保留少量较好的部分计划；离线或较低频率下用大邻域搜索，尝试交换批成员、拆批、合批和移动启动时刻。每次修改都重新推进全局 FCFS 事件，不能只替换一个批的独立耗时。

| 主目标 | 候选产生可用的启发信息 | 最终评价 |
|---|---|---|
| 最小 $M$ | 避免长尾批太晚开始，寻找读算窗口互补 | 全局预测的最后完成时刻 |
| 最大满足率 | 优先包含仍可按时完成的请求，考虑同批共同截止时间 | 净增加的按时请求数，不能只看最早截止时间 |
| 最小平均 TTFT | 短服务批、能较快完成较多请求的批 | 所有请求完成时间之和 |
| 最小归一化 TTFT | 对较小 $T_i^0$ 的延迟更敏感 | 按 $1/T_i^0$ 加权的完成时间之和 |

这些只是缩小候选集的方式，不是最优性定理。SLO 目标出现平局时可用平均 TTFT 作次目标，并施加共同的老化保护；不得通过永久搁置过期请求提高表面结果。

## 10. 仿真应该回答哪些有研究价值的问题

### 10.1 实验顺序与强基线

先校准 $g_\ell$ 与申请规则，再做解析和小规模精确验证，最后做在线规模实验。基础对照全部共用统一队列和同一个 FCFS 服务器。

| 对照 | 用途 |
|---|---|
| 到达序组批、空闲即领 | 检查简单晚绑定已经能解决多少问题 |
| 短服务或截止时间组批、空闲即领 | 排除一般优先级排序的收益 |
| 固定同类批、固定混合批 | 分离组批结构的影响 |
| 同一组批器，只增加延迟领取 | 测量错峰本身的增量 |
| 同一动作与预测器，静态成本换实时可观测状态 | 测量存储信息的增量 |
| 小规模完整动作空间的离线最优 | 量化启发式差距 |

这些是当前架构下的明确策略定义，不应把某个实际系统的完整调度机制改名后宣称已经复现。此前按 worker 本地队列和缓存亲和定义的路由基线，在本架构中有不同适用边界。

### 10.2 要寻找的边界

| 研究问题 | 扫描变量 | 需要得到的结论 |
|---|---|---|
| batch 计算收益多大才值得绑定短请求 | 实测画像、批大小、前缀与后缀分布 | 计算节省抵消排队和同步损失的分界 |
| 混合批是否真的平缓存储压力 | 读算相关性、申请规则、共享带宽 | 窗口需求下降是否转化为其他实例更早完成 |
| 错峰何时值得牺牲 Idle | 负载、层耗时、实例数和 FCFS 队列状态 | 正、零、负收益区域，最合适的启动偏移尺度 |
| 目标冲突有多大 | 固定与倍数 SLO、长短比例 | $M$、满足率、两种平均时延的取舍曲线 |
| 近似算法离最优有多远 | 请求数、候选数、搜索时间预算 | 可认证 gap、求解耗时及未能证明最优的比例 |
| 观测错误会不会使错峰适得其反 | 报价滞后、速率误差、计算画像误差 | 比简单规则更差的阈值与恢复能力 |

基础实验固定一个共享瓶颈。之后增加固定分片与路径差异时，必须扩展 FCFS 所作用的资源范围，不能仍用一个全局速率等式代表多条独立瓶颈。

### 10.3 验证、统计与验收

算例及实现应检查正的读取量守恒、FCFS 前序申请优先、剩余带宽分配、层间依赖、同刻事件确定性、统一队列唯一归属，以及没有预先派发或等待期加载。NPU 各状态之和必须等于统一观测窗口内的设备总时间。

相同种子共享到达 trace 和外生负载，动作导致的服务变化由各自仿真演化。先冒烟确认 SLO 不总是全满足或全失败，再冻结参数做至少 10 个种子的正式对照，报告配对差值和 95% 置信区间。有限请求集全部排空；持续流量按统一到达 cohort 随访，超时和未完成请求计入，不能只统计完成较快的请求。

开环固定到达率，闭环固定客户端数并在完成后继续产生请求，应分别报告。batch 改变计算秒数时，即使开环也可能改变 NPU 时间占比；闭环因响应加快而增加到达率时，不能据此声称物理带宽容量增加。

正式结果至少包含各目标曲线、长短请求分组时延和满足率、Compute/STALL/Idle 分解、存储利用率与申请缺口、代表性 FCFS 时间线，以及小规模上下界。接近最优的结论必须标明候选空间、时间精度和求解 gap；收益结论必须扣除调度等待和计算开销。

如果结果显示，简单短服务组批与空闲即领已接近精确参考，就没有必要增加错峰控制。如果错峰只在某种申请规则和极窄负载范围内有效，应明确限制适用范围。研究最终应能决定，何时组批、如何组批、何时值得让一个空闲实例再等一会儿。
