## 1. 成本结构(为什么慢)

k16 mpcS 实测:3409 决策 × 54652 候选评分 = 28848s,**均摊 8.5s/决策 ≈ 16 候选 × 0.53s/候选**。每候选成本 = `_clone_forecast(est0)`(引擎级副本)+ `forecast_drain`(在副本里把全部 240 条请求排空,事件量 ∝ 队列深度,r1.1 下队列持续 50~100+)。采样证实热点是纯 Python 对象属性赋值/字典查找(解释执行),无 IO、无锁、无系统调用。

**并行化的结构依据**:同一决策点内,候选 `for act in actions:` 的各次推演从**同一个 est0 出发、各自在独立副本上运行、互不读取对方的产物**——"想象副本"天然互相独立。单 run 内决策点链式依赖(前序动作决定后续状态),不可并行;run 间并行(进程分片)已在使用。唯一可挖的就是决策内的候选间并行,而它恰好占满了成本。

## 2. 目标与非目标

**目标**:候选评分(含 base 动作推演)并行到 N 个进程;8 核机器预期 ≥4×(k16 mpcS 8h → ≤2h);实现带开关,默认串行路径**一行不动**。

**非目标(全部排除,因为改变结果)**:
- 降事件预算 / 砍候选数(beam/J_width/K_req)/ 跳过"看似 tie"的稳态决策点;
- Fraction → float(事件排序边界会变);
- 增量推演/影响域裁剪(需先证明等价,属后续研究项,不在本设计);
- 跨决策点并行(结构上不可能,决策链式依赖)。

## 3. 串行语义的精确分析(等价性论证的代码证据)

### 3.1 decide() 的评分序列(search.py:468-518)

每个决策点产生一个**严格有序**的推演序列:第 0 项 = base 动作在 `est_base` 上的排空(481),第 1..M 项 = 各候选在 `est0` 的 clone 上的排空(502-503)。序列顺序 = `actions` 列表顺序(确定性生成:`_compose_bw` 注入 + 前缀枚举 + 去重截断,无 RNG)。

### 3.2 唯一的顺序依赖①:跨候选共享的事件预算池 `budget[0]`

`budget = [self.max_events]`(471)是**单决策内所有推演共享的计数池**:
- `forecast_drain` 进入时快照剩余(`eng.max_events = event_budget[0]`,366);
- 正常完成按实际消耗扣减(374);
- 耗尽则池清零、返回 None(369-371),候选循环顶 `budget[0] <= 0` → break(499)。

因此候选 i 的**进入预算** R_i = max_events − Σ_{j<i} c_j,c_j 为前序各项的实际消耗。这是真实存在的顺序依赖,并行方案必须精确复现(见 §4.2 重放)。

### 3.3 唯一的顺序依赖②(已排除):`_d_hist` 共享累计分布

`bw_demand` 每次调用执行 `hist.update(d)`(policies.py:243-244),而推演世界的延续策略就是共享实例 `self.pi`(`build_forecast_engine(snap, scn, self.pi)`)——推演中确实会写 `self._d_hist`。**但它在本方案下不构成顺序依赖,论证**:
1. d[rid] = V/c,由请求静态 token 数决定,**同一 rid 的值是常数**;
2. 推演世界的 specs **只来自 snap.requests**(search.py:176-180)——即当前已到达请求,无未来到达注入(排空语义);
3. 本决策点第 472 行 `base = self.pi.decide(snap, scn)` 必先执行,它调用 `bw_demand(snap, hist)` 已把**当前全部已到达 rid** 写入 hist;
4. 故此后一切推演中的 `hist.update(d)` 都是**幂等写入**(同 rid 同常数),hist 的键值集与 P75 阈值 d_heavy 在决策点内恒定;
5. 推演读到的 hist 视图与候选执行顺序无关 → 候选评分在该视图下是纯函数。

(跨决策点 hist 随新到达 rid 增长,由主进程串行推进,不受决策内并行影响。)

### 3.4 唯一的顺序依赖③(不可先验排除,靠验证兜底):budget_s 墙钟

循环顶的 break 条件是 `墙钟超 budget_s **或** budget[0] <= 0`(499)。并行版更快 → 墙钟触发点只会更晚或不触发。**若串行基线从未因墙钟 break,则两者候选集合相同,结果逐位一致**。无法从代码先验证明"从未触发"(k16 mpcS 均摊 8.5s/决策,不排除个别决策逼近 3600s)——处理:①`n_overrun` 计数纳入对拍字段(现 run_cell 未记录,实现时补上);②若并行版 n_overrun < 串行版,说明串行版发生过墙钟触发,**如实报告并停止合入**(此时"更快"会真实地改变搜索行为,超出本设计授权)。

### 3.5 其余等价性要素

- **score_of**(379-404)是纯函数;`Fs` 字典迭代序 = `w.requests.items()` 顺序 = rid 升序(确定性),浮点累加顺序固定;
- 每个候选推演在 worker 内运行**与串行完全相同的代码路径**(同样的 clone→drain→score),不重排任何运算;
- MPC 搜索路径无 RNG(已核:search.py/engine.py 无 numpy.random 引用;Observable 噪声 sigma=0 不生效);
- tie-break 与 gate 判定(510-517)在主进程重放后按串行逻辑执行,输入(各 score)逐位相同 → 输出相同。

## 4. 方案设计

### 4.1 执行模型:fork-per-decision(主选)

主进程照旧完成:build est0 → base/self.pi 调用(hist 定型)→ 候选生成 `actions`(全部串行、轻量)。然后:

```text
对每个决策点:
  序列 S = [base] + actions                       # 有序,M+1 项
  fork N 个 child(ctx='fork', 继承 est0 与全部状态,零序列化)
  child_k: 对分到的下标子集 {i∈S}: child_est = est0.clone_for_search()
           (满预算 max_events 推演) → 记录 (i, c_i, 截断标志, Fs_i)
           经 pipe 返回,exit                          # child 内不写任何共享状态
  主进程按原序重放(§4.2)→ 得到与串行逐位相同的 (best, 计数器增量)
```

- **为什么满预算推演是安全的**:R_i ≤ max_events 恒成立,给每个候选满预算 max_events 跑出的推演,其内部事件序列与"以 R_i 进入"的前 R_i 个事件**完全相同**(预算检查只在事件间,不影响事件内容);差异仅在于满预算版可能跑完(R_i 不够时串行版截断)——重放负责丢弃这种情况。
- **fork vs 常驻池+pickle snap**:fork 继承 est0 零拷贝、无状态同步;每决策 N 次 fork 的开销(N×~10ms)相对 8.5s/决策可忽略(3409 决策 × 6 × 10ms ≈ 3.4min/8h)。回退路径见 §8。
- **base 推演**(est_base)同样进池(它是序列第 0 项)。
- child 内只用纯 Python 推演路径(不触碰 numpy BLAS 线程),规避 macOS fork+线程的已知坑。

### 4.2 预算池重放(顺序依赖①的精确复现)

主进程收集全部 (i, c_i, 截断标志, Fs_i) 后,按原序执行:

```text
cum = 0; accepted = []
for i in 0..M:                       # 串行语义的逐项判定
    R_i = max_events - cum
    if 墙钟超 budget_s or R_i <= 0:  # 循环顶检查(499 行语义)
        n_overrun += 1; break        # 墙钟条件在并行版几乎不触发,见 §3.4
    if c_i ≤ R_i 且未截断:           # 串行下该推演正常完成
        接受 Fs_i → score_of → 计数/score 累计(与串行 506-513 同逻辑)
        cum += c_i
    else:                            # 串行下会截断:返回 None → skip,
        break                        # 池清零 → 循环顶 break(n_overrun += 1)
```

截断候选的并行推演结果被丢弃(串行下它也返回 None);其后所有项因 R=0 不再接受——与串行逐位一致。

### 4.3 接口与开关

- `MPCPolicy(..., par_workers: int = 0)`:0/1 = 走**现有串行代码路径(原样不动)**;≥2 = 并行分支。环境变量 `MPC_PAR` 为实验脚本的全局默认。
- 新模块 `sim/cq/par_eval.py`:`par_eval_batch(est0, items, n_workers) -> List[(i, c_i, truncated, Fs)]`,失败(fork 异常/child 崩溃)时抛出,由 decide 捕获后**整决策点回退串行重算**(保证不因基础设施故障改变行为,只损失该决策点的加速)。
- `run_cell` 记录字段补 `n_overrun`(对拍需要的口径完整性)。

### 4.4 计数器语义

n_decides/n_searched/n_fallback/n_tie/n_deviate/n_scored 全部在主进程重放阶段按串行逻辑累加;n_overrun 同(§3.4)。child 返回的中间计数不入账。

## 5. 等价性论证汇总(为什么"一个字节都不变")

| # | 串行语义要素 | 并行方案下的保证 |
|---|---|---|
| 1 | 候选序列有序且确定性生成 | 生成留在主进程串行,顺序不变 |
| 2 | 每项推演 = f(est0, act, 进入预算, hist 视图) | fork 继承同一 est0;hist 视图在 472 行后恒定(§3.3);进入预算由重放复现(§4.2) |
| 3 | 事件预算池跨项累计 | 满预算推演 + 原序重放,截断/接受/终止点逐位复现 |
| 4 | score_of 纯函数、浮点累加顺序固定 | worker 内跑同一代码路径,顺序不变 |
| 5 | tie-break/gate/计数器 | 重放后在主进程按串行逻辑执行,输入逐位同 |
| 6 | 无 RNG、Observable sigma=0 | 不受进程边界影响 |
| 7 | budget_s 墙钟 break | 唯一先验不可排除项:n_overrun+结果对拍兜底;不等→停(§3.4) |

## 6. 验证方案(四层,全部通过才合入)

- **V0 单测对拍**(`tests/test_cq_par.py`):小工况(如 40 条 1:1、短 makespan)下,同一决策序列 `par_workers=0` vs `par_workers=4`,对拍:①每决策 JointAction 逐位;②全部计数器含 n_overrun;③**构造预算截断工况**(max_events 调小使 R_i 耗尽)验证重放等价——截断位置、skip 集合、n_overrun 与串行一致。
- **V1 run 级对拍**(`tools/e26e_replay_check.py`,复用 E26e 二轮对拍逻辑):`MPC_PAR=6` 重跑 k4@0 的 mpcS/mpcT/local 三臂,三级产物逐位对拍:①records 结果性字段(排除 wall_s/ctrl_time_s/ctrl_p50/95);②`gantt.json.gz` 桶数据;③`requests.json.gz` 逐请求 F_s。**n_overrun 必须相等**。
- **V2 加速比基准**:k4@0 mpcS(串行基线 10932s)并行版目标 ≤3000s;记录加速比对 N∈{2,4,6} 的曲线,选默认值。
- **V3 合入后终验**:k16 mpcS(串行基线 28848s)并行重跑,V1 同口径对拍归档 records;预期墙钟 ≤2h。加速比与对拍结论写入 E26e 结果文档 §8 或新结果附注。

## 7. 验收标准

1. V0/V1/V3 全部逐位一致(含 n_overrun);**任何一项不一致 → 回退开关默认串行,如实记录分歧样本与根因,不合入**。
2. V2 加速比 ≥4×(6 worker);fork 稳定性在 macOS 冒烟通过(≥3 个完整决策点无崩溃)。
3. 全量 pytest 绿(含既有 193 个 + 新增 V0);串行路径回归:E26e 任一格点 `MPC_PAR=0` 重跑对拍逐位一致(证明默认行为零扰动)。
4. 设计文档本体的 §3.3/§3.4 论证在实现 PR 中以注释回链(hist 幂等、墙钟兜底)。

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| macOS fork + 潜在线程(numpy BLAS)崩溃 | child 仅走纯 Python 推演路径;冒烟;不稳则回退**常驻 spawn 池 + snap 序列化分发**(worker 自 build est0,多付 N 次 build,fork 语义不变),再不稳则维持串行 |
| 串行基线确有 budget_s 墙钟触发 | n_overrun 对拍暴露 → 停止合入并报告(此时"更快"=更多候选被评估=行为变化,超出"零结果影响"授权;需另行立项改口径) |
| 内存:N 个 child 各持 est0+逐候选 clone | 与串行峰值同量级(串行也是逐候选 clone);child 用完即退 |
| ctrl_time_s/wall_s 变小 | 预期内环境字段,对拍 SKIP 列表现有口径 |
| fork-per-decision 开销被低估 | V2 实测;若开销占比 >15% 再评估常驻池方案 |

## 10. 预期收益与局限

- 收益:6 worker 下 k16 mpcS 8.0h → ~1.5-2h,k4 全部 MPC 臂 9.3h → ~2.5h;E26e 若重跑全矩阵从 ~31 CPU 小时降到 ~10;λ/α 扫描从不可行变为可行(单格点 MPC 臂 ~0.5h)。
- 局限:不减少总计算量(是并行不是裁剪);单决策内部的长尾(最大候选)决定下限;8 核机器的并行度上限即 ~6-7;若未来 budget_s 改为实际部署档(毫秒级),本并行失去意义(预算早于并行度耗尽)。
