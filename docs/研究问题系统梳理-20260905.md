## 先看懂一句话

传统推理系统看到“KV Cache 命中”后，通常会倾向于把 KV 取回来。

本项目研究的是：

> 当共享 KV 存储正在拥塞时，系统能否知道“这次取回现在并不划算”，并把请求改派、换副本、部分重算、完整重算、复制或预取？

所以，这不是单纯的 KV-aware routing，也不是单纯的 fetch-vs-recompute。真正研究的是一个跨层反馈闭环：

```text
存储现在拥不拥塞？
        │
        ▼
调度器/引擎能不能看到这个状态？
        │
        ▼
请求应该去哪台 GPU、读哪个副本、取多少 KV、还是直接重算？
        │
        ▼
这个决定又会改变 GPU、网络和存储的压力
```

## 研究问题总览

在这个总问题下面，必须先把三类基础问题说清楚。否则后面的策略对比会变成“拿几个策略跑分”，却无法解释信息从哪里来、为什么能被调度器使用，以及它最终改善了哪一类资源状态。

### A. 存储侧到底应该暴露什么状态？

只纳入**计算侧在请求发出前很难准确感知、只有存储侧才能直接知道**的状态。例如某个 mem/ssd tier 当前还剩多少有效服务能力、已有多少字节在途、共享 fabric 是否被其他传输占用、某个副本是否正在降级或接近容量上限。

GPU 队列长度、GPU 利用率、worker 本地缓存是否命中，则不属于这个问题，它们是计算侧自身可以观测或维护的状态。请求完成后的 TTFT 也不能替代存储侧状态，因为它只能事后反映端到端结果，不能在决策前解释“这次访问为什么会慢”。

### B. 这些状态应该如何跨层提供？

需要同时回答状态的存储、传输、更新和消费方式：

```text
存储节点内部真实状态
        │  周期采样 / 事件更新
        ▼
StorageStateSnapshot（带时间戳、版本、TTL、置信度）
        │  调度器读取 / storage quote 按请求估计
        ▼
Router：选 worker / replica / tier
Engine：选 local / fetch / partial / recompute / F
        │
        ▼
GPU 与存储资源利用率发生变化，反馈到下一轮状态
```

当前仿真已经有这个接口雏形，但仍是进程内对象直接读取，没有真正的序列化、RPC、共享内存或传输开销。因此后续需要区分“接口语义已经验证”和“接口实现成本尚未验证”。

### C. 首要结果到底改善了什么？

结果展示的第一层应该是资源利用率，而不是先看 goodput：

1. GPU/NPU 利用率：计算侧的实际忙碌程度、各设备之间的均衡程度，以及是否因为过度 fetch 或重算造成计算侧过载。
2. 存储带宽利用率：每个 mem/ssd tier 和共享 fabric 的有效带宽占用、前台/后台流量分解，以及是否出现某个资源长期饱和而其他资源空闲。
3. 在资源利用率解释清楚之后，再看 goodput、SLO rate、TTFT P95/P99、稳定性、复制成本和缓存收益。

利用率不是越高越好。正确的判读是：在 SLO 约束下，是否减少了无效空转和局部过载，让 GPU/NPU 与存储带宽更接近可用容量，同时避免把瓶颈从一侧推到另一侧。

本文后面的“策略为什么这样选”和“五个真正要回答的问题”，都是这三类基础问题的下游验证。

### 1.2 一次请求究竟发生什么

一个命中 KV 的请求大致经过五步：

1. **请求来了**：请求带有 prefix class、KV 大小、suffix 长度和 TTFT SLO。
2. **选计算节点**：调度器决定把请求交给哪台 GPU。持有本地 KV 的 worker 不一定是最优的，因为它也可能很忙。
3. **选恢复方式**：Engine 在 local、fetch、partial fetch、recompute 之间选择。
4. **如果要 fetch**：数据依次经过路径延迟、源 tier、共享 fabric；前台 fetch 竞争这条链路，后台复制当前只竞争源/目的 tier（见 1.3）。
5. **请求完成后改变未来状态**：前缀可能进入本地 LRU；后台控制器可能复制、迁移、降层、淘汰或预取。

因此，每次决策真正面对的是：

```text
候选 worker
  × 候选副本和 tier
  × local / fetch / partial / recompute
  × partial 的取回比例 F
  × 是否与 GPU 计算重叠
```

v2 中这些选择由一个 `Decision` 一次性返回，而不是拆成互不知情的几个模块。这正是“联合调度”的仿真实现。

### 1.3 计算侧到存储侧的网络当前怎么仿

这是当前模型中必须单独说清楚的一层：项目现在仿真的不是完整的 RDMA/交换机/网卡网络，而是“路径延迟 + 共享 fabric 带宽”的抽象。

#### v1：网络被合并进 backend 服务时间

v1 只有一个或多个 `SharedKVStorage` backend。一次 fetch 的成本由：

```text
KV bytes / backend 有效带宽
    + 固定 t_base
    + backend 排队/并发竞争
```

来表示。计算 worker 到 backend 之间没有独立的 path、NIC、fabric 或链路队列。也就是说，v1 可以回答“共享存储服务能力动态变化时会怎样”，但不能回答“网络路径本身如何拥塞”。

#### v2：显式加入 path latency 和共享 fabric

v2 的 fetch 执行链在 [`sim/engine2.py`](../sim/engine2.py) 中是严格串行的：

```text
worker
  → path_lat[worker][node]
  → source tier service
  → shared fabric service
```

其中：

- `path_lat` 是 worker 到 storage node 的静态传播/访问延迟矩阵，默认是 2/4/8 ms 三档；
- 每个 node 的 `mem` 和 `ssd` 是独立的流体服务资源，各自有 nominal bandwidth、背景负载和 processor sharing；
- `fabric` 是一个所有 worker、node 和 fetch 共享的 `SharedKVStorage` 资源，默认 nominal bandwidth 为 120 GB/s；
- fabric 也有自己的背景负载、排队和并发竞争；
- `AccessCostQuery` 估计的 fetch 时间是 `path latency + tier estimate + fabric estimate`；
- partial 模式只把完整 fetch 链与 GPU 计算重叠，tier 内部和 fabric 内部目前不做更细粒度 pipeline。

#### 当前网络模型明确没有仿真的内容

下面这些内容当前没有单独建模，不能把当前结果解释成完整网络仿真：

- 每条 worker→node 链路自己的带宽和队列；
- NIC、交换机端口、队列调度和多跳路由；
- RDMA 拥塞控制、重传、丢包和 head-of-line blocking；
- tier 与 fabric 的并行传输，而不是当前的串行服务链；
- 不同流量类别的优先级和 QoS；
- 网络故障、链路失效和拓扑重路由。

因此，当前 E5/E6/E9 研究的是**路径异构 + 共享 fabric 瓶颈**，不是完整网络协议行为。

#### 一个容易误解的地方：复制流量当前没有经过 fabric

前台 fetch 会调用 source tier 和 fabric；但当前 `_ctrl_loop()` 中的 replication/migration 只让 source tier 和 destination tier 同时提交传输，**没有额外调用 `world.fabric.submit()`**。因此：

- 复制会和源、目的存储层竞争；
- 复制当前不会和前台流量竞争共享 fabric；
- E8/E11/E13 中的复制网络代价被低估了一部分。

如果下一步要研究“复制是否挤压前台 fetch”，需要让 replication 显式经过 path/fabric，并决定复制是单向流、双向流还是由存储节点之间的独立网络承载。这是网络模型的明确后续改进点。

## 2. 仿真里分别模拟了什么

不要把当前项目理解成一个完整生产系统的复制品。它是一个围绕研究问题裁剪出来的离散事件模型。

### 2.1 计算侧

- 每个 worker 有一个 GPU prefill 队列。
- prefill 时间由 token 数查表并插值。
- GPU 背景负载通过 reserved-capacity 模型降低可用服务速率。
- 当前主要模拟 TTFT 和 prefill，不模拟完整 decode。

代码在 [`sim/gpu.py`](../sim/gpu.py)。

### 2.2 存储侧

- 每个存储资源有固定 nominal bandwidth。
- 背景流量让有效容量动态变化。
- 多个传输使用 processor sharing 共享剩余带宽。
- v2 有多个 storage node，每个 node 有 mem/ssd 两层，并共享一个 fabric。
- 前台 fetch、预取会占用 tier+fabric；复制/迁移当前占用源/目的 tier，回写当前只提交目标 mem tier。具体边界见 1.3。

代码在 [`sim/storage.py`](../sim/storage.py) 和 [`sim/topology.py`](../sim/topology.py)。

### 2.3 信息侧

这里要先区分“存储侧独有状态”和“计算侧已有状态”。研究对象不是把所有能测到的指标都塞给调度器，而是找出计算侧在请求发出前难以准确推断、存储侧能够直接维护的状态。

#### 应该研究的存储侧状态

1. **有效服务能力**：当前 tier/fabric 的 nominal bandwidth、背景流量占用、剩余有效带宽和每个在途传输能分到的带宽。GPU 只能看到自己发出的请求变慢，无法在请求发出前知道服务能力已经被其他租户或后台流量吃掉。
2. **存储内部工作量**：排队请求数、inflight bytes、尚未完成的剩余工作量、当前并发传输数，以及由这些量推导出的预计服务时间。这些是存储服务内部的工作状态，不能用 GPU queue 代替。
3. **共享资源竞争**：某个 mem/ssd tier 的压力、共享 fabric 的压力、前台与后台流量占比，以及某条访问路径上各段的成本分解。尤其是 fabric 竞争，单个 GPU 或单个 worker 无法独立观测。
4. **数据放置和可用性**：副本在哪个 node/tier、是否可读、是否正在复制/迁移、容量剩余和可驱逐空间。这些由目录和存储控制器维护，计算侧最多只能拿到不完整或陈旧的副本信息。
5. **状态质量**：采样时间、版本/epoch、有效期 TTL、估计置信度，以及资源是否处于 degraded/故障状态。没有这些元信息，调度器无法判断一个“低压力”读数是否已经过期。

下面这些不属于“存储侧独有状态”：GPU 队列、GPU/NPU 利用率、worker 本地缓存命中、请求已经等待了多久。这些应该作为计算侧信号单独输入，而不能冒充 storage signal。

#### 当前仿真实际提供了什么

`SharedKVStorage` 保存 ground truth，包括 active transfers、remaining bytes、背景负载、已服务字节和 nominal bandwidth。普通策略不能直接访问这些内部字段，只能通过 `StorageObservable` 获得：

- `q`：采样后的队列深度；
- `inflight`：采样后的在途字节；
- `util_ema`：背景流量与前台服务合成后的利用率 EMA；
- `bw_share_ema`：并发传输下的带宽份额 EMA。

`AccessCostQuery` 再把这些状态转成一次面向请求的 `quote`：总时间、压力等级、置信度、tier 时间、fabric 时间和路径延迟。Oracle 才能读 ground truth 和 `hypothetical_*`。

代码在 [`sim/quote.py`](../sim/quote.py)、[`sim/storage.py`](../sim/storage.py) 和 [`sim/topology.py`](../sim/topology.py)。

### 2.4 状态接口：怎么存、怎么传、怎么更新、怎么消费

当前代码已经有“真实状态 → 可观测快照 → 请求级 quote”的雏形，但接口成本还没有被仿真。后续设计应明确分成三层。

#### 1. 存储：权威状态和快照状态分开

权威状态留在存储节点/存储控制器内部，保存队列、inflight bytes、有效带宽、容量、健康和副本变更。对外不直接暴露所有内部对象，而是生成按资源划分的快照：

```text
StorageStateSnapshot {
  resource_id, resource_type, timestamp, epoch, ttl,
  effective_bw, utilization, queue_bytes, inflight_bytes,
  active_transfers, free_capacity, replica_state,
  foreground_bw, background_bw, confidence
}
```

当前仿真中，权威状态就是 `SharedKVStorage`，快照缓存就是 `StorageObservable`；v2 的副本和容量元数据由 `MetadataDirectory` 保存。当前没有独立的序列化格式和状态存储服务，这一点不能假装已经验证。

#### 2. 传输：周期快照和请求级 quote 分工

建议把接口分成两种节奏：

- **周期快照**：存储侧主动推送或由调度侧拉取低频状态，携带 timestamp、epoch、TTL 和 confidence，用于调度器筛掉明显过载的资源。
- **请求级 quote**：调度器带着 `worker、node、tier、KV bytes、action` 查询预计代价，返回 `tier_time + fabric_time + path_time` 和压力等级，用于在候选动作之间做细粒度排序。

当前仿真对应的是：`StorageObservable` 周期采样，`AccessCostQuery.estimate()` 按请求计算 quote。采样间隔、EMA、噪声和滞回是仿真参数；当前进程内直接读对象，不模拟 RPC、共享内存、序列化、消息丢失和传输延迟。

#### 3. 更新和消费：每条状态必须能追溯到一次决策

状态更新链应该是：

```text
存储传输开始/完成、背景负载变化、复制迁移、容量变化
        ↓
存储侧更新权威状态与 epoch
        ↓
快照采样、EMA、TTL/置信度更新
        ↓
Router 选择 worker/replica/tier
Engine 选择 local/fetch/partial/recompute 和 F
        ↓
记录 quote、实际链路耗时、资源利用率和决策结果
```

这样才能回答“是状态信息本身有效，还是 quote 计算方式有效”。当前策略中的 `default2`、`joint2` 通过 `StorageObservable/AccessCostQuery` 消费存储信息；`static2` 只看 nominal cost；`oracle2` 才能直接使用真实状态。Engine 最终只执行 `Decision`，不直接读取存储内部队列。

### 2.5 负载侧

同一个随机种子生成相同 trace，保证不同策略使用 CRN。当前负载包括：

- Poisson 请求；
- 不同 prefix class 和命中率；
- 同步 burst/incast；
- 多轮 session；
- session 内快慢混合；
- 热度随时间漂移。

代码在 [`sim/workload.py`](../sim/workload.py)。

### 2.6 结果侧：先看资源利用率，再看服务指标

结果指标必须按“资源状态 → 服务结果 → 机制代价”分层。首要指标是前两类资源利用率。

#### 第一层：首要指标

- **GPU/NPU 利用率**：每个设备的忙碌比例、均值、P95/峰值和设备间离散度。当前仿真只实现 GPU prefill，未来加入 NPU 或 decode 后沿用同一指标定义。
- **存储带宽利用率**：每个 node 的 mem/ssd 和共享 fabric 的 `实际服务带宽 / nominal bandwidth`，并分别记录背景带宽、前台 fetch/partial、预取、复制/迁移和回写流量。

利用率要和资源位置一起看：平均值可能掩盖某个 tier/fabric 长时间饱和，也可能掩盖 GPU 低利用而存储高利用的单侧瓶颈。因此至少需要均值、P95/峰值、各资源之间的差异，以及前台/后台拆分。

当前代码的实现状态也要如实记录：

- GPU 的 `w*_util_mean` 已经进入汇总结果；
- v2 的 `s*_util`、`s*_fg` 已经进入时间序列，但存储利用率尚未进入正式汇总中的均值/P95/峰值字段；
- 因此在下一轮正式实验前，应先把存储带宽利用率补成一等汇总指标，否则结果文档会继续偏向 goodput 和 TTFT。

#### 第二层：服务结果指标

- goodput：在 TTFT SLO 内完成的请求率；
- SLO rate；
- TTFT P95/P99；

#### 第三层：机制和代价指标

- GPU 和存储队列峰值；
- fetch/recompute 比例；
- quote 误差；
- 复制流量；
- 预取浪费字节；
- 本地缓存命中、冗余和覆盖率。

代码在 [`sim/metrics.py`](../sim/metrics.py)。

## 3. baseline 从哪里来：已有调研与当前精确程度

### 3.1 当前仓库确实做过相关调研

baseline 不是凭印象命名的。仓库中已有两层调研材料：

1. [`docs/ChatGPT-KV感知调度调研-20260901-0116.md`](ChatGPT-KV感知调度调研-20260901-0116.md) 和 `discussions/` 下的调研记录，先把研究问题从一般 KV-aware routing 收敛到动态 storage pressure。
2. [`docs/五工作的Scheduler-Engine修改与主流默认实现-20260904.md`](五工作的Scheduler-Engine修改与主流默认实现-20260904.md)，把 TensorCast、Kairos、Cascade、AAFLOW+、CacheFlow 与 Dynamo、MindIE Motor、vLLM、SGLang、LMCache 放到同一条请求流程中，区分 Scheduler、Engine 和 KV data layer 分别改变什么。

这次又对照了截至 2026-09-06 可访问的官方文档/官方仓库。核查结果不是“所有 baseline 都已经精确复刻”，而是下面三种情况：

- **行为基线**：仿真直接抽象某个系统的默认行为，例如命中后复用/取回、Round-Robin、load balance。
- **机制基线**：仿真抽象某篇工作解决的决策机制，例如静态 fetch/recompute、partial recovery、SLO budget。
- **本方向策略**：在相同动作空间上增加 storage pressure、quote 或协同控制。

后续论文或汇报中，必须使用“Dynamo-like / Cascade-like / AAFLOW+-style”这样的表述，不能把当前策略名称写成真实系统的源码复现。

### 3.2 调研得到的 baseline 事实

#### Dynamo：调度层的 KV-aware + active-load baseline

官方 Dynamo 文档描述的 KV router 不是“只要有 KV 就一定把请求送过去”。它会结合 worker 的 prefix overlap 和 active prompt/decode load 进行评分，worker 通过 KV events 更新缓存状态；没有 KV events 时可以退化为基于路由预测的缓存状态或 load-only 路径。

这对应本项目中的：

- `default2`：Dynamo-like worker/load/KV overlap 路由 + vLLM-like 命中后复用；
- `tensorcast2`：不是 Dynamo 复现，而是另一个 locality + load 联合路由机制的参照；
- `nearest2`：只能叫“credit/tier-style 静态副本选择”，不能说是 Dynamo 当前完整副本/存储路径策略。

当前仿真没有复现 Dynamo 的以下细节：block-level prefix tree、active decode blocks、KV event transport、router temperature、prefill/decode 分离路由。因此 E5 的 `default2` 是机制对照，不是 Dynamo 代码级 baseline。

官方核查：

- [Dynamo KV-aware routing](https://docs.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/kv-aware-routing)
- [Dynamo Router Design](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/router-design)
- [Dynamo Frontend KV routing configuration](https://docs.nvidia.com/dynamo/kubernetes/kv-aware-routing/using-the-dynamo-frontend)

#### MindIE Motor / MindIE-PyMotor：调度层的 load balance 和 cache affinity baseline

MindIE Motor 的官方文档把调度算法区分为 load balance 和 cache affinity。PD 分离场景使用 DIGS scheduler，单机 Prefix Cache 场景使用 default scheduler；cache affinity 需要显式打开，并通过 kv-conductor 和 KV events 查询各实例的 prefix 命中，再与实例负载融合。

这对应本项目中的：

- v1 `load`：只看 GPU/worker 负载的简化 baseline；
- v1 `kv`：只看 KV locality 的简化 baseline；
- `default2`/`tensorcast2`：把“负载 + KV 命中”抽象成可比较的路由机制。

当前仿真没有复现 MindIE Motor 的 ZMQ/SHM workload path、kv-conductor 的 block-level prefix 索引、PD 角色和 NPU/CPU/Disk 分层权重。因此这里也是行为/机制抽象，不是 PyMotor 的直接运行结果。

官方核查：

- [MindIE Motor 官方 KV Cache 亲和性调度说明](https://github.com/Ascend/MindIE-Motor/blob/master/docs/zh/user_guide/features/kvcache_affinity.md)
- [MindIE Motor 官方 Coordinator 配置](https://www.hiascend.com/document/detail/zh/mindie/230/mindiemotor/motordev/mindie_service0252.html)
- [MindIE-PyMotor 官方 scheduler client 源码](https://github.com/Ascend/MindIE-PyMotor/blob/master/motor/coordinator/scheduler/runtime/scheduler_client.py)

#### vLLM：推理引擎的 prefix cache baseline

当前 vLLM 官方 API 文档显示，`enable_prefix_caching` 的 `CacheConfig` 默认值为 `True`；官方设计文档描述了 hash-based block prefix cache、请求完成后的 free，以及 free queue 上的 LRU eviction。vLLM 的 KV offloading buffer 默认不启用，只有设置 `kv_offloading_size` 或显式配置 KV connector 才会引入 CPU/远端 offload。

这对应本项目中的：

- `alwaysfetch2`：命中 prefix 后走恢复，不引入动态存储压力判断；
- `LocalKVCache`：当前是 class-level LRU，抽象了本地 prefix cache，但不是 vLLM 的 block-level hash/LRU 实现；
- `static2` / `partial_static2`：不是 vLLM 默认策略，而是用来和已有研究机制比较的额外 action policy。

因此，不能把 `alwaysfetch2` 写成“vLLM 默认远端取回策略”的严格复现。更准确的说法是：它是 vLLM-style prefix hit/reuse 的最小行为抽象。

官方核查：

- [vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/)
- [vLLM CacheConfig](https://docs.vllm.ai/en/latest/api/vllm/config/cache/)

#### SGLang：推理引擎的 RadixAttention/HiCache baseline

SGLang 的官方资料把 HiCache 描述为 GPU、CPU、外部存储三层层次化 KV cache；`--enable-hierarchical-cache` 默认关闭，开启后才配置 storage backend、prefetch policy 和 write policy。也就是说，SGLang 的普通 prefix reuse、HiCache 三层存储和外部 backend 不能混成一个“默认策略”。

这对应本项目中的：

- `alwaysfetch2`：只抽象“已有 KV 就复用/恢复”；
- mem/ssd/fabric 拓扑：抽象 HiCache/Mooncake 类多层 KV data path；
- E10/E15/E18：研究主动 prefetch、writeback 和 cache retention，但不是 SGLang HiCache 的源码复现。

当前仿真没有复现 RadixAttention 的 radix tree、page-level matching、HiCache 的具体异步 prefetch threshold、storage backend protocol 或 PD disaggregation。

官方核查：

- [SGLang HiCache](https://github.com/sgl-project/sglang/blob/main/docs_new/docs/advanced_features/hicache.mdx)
- [SGLang server arguments and defaults](https://github.com/sgl-project/sglang/blob/main/docs/advanced_features/server_arguments.md)

#### LMCache：KV data layer，不是调度器 baseline

LMCache 官方定位是 KV cache management layer / connector。它提供分层存储、跨 engine 复用、远端 backend 和 observability，但不应被当作一个和 Dynamo、Motor 同类型的全局调度策略。

这对应本项目中的：

- `StorageConfig`、mem/ssd/fabric 和 `MetadataDirectory`：抽象 LMCache/Mooncake 类的分层共享 KV data path；
- `quote`、fetch bytes、queue 和 background load：抽象数据层需要向上提供的访问成本信息；
- `tools/calibrate.py`：未来用真实 LMCache 吞吐/inflight 数据标定当前模型。

当前仿真没有调用真实 LMCache connector，也没有复现 LMCache 的 chunk、异步 transfer、具体 backend protocol 和 metrics API。因此 LMCache 是数据层参照和未来标定对象，不是当前实验中的一个“策略选手”。

官方核查：

- [LMCache 官方介绍](https://docs.lmcache.ai/)
- [LMCache vLLM Quickstart](https://docs.lmcache.ai/getting_started/quickstart.html)
- [vLLM KV offloading configuration](https://docs.vllm.ai/en/latest/api/vllm/config/cache/)

### 3.3 当前 baseline 应该怎样命名

为了不误导，建议统一使用以下命名：

```text
默认行为：        vLLM-style hit/reuse、Dynamo-like KV+load、Motor-like load/cache-affinity
已有机制：        AAFLOW+-style static、CacheFlow-style partial、Cascade-like budget
本方向：          dynamic storage quote、joint action、coordination、storage controller
上界/诊断：       oracle、clairvoyant、fluid relaxation
```

其中 `-style` 或 `-like` 很重要：它表示我们在相同仿真框架中抽取了该机制的关键决策变量，而不是声称已经运行了对应系统的真实默认实现。

## 4. 策略为什么这样选

策略并不是要代表所有已有系统，而是给每个研究问题提供一个“能说明问题的参照”。可以把它们分成五类。

### 第一类：默认行为

- `alwaysfetch` / `alwaysfetch2`：KV 命中就取，代表“存在即恢复”的默认思路。
- `default2`：GPU load 加 KV credit/tier 优先，抽象 Dynamo-like 的 KV+load 路由与 vLLM-style 命中复用的组合。
- `nearest2`：mem 优先、路径最近，代表只看静态位置和 tier 的副本选择。

它们用于回答：现有的 locality、tier credit 和命中即取，在动态存储压力下会不会失效？

### 第二类：已有机制的静态版本

- `static` / `static2`：用 nominal bandwidth 比较 fetch 和 recompute，对应 AAFLOW+ 式静态成本思想。
- `partial_static2`：使用固定成本选择 partial 比例，并允许 I/O 与计算重叠，对应 CacheFlow 式部分恢复能力。
- `cascade2`：使用 SLO budget 和 guardband 做 request-level 恢复决策，对应 Cascade 类预算思想。

它们用于回答：已有的 fetch/recompute、partial recovery、SLO budget 机制，如果看不到实时 storage pressure，会发生什么？

### 第三类：本方向的动态策略

- `dynamic` / `joint2`：读取 storage observable 或 cost quote，把动态压力加入决策。
- `joint2` 在 v2 中同时枚举 worker、replica、tier、action 和 partial fraction F。

它们用于回答项目的主问题：动态存储信息是否带来静态 cost model 没有的收益？

### 第四类：协同和主动控制

- `coord2`：在 joint2 上加入滞回、影子在途流量和随机分流，专门对付羊群和振荡。
- `reactive` / `predictive` controller：不改变前台引擎，只改变什么时候复制或迁移。
- `prefetch`、`writeback`、cache protection：研究本地缓存和共享副本的主动管理。

这些不是某一个已有框架的直接复刻，而是为了隔离“前台引擎能力”和“存储控制能力”之间的关系。

### 第五类：上界和诊断策略

- `oracle` / `oracle2`：知道当前真实资源状态，但逐请求决策，不知道未来。
- `clairvoyant2`：额外知道未来一段时间的请求。
- `clairfluid2`：在同步 burst 下用 GPU lane/storage lane 的流体吞吐比例分配。

它们不是可部署方案，而是用来回答：

- 当前策略损失来自信息不准，还是来自决策结构？
- 知道未来是否真的有吞吐价值？
- “全局协同没有额外吞吐收益”是否只是启发式上界太弱？

已有框架和默认行为的详细映射见[相关工作对比文档](五工作的Scheduler-Engine修改与主流默认实现-20260904.md)。这里的映射是机制抽象，不声称真实系统内部实现完全相同。

## 5. 三个基础架构问题

上面的三类问题不是附属的工程说明，而是本项目首先要回答的研究问题。它们决定后面比较的 baseline 是否公平、策略是否真的使用了存储侧信息，以及实验结果应该怎样解释。

### 5.1 什么状态值得从存储侧提供出来？

判定标准不是“能不能采集”，而是“计算侧在决策前是否难以准确获得”。当前最有研究价值的候选状态是：

- tier/fabric 的有效剩余带宽和背景占用；
- 排队请求数、inflight bytes、并发传输和预计服务时间；
- 副本所在 node/tier、可读性、容量压力和迁移/复制状态；
- 采样时间、epoch、TTL、置信度和健康状态。

要排除 GPU queue、GPU/NPU 利用率、本地 KV 命中和请求历史延迟，因为这些不是存储侧独有信息。E3 的 `util / queue / bw / quote` 扫描已经在比较不同存储信号，但下一步应把信号按“存储侧可直接知道”和“计算侧可自行知道”重新归类。

### 5.2 状态接口应该怎样设计才真的能被跨层使用？

接口至少要能回答四个问题：

1. **怎么存**：权威状态在存储节点/控制器，快照按 resource 保存，副本和容量由 metadata directory 保存。
2. **怎么传**：周期 snapshot 传资源状态，请求级 quote 传本次访问的大小、目标和预计代价；两者都必须带时间戳、epoch、TTL 和 confidence。
3. **怎么更新**：传输开始/完成、背景负载变化、复制迁移和容量变化更新权威状态，再通过采样/EMA/事件刷新快照。
4. **怎么参与计算**：Router 用 snapshot 筛选 worker/replica/tier，Engine 用 quote 选择 local/fetch/partial/recompute 和 F，并把实际耗时回写为校准数据。

当前仿真只验证了接口语义和信息边界，尚未验证 RPC/共享内存、序列化、消息丢失、传输延迟、版本冲突和接口 CPU 开销。因此不能把 `StorageObservable` 直接称为生产级接口实现。

### 5.3 最终应该用什么指标判断接口和策略是否有价值？

每个实验的结果展示顺序应固定为：

```text
GPU/NPU 利用率与均衡性
        ↓
mem/ssd/fabric 带宽利用率与前后台拆分
        ↓
goodput / SLO / TTFT tail
        ↓
fetch-recompute、复制、预取、缓存和 quote 代价
```

只有当第一层说明了瓶颈如何变化，第二层才能说明服务质量是否改善。当前 GPU 利用率已有汇总，存储带宽利用率还需要补充正式汇总字段；因此下一轮实验的验收标准之一，就是所有 v2 结果必须同时给出 per-tier、fabric 和 GPU 的利用率摘要。

## 6. 五个真正要回答的问题

下面不按 v1、v2、v3、v4 讲，而按研究问题讲。实验编号只是证据的位置。

### 问题一：存储压力是否应该成为调度器的一等信号？

**直观场景**：同一份 KV 在目录里都显示可用，但某个存储节点此刻正在被背景流量占满。只看“KV 在哪里”的策略会继续把请求送过去；看实时压力的策略应该改走其他路径或直接重算。

**仿真怎么做**：

- E1a 扫描 storage background × GPU background，寻找动态策略真正有收益的区域。
- E1b 把稳定背景换成方波背景，区分“知道平均带宽”和“知道当前状态”。
- E3 扫描 `util / queue / bw / quote`、状态陈旧度和噪声，研究接口应该暴露什么。
- E12 额外给 GPU 也加入误差，避免只给 storage 加噪声造成不公平。
- E16 更换 slow/fast 参数档位，检查策略排序是否依赖占位参数。

**比较谁**：

```text
static cost  ←→  dynamic observable/quote  ←→  oracle
```

P1/static 是关键基线，P2/joint 是本方向策略，Oracle 用来量出信息误差还剩多少空间。P0/always fetch 只做 sanity check。

**当前回答**：动态存储压力在“存储拥塞、GPU 还有余量”时价值最大；有效带宽和 cost quote 比单纯 queue depth 更可靠；100–500ms 级反馈大体足够。

### 问题二：请求应该去哪台 GPU、读哪个副本？

**直观场景**：持有本地 KV 的 worker 可能很忙，最近的副本可能正在排队，远一点但空闲的副本反而更快。

**仿真怎么做**：

- E2 用两个 backend：一个持有热点但拥塞，另一个较空闲，观察 KV locality 是否放大热点。
- E5 用四个 worker：忙 worker 持有本地 KV，空闲 worker 没有本地 KV，制造 locality 与 GPU load 冲突。
- E6 用多副本、mem/ssd 和不同路径背景，专门研究副本选择。
- E9 用陈旧反馈和同步 burst，观察多个请求是否同时冲向同一副本。

**比较谁**：

```text
Round-Robin
    → 只看 GPU load
    → 只追 KV locality / tier credit
    → locality + load 的已有机制
    → joint2 动态联合选择
    → oracle
```

**当前回答**：KV locality 不是越强越好。动态副本选择可以接近 Oracle；陈旧 quote 会造成羊群，需要影子在途流量、滞回或分流。

### 问题三：命中后到底应该 fetch、partial 还是 recompute？

**直观场景**：fetch 看起来只需要传输 10GB，但如果源 tier 和 fabric 正在排队，完整重算可能更快；如果只取回一部分，则要比较 I/O 和 GPU 计算是否能够重叠。

**仿真怎么做**：

- v1 E1/E4 先比较完整 fetch 和完整 recompute。
- E7 把 partial 和 overlap 开放给所有策略，只改变信息源，避免把“动作能力”和“动态信息”混在一起。
- E12 用 cascade2 做对等的 SLO budget 基线。
- `joint2` 在 F∈{0,25%,50%,75%,100%} 上搜索，`joint2_seq` 去掉 overlap 做消融。

**比较谁**：

```text
always fetch
    → static fetch/recompute
    → static partial + overlap
    → dynamic joint action + F
    → oracle
```

**当前回答**：partial 这个动作本身并不保证有效。动态拥塞下，静态 partial 可能把不该承诺的 I/O 流量继续压进热点；真正有价值的是“动态信息 + partial action”的组合。

### 问题四：存储侧应该什么时候复制、迁移、预取和淘汰？

**直观场景**：热点 KV 只有一个副本，复制可以减轻热点；但复制本身也会占用存储和网络。预取可以减少下一轮等待，但可能在真正使用前被大对象挤出去。

**仿真怎么做**：

- E8 关闭本地缓存，只比较 none/reactive/predictive/full replication，隔离存储控制器收益。
- E10 研究压力门控预取、重算回写和跨 worker 缓存协同。
- E11 加入有限容量、mem/ssd 跨层降级、冷类迁移、容量淘汰和热度漂移。
- E13 用 engine × controller 2×2 实验测交互效应。
- E15/E17a 逐步把预取预测从类级下沉到 session 级。
- E18a 增加预取条目保护和准入，区分“预测错了”和“预测对但缓存留不住”。

**比较谁**：

```text
无控制
    → 反应式复制
    → 预测式复制
    → 静态全副本上界
```

预取则比较：

```text
无预取 → 无脑预取 → 压力门控 → 会话预测 → 会话预测+缓存保护
```

**当前回答**：存储控制和引擎感知是互补的。只复制但不让引擎看见新副本，收益很小；预取浪费的主要根因不是单纯预测粒度，而是容量 churn，因而需要“预测 + 保护/准入”。

### 问题五：全局协同到底改善吞吐还是改善稳定性？

**直观场景**：每个请求单独看都觉得同一个资源最快，但所有请求都这样选择后，就会形成 GPU 车队或存储羊群。

**仿真怎么做**：

- E4 用 150 请求热点 burst 观察局部最优造成的车队。
- E9 用陈旧反馈制造副本羊群，比较 greedy joint2 和 coord2。
- E9b 加入知道未来的 list-scheduling。
- E14 在容量受限和热度漂移下复检未来视线。
- E18b 用 fluid-opt 检查 list-scheduling 的结果是不是因为启发式太弱。

**比较谁**：

```text
逐请求 greedy
    → shadow load / hysteresis / randomized coordination
    → per-request oracle
    → future-aware list scheduling
    → fluid upper bound
```

**当前回答**：在当前 burst 和漂移场景中，未来视线没有带来额外吞吐；协同的主要收益是降低队列峰值、P95/P99、羊群和振荡。因此后续应该把协同定义成稳定性控制问题，而不是泛泛追求全局吞吐最优。

## 7. 目前可以把仿真结果压缩成五个判断

1. **实时 storage pressure 是独立有价值的信号**，尤其在 storage 过载而 GPU 尚有余量时。
2. **KV locality 必须和 storage pressure 联合考虑**，否则会把热点放大。
3. **恢复动作必须动态选择**，静态的 fetch/recompute/partial 成本在拥塞时会失效。
4. **存储控制必须和状态可见性一起建设**，只改存储侧或只改引擎侧都不完整。
5. **全局协同当前更像稳定性控制器**，主要价值是削峰、抑振荡和改善尾延迟。

## 8. 现在还不能直接下的结论

### 8.1 还没有 decode，因此不能声称完整 serving 收益

当前模型主要是 prefill/TTFT。重算消耗 GPU 后，真实系统中的 decode、continuous batching 和 TPOT 可能受到影响。下一步首先要回答：

> 加入 decode 资源竞争后，joint2 的 TTFT 收益是否会以 TPOT 恶化为代价？

### 8.2 还没有真实硬件标定，因此绝对数字不能外推

当前参数已做公开区间核查，但仍需用 `tools/calibrate.py` 实测：

- GPU prefill 曲线；
- LMCache L1/L2 吞吐和并发行为；
- NVMe 的并发—吞吐曲线；
- RDMA path 和 fabric 共享；
- 真实 prefix/session trace。

目前更可信的是机制和相对排序，不是具体的秒数和 req/s。

### 8.3 fluid-opt 只覆盖特定结构

E18b 的流体上界适用于当前同步 burst 的 GPU/storage 两车道抽象，不能直接推广到多类 prefix、多租户、decode、失败和动态复制的完整系统。

## 9. 后续设计时应该从哪里接着做

后续不建议继续按“再加一个策略、再加一个实验”的方式扩展。每个新实验先明确它属于下面哪一类：

```text
A. 改变信息：freshness / noise / quote / observability
B. 改变动作：worker / replica / F / overlap / recompute
C. 改变控制：replication / prefetch / eviction / admission
D. 改变目标：GPU/NPU 利用率 / storage bandwidth 利用率 / goodput / tail / stability / fairness / cost
E. 改变真实性：decode / real trace / hardware calibration
```

当前最值得优先做的是：

1. **先补资源利用率汇总**：为每个 GPU、mem/ssd tier 和 fabric 增加均值、P95/峰值及前台/后台带宽拆分，作为后续实验的固定首图。
2. **Decode-aware 版本**：验证最可能改变现有结论的建模缺口。
3. **真实标定和 trace 回放**：把机制结论推进到可迁移性验证。
4. **稳定性目标的正式化**：用队列峰值、P99、振荡和公平性定义协同收益。
5. **预取准入的参数边界**：研究保护 horizon、cache capacity 和 partial prefetch。
6. **最小接口原型**：验证 `StorageObservable / CostQuote → Router → Engine` 的真实开销。
