## 1. 一句话研究定位

本项目研究的是：

> 当共享 KV 存储因为带宽、排队或路径拥塞成为动态瓶颈时，如何把存储侧实时服务状态反馈给全局调度器和推理引擎，并在请求路由、副本选择、KV 取回、部分重算、完整重算、复制、迁移和预取之间进行跨层协同决策。

因此，项目的核心并不是一般意义上的 KV-aware routing，而是一个反馈控制问题：

```text
Storage Pressure
        ↓
Observable / Cost Quote
        ↓
Cross-layer Scheduling Decision
        ↓
GPU、存储、网络的资源竞争
        ↓
新的压力状态
```

最核心的研究判断是：

> Cache Hit 不等于一定应该 Fetch。KV 是否存在只是第一维信息，当前取回是否值得才是第二维信息。

## 2. 总研究问题与子问题

### 总问题

在共享分布式 KV 存储拓扑下，实时存储压力感知是否能够显著改善推理服务的 goodput、SLO 命中率和尾延迟？如果能够，收益的来源、适用边界和实现条件分别是什么？

这个总问题可以拆成四层。

| 层次 | 研究问题 | 关键变量 | 当前状态 |
|---|---|---|---|
| 信息层 | 存储侧应该暴露什么状态，反馈要多新鲜，误差多大可接受？ | signal、freshness、noise、quote error | 基本回答 |
| 请求决策层 | 请求去哪台 GPU、读哪个副本、走哪条路径、取回还是重算？ | worker、replica、path、action、F | 基本回答 |
| 协同控制层 | 如何避免羊群、车队、队列外部性和局部最优？ | shadow load、hysteresis、admission、batch allocation | 已有阶段性结论 |
| 存储管理层 | 什么时候复制、迁移、预取、淘汰？引擎如何利用这些变化？ | replication、tiering、capacity、prefetch、cache policy | 已有阶段性结论，仍需鲁棒性验证 |

## 3. 想研究的系统架构

### 3.1 逻辑架构

项目研究的是一条包含全局调度器、推理引擎、本地缓存、共享 KV 存储和存储控制器的闭环。已有架构图见[共享 KV 感知调度架构图](../discussions/共享KV存储感知调度-16x9.png)。

![共享 KV 感知调度架构图](../discussions/共享KV存储感知调度-16x9.png)

在仿真中，逻辑架构可以简化为：

```text
请求生成器
    │  prefix class / KV 命中 / session / burst
    ▼
全局推理调度器
    │  D1: worker；D2: replica/path；D3: action/F
    │  读取 StorageObservable / AccessCostQuery
    ▼
┌─────────────────────────────────────────────────────────────┐
│ 计算节点 worker                                               │
│                                                               │
│  GPU Prefill Queue ── local HBM KV Cache ── Engine            │
│       │                         │                             │
│       │                         └─ local / fetch / partial    │
│       │                            / recompute / prefill      │
└───────┼───────────────────────────────────────────────────────┘
        │ fetch / replicate / writeback
        ▼
共享高速网络 Fabric
        │
        ├── Storage Node 0: mem tier / ssd tier
        ├── Storage Node 1: mem tier / ssd tier
        └── Storage Node 2: mem tier / ssd tier
                │
                └── Metadata Directory：class → 副本集合

Storage Controller
    └── replication / migration / tiering / eviction
```

这里有两条相互作用的路径：

1. **前台请求路径**：请求选择 worker 后，Engine 决定从本地缓存、远端副本或 GPU 重算完成前缀恢复。
2. **后台控制路径**：存储控制器根据热点、容量和压力状态，异步复制、迁移、降层或淘汰 KV；这些变化通过目录和 cost quote 对前台决策生效。

### 3.2 一次请求经过哪些决策点

项目把端到端流程拆成以下决策点。v1 只实现其中一部分，v2 把它们放进一个共享分布式拓扑中。

| 决策点 | 真实系统中的含义 | 仿真中的实现 | 主要实验 |
|---|---|---|---|
| D0 | 请求到达、prefix 匹配和 KV 是否命中 | `workload.py` 生成 prefix class；`Request` 携带 hit、prefix bytes、suffix tokens | E1–E18 |
| D1 | 选择哪个计算 worker | v1 的 `Scheduler` / `route()`；v2 策略枚举 worker | E2、E5 |
| D2 | 选择哪个副本和路径 | `MetadataDirectory.holders()` + 静态或动态 replica cost | E6、E8、E9 |
| D3 | fetch、partial、recompute 还是 prefill | `Decision.action`；v2 枚举 `F={0,.25,.5,.75,1}` | E1、E7、E12 |
| D4 | I/O 与 GPU 计算是否重叠 | `EngineV2` 中 `overlap=True` 时取两条链路完成时间的 max | E7、E12 |
| D5 | 请求完成后是否写本地缓存 | `LocalKVCache` 的 LRU；服务完成后写入 prefix KV | E5、E10、E15、E17、E18 |
| D6 | 是否主动产生共享副本 | `CtrlConfig` 控制器；复制流量也占用 tier/fabric | E8、E11、E13、E17 |
| D7 | 预取、回写、淘汰如何影响未来请求 | `Prefetcher`、writeback、保护集合和容量准入 | E10、E15、E17、E18 |

研究重点不是单独优化某一个决策点，而是研究这些决策点之间是否需要共享同一套存储状态信息。

### 3.4 存储和 GPU 的执行模型

#### 存储侧

每一个存储资源都有固定 nominal 带宽，但有效服务能力会随背景负载变化：

```text
available_capacity(t) = max(0, nominal_bandwidth - background_load(t))
```

多个前台传输使用 processor sharing 共享剩余带宽；传输完成后，其余传输重新分配带宽。v2 中一次 fetch 的链路是：

```text
worker → path latency → source tier service → shared fabric service
```

复制、迁移和 writeback 也使用同一套资源，因此它们会和前台 fetch 竞争。

#### GPU 侧

GPU 使用预填充时间查表和分段线性插值，任务进入每个 worker 的 FCFS 流体队列。背景 GPU 负载通过 reserved-capacity 模型体现：

```text
effective_prefill_time = nominal_prefill_time / (1 - gpu_background)
```

当前版本主要模拟 prefill 和 TTFT，不模拟完整 decode。这是后续最重要的扩展边界。

### 3.5 信息边界

为了让策略对比具有意义，非 Oracle 策略不能直接读存储真实内部状态。

| 信息 | 普通策略 | Oracle |
|---|---|---|
| KV 是否存在、在哪里 | 可以 | 可以 |
| 本地缓存是否命中 | 可以 | 可以 |
| GPU 队列 | 当前模型允许读取 GPU 侧状态；E12 可切换到 `GpuObservable` | 读取真值 |
| 存储队列、背景负载、有效带宽 | 只能读 `StorageObservable` / `AccessCostQuery` | 读取 ground truth / hypothetical |
| 未来请求 | 不可以 | `clairvoyant` 变体可以 |
| 副本和容量变化 | 通过目录可见 | 直接读取真实目录和资源状态 |

这条边界对应研究问题本身：比较的是信息源和跨层决策能力，而不是给某个策略额外开放内部状态。

## 4. 策略体系：每个策略为什么存在

本项目的策略不是随意堆出来的。每一个策略都承担一种参照系：主流默认、已有论文机制、本方向机制、消融或上界。已有工作的详细 Scheduler/Engine 映射见[相关工作对比文档](五工作的Scheduler-Engine修改与主流默认实现-20260904.md)。下表中的“映射”表示本项目采用的机制抽象，不等同于声称真实系统内部代码完全相同。

### 4.1 v1 策略：先隔离“动态信息”和“路由层”的价值

| 名称 | 代码 | 决策方式 | 参照来源/理由 |
|---|---|---|---|
| P0 `alwaysfetch` | `policies/always_fetch.py` | 命中即 fetch | 主流 KV cache 默认行为的 sanity baseline；回答“如果永远取缓存会怎样” |
| P1 `static` | `policies/static_cost.py` | 用 nominal bandwidth 比较 fetch 与 recompute | AAFLOW+ 式静态 fetch/recompute cost；核心静态基线 |
| P2 `dynamic` | `policies/dynamic_cost.py` | 用陈旧/EMA/带噪存储观测估计 fetch cost | 本方向最小机制；与 P1 只差信息是否动态 |
| P3 `dynamic+routing` | `policies/storage_aware_routing.py` | 联合选择 worker 和 fetch/recompute | 回答全局调度器是否也必须感知 storage pressure |
| P4 `oracle` | `policies/oracle.py` | ground truth hypothetical cost | 上界和诊断工具；不是全局离线最优 |
| `rr` | `policies/routing_baselines.py` | Round-Robin 路由，engine 固定静态决策 | 无 locality、无负载感知的路由基线 |
| `load` | `policies/routing_baselines.py` | 只看 GPU 队列 | 说明只做计算负载均衡是否足够 |
| `kv` | `policies/routing_baselines.py` | 优先持有 KV 的 worker | 对应传统 KV-locality-aware routing，专门用于观察热点正反馈 |

E1 中 P1/P2/P4 用来隔离动态存储信息的收益；E2 中 engine 固定为 P1，只改变 route，用来隔离路由层的收益；E4 把全部策略放入 incast，用来观察局部决策的群体外部性。

### 4.2 v2 策略：把五个架构问题放入共享分布式拓扑

| 名称 | 决策方式 | 参照来源/理由 | 主要实验 |
|---|---|---|---|
| `alwaysfetch2` | local 命中则 local，否则静态选副本并 fetch | vLLM/SGLang 类命中即取默认 | E5、E7 |
| `default2` | GPU load + KV credit/tier 优先，命中即 fetch | Dynamo KV-credit router + vLLM 命中处理的抽象 | E5、E12 |
| `tensorcast2` | locality + GPU load，使用静态传输成本 | TensorCast 类跨 worker locality/load 联合路由 | E5 |
| `nearest2` | mem 优先、路径最近，不动态看压力 | Dynamo credit 式副本选择 | E6 |
| `rrrep2` | 副本间盲轮询 | 排除“只要均匀轮询就能解决热点”的可能性 | E6 |
| `static2` | nominal cost 下选 worker、replica、fetch/recompute | AAFLOW+ 式静态成本决策 | E6、E7、E13、E14 |
| `partial_static2` | 静态选择 F，并允许 I/O/计算 overlap | CacheFlow 式部分恢复机制 | E7 |
| `cascade2` | SLO budget + guardband 的 request-level fetch/recompute | Cascade 类恢复/重算预算思想；用于对等比较 | E12、E16 |
| `joint2` | 动态 quote 驱动的 worker × replica × action × F 联合选择 | 本方向主策略 | E5–E8、E10–E18 |
| `coord2` | joint2 加滞回、影子流量和随机分流 | 本方向的抗羊群/抗振荡消融 | E9 |
| `static2dyn` | static2 的 action 仍静态，但 replica 选择改读动态 quote | 机制归因消融，不对应独立论文 | E17b |
| `oracle2` | ground truth hypothetical 联合选择 | 动态策略上界；逐请求 Oracle，不看未来 | E5–E9、E12–E18 |
| `clairvoyant2` | 在 oracle 基础上读取未来请求，做 list scheduling | 检验未来视线和全局分配价值 | E9b、E14、E18b |
| `clairfluid2` | 同步 burst 下按 GPU/storage 车道吞吐比例分配 | 流体松弛对照，检验 list scheduling 是否造成假象 | E18b |

这里有一个重要的控制变量原则：E7 让所有策略共享 partial + overlap 动作空间，只改变信息源；E8 统一使用 joint2，只改变存储控制器；E13/E17b 把“引擎能力”和“控制器能力”做因子拆分。这样才能区分“动作本身有效”和“动态信息让动作选对了”。

## 5. E1–E4：v1 仿真研究什么、怎么实现

v1 是单/多 backend 的简化模型，重点不是完整拓扑，而是先验证动态存储压力这个核心变量是否值得研究。

### 5.1 v1 的系统结构

```text
Poisson / burst 请求
        │
        ▼
Scheduler：选择 worker/backend
        │
        ├── Worker GPU FCFS prefill queue
        └── SharedKVStorage：固定 nominal 带宽 + 动态背景 + PS
                │
                └── StorageObservable：给 P2/P3 的陈旧/EMA/噪声视图
```

v1 的单请求动作只有：

- `fetch`：从 backend 取完整 prefix，再计算 suffix；
- `recompute`：GPU 对完整 prompt 重算；
- `prefill`：cache miss 的全量 prefill。

### 5.2 实验清单

| 实验 | 研究问题 | 场景和实现 | 策略 | 为什么这样选 |
|---|---|---|---|---|
| E1a | 动态压力相对静态 cost 是否有额外价值？ | 单 storage；扫描 background storage × background GPU；稳定负载网格 | P0/P1/P2/P4 | P1/P2 是核心对照，P0 做 sanity，P4 给出上界；是整个方向的 go/no-go |
| E1b | 动态变化本身是否重要，而不只是平均负载？ | 同均值下使用方波 background，观察 pressure 变化与策略切换 | P0/P1/P2/P4 | 区分“知道平均带宽”和“知道当前有效服务能力” |
| E2 | KV locality 会不会把请求推向热点 backend？ | 2 backend；A/C 只在热点 S_A，B 双持有，S_A 高背景、S_B 低背景 | RR / Load / KV-aware / P3 / P4 | RR 看无感知，Load 只看 GPU，KV 看传统 locality，P3 加 storage pressure，P4 作上界；engine 固定 P1 隔离 routing |
| E3 | 存储层应该暴露什么信号、需要多实时？ | storage bg 两个格点；扫 util/queue/bw/quote × freshness × noise | P1 / P2 / P4 | P1 是静态参照，P2 承担信号扫描，P4 计算可用 headroom |
| E4 | incast 下局部决策是否会形成群体外部性？ | 150 个热点 prefix 在 1 秒内到达，记录队列、重算比例、恢复时间 | P0/P1/P2/P3/P4 | 同时比较默认、静态、动态、路由和 Oracle，专门观察 tail 和车队效应 |

### 5.3 v1 研究结果应如何解读

E1–E4 不是在证明所有 KV cache 机制，而是在回答一个更窄的问题：

> 如果 storage pressure 不进入决策，后续是否还有必要研究共享 KV 拓扑和跨层控制？

E1 通过 go/no-go 后，项目才进入 v2。E2–E4 则分别把问题推进到 routing、signal interface 和 burst stability。

## 6. E5–E9：v2 仿真研究完整共享 KV 拓扑

### 6.1 v2 新增了什么

v2 将系统扩展为：

- 4 个计算 worker；
- 每个 worker 一个有限容量 local KV cache；
- 3 个 storage node；
- 每个 storage node 有 mem 和 ssd 两层；
- 所有请求共享 fabric；
- MetadataDirectory 记录副本位置和容量占用；
- `AccessCostQuery` 将 path、tier、fabric 和压力合成为 fetch quote；
- `Decision` 一次性携带 worker、node、tier、action、F 和 overlap。

因此，v2 的核心变化是：v1 的“选 worker + 选 fetch/recompute”变成了：

```text
worker × replica × tier/path × action × partial fraction F
```

### 6.2 实验清单

| 实验 | 架构问题 | 场景和实现 | 策略 | 为什么这样选 |
|---|---|---|---|---|
| E5 | 请求应该在哪个计算节点执行？ | w0/w1 忙且有本地热点缓存，w2/w3 空闲；制造 locality 与 GPU load 冲突 | rr2 / load2 / default2 / tensorcast2 / joint2 / oracle2 | 从无感知、只看 GPU、主流 credit、TensorCast locality/load 到本方向动态联合，逐层增加信息 |
| E6 | 从哪个副本、哪条路径读取？ | A 有 3 副本；mem/ssd、路径延迟和方波背景不同 | nearest2 / rrrep2 / static2 / joint2 / oracle2 | 比较 tier 优先、盲轮询、静态成本、动态 quote 和真值选择 |
| E7 | fetch、partial 还是 recompute？ | 副本集中在高压节点，背景逼近饱和；所有策略共享 partial+overlap | alwaysfetch2 / static2 / partial_static2 / joint2 / joint2_seq / oracle2 | 把“partial 动作有效”和“动态信息能选对 partial”分开；`joint2_seq` 是 overlap 消融 |
| E8 | 何时复制、迁移或预取？ | 热点 A 只有一个高压副本，其他节点空闲；关闭 local cache 隔离存储控制 | none / reactive / predictive / full-static | 统一使用 joint2，只改变存储控制器；full-static 是静态全副本上界 |
| E9 | 如何避免热点、争抢和局部最优？ | 双副本反相背景 + 200ms 陈旧反馈 + 同步 burst，制造羊群 | joint2 / coord2 / oracle2 | joint2 表示逐请求贪心，coord2 加影子流量/滞回/抖动，oracle 分离信息误差与协同误差 |

### 6.3 v2 的关键实现语义

E5–E9 的策略都通过 `sim/policies2.py` 的 `decide(req)` 返回一个完整 `Decision`，而不是只返回一个 action。这样可以保证：

- 同一个候选 worker 可以使用不同副本；
- 同一个副本可以有不同 tier/path cost；
- partial 的 F 和 overlap 进入执行时间；
- 控制器产生的新副本能被动态策略观察到；
- Oracle 和普通策略的动作空间保持一致，只改变信息源。

## 7. E9b–E12：第一轮机制修正和对等基线

这一组实验不是单纯增加功能，而是处理 v2 结果中可能被质疑的三个问题：Oracle 的矛盾尾延迟、存储控制的跨层耦合、GPU 侧真值可见。

| 实验 | 要验证的问题 | 仿真实现 | 策略/变体 | 选择理由 |
|---|---|---|---|---|
| E9b | Oracle 的“P99 更高但 SLO 更高”是否是 bug？ | 复用 E9 burst；记录逐请求 action breakdown；加入未来 trace 的 list scheduling | joint2 / oracle2 / clairvoyant2 | 把逐请求 perfect information 与看见未来的全局分配分开；验证 GPU recompute lane 的车队效应 |
| E10 | 压力门控预取、重算回写和本地缓存协同是否有效？ | 会话负载 + 12GB local cache + 多类容量 churn；引擎统一 joint2 | none / always / gated / gated+writeback / gated+writeback+coord | none 是无预取参照，always 是反例，gated 测压力门控，writeback 测重算产物复用，coord 测跨 worker 冗余代价 |
| E11 | 跨层复制、迁移和容量淘汰能否跟随热度漂移？ | 6 类 prefix、有限 mem capacity、周期性热度漂移；目录硬约束不产生孤儿副本 | static / cross-tier / tiered+migrate+evict / nocap upper | 隔离跨层降级、冷类迁移和容量淘汰；nocap 是容量上界 |
| E12 | GPU 预测误差会不会改变 joint2 结论？Cascade 类基线如何公平比较？ | 新增 `GpuObservable`，扫描 GPU noise/staleness；双方读同样的 GPU/storage 观测 | default2 / cascade2 / joint2 / oracle2 | Cascade-like 提供 SLO budget + guardband 的对等 request-level baseline；joint2 体现联合 F/replica/worker 决策 |

### 7.1 E12 的公平性原则

E12 之前 GPU 侧默认可读真值，E12 对 joint2 和 cascade2 同时加入 GPU 观测误差。这样比较的是：

- 相同 GPU 预测误差；
- 相同 storage quote；
- 不同的决策结构。

否则无法判断收益到底来自 joint2 的联合决策，还是来自它获得了更准确的 GPU 信息。

## 8. E13–E18：第二轮机制归因和缓存/先知边界

这一组实验把前面“看起来有效”的机制拆开，判断收益究竟来自什么。

| 实验 | 研究问题 | 仿真实现 | 策略/变体 | 为什么这样选 |
|---|---|---|---|---|
| E13 | 引擎能力与存储控制器是替代还是互补？ | E8 场景做 2×2：engine={static2,joint2} × controller={none,predictive} | 4 格因子实验 | 直接估计交互效应，不把“强引擎自稳”当成未经验证的解释 |
| E14 | 未来视线在容量约束和热度漂移下是否有吞吐价值？ | E11 场景关闭控制器，比较当前决策和未来 trace | joint2 / oracle2 / clairvoyant2 | 检验 E9b 的“未来视线收益有限”能否推广到连续漂移场景 |
| E15 | 类级轮间隔预测能否降低预取浪费？ | 混合快/慢 session，同一 prefix class 内速度不同 | none / gated / predictive-class | 直接验证类级 EMA 是否能识别下一轮需求 |
| E16 | 结论是否依赖占位参数？ | E7/E12 场景替换 slow/fast bandwidth profile | alwaysfetch2 / static2 / cascade2 / joint2 / oracle2 | 只改变物理参数档位，观察策略排序是否保持 |
| E17a | 预测粒度应下沉到 session id 吗？ | Request 携带 sid；按 session 自身 gap 做预测 | gated / predictive-class / predictive-session | 区分类内混合 session，验证 E15 的失败是否只是粒度问题 |
| E17b | E13 的互补性是否确实来自动态副本可见性？ | E13 场景增加 static2dyn，只升级副本选择，不升级 action cost | static2 / static2dyn / joint2 × none/predictive | 单独打开“看见新副本”这一个能力，完成机制归因 |
| E18a | 预取浪费根因是预测还是缓存 churn？ | 在 E17a 上增加保护集合和预取准入 | gated / session / protect / session+protect | 分离“该不该搬”和“搬来后能否留住” |
| E18b | 未来视线不占优是否只是 list heuristic 的产物？ | E9b burst；加入 GPU/storage lane 吞吐的 fluid-opt 分配 | joint2 / oracle2 / clairvoyant-list / clairvoyant-fluid | 用流体松弛检验“逐请求 Oracle 已接近吞吐上界” |

### 8.1 E13、E17b 的因子逻辑

E13 和 E17b 是当前最重要的机制归因实验。它们不只是比较策略分数，而是比较效应：

```text
controller_effect(engine)
  = goodput(engine, predictive) - goodput(engine, none)
```

E13 先确认是否存在交互效应，E17b 再把 static2 的动态副本选择单独打开。如果 static2dyn 的 controller effect 接近或超过 joint2，说明互补性主要由副本可见性承载，而不是由“完整动态 action cost”模糊解释。

### 8.2 E15–E18a 的机制链

```text
E15：类级预测无效
        ↓
E17a：会话级预测仍被容量 churn 破坏
        ↓
E18a：保护与准入修复“搬来但留不住”
        ↓
后续：研究弹性准入、partial prefetch 和容量相变
```

## 9. 如何阅读当前仿真结果

### 9.1 每组实验在隔离什么变量

| 对比方式 | 能回答的问题 | 不能回答的问题 |
|---|---|---|
| P1 vs P2 | 动态 storage information 是否有价值 | 不能单独说明 routing 是否有价值 |
| RR/Load/KV vs P3 | storage-aware routing 是否打破热点 | 不能把收益归因到 partial/recompute |
| static2 vs partial_static2 vs joint2 | partial 动作与动态信息的交互 | 不能代表真实 CacheFlow 全部能力 |
| E8 none/reactive/predictive/full | 存储控制器收益和阈值边界 | 不能分离引擎是否能看见副本 |
| E13 2×2 | 引擎能力和控制器的交互 | 不能解释交互的具体信息通道 |
| E17b | 副本可见性是否是交互载体 | 不能说明所有引擎差异都来自副本选择 |
| oracle vs clairvoyant | 当前信息和未来信息的价值差 | clairvoyant 若为启发式，不能直接当数学最优 |
| E18b fluid-opt | 特定 burst 结构下的流体上界 | 不能覆盖一般多资源在线调度 |

### 9.2 指标和它们代表的研究含义

| 指标 | 研究含义 |
|---|---|
| goodput | 在 TTFT SLO 下完成的有效请求率；主要吞吐目标 |
| SLO rate | 某类请求或 burst 窗口的服务成功率；观察公平性和热点类受损 |
| TTFT P95/P99 | 用户体验和尾延迟；也是羊群、车队和容量 churn 的直接结果 |
| storage queue peak | 存储热点和控制器削峰效果 |
| GPU utilization / queue | 重算是否把瓶颈转移到 GPU |
| fetch/recompute fraction | 策略如何在存储车道和 GPU 车道之间分流 |
| quote MAPE | storage interface 是否足够准确 |
| replication bytes | 控制器的额外资源成本 |
| prefetch wasted bytes | 预取的真正浪费成本 |
| cache redundancy / coverage | 协同缓存的空间效率和局部命中代价 |

## 10. 第一条主线：动态存储反馈是否真的有价值

### 3.1 研究问题

静态 nominal bandwidth 或固定 cost model，是否足以支持 KV-aware 调度？如果存储有效服务能力随着背景负载、排队和并发变化，实时反馈能带来多少额外收益？

### 3.2 当前证据

- E1 证明收益集中在“存储过载、GPU 尚有余量”的区域。
- E1b 证明相同均值负载下，动态方波背景比稳定背景更需要实时反馈。
- E3 证明有效带宽和 cost quote 比单纯 queue depth 更有用，100–500 ms 级反馈基本可用。
- E6/E7 证明静态副本选择和静态 partial recompute 在动态拥塞下可能系统性失效。
- E12 证明在当前场景中，联合策略对 GPU 侧预测噪声和陈旧度具有较强稳健性。
- E16 证明在已核查的慢、快参数档位下，策略排序保持一致。

### 3.3 当前结论

项目的第一个核心 claim 已经得到仿真支持：

> 收益来自实时存储状态信息，而不是单纯来自“允许重算”这个动作。

工程含义是，存储层可以优先提供周期性广播的有效吞吐、可用带宽或访问成本估计，不必把每个请求都变成一次强同步 RPC。

### 3.4 尚未完全回答的问题

- 存储 quote 在真实 LMCache/NVMe/RDMA 并发下是否仍然具有当前模型中的可预测性？
- processor sharing 是否足以描述真实设备的并发—吞吐关系？
- 当 decode 也消耗 GPU 资源时，storage feedback 的收益区域是否会移动？
- quote 的控制面开销、采样开销和元数据开销是否会抵消部分收益？

## 11. 第二条主线：KV 恢复是否应该成为联合动作选择

### 4.1 研究问题

请求到达后，系统应如何联合选择：

- 哪台计算节点执行；
- 哪个 KV 副本和存储层提供数据；
- 是否绕开当前路径；
- fetch、partial fetch、完整 recompute 还是 local hit；
- partial fetch 的比例 F 取多少；
- 是否与 GPU 计算重叠。

### 4.2 当前证据

- E2/E5 证明只追求 KV locality 会将请求集中到热点存储节点。
- E6 证明默认的“mem 优先 + 最近路径”在动态压力下会把大量请求砸向拥塞副本。
- E7 证明静态 partial recompute 在动态拥塞下可能比纯重算更差。
- E12 证明 joint2 相比 Cascade-like request-level 二选一策略仍有明显优势，主要来自全局联合的 worker、replica、F 和 overlap 决策。

### 4.3 当前结论

最准确的抽象不是“命中则恢复”，而是：

> KV 恢复是一个受 GPU、存储、网络和副本状态共同影响的跨层动作选择问题。

静态成本只能回答“理论上哪条路径便宜”，不能回答“现在插入这笔请求后哪条路径仍然便宜”。

### 4.4 尚未完全回答的问题

- 当前动作选择主要基于 TTFT，加入 decode 和 continuous batching 后，partial/recompute 的最优边界如何变化？
- 请求取消、超时和 fetch 不可撤销时，动态策略是否仍然稳健？
- 是否需要把“插入这笔请求对后续请求造成的边际影响”显式纳入 quote？
- 不同优先级、不同 SLO 请求之间如何进行公平的资源分配？

## 12. 第三条主线：控制与感知是否必须成对建设

### 5.1 研究问题

存储侧主动复制、迁移、分层和淘汰，是否能够独立产生收益？还是必须让推理引擎能够实时看见这些变化，控制器才真正有效？

### 5.2 当前证据

- E8 发现引擎的动态重算会改变存储利用率，使控制器的高阈值反应式策略无法触发。
- E10/E11 证明复制、重算回写、跨层迁移和容量淘汰存在明显耦合。
- E13 的 2×2 实验显示，存储控制器在 joint2 上的收益远高于 static2。
- E17b 通过 `static2dyn` 直接验证：只把动态副本选择能力加入 static2，控制器收益便显著放大。

### 5.3 当前结论

项目已经得到一个比“强引擎不需要存储控制”更准确的结论：

> 存储控制与状态感知是互补基础设施。改变存储状态但不让引擎看见，控制器收益会被浪费；让引擎看见状态但没有控制动作，又无法改变资源结构。

这意味着真实系统的落地不能只改 LMCache 或只改 Dynamo/vLLM，而要同时定义：

1. 存储状态和 cost quote 的接口；
2. 引擎消费这些状态的决策接口；
3. 复制、迁移、淘汰和回写的控制接口。

## 13. 第四条主线：全局协同的价值究竟是什么

### 6.1 研究问题

逐请求贪心已经能够读取当前状态时，还需要全局调度、未来视线或批量分配吗？全局协同究竟提高吞吐，还是只改善稳定性？

### 6.2 当前证据

- E4 发现逐请求精确决策会形成 GPU 车队效应。
- E9 发现陈旧反馈会使请求形成副本羊群。
- E9b/E14 发现 list-scheduling 式未来视线在当前场景中没有带来吞吐提升，连续漂移场景甚至出现负收益。
- E18b 进一步用流体最优批分配验证，在同步 burst 场景中，流体最优与逐请求 Oracle 基本持平。

### 6.3 当前结论

当前最稳妥的研究定位是：

> 全局协同的主要价值是稳定性控制，而不是平均吞吐提升。

稳定性包括：

- 降低队列峰值；
- 降低 P95/P99；
- 抑制副本振荡；
- 抑制羊群和车队；
- 控制 fetch/recompute 的资源比例；
- 限制单个请求对后续请求的负外部性。

### 6.4 需要谨慎限定的地方

目前的 fluid-opt 主要覆盖同步 burst 和 GPU/storage 两类车道，不能直接推出“任何场景下全局协同都不提高吞吐”。仍需要在以下场景中验证：

- 多类 prefix；
- 多副本异构路径；
- 容量约束；
- 动态复制；
- decode 资源共享；
- 请求优先级和多租户。

## 14. 第五条主线：预取的真正问题是预测还是缓存管理

### 7.1 研究问题

预取是否能够降低恢复延迟？如果预取浪费严重，根因究竟是无法预测下一次请求，还是本地缓存无法留住已经预取的 KV？

### 7.2 当前证据链

| 实验 | 尝试 | 结果 | 机制判断 |
|---|---|---|---|
| E10 | 压力门控预取 | 比无脑预取更好，但浪费仍高 | 只看当前压力不够 |
| E15 | 类级会话预测 | 浪费率不降反升 | 类内快慢会话被平均 |
| E17a | 会话身份级预测 | 仍然失败 | 预取条目被容量 churn 挤掉 |
| E18a | 会话预测 + 缓存保护/准入 | 浪费字节降至约四分之一，P95 最优 | 预测与留存必须组合 |

### 7.3 当前结论

预取问题可以拆成两个不同问题：

1. 这份 KV 是否值得提前搬过来？
2. 搬过来以后，是否有足够的缓存空间把它留到真正使用时？

当前结果说明第二个问题比第一个问题更关键。

因此，后续应重点研究：

- 预取条目的优先级；
- 活跃会话保护；
- 预取准入；
- 按字节比例的弹性准入；
- partial prefetch；
- 不同缓存容量下的相变。

## 15. 当前项目已经形成的主要结论

可以把 E1–E18 压缩成以下八条结论：

1. 存储压力是推理调度中独立于 GPU 负载的有效状态变量。
2. KV locality 与 storage pressure 必须联合考虑，否则 locality 可能放大热点。
3. Cache Hit 不等于应该 Fetch，fetch/recompute/partial 必须动态联合选择。
4. 静态 partial recompute 在动态拥塞下可能比完整重算更危险。
5. 存储控制和引擎感知是互补关系，不能只改其中一侧。
6. 全局协同的主要收益是削峰、抑振荡和改善尾延迟。
7. 预取浪费的治本方向是“预测 + 缓存管理”，单纯提高预测粒度不够。
8. 当前机制结论对已测试的现实参数档位基本稳健，但绝对数字仍需真实标定。

## 16. 尚未闭环的关键研究问题

### 9.1 Decode-aware 调度

这是当前最大的有效性风险。

现有仿真主要关注 TTFT，没有完整模拟 decode、continuous batching 和 TPOT。重算消耗的 GPU 资源可能影响已经进入服务阶段的请求，因此需要回答：

> 当 prefill、KV restore 和 decode 共享 GPU 时，动态存储感知调度的收益是否仍然成立？

建议新增一条主线，至少包含：

- P/D 混部或分离；
- decode token service；
- continuous batching；
- prefill 抢占或 chunking；
- TTFT 与 TPOT 的联合 SLO；
- 对在服务请求的公平性影响。

### 9.2 真实硬件和真实 trace

目前参数已经做过公开区间核查，但还没有完成真实硬件标定。需要使用 `tools/calibrate.py` 补齐：

- GPU prefill 曲线；
- LMCache L1/L2 取回吞吐；
- 并发—吞吐关系；
- NVMe 队列行为；
- RDMA 路径延迟和 fabric 共享；
- 真实 prefix 长度、会话间隔和输出长度分布。

当前能够声称的是机制层和相对排序结论，不能把仿真中的绝对延迟直接外推到生产系统。

### 9.3 稳定性控制的正式定义

后续不宜再泛泛讨论“全局最优”，而应把协同目标定义为控制问题：

- 队列峰值约束；
- P99 约束；
- storage/GPU 利用率平衡；
- 副本切换率约束；
- fetch/recompute 配额；
- 多租户公平性；
- 控制器动作成本。

### 9.4 预取保护的参数边界

E18 已证明方向有效，但还没有回答：

- horizon 取多大最合适；
- 保护多少类、多少字节；
- 大 prefix 是否应该部分预取；
- cache capacity 多小时保护策略才开始有效；
- 准入过严和浪费过高之间的边界在哪里。

### 9.5 故障、失效和一致性

当前模型主要研究性能压力，尚未系统研究：

- 存储节点失效；
- 副本暂时不可用；
- 复制过程中的一致性窗口；
- metadata 延迟或错误；
- 网络分区；
- 复制流量与前台流量的优先级。

## 17. 建议的后续研究顺序

### P0：先补 decode-aware 版本

原因：这是最可能改变当前主要结论的建模缺口，也与最早 E1/E4 中已经观察到的 GPU 近饱和反噬直接相关。

核心验收：

- joint2 相比 static/cascade 的优势是否仍存在；
- TTFT 改善是否以 TPOT 恶化为代价；
- GPU 高负载下是否需要准入、配额或优先级控制；
- 存储压力反馈的收益区域是否发生移动。

### P1：完成真实标定和 trace 回放

核心验收：

- 仿真 TTFT 分布与实测误差；
- quote 误差；
- 并发—吞吐拟合；
- 策略排序是否保持；
- 真实 trace 下会话预取和缓存保护是否仍有效。

### P2：把协同重新定义为稳定性控制

核心验收：

- P95/P99 和队列峰值；
- 副本振荡；
- 资源利用率均衡；
- 控制动作开销；
- 多租户公平性。

### P3：做接口原型

将仿真中的机制落成最小可验证接口：

```text
StorageObservable / CostQuote
        ↓
Global Router
        ↓
Inference Engine
        ↓
Replication / Prefetch Controller
```

需要实际测量：

- 状态广播开销；
- quote 查询开销；
- metadata 更新延迟；
- 控制器动作延迟；
- 信息陈旧对结果的影响。

## 18. 最终研究边界

当前项目不应该继续被表述成“又一个 KV-aware routing 方案”。更准确的研究定位是：

> 共享 KV 存储成为动态瓶颈时，如何通过存储服务状态反馈，把全局路由、KV 恢复、GPU 计算和存储控制组成一个跨层反馈调度系统，并刻画这一系统的收益区域、稳定性边界和落地接口。

项目下一阶段最重要的不是继续增加更多策略，而是跨过三道验证门：

1. 有 decode 时还成立吗？
2. 用真实硬件和 trace 时还成立吗？
3. 能否从仿真策略落成真实系统中的信息接口和控制闭环？
