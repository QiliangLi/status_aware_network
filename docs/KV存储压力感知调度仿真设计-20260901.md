## 1. 背景与研究问题

### 1.1 问题定义

**KV Storage Pressure-Aware Cross-Layer Inference Scheduling**：当共享 KVCache 存储因带宽 / 排队成为*动态*瓶颈时，把存储侧实时服务能力反馈给计算侧（全局调度层 Dynamo/Motor + 推理引擎层 vLLM/SGLang），使系统在 **Fetch / Recompute / Reroute** 等动作间动态选择，而不是默认"Cache Hit 就一定读缓存"。

对请求 r、候选 worker i、动作 a：

$$
T_{fetch}(r,i) = T_{storage\_queue} + \frac{KVBytes(r)}{B_{eff}} + T_{base} + T_{prefill}(suffix)
$$

$$
T_{recompute}(r,i) = T_{gpu\_queue} + T_{prefill}(prompt)
$$

$$
a^* = \arg\min_{a \in \{fetch,\ recompute\}} T_a \quad \text{s.t.} \quad TTFT \le SLO
$$

核心口号：**Cache Hit ≠ 一定应该 Fetch**；"KV 是否存在"只是第一维，"这份 KV 现在是否值得取"才是第二维。

### 1.2 核心 Claim（本仿真必须证明的东西）

> **收益来自"实时存储状态信息"，而不是来自"允许重算"这个动作本身。**

因此主对比永远是 **P2（动态压力感知）vs P1（静态 cost model）**。如果只对比 P2 vs P0（Always Fetch），审稿人/领导可以说"那只是因为你允许重算了"。P0 仅作 sanity baseline。

### 1.3 已有工作已证明的结论（本仿真**不重复验证**）

| 已证明结论 | 出处 |
|---|---|
| Fetch/Recompute 存在 crossover，低带宽下重算可能更优 | AAFLOW+ (arXiv:2607.10987) |
| I/O 与重算可细粒度混合并行（token/layer/GPU 3D），优于二选一，TTFT 降 10–62% | CacheFlow (arXiv:2604.25080) |
| KV 传输太贵时可将 Prefill 挪到 Decode GPU（deflection），P95 TTFT 最多降 81% | Kairos (arXiv:2607.02043) |
| KV locality 应进入 routing，与计算负载联合决策 | TensorCast (arXiv:2608.06007) / Preble |
| KV tier/restore cost + SLO budget 联合决定调度与 restore/recompute，goodput 最多 2.4× | Cascade (arXiv:2608.06557) |

**不做**的实验（只作为 baseline 或 sanity check）：

- ❌ 扫 10/20/40/80 Gbps 比较 Always Fetch vs Always Recompute（AAFLOW+/CacheFlow 已做）
- ❌ 证明 partial recompute 优于 full recompute（CacheFlow 已做得很深）
- ❌ 证明 Decode GPU 有空时能做 Prefill（Kairos 已做）
- ❌ 单纯证明 KV locality 应进 routing（TensorCast 已做）

### 1.4 研究缺口（本仿真要回答的）

四个关键词：**动态**（nominal 带宽不变、有效服务能力动态变化）、**共享**（多 worker 共享同一存储）、**跨实例**（reroute）、**跨层**（scheduler + engine 两级响应）。

没有任何已有工作系统回答：

1. 实时 storage pressure 相对静态 cost model 有多少**额外**收益？（E1，go/no-go）
2. KV locality routing 会不会在存储热点下把请求推向拥塞存储、形成正反馈热点？（E2）
3. 存储侧应暴露什么信号（utilization / queue / 有效带宽 / cost quote）、需要多实时？（E3）
4. 热点 prefix 触发 KV restoration incast 时能否保护尾延迟？（E4）

## 2. 仿真目标与验证策略总览

| 实验 | 核心问题 | 自变量 | 主输出 | 若结果不好的含义 |
|---|---|---|---|---|
| **E1（go/no-go）** | 实时存储状态是否比静态 cost model 有额外价值？ | 背景存储负载 × 背景GPU负载 | P2 vs P1 goodput 增益热图 | 方向基本不成立 |
| **E2** | KV locality 在存储热点下是否导致错误 routing（热点正反馈）？ | routing 策略 | 各策略 goodput / P95 TTFT / 热点放大曲线 | 只需改 engine，不需改全局调度层 |
| **E3** | 哪种信号足够？需要多新鲜？ | 信号类型 × 更新间隔 × 噪声 | 增益 vs 新鲜度曲面 | 决定接口设计（这是给存储侧 API 的需求文档） |
| **E4（附加）** | KV restoration incast 下能否保护 P95/P99？ | burst 规模 | 时序图 + 恢复时间 | 放大展示 E1/E2 价值 |

Go/No-Go 判据（E1）：在**现实可达**的负载组合区（存储 offered load ≥ 80%、GPU 背景负载 ≤ 70%）内，若 P2 相对 P1 的 goodput 增益不存在 ≥ 10% 的连通区域，方向存疑，停止投入真实系统。

## 3. 系统模型

### 3.1 架构与两层决策面

```text
                       Request Generator
                       (Poisson + prefix 分布 + hot prefix)
                              │
                              ▼
                    ┌──────────────────┐
                    │ Global Scheduler │  ← 决策1：请求发给哪个 worker
                    │ Dynamo / Motor   │     （P3 才启用；P0–P2 固定路由）
                    └────────┬─────────┘
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
          Worker 0         Worker 1  ...   Worker N-1
       ┌───────────┐    ┌───────────┐    ┌───────────┐
       │  Engine   │    │  Engine   │    │  Engine   │  ← 决策2：fetch or recompute
       │vLLM/SGLang│    │vLLM/SGLang│    │vLLM/SGLang│
       └─────┬─────┘    └─────┬─────┘    └─────┬─────┘
             │                │                │
             └────────────────┼────────────────┘
                              ▼
                    ┌────────────────────┐
                    │ Shared KV Storage  │  固定总带宽 + 动态背景负载
                    │ (V0: 1个; V1: 2个) │  + processor sharing
                    └────────────────────┘
```

**刻意保留两层决策**，因为后续要分别回答两个问题：

1. 只改 vLLM/SGLang（engine 感知存储）够不够？
2. Dynamo/Motor（全局调度层）是否也必须感知存储压力？

V0 中 P0–P2 只用 engine 决策（路由用最简单的 KV-aware 固定规则），P3 才启用 global routing。

### 3.2 请求模型

```python
@dataclass
class Request:
    id: int
    arrival_time: float
    prefix_class: str        # A/B/C/D，决定 cached_prefix_tokens
    cached_prefix_tokens: int  # 0 表示 cache miss
    suffix_tokens: int       # prompt = cached_prefix + suffix
    kv_bytes: int            # 由模型结构计算
    ttft_slo_ms: float
    # 以下由仿真运行时填充
    worker_id: int = -1
    action: str = ""         # "fetch" | "recompute" | "prefill_only"(miss)
    t_fetch_done: float = -1.0
    t_prefill_start: float = -1.0
    t_prefill_done: float = -1.0  # 即 TTFT 完成点（V0 不模拟 decode）
```

**KV 大小公式**（不要拍脑袋，从模型结构算）：

$$
KVBytes/token = 2 \times N_{layer} \times N_{kv\_head} \times D_{head} \times bytes
$$

默认模型（GQA、80 层、8 KV heads、head_dim=128、BF16）：

$$
2 \times 80 \times 8 \times 128 \times 2B = 320\ KB/token
$$

即 32K prefix ≈ 10.24 GB，64K ≈ 20.5 GB。

**请求类别分布**（同时编码"prefix 长度混合"与"热点"两个维度）：

| 类别 | cached prefix | 占比（命中内部） | 说明 |
|---|---:|---:|---|
| A | 32K (10.24 GB) | 40% | **热点 prefix**，E4 burst 源 |
| B | 16K | 20% | 次热点 |
| C | 8K | 15% | 短 prefix |
| D | 64K (20.5 GB) | 25% | 长 prefix |

- 整体 cache hit ratio = 70%（30% 请求 `cached_prefix_tokens=0`，必走 prefill）
- suffix 固定 1K tokens（V0 不做 suffix 分布，减少变量）
- 到达过程：Poisson(λ)，默认 λ = 5 req/s

**需求量自洽性核算**（默认参数下）：

- 命中请求平均 prefix ≈ 0.4×32K + 0.2×16K + 0.15×8K + 0.25×64K = 33.2K tokens ≈ 10.6 GB
- 前台存储需求 ≈ λ × 70% × 10.6 GB ≈ **37 GB/s**（B_total=100 GB/s 时占 37%，给背景负载扫描留出空间）
- 全部重算时 GPU 需求 ≈ λ × 33.2K+ ≈ 170K tokens/s，摊到 4 workers ≈ 每worker 27%（单卡能力 ≈ 156K tokens/s，见 3.3）

### 3.3 计算侧（GPU）模型

不模拟 kernel，只模拟两样东西：

**① Prefill 时间曲线**（离线 profile 拟合，占位数据待真实标定）：

| prefill tokens | 时间 |
|---:|---:|
| 4K | 30 ms |
| 8K | 55 ms |
| 16K | 105 ms |
| 32K | 205 ms |
| 64K | 410 ms |

近似线性 ≈ 6.4 μs/token → 单 worker 饱和能力 ≈ 156K tokens/s。实现为查表 + 分段线性插值。

**② 每个 worker 一个 FCFS Prefill 队列** + 背景负载采用 **reserved-capacity 模型**：背景占用 bg_gpu 的 GPU 时间，prefill 任务在剩余 (1 − bg_gpu) 容量上服务：

$$
T_{prefill}^{eff}(tokens) = \frac{T_{prefill}(tokens)}{1 - bg\_gpu}
$$

- bg_gpu 由实验场景配置（可分段变化），是 E1 的纵轴自变量
- worker 对外可观测：当前队列内排队任务的总服务时间（供策略估计 $T_{gpu\_queue}$）
- V0 **不模拟 decode**（理由与偏置方向见 §10）；TTFT 是唯一端到端时延指标

### 3.4 存储模型（本仿真最关键的组件）

**不要**写成 $T_{fetch} = KVBytes/BW$。要模拟的是：**nominal 带宽不变，有效服务能力动态变化**。

```text
B_total = 100 GB/s（固定 nominal）
B_bg(t) = 背景负载（分段常数，实验控制）
foreground 可用容量 cap(t) = max(0, B_total − B_bg(t))
```

**① Processor Sharing（并发 fetch 均分可用容量）**，而非单请求 FCFS：

n 个活跃 fetch 各分得 cap(t)/n；有传输完成后剩余的重新均分。这能自然模拟 incast 争抢。若需更真实，可加按 bytes 加权的选项（默认均分，记为配置项）。

**② 排队**：当 cap(t) 被完全占用且有 pending fetch 时，等待队列增长。fetch 的真实代价：

$$
T_{fetch}^{true} = T_{queue} + \frac{KVBytes}{share\_rate} + T_{base}
$$

- T_base 默认 5 ms（固定开销）
- **饿死角点**：B_bg(t) ≥ B_total 时前台完全饿死、队列无界增长。持续背景负载上限设 100 GB/s，瞬时（burst pattern）允许超过，这正是 static 策略爆炸、dynamic 策略切换的戏剧性场景。

**③ 背景负载模式**（实验的控制变量）：

| 模式 | 形状 | 用途 |
|---|---|---|
| stable | 常数 | E1 主扫（区分"系统性估计偏差"） |
| step / square-wave | 低↔高周期切换 | E1b（区分"时间性失配"，static 看不到变化） |
| burst | 短时尖峰超过 B_total | E4 |

### 3.5 双世界设计（Ground Truth vs 可观测状态）⭐

这是实验有效性的关键设计，**估计器与真实存储必须是两个对象**，否则 P2 ≡ P4，实验失去意义。

```text
┌─────────────────────────────┐        ┌─────────────────────────────┐
│      Ground Truth 世界       │        │       Compute 可见世界       │
│  storage.get_state()        │  每 Δms │  observable snapshot:       │
│  真实队列/份额/完成时刻      │ ──────▶ │  • 状态年龄 = Δms + 抖动     │
│  （仅 Oracle 可访问）        │  采样   │  • B_eff 经 EMA 平滑         │
│                             │        │  • 可加乘性噪声              │
└─────────────────────────────┘        └──────────┬──────────────────┘
                                                  │
                                       policies 读取此视图
                                       estimate_fetch_time(bytes)
                                       = queue_est + bytes/B̂_eff + T_base
```

- 默认观测参数：更新间隔 Δ = 50 ms，EMA 半衰期 100 ms，乘性噪声 lognormal σ = 0.1（E3 中全部变为自变量）
- Oracle（P4）读 ground truth 且可预测自身插入后的精确完成时间；P2 只能看陈旧视图
- 由此自然支持 E3 的"新鲜度 × 信号类型"扫描

### 3.6 请求生命周期（事件流）

```text
1. arrival
2. Global Scheduler 选 worker（P0–P2: KV-aware 固定规则；P3: cost 路由；miss 请求按 GPU 队列最短）
3. Engine 决策（仅命中请求）：
   ├─ fetch     → 提交 storage（进入 processor sharing）→ KV ready → 入 GPU 队列 prefill(suffix)
   └─ recompute → 直接入 GPU 队列 prefill(prefix + suffix)
   （miss 请求 → 直接 prefill(suffix)）
4. prefill 完成 → 记录 TTFT，请求结束（V0）
```

V0 简化：**fetch 提交后不可撤销**（没有 timeout 回退重算）。"超时回退"作为 P2b 可选变体（见 §4.6），若实现可单独消融。

## 4. 策略（Policy）

| 策略 | 决策层 | 看到的信息 | 决策规则 |
|---|---|---|---|
| **P0 Always Fetch** | engine | 仅 cache hit 与否 | 命中即 fetch（sanity baseline） |
| **P1 Static Cost** | engine | nominal 配置带宽、GPU 队列 | $\hat T_{fetch}=KVBytes/B_{nominal}+T_{base}$ vs $\hat T_{recompute}$，取小 |
| **P2 Dynamic Storage-Aware** | engine | §3.5 可观测存储视图 + GPU 队列 | $\hat T_{fetch}=T_{queue}^{est}+KVBytes/\hat B_{eff}+T_{base}$ vs $\hat T_{recompute}$，取小 |
| **P3 Storage-Aware Routing** | scheduler + engine | 同 P2，但 per-worker、per-backend | $Cost(i)=\min\{T_{fetch}(i),\ T_{recompute}(i)\}$，$i^*=\arg\min_i Cost(i)$，engine 执行被选动作 |
| **P4 Oracle** | engine（+routing 可选） | ground truth + 精确预测自身插入 | 永远选真实最快动作/worker |

**P4 实现说明**：仿真对给定状态是确定性的，Oracle 用与 storage 相同的 advance 机制在"假设我插入这个传输"的副本上计算精确完成时间（selfish 精确预测，不要求全局最优组合）。它的意义不是部署，而是量化"还有多少理论收益没拿到"。

**E2 附加 routing baseline**：Round-Robin、Load-aware（最短 GPU 队列）、KV-aware（最大命中 tokens，平手看负载）——对应现有系统（Dynamo 现状 ≈ KV-aware + load）。

**滞回（hysteresis）**：P2/P3 默认带简单滞回（动作切换需估计优势 > 10% 且持续 ≥ 2 个观测周期），防止所有 worker 同步抖动造成振荡；振荡本身用 flip-rate 指标监控（§5.4），滞回开/关作为消融项。

## 5. 指标体系

### 5.1 一级指标（判断方向成败）

| 指标 | 定义 | 用在哪 |
|---|---|---|
| **SLO Goodput** | 满足 TTFT ≤ SLO 的完成请求数 / 测量时长（req/s）。V1 起 加 TPOT 约束 | 所有实验主指标 |
| **TTFT P50/P95/P99** | 经验分位数 | 所有实验 |
| **Goodput Gain(P2,P1)** | $(G_{P2} − G_{P1}) / G_{P1}$ | **E1 核心热图量** |
| **Oracle Gap** | $\frac{G_{P4} − G_P}{G_{P4} − G_{P1}}$（分母 ≤0 时记 N/A） | 衡量 P2/P3 拿到了多少理论空间 |

### 5.2 二级指标（机制与资源侧写）

| 指标 | 定义 | 说明 |
|---|---|---|
| Throughput | 完成请求数 / 时长（不区分 SLO） | 与 goodput 的差 = SLO 违约量 |
| Fetch/Recompute 比例 | 随时间滚动的动作占比 | 机制展示（Fig B 主角） |
| Storage utilization | $(B_{bg} + 前台实际吞吐)/B_{total}$ | 事后核算实际 offered load |
| Storage queue depth | pending fetch 数 + inflight bytes | 时间序列 |
| Effective BW | cap/n_active 的实际分配率 | 时间序列 |
| GPU utilization | prefill 占用 / 可用容量 | 时间序列 |
| GPU prefill queue | 排队任务数 / 排队服务时间 | 时间序列 |
| KV fetch bytes 总量 | Σ 被取回的 KV 字节 | 资源转移量："存储字节被重算替代" |
| Recompute tokens 总量 | Σ 重算 token 数 | GPU 代价 |

### 5.3 诊断指标（正确性与鲁棒性）

| 指标 | 定义 | 回答什么 |
|---|---|---|
| **动作一致率** | P2 所选动作与 P4 事后最优动作一致的比例 | 预测错误的来源是噪声还是结构 |
| **Misroute 率（E2）** | 被路由进热点 backend 但 oracle 会选别处的请求比例 | locality 是否放大热点 |
| **Flip rate** | 每 worker 每秒动作切换次数 | 振荡检测 |
| **公平性 Jain index** | 按 prefix 类别的 goodput 公平指数（V1 起） | 动态策略是否牺牲某类请求 |

### 5.4 统计方法

- **多种子**：默认 10 个种子，报告均值 ± 95% CI（t 分布）；热图取种子中位数
- **Common Random Numbers**：同一种子下所有策略共享同一条到达 trace 与背景负载 schedule（公平对比的前提，实现为 per-seed 生成 trace 后重放）
- **预热剔除**：前 20 s 的事件不进统计；运行至 ≥ 20,000 请求或 300 s
- 时间序列采样间隔 10 ms，落盘 parquet

## 6. 实验设计

### 6.1 E1：动态存储压力 × GPU 余量（go/no-go）

**目的**：证明"实时存储状态信息"本身有价值，而非"允许重算"有价值。

**因子设计**（两个自变量都通过**背景负载**注入，与前台流量解耦）：

- 横轴：背景存储负载 B_bg ∈ {0, 20, 40, 60, 80, 100} GB/s
  （前台恒定 ≈37 GB/s → 实际 offered load ≈ 37%–137%）
- 纵轴：背景 GPU 负载 bg_gpu ∈ {20%, 40%, 60%, 80%, 90%}
- 策略：P0 / P1 / P2 / P4，CRN 同 trace
- λ = 5 req/s，4 workers，1 storage，prefix 分布按 §3.2

**E1a（stable）**：B_bg 恒定。区分的是"系统性估计偏差"——static 只会 nominal/100GB/s，dynamic 知道当前只剩 20GB/s。

**E1b（square-wave，第二轮）**：B_bg 在 (mean−40, mean+40) GB/s 间以 60 s 周期方波切换（瞬时峰值 140 GB/s > B_total，制造短暂饿死）。区分的是"时间性失配"。只在 E1a 高增益对角线附近取 3×3 子网格。

**主输出（Fig A）**：

```text
        Goodput Gain: P2 vs P1 (%)
GPU bg
 20% │   4  15  35  52  63  55
 40% │   3  10  30  52  61  55      ← 预期收益区：
 60% │   2   8  20  35  42  36         存储 offered ≥80%
 80% │   0   1   3   7  10   6         且 GPU bg ≤70%
 90% │   0   0   1   2   3   1
     └──────────────────────────
       37  57  77  97 117 137   ← storage offered load (%)
```

（数字为假设占位。）叠加 +10% 等高线与 oracle-gap 标注。

**判读**：收益区不存在 → no-go；收益区存在且在现实可达负载范围内 → 通过，进入 E2/E4。

### 6.2 E2：存储热点下的 Routing（V1）

**目的**：验证 **"cache locality amplifies storage hotspots"** —— KV-aware routing 为追求命中把请求推进拥塞存储，形成正反馈；storage-aware routing 能否打破。

**拓扑**：4 workers、2 backends（w0,w1 → S_A；w2,w3 → S_B）。

**场景构造**：热点 prefix A 只存在于 S_A；B 两边都有；长尾类别对半。S_A 背景负载 80 GB/s（HOT），S_B 10 GB/s（IDLE）——KV locality 与存储压力**刻意冲突**。

**对比策略**：Round-Robin / Load-aware / KV-aware（≈Dynamo 现状）/ **KV+Storage-aware（P3）** / Oracle。

**输出（Fig C）**：各策略 goodput、P95 TTFT 分组柱状图；S_A vs S_B queue depth 时序（展示 KV-aware 的热点放大 vs P3 的削峰）；misroute 率。

### 6.3 E3：信号设计（接口需求文档）

**目的**：直接回答"存储侧应该暴露什么 API、需要多实时"——本实验的结论就是未来 LMCache/存储层接口的验收标准。

在 E1 最高增益格点（默认 bg=80 GB/s, gpu_bg=40%）做三因子：

| 因子 | 取值 |
|---|---|
| 信号类型 | 仅 utilization / 仅 queue depth / 仅 effective BW / **cost quote（完整估计）** |
| 更新间隔 | 0（完美实时）、10、50、100、200、500、1000 ms |
| 乘性噪声 σ | 0、0.1、0.3 |

**输出（Fig D）**：四条"增益 vs 新鲜度"曲线（每信号类型一条）+ 噪声虚线。

**期望得出的工程结论**（示例格式）：*"cost quote 在 100 ms 新鲜度下保留 ≥90% 收益 → 不需要 per-request 强同步 RPC，周期性状态广播即可"*，或相反。

### 6.4 E4：Burst / KV restoration incast（附加）

**目的**：放大展示动态策略对尾延迟的保护，最贴近生产价值（真实存储问题常是"瞬时 100 个 KV 恢复打到同一 backend"，而非"24 小时只有 20GB/s"）。

**设置**：λ=5 req/s 稳态运行 120 s → t=120 s 起 1 s 内注入 150 个 A 类请求（同一热点 32K prefix）→ 观察 60 s 恢复期。策略 P0/P1/P2/P3/P4 全对比。

**输出（Fig B，四联时序图）**：

```text
面板1: B_bg(t) 与 storage queue depth    —— 突发发生、队列暴涨
面板2: fetch/recompute 比例              —— static 继续 fetch；dynamic 切重算
面板3: storage 有效带宽 / GPU utilization —— 瓶颈转移可视化
面板4: 滚动 P95 TTFT                     —— static 爆炸、dynamic 压回
```

另报：窗口内 P95/P99 TTFT、storage queue 峰值、恢复时间（滚动 P95 回落到基线 1.2× 以内所需时间）。

### 7.3 关键接口

```python
class SharedKVStorage:
    """Ground truth 世界。Oracle 之外任何策略不得调用 get_state()。"""
    def submit_fetch(self, req_id: int, kv_bytes: int) -> simpy.Event: ...
    def get_state(self) -> StorageState:              # 真实状态（仅 P4）
        ...
    def advance_to(self, t_now: float) -> None: ...
    def hypothetical_fetch_time(self, kv_bytes: int) -> float:
        """P4 专用：假设'现在插入该传输'，按当前份额与已知未来 B_bg
        计算精确完成时间（在副本上模拟，不改动真实状态）。"""

class StorageObservable:
    """Compute 可见世界。独立进程每 Δms 采样 ground truth。"""
    def snapshot(self) -> ObservableState: ...         # 含状态年龄、EMA B_eff
    def estimate_fetch_time(self, kv_bytes: int) -> float:
        """T̂ = queue_est + bytes / B̂_eff + T_base，可加乘性噪声。
        与 hypothetical_fetch_time 是两个对象 —— 这是实验有效性的前提。"""

class Policy(Protocol):
    def decide(self, req: Request, view: WorkerView) -> Action: ...
    # WorkerView 聚合：本 worker GPU 队列估计 + 所属 storage 的 ObservableState
```

### 7.4 Processor Sharing 的事件驱动实现

分段恒定速率下的精确流体模型。任何改变速率或集合的事件（fetch 提交 / fetch 完成 / B_bg 变化 / 观测采样 tick）都先调用 `advance_to(t)`：

```python
def advance_to(self, t_now):
    dt = t_now - self.last_t
    cap = max(0.0, self.B_total - self.B_bg_at(self.last_t))
    if self.active:
        rate = cap / len(self.active)          # 均分（可配置按 bytes 加权）
        for tr in self.active:
            tr.remaining -= rate * dt
        # remaining <= 0 者：按比例回推出精确完成时刻，触发完成事件
    self.last_t = t_now
```

事件循环：每次 advance 后，在当前速率下重算各传输的**最早完成时刻**，用 `simpy.Environment.timeout` 调度下一次 advance+完成。由于速率分段恒定，完成时间是精确的（非近似）。

**不变量（单元测试断言）**：

1. 字节守恒：Σ(实际传输字节) ≤ cap × dt + ε（任意区间）
2. remaining 永不为正误差累计（完成即移除）
3. 同种子完全确定性（diff 结果文件逐字节一致）
4. 单传输无背景时完成时间 = bytes/B_total + T_base ± 1e-6
5. 策略单调性 smoke test：E[G_P4] ≥ E[G_P2] ≥ E[G_P1] ≥ E[G_P0]（在探索网格上应成立，违反 = bug）

## 10. 已知简化与偏置方向（写论文/汇报时要声明）

| 简化 | 偏置方向 | 缓解 |
|---|---|---|
| V0 不模拟 decode | **高估**重算收益（重算占满 GPU 会恶化 TPOT，V0 看不到） | V2 加入 P/D 与 TPOT；M1 结论只声明 TTFT/goodput |
| fetch 不可撤销（无 timeout 回退） | 低估动态策略收益（真实系统可中途放弃） | P2b 消融变体 |
| prefill 曲线占位数据 | crossover 位置不准，但**相对比较**（P2 vs P1）稳健 | 真实 GPU microbenchmark 替换后重跑 |
| 均分 processor sharing（非加权） | 高估大传输延迟、低估小传输 | 加权选项 + LMCache 标定 |
| 无网络/RDMA 拓扑细节 | 存储路径单瓶颈假设 | 由 B_eff 吸收；LMCache L2 吞吐（submit→complete 端到端）可标定 |
| suffix 固定 1K | 减少变量 | 后续换真实 trace（ShareGPT/BurstGPT/生产 trace） |

## 11. 标定路径与真实系统对接

1. **模拟器标定**：LMCache 已暴露 L1↔L2 端到端吞吐（含 adapter queue + 网络 + 磁盘 I/O）、inflight L2 loads/stores、L2 usage——恰好对应本仿真的 $B_{eff}$ 与 $T_{queue}+T_{IO}$。用其微基准数据拟合 `storage.py` 参数。
2. **GPU 标定**：目标卡上跑 vLLM prefill microbenchmark（4K–64K），替换 PrefillCurve 表。
3. **落地映射**：Dynamo KV-aware router 现有 cost = KV overlap + tier credit + load；本工作即**再增加一项 storage service cost**。E2/E3 结论直接成为该改动的需求说明。Engine 侧对应 vLLM/SGLang 的 fetch-vs-recompute 决策与（可选）timeout 回退。

```text
Simulation ──找收益区域──▶ LMCache 真实测吞吐/队列 ──校准──▶ 原型（Dynamo + LMCache + vLLM）
```
