## 问题⑫：预取条目的缓存保护与准入

### 问题定位

浪费机制（E17a）：快会话的预取条目在使用前被大类（21.5GB 的 D）churn 挤掉、下轮再预取——
"搬得越勤，白搬越多"。LRU 的驱逐依据是最近使用时间，对"即将被使用"的预取条目失明。

### 方案（E18 面板 A）

`LocalKVCache` 增加两个机制（`PrefetchConfig.protect=True` 启用）：

1. **活跃会话保护**：预取器维护"快会话活跃类"集合（该类最近观察到的会话轮间隔 < horizon），
   这些类的条目在驱逐时优先豁免（全被保护时退回 LRU，防死锁）。
2. **预取准入**：预取前检查目标缓存——若 空闲 + 可回收（非保护）字节 < 预取字节，则跳过
   （避免预取本身触发驱逐连锁）。

E18a 变体：gated（基线）/ session（E17a 复检）/ **protect** / **session+protect**。
**假设 H12**：protect 使浪费率 ≤ 0.5 × gated，goodput 不降。

### 验收标准

- waste(protect) ≤ 0.5 × waste(gated) 且 goodput ≥ gated − 1%；
- 保护不造成容量死锁（无异常、n_arr 覆盖率正常）。

## 问题⑬：流体最优批分配（离线上界的可实现形态）

### 问题定位

E9b/E14 的先知是 list-scheduling 启发式；"未来视线换不来 goodput"的结论需要
一个**渐近最优**的对照才稳固。同步 burst 场景下，流体松弛有闭式解。

### 方案（E18 面板 B）

`ClairvoyantFluid2`：检测同步 burst（horizon 内同类命中 ≥ 20）时，按流体最优把批请求
在两类车道间按吞吐比例分配——GPU 车道吞吐 λ_g = Σ_w rate_w / t_prefill，
存储车道吞吐 λ_s = Σ_replicas cap_t / kv_bytes；分配比例 x* = λ_g/(λ_g+λ_s)。
非 burst 时退化为逐请求 Oracle。E18b（E9b 场景）对比：
joint2 / oracle2 / clairvoyant2(list) / **clairvoyant-fluid**。
**假设 H13**：fluid 的 burst 窗口 makespan/SLO 率 ≥ oracle2（至少持平，P99 显著改善）。

### 验收标准

- win_slo(fluid) ≥ win_slo(oracle2) − 1pp，且 win_p99(fluid) < win_p99(oracle2)；
- 若不成立，"启发式先知已够好"的结论升级为"流体最优也不占优"。
