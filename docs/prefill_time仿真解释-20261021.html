三句话结论

  • 这套脚本回答一个问题：一个请求（或一批请求）做 prefill，芯片要算多久、要从存储搬多少 KV 缓存。它不算排队，不算网络，只算芯片上一层流水线的纯计算时间。
  • 旧版把「逐字生成答案」的公式拿来算「一次算完新输入」，漏掉随新 token 数增长的全部注意力计算，还漏掉两道工序。修正后，真实 trace 上的 prefill 时延估计变为旧版的 2.4 倍。
  • 修正版与教科书公式逐项对账通过。但它是「理想车间」的下界：真实生产系统还要慢 2 到 3 倍。用它比较方案快慢可信；用它报绝对时间，必须先校准。

0术语

本文的专用词都在本节定义。定义按本文用法写。读者只读本文即可，不需要别的材料。

token ／词元
模型读写的最小文字单位。一个汉字约等于一到两个 token。
上下文 ／context
一次请求里已有的全部 token。模型回答问题前，先读完整段上下文。
prefill ／预填充
把新收到的输入 token 一次算完。本文仿真的对象。输入越长，prefill 越久。
decode ／解码
答案逐字生成。每个步骤只算一个新 token。本文仿真不算 decode。
层 ／layer
模型的计算单元。GLM5 有 78 层，全部串行。数据穿过 78 层，答案才出来。
注意力 ／attention
每层的工序之一。每个新 token 回看上下文，找出与它相关的部分，再合并信息。
MLA
注意力用的压缩记忆格式。每个 token 的记忆压缩成 576 个数。本文称这段压缩记忆为「KV 向量」。
KV 缓存 ／KV cache
已算过的上下文 token 的 KV 向量集合。存起来后，再次对话不必重算旧的部分。
前缀命中 ／prefix hit
新请求的上下文开头与缓存里已有的一段完全相同。命中的部分不用重算，但它的 KV 向量必须搬进芯片内存。
DSA 稀疏注意力
GLM5 用的省力版注意力。新 token 不回看全文，只看打分最高的 2048 个 token。打分由「索引器」完成。
索引器 ／lightning indexer
每层的小打分网络。它给上下文的每个 token 打一个分。之后取分数最高的 2048 个。
top-2048
每个新 token 实际回看的 token 数量上限。这是 DSA 的固定参数。
MoE 专家
每层有 256 个「专家」小网络。每个 token 只走 8 个，另加 1 个所有 token 都走的共享专家。选哪些专家由路由器决定。
NPU
算力芯片。本仿真用型号 D950PR：FP8 每秒 1024 万亿次乘加，FP16 每秒 512 万亿次，内存带宽每秒 1600 GB。
HBM ／高速内存
NPU 卡上的内存。权重和 KV 向量都放在这里。带宽每秒 1600 GB（十进制）。
FLOPs
浮点乘加次数。乘一次加一次计 2 次。做一道乘法题的工作量单位。
算力受限
一道工序的用时由「做多少乘加」决定。料已在手边，手速不够。
访存受限
一道工序的用时由「搬多少字节」决定。手速够快，等料。
roofline
本文仿真的核心公式。一道工序的用时取两个值的较大者：乘加数 ÷ 算力，字节数 ÷ 带宽。
kernel
芯片上执行一道工序的程序。启动一个 kernel 有 7 微秒固定开销。
DP ／数据并行
32 张卡各拿不同的请求，各算各的。每张卡存全部权重。
EP ／专家并行
256 个专家平摊到 32 张卡，每卡 8 个。token 的专家部分经互连总线送到专家所在的卡。
bs ／每卡 batch
一张卡同时 prefill 的请求数。脚本约定：bs 增大时，DP 卡数 = 32 ÷ bs。全局并发恒为 32 个请求重新分组。
input_length
trace 里的字段。上下文全长，单位 token。含本次的新 token。
u_tokens
trace 里的字段。本次要 prefill 的新 token 数。等于上下文全长减去命中的部分。

1这套仿真在算什么

一个请求到达时，上下文有两部分。前缀命中的部分不必重算，但它的 KV 向量要从存储搬进 HBM。新到的部分（u_tokens 个）必须逐层算完。这套仿真回答两个数：

  • 每层计算时间（微秒）。新 token 穿过一层流水线要多久。乘 78 层，得到这个请求的 prefill 计算时间。
  • 每层 KV 加载量（GB）。命中前缀的 KV 向量一共多少字节。这个数给存储调度研究用。

数据穿过一层，要经过 7 道工序。下图按真实比例画出典型工况（上下文 8192、新 token 512）下每道工序的耗时。

两个脚本只差一点：prefill_time_single.py 固定一张卡算一个请求；prefill_time_batch.py 允许一张卡同时算 bs 个请求，另给「一批长短不同的请求」的估法。两者的算子公式逐字相同。

2仿真原理

2.1 每道工序：roofline

每道工序的用时取两个值的较大者：

工序用时 = max( 乘加次数 ÷ 有效算力 , 搬运字节数 ÷ 有效带宽 ) ＋ 固定开销

有效算力 = 峰值 × 0.8。这个 0.8 是外部仿真器给的折扣，代表 kernel 级效率。固定开销含每次 7 微秒的 kernel 启动，和每 128 条数据一次的流水线下限。roofline 说的是：料少时等料（访存受限），料多时比手速（算力受限）。交点在「每份权重摊到 320 个 token」附近。这个数有公式：算力 ÷（2 × 带宽）＝ 320。

2.2 两个输入怎么影响工序

输入字段与各工序的关系（逐 token 的工作量）
工序乘加量由什么决定每 token 每层乘加精度
① 索引器投影固定17 MFLOPsFP8
② 打分新 token 数 × 上下文全长（唯一的二次项）65（上下文 8k）到 536（64k）FP8
③ 取 KV最多 2048 条，且不超过上下文—（按字节计）FP8 字节
④ 注意力核心固定：2048 条 × 64 头 ×（576＋512）维285 MFLOPsFP16
⑤ MLA 投影固定：6 个投影矩阵330 MFLOPsFP8
⑥ 专家固定：9 个专家 × 3 个矩阵680 MFLOPsFP8
⑦ 通信新 token 数（卡间送取）—（按字节计）—

线性部分（①⑤⑥，加 dense 层的 MLP）折合每 token 乘以 79.6 亿次乘加，相当于激活参数 397 亿。同类的 DeepSeek-V3 是 370 亿。数量级一致。

2.3 bs 语义

脚本约定：bs 是每卡请求数。bs 增大时，DP 卡数按 32 ÷ bs 减少，全局仍是 32 个请求重新分组。两个后果：

  • 每卡的专家数变为 8 × bs。访存受限时，每卡要读的专家权重也变为 bs 倍。
  • 每卡的总 token 数 = bs × 新 token 数。计算量只随这个总数走，与分组方式无关。

因此，批处理只在访存受限区省时间。新 token 多的时候（算力受限），合批不省时间。这符合推理服务的常识：合批对逐字生成收益大，对长输入 prefill 收益小。

2.4 KV 加载量

命中前缀有 1408 字节每 token 每层（MLA 向量 1152 ＋ 索引 K 256）。全部 78 层相加，得到这个请求要从存储搬的总字节数。这个口径与仓库存储调度实验（E23 系列）一致。

3旧版仿真错在哪

旧版抄自外部仿真器（文件 GBK 编码，在 Python 3 下无法运行，已修）。除编码外，有三个大错误和三个小错误。每个错误写四项：错在哪、差多少、怎么发现、依据。

大错误一：拿「逐字生成」的公式算「一次算完新输入」（F1）

错在哪：旧版的打分、取 KV、注意力核心都不随新 token 数增长。那是 decode 的算法：每步只算一个 token。prefill 的新 token 有几百到几万个，每个都要打分、选 top-2048、做注意力。

差多少：上下文 8192、新 token 512 的工况，注意力加索引侧从 64 微秒变为 657 微秒（每层）。这是三个错误里影响最大的一个。

依据：DeepSeek-V3.2 报告（arXiv:2512.02556）；vLLM 官方博文 2025-09-29；FlashMLA 仓库的接口（每个 token 各带一份 2048 选中项）。

大错误二：漏了两道工序（F10），注意力口径也错（F11）

错在哪：其一，一层里 6 个投影矩阵（把数据送进注意力、再送回来）完全没算。其二，注意力核心按「每头 192＋256 维」数乘加，但它读的料是 576 维压缩格式。按真实 kernel 的口径（576＋512 维），乘加量是旧口径的 2.1 倍。

差多少：投影每 token 每层 3.3 亿次乘加，占线性工序的三分之一。两项合计，旧版少算全部乘加的四分之一到三分之一。

依据：MLA 定义见 DeepSeek-V3 报告（arXiv:2412.19437）；kernel 口径见 FlashMLA 稀疏 prefill 接口（输入 576 维，输出 512 维）。

大错误三：打分结果的写回量高估 16 倍（F9）

错在哪：旧版按「32 个头各写一份打分」计字节。真实 kernel 在内部把 32 个头加成一个分。每个（新 token，上下文 token）对只写一个数，不写 32 个。

差多少：长上下文工况，这一项从每层 1686 微秒变为 341 微秒。修正后这项只由乘加决定，写多少字节不再影响结果。

依据：DeepGEMM 仓库的 mqa_logits 说明（输出形状是二维，头在 kernel 内归约）。

三个小错误
编号错在哪差多少
F5 单位字节数按 1024 进制折算，带宽按 1000 进制给。两种进制混用。访存项低估 7%
F6 因果性打分一律扫全文。第 i 个新 token 只看得到它前面的部分。首轮长输入高估到 2 倍
F4 通信前 3 个 dense 层没有专家，却计了专家互连通信。3 层，量小

6怎么知道修对了

验证脚本 prefill_time/validate_prefill_time.py 一次运行产出全部证据。四道对账全部通过：

  1. 与教科书对账。独立数每道工序的乘加和字节，再算理论时间。算力受限区，脚本 ÷ 理论 = 1.000 到 1.07。多出的部分是固定开销，逐项可解释。
  2. 极限行为。三段式曲线的换挡点落在解析值 320（见图 2）。公式是 算力 ÷（2 × 带宽）。
  3. bs 自洽。每卡专家计算时间 ÷ bs 恒定。「bs 个请求各 ut 个新 token」与「1 个请求 ut×bs 个新 token」在算力受限区比值 1.00 到 1.05。
  4. 外部锚点。模型 FP16 有效算力 409.6 TFLOPS，与昇腾 950 上的实测 410 同值（见 5.2 表）。

回归测试：仓库全量 pytest tests/ 240 个用例通过，用时 488 秒。本次改动不进入 sim/ 与 tests/ 的任何代码路径。

7怎么用

# 单请求：每行输出 per_layer_us（每层微秒）与 per_layer_kv_gb（每层 GB）
python prefill_time/prefill_time_single.py [trace.jsonl]

# 每卡 batch=4 跑同一条 trace（bs 超过 8 会告警）
python prefill_time/prefill_time_batch.py [trace.jsonl] 4

# 不带参数：默认读 mooncake_trace/derived/conversation_trace.jsonl.hit.jsonl

代码调用：per_request(input_length, u_tokens, bs) 返回每层时间与每层 KV 字节；per_batch([(il1, ut1), (il2, ut2)], bs) 给长短混合的一批，按最长请求对齐计算（padding 上界），KV 按各请求精确求和。

输入 jsonl 必须含 input_length 与 u_tokens 两个字段。本仓库两套 trace 的口径：Mooncake 每 512 token 一块，AgentX 每 64 token 一块。容量与缓存结论不得跨 trace 互推。
