三句话结论

  • GLM5 的全部计算都是矩阵乘。矩阵乘的代价只由形状决定。形状全部写在模型配置里。所以每个 token 的计算时间可以事先数出来——这就是仿真成立的原因（§2）。
  • 旧版把「逐字生成」的公式拿来算「一次算完新输入」，又漏掉两道工序。修正后，真实 trace 上的 prefill 时延估计变为旧版的 2.4 倍（§4、§5）。
  • 修正版与教科书逐项对账通过。但它是「理想车间」：不含排队与调度，真实生产系统再慢 2 到 3 倍（§6）。比较方案可信；报绝对时间必须先校准。

0术语

本文的专用词都在本节定义。读者只读本文即可。

token
模型读写的最小文字单位。一个汉字约等于一到两个 token。
上下文
一次请求里已有的全部 token。模型回答前，先读完整段上下文。
prefill ／预填充
把新收到的输入 token 一次算完。本文仿真的对象。
decode ／解码
答案逐字生成。每个步骤只算一个新 token。本文仿真不算 decode。
层
模型的计算单元。GLM5 有 78 层，串成一列。数据穿过 78 层，答案才出来。
隐状态
一个 token 在模型内部的表示：6144 个数组成的向量。每层把它变换一次。
矩阵乘 ／GEMM
一组数乘一张权重表，得到一组新数。模型的全部计算由它拼成。
FLOPs
浮点乘加次数。乘一次加一次计 2 次。做一道矩阵乘的工作量单位。
FP8 / FP16
每个数占 1 字节 / 2 字节的浮点格式。
峰值算力
芯片每秒乘加次数的上限。D950PR：FP8 每秒 1024 万亿次，FP16 每秒 512 万亿次。
NPU
算力芯片。本仿真用型号 D950PR。
HBM
NPU 卡上的高速内存。权重和缓存都放在这里。带宽每秒 1600 GB（十进制）。
kernel
芯片上执行一道工序的程序。启动一个 kernel 有 7 微秒固定开销。
注意力 ／attention
每层的第一块。token 之间在这里交换信息：带着问题去查上下文。
头
注意力里并行的 64 套打分与加权。各自有自己的问句。
MLA
注意力用的压缩格式。一个 token 在一层的记忆压成 576 个数。
KV 向量
一个 token 在一层的压缩记忆：576 个数。全体上下文的 KV 向量合称 KV 缓存。
摘要
一个 token 留给打分器看的 128 个数。打分只看摘要，不看全文。
DSA 稀疏注意力
GLM5 的省力版注意力：先给全文打分，每个新 token 只细看分数最高的 2048 个 token。
索引器 ／lightning indexer
每层的打分网络。给每个（新 token，旧 token）对打一个分。
top-2048
每个新 token 实际细看的 token 数上限。DSA 的固定参数。
MoE 专家
每层的第二块：256 个「专家」小网络。每个 token 只走 8 个，另加 1 个共享专家。
路由器 ／router
每层开头的小网络。按 token 的隐状态挑 8 个专家。
DP ／数据并行
32 张卡各拿不同的请求。每张卡存全部权重。
EP ／专家并行
256 个专家平摊到 32 张卡，每卡 8 个。token 经互连总线送到专家所在的卡。
bs ／每卡 batch
一张卡同时 prefill 的请求数。脚本约定：bs 增大时 DP 卡数 = 32 ÷ bs，全局并发恒为 32 个请求重新分组。
算力受限 / 访存受限
一道工序的用时由乘加数决定（料在手边，手速不够），或由搬运字节数决定（手速够快，等料）。
roofline
本文仿真的核心公式。工序用时取较大者：乘加数 ÷ 算力，字节数 ÷ 带宽。
input_length / u_tokens
trace 的两个字段。前者是上下文全长（含新 token），后者是本次要算的新 token 数。

1模型长什么样

要理解仿真，先要看清两件事：一个 token 在一层里走什么路；这条路要经过哪些矩阵乘。本节从零讲结构。

1.1 全景：78 层的塔

模型是一个函数：读一段 token，写出下一个 token。内部是 78 层完全相同的结构，串成一列。一个 token 进入模型后，不再是一个字，而是 6144 个数，叫隐状态。每层把隐状态变换一次。第 78 层之后，隐状态接词表，变成下一个 token 的概率。

1.2 一层的内部：两条路

隐状态进入一层后，先走注意力块，再走专家块，离开时仍是 6144 个数。注意力块让 token 之间传信息：新 token 带着问题，去查旧 token 的记忆。专家块对每个 token 独立加工：查完的信息在这里深度变换。两块都是矩阵乘的堆叠。

1.3 prefill 与 decode 走同一条路，但人数不同

prefill 一次送来 u_tokens 个新 token。每个新 token 都要完整走一遍这 7 步：都要造问句、都要给全文打分、都要选 top-2048、都要过专家。这是理解旧版错误的钥匙：token 数量翻倍，这条路的计算量就翻倍。

decode 每次只有 1 个新 token 走这条路。旧版仿真抄来的公式，正是按「每次 1 个 token」写的。

2为什么时间可以这样算

2.1 全部计算都是矩阵乘，矩阵乘的代价只由形状决定

一条路再长，也只是矩阵乘的串联。一次矩阵乘的代价由两个数完全决定：

乘加次数 = 2 × 输入个数 × 输出个数
搬运字节 = 权重（输入个数 × 输出个数 × 每数字节）＋ 激活（输入 ＋ 输出）

输入个数、输出个数都写在模型配置里，是常数。所以每个新 token 在每层触发的乘加次数与搬运字节，全部可以事先数出来。芯片速度也是常数。时间 = 工作量 ÷ 速度。没有别的来源。

手算一遍：第 5 步的 o 投影（每个 token）。输入 64 头 × 256 数 = 16384 个数，输出 6144 个数，权重用 FP8（每数 1 字节）。

乘加次数 = 2 × 16384 × 6144 = 2.01 亿次
权重字节 = 16384 × 6144 × 1 字节 ≈ 100.7 MB
时间上限一 = 2.01 亿 ÷ 8192 亿/秒 = 0.246 微秒   （有效算力 = 峰值 1024 × 0.8）
时间上限二 = 100.7 MB ÷ 1280 GB/秒 = 0.079 微秒   （有效带宽 = 1600 × 0.8）
o 投影用时 = max(0.246, 0.079) = 0.246 微秒       （算力受限）

仿真器对每道工序做同样的三行计算，全部工序相加，再乘 78 层。这就是仿真的全部原理。

2.2 roofline：先等料，还是先比手速

一次矩阵乘的时间取两个上限的较大者。token 少时，权重读是主导：一张 100 MB 的权重表，摊给 1 个 token 还是摊给 1000 个 token，差别巨大。token 多时，乘加是主导：每个 token 的乘加数固定，加 token 只加手速时间。换挡点在「每份权重摊到 320 个 token」，公式是 算力 ÷（2 × 带宽）＝ 320。

2.3 三个为什么

问题答案
为什么每个新 token 的计算量相同？同一条路、同一批矩阵。路里唯一的变量是上下文长度：它只影响第 2 步打分。
为什么上下文变长，只有注意力侧变贵？第 2 步要给每个旧 token 打分：乘加 = 新 token 数 × 上下文全长。专家块只看当前 token，与上下文无关。
为什么一层的工序可以直接相加？工序串行，一层的时间是各工序时间之和。78 层结构相同，再乘 78。

3.3 两个脚本与 bs 语义

prefill_time_single.py 固定一张卡算一个请求。prefill_time_batch.py 允许一张卡同时算 bs 个请求。两者的算子公式逐字相同。

bs 的语义要看清：bs 增大时，DP 卡数按 32 ÷ bs 减少。全局仍是 32 个请求重新分组，每卡本地专家数变为 8 × bs。后果有两条：

  • 每卡的 token 总数 = bs × 新 token 数。计算量只随这个总数走，与分组无关（守恒检查见 §7）。
  • 访存受限时，每卡要读的专家权重变为 bs 倍。所以批处理只在访存受限区省时间。

3.4 KV 加载量

命中前缀的每个 token 每层 1408 字节（压缩记忆 576 数 × 2 字节，加摘要 128 数 × 2 字节）。78 层相加得到总加载量。这个口径与仓库存储调度实验（E23 系列）一致，供存储侧研究用。

4旧版仿真错在哪

旧版抄自外部仿真器（文件 GBK 编码，在 Python 3 下无法运行，已修）。对照 §1.2 的结构图，三个大错误和三个小错误都落在具体位置上。

大错误一：把「每次 1 个 token」的公式用于「一次 ut 个 token」（F1）

结构位置：①②③④ 全部。§1.3 说过，每个新 token 都要完整走一遍这条路。

错在哪：旧版的打分、取记忆、注意力核心不随新 token 数增长。那是 decode 的算法（每次 1 个 token）。prefill 的新 token 有几百到几万个。

差多少：上下文 8192、新 token 512 的工况，注意力加索引侧从 64 微秒变为 657 微秒（每层）。三个错误里影响最大。

依据：DeepSeek-V3.2 报告（arXiv:2512.02556）；vLLM 官方博文 2025-09-29；FlashMLA 接口（每个 token 各带一份 2048 选中项）。

大错误二：漏了第 ⑤ 步的投影（F10），第 ④ 步口径也错（F11）

结构位置：⑤ 的 6 个矩阵没算；④ 按「每头 192＋256」数乘加，但读的料是 576 维压缩记忆。

错在哪：6 个投影矩阵全部漏掉。第 ④ 步的真实 kernel 在压缩空间工作（576＋512 维），乘加量是旧口径的 2.1 倍。

差多少：投影每 token 每层 3.3 亿次乘加，占线性工序三分之一。两项合计，旧版少算全部乘加的四分之一到三分之一。

依据：MLA 定义见 DeepSeek-V3 报告（arXiv:2412.19437）；kernel 口径见 FlashMLA 稀疏 prefill 接口（输入 576 维，输出 512 维）。

大错误三：打分写回量高估 16 倍（F9）

结构位置：② 的收尾动作——把分数写回内存。

错在哪：旧版按「32 个头各写一份分数」计字节。真实 kernel 在内部把 32 个头加成一个分。每个（新 token，旧 token）对只写一个数。

差多少：长上下文工况，这一项从每层 1686 微秒变为 341 微秒。修正后这项只由乘加决定。

依据：DeepGEMM 仓库的 mqa_logits 说明（输出是二维，头在 kernel 内归约）。

7怎么知道修对了

验证脚本 prefill_time/validate_prefill_time.py 一次运行产出全部证据。四道对账全部通过：

  1. 与教科书对账。独立数每道工序的乘加和字节，再算理论时间。算力受限区，脚本 ÷ 理论 = 1.000 到 1.07。多出部分是固定开销，逐项可解释。
  2. 极限行为。三段式曲线的换挡点落在解析值 320（见 §2.2 图）。
  3. bs 自洽。每卡专家计算时间 ÷ bs 恒定。「bs 个请求各 ut 个新 token」与「1 个请求 ut×bs 个新 token」在算力受限区比值 1.00 到 1.05。
  4. 外部锚点。模型 FP16 有效算力 409.6 TFLOPS，与昇腾 950 实测 410 同值（见 §6.2）。

回归测试：仓库全量 pytest tests/ 240 个用例通过，用时 488 秒。本次改动不进入 sim/ 与 tests/ 的任何代码路径。

8怎么用

# 单请求：每行输出 per_layer_us（每层微秒）与 per_layer_kv_gb（每层 GB）
python prefill_time/prefill_time_single.py [trace.jsonl]

# 每卡 batch=4 跑同一条 trace（bs 超过 8 会告警）
python prefill_time/prefill_time_batch.py [trace.jsonl] 4

# 不带参数：默认读 mooncake_trace/derived/conversation_trace.jsonl.hit.jsonl

代码调用：per_request(input_length, u_tokens, bs) 返回每层时间与每层 KV 字节；per_batch([(il1, ut1), (il2, ut2)], bs) 给长短混合的一批，按最长请求对齐计算，KV 按各请求精确求和。

输入 jsonl 必须含 input_length 与 u_tokens 两个字段。本仓库两套 trace 的口径：Mooncake 每 512 token 一块，AgentX 每 64 token 一块。容量与缓存结论不得跨 trace 互推。
