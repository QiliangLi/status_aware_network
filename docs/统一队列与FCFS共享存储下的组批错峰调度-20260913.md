# 统一队列与 FCFS 共享存储下的组批错峰调度

| 项目 | 约定 |
|---|---|
| 研究问题 | 通过 batch 成员选择、领取顺序与开始时刻，改变全局读取竞争和计算节奏 |
| 队列组织 | 调度器维护唯一的请求等待队列，实例完成一批后再领取下一批 |
| 存储纪律 | 按读取提交顺序优先满足申请速率，余量继续分给后续读取 |
| 主要目标 | 分别优化全部完成时间、SLO 满足率、平均 TTFT、平均归一化 TTFT |
| 解释指标 | 全局 NPU Compute、STALL、Idle 与存储带宽利用率 |
| 文档范围 | 独立的问题分析、形式化模型、复杂度论证、求解方法与实验设计 |
| 数值性质 | 算例采用公开列出的假设参数，不代表实测性能或已证明的最优调度 |
| 日期与单位 | 2026-09-13；秒、十进制 GB、GB/s |

## 1. 现在要决定什么

**调度器决定哪些请求一起执行，以及什么时候让空闲实例领取这一批。存储按固定 FCFS 规则响应由这些决定产生的读取。**

```text
请求到达 → 调度器统一等待队列
                    ↓ 空闲实例领取一个合法 batch
              开始执行并读取第一层 KV
                    ↓
              本层计算与下一层读取重叠
                    ↓
              整批完成 prefill，产生首 token
                    ↓
              实例再次向调度器领取 batch
```

组批影响计算效率，也影响每层需要多少数据、多久后消费这些数据。领取时刻决定读取进入存储 FCFS 序列的位置。一批较大的首层读取，可能排在其他实例稍后发起的下一层读取之前，使后者不能及时开始计算。

这里的“错峰”包括改变批次组成、先启动哪一批，以及必要时让空闲实例暂缓领取。它不要求所有实例永远避开并发读取。当多个批的申请速率之和不超过可用带宽时，并发执行可能正好合适。

### 1.1 完整假设与能力边界

| 条件 | 本文设定 |
|---|---|
| KV 可见性 | 所有实例看到相同全局 KV 目录，消除 worker 本地命中优势 |
| KV 读取 | 所有命中的前缀 KV 均从共享存储读取，无主动重算、跨请求读取去重或本地缓存短路 |
| 放置与选源 | KV 放置固定，采用单副本或所有策略相同的固定选源规则，不优化复制和缓存迁移 |
| 等待请求 | 只在调度器保留输入和元数据，不预先派发，不提前读取 KV |
| 实例状态 | 每个实例最多一个活动 prefill 批，无本地等待批；本批完成后才领取下一批 |
| 层间流水 | 开始执行时读取第一层；计算第 $\ell$ 层时最多加载第 $\ell+1$ 层 |
| 批执行边界 | 主模型采用完整 prefill 批，本层成员的 KV 齐备后执行本层批计算；成员在最后一层完成后产生首 token |
| 有限容量 | 固定模型、共同最大请求数与 token 预算、共同容量检查；需要保留的 KV 不能因按层计算就假设立即释放 |
| 计算资源 | 同构实例、固定模型与并行配置，使用分配给 prefill 的固定资源；其他任务的影响固定或共同建模 |
| 请求完成 | 统计到首 token，不模拟逐 token decode；首 token 输出的固定开销可并入末层 |
| 公平比较 | 所有策略共享执行能力与申请速率规则，不拒绝或丢弃困难请求来提高满足率 |
| 信息边界 | 普通调度器只用请求信息、计算 profile 与存储可观测反馈；存储内部真值和未来 trace 单列为 Oracle 或离线参考 |

相比允许本地等待与改派的架构，统一队列消除了“已派发却未执行”的状态，因而本模型无需 re-schedule。相比可优化存储优先级的架构，FCFS 服务规则固定，优化变量集中到全局组批和开始时刻。这两项是研究范围的明确调整。

整批同步是本文声明的执行模型。若实际引擎支持把已就绪成员拆出来单独计算，应将“拆批”作为所有策略共同拥有的新能力重新比较。不能在一个方案中使用整批等待，在另一个方案中默认成员独立完成。

只看 prefill 时，所得吞吐称为 prefill 完成吞吐或 prefill goodput。完整生成吞吐还受后续阶段约束，不由本模型直接保证。

## 2. batch 为什么能够提高计算效率

### 2.1 请求数量与 token 数是不同维度

设请求 $i$ 命中前缀长度为 $H_i$，尚需执行 prefill 的后缀长度为 $U_i$。一个批 $\mathcal B$ 的请求数、实际计算 token 数和 attention 工作量代理分别为

$$
n_{\mathcal B}=|\mathcal B|,\qquad
T_{\mathcal B}=\sum_{i\in\mathcal B}U_i,
$$

$$
A_{\mathcal B}=\sum_{i\in\mathcal B}
\left[U_iH_i+\frac{U_i(U_i+1)}2\right].
$$

$A_{\mathcal B}$ 数的是因果 attention 的 query-key 对，忽略固定的头数、维度等乘数。后缀里的每个 token 既访问已有前缀，也访问本次后缀里不晚于自己的 token。不同请求之间不做交叉 attention。

因此，“一个长请求”必须说明长在哪里。$H_i$ 大意味着需要读取较多 KV，也会增加后缀 attention 的上下文；$U_i$ 大意味着较多新 token 的线性层和 attention 计算。长命中、短后缀可以是读多算少，短命中、长后缀也可以是读少算多。

| 批的区别 | 即使其他维度相同，也可能改变什么 |
|---|---|
| 请求数不同 | 请求管理、变长序列元数据和小 kernel 数量 |
| $T_{\mathcal B}$ 不同 | 线性层矩阵乘规模、并行度和权重访问摊销 |
| $H_i,U_i$ 分布不同 | attention 的计算量、访问量及 kernel 形状 |
| 最长序列和长度差异不同 | padding 浪费、变长 kernel 的负载分布 |

一个含 16 个很短后缀的批，未必比一个长后缀请求提供更多矩阵乘工作。把“batch size”只写成请求数，会隐藏主要的计算差异。

### 2.2 计算收益主要来自更合适的矩阵形状

对固定的线性层，多个请求的后缀 token 可以沿 token 维拼接，使用共同的权重执行矩阵乘。粗略地，计算量随 $T_{\mathcal B}$ 增长；小矩阵可能受启动开销、权重访问及并行度限制，增大 token 维可以降低每 token 时间。足够大后，硬件进入饱和区，继续加请求主要增加批耗时。

NVIDIA 的矩阵乘与全连接层性能指南说明了矩阵形状、算术强度和 tile 数量对效率的影响。这里借用机制，不把某一 GPU 的饱和阈值直接套到 NPU。[NVIDIA 矩阵乘指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)、[全连接层指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-fully-connected/index.html)

可用以下分解帮助建立 profile，而不将它当作未经标定的精确性能公式

$$
c_{\mathcal B\ell}
\approx t_{\mathrm{launch}}(n_{\mathcal B})
+t_{\mathrm{linear}}(T_{\mathcal B})
+t_{\mathrm{attention}}(\{H_i,U_i\}_{i\in\mathcal B})
+t_{\mathrm{other}}(\mathcal B).
$$

其中每个 kernel 内可用计算量与本地访存量的 roofline 关系解释性能。这里的本地 HBM 带宽属于计算 profile；本文调度的共享存储带宽是另一项资源，二者不能混用。

prefill 本身已包含多个 token，单请求也可能使硬件充分忙碌。SARATHI 在其指定模型和 GPU 上观察到部分 prefill 配置在 batch=1 时已接近计算饱和，扩大 batch 后每 token 时间变化较小。该结果说明不能预设所有 prefill 都有很大的组批收益。[SARATHI，§3.1 与图 3](https://www.microsoft.com/en-us/research/uploads/prod/2023/09/sarathi_preprint.pdf)

### 2.3 长短混合是否浪费计算，取决于执行方式

使用 padding 的实现可能把短序列补齐到批中最长序列，带来额外工作。使用 packed 或变长 attention 时，不应再按“请求数乘最长长度”计算全部有效 token，也不能把批中所有 token 当成一条大序列计算 attention。

即使消除了 padding，长度差异仍可能影响 kernel 的分块、负载分配和调用开销。准确做法是固定实际使用的实现，测量每层或整次 prefill 的耗时表

$$
c_{\mathcal B\ell}=g_\ell(n_{\mathcal B},T_{\mathcal B},\{H_i,U_i\}).
$$

同一批相对成员单独执行的计算加速为

$$
\gamma_{\mathcal B}
=\frac{\sum_{i\in\mathcal B}\sum_\ell c_{\{i\}\ell}}
{\sum_\ell c_{\mathcal B\ell}}.
$$

$\gamma>1$ 表示有效计算耗时减少，但这只计算 kernel 时间。等待组批、KV 读取和其他实例受到的影响，均需在端到端评价中补上。

### 2.4 batch 应当怎么设

应配置共同的可行范围，再由调度器选择实际成员和大小。

| 配置 | 用途 | 建议确定方法 |
|---|---|---|
| 最大请求数 $n_{\max}$ | 限制请求管理与批内绑定规模 | 扫描请求数并测量开销、尾延迟 |
| 最大计算 token 数 $T_{\max}$ | 限制一次计算规模 | 找每 token 耗时趋于平缓的区间 |
| 容量可行检查 $\operatorname{Fit}(\mathcal B)$ | 确保模型、所需 KV 与工作区放得下 | 使用固定实现的容量核算，保留必要 KV |
| 长度组合规则 | 控制 padding 或变长 kernel 效率 | 对相同 token 数的不同长度组合测量 |
| 最长组批等待 $\tau_{\mathrm{batch}}$ | 防止低流量下为了凑批无限等待 | 按业务时延预算设置，所有策略相同 |

主模型不切 chunk，因而每个请求自身必须能够满足 token 与容量限制。超出限制的请求不能被静默丢弃，应在模型扩展时明确分块及 KV 保留规则。

vLLM 的文档区分 token 预算与请求数维度，并说明 token 预算会影响执行粒度及性能。本文沿用“按 token 管理计算规模”的思想，不复制其包含其他阶段的完整调度纪律或直接采用其默认参数。[vLLM 性能调优](https://docs.vllm.ai/en/latest/configuration/optimization/)

实际组批可按三步进行。先剔除不满足容量和 token 预算的组合，再依据 profile 保留计算效率有差异的候选，最后按选定的全局目标比较立即派发与短暂等待。没有足够计算收益时，单请求执行应始终是合法候选。

## 3. FCFS 按需分配的精确定义

### 3.1 三种带宽量分别表示什么

| 符号 | 含义 |
|---|---|
| $V_f$ | 读取 $f$ 必须传输的数据量，单位 GB |
| $q_f$ | 读取提交时声明的申请速率，单位 GB/s |
| $b_f(t)$ | 存储在时刻 $t$ 实际分给该读取的速率 |
| $q_f^{\mathrm{need}}$ | 为赶上计算消费时限所需的速率，是分析量 |

FCFS 按**读取提交时间**排序，不能按请求最初到达时间排序。后续层的读取只有合法提交后才能进入该序列。

将当前未完成读取按提交时间和固定同刻平局规则排序为 $f_1,\ldots,f_m$。在单共享瓶颈容量 $\beta(t)$ 下

$$
b_{f_k}(t)=\min\left(q_{f_k},
\left[\beta(t)-\sum_{j<k}b_{f_j}(t)\right]_+\right).
$$

早提交的读取先获得其申请速率，余量继续分给后面的读取。它不要求队首独占链路，也不按请求平均分带宽。所有读取均申请不低于链路容量时，才退化为队首独占。

读取完成、读取新提交或容量变化时重新分配，已有读取保持原顺序。由这个规则可知

$$
\sum_f b_f(t)=\min\left(\beta(t),\sum_f q_f\right).
$$

这是相对于申请速率的尽力服务。若总申请速率低于物理容量，存储不会擅自超额发送。因而有未完成数据，也可能出现带宽未满；必须区分申请不足和容量竞争。

### 3.2 申请速率必须有明确来源

FCFS 分配规则本身没有定义 $q_f$，仍需给出统一的申请规则。为使模型与算例可复现，本文采用以下**建模具体化**，所有候选调度共享该规则。

设实例入口速率上限为 $P_w$。首层没有前一层计算可供掩盖，因此尽快读取；后续层按前一层的计算窗口申请速率

$$
q_{\mathcal B1}=P_w,\qquad
q_{\mathcal B\ell}=\min\left(P_w,
\frac{V_{\mathcal B\ell}}{c_{\mathcal B,\ell-1}}\right),\quad\ell\ge2.
$$

本文假设计算耗时严格为正，申请速率在一次读取期间固定。若因为 FCFS 排队而未拿到足额速率，该层可能迟到，随后仍按原申请速率完成。调度器不能为某个策略临时提高申请值。

这条规则使“按计算需要申请”成为可检验机制，但它是补充的执行约定，不是 FCFS 的数学定义，也不是已核实的引擎默认行为。另一项必要的敏感性对照是所有层始终申请 $P_w$。若实现支持在读取过程中按剩余数据和剩余时间更新申请，也须统一更新规则，并作为另一组执行模型比较。

因此，后文公式允许一般给定的 $q_f$；数值算例与指定算法的理论界使用本节的固定申请规则。

### 3.3 FCFS 下，一个新批如何影响其他实例

在上述固定申请规则下，一个新提交到队尾的读取不会减少排在它前面的读取已获速率。它会占用剩余带宽，并可能挡住**随后才提交**的其他实例下一层读取。

所以全局影响包含未来的提交次序。仅观察“当前还有多少带宽”不足以决定是否领取新批。还需要观察其他实例何时结束本层计算、何时发起或消费下一层读取，以及新批的读取在那时是否仍未完成。

存储纪律已经固定，不再搜索 SLO 优先、短读取优先或按 NPU 状态重排服务。调度器通过组批和领取时刻间接改变进入 FCFS 的读取序列。

## 4. 长短合批降低了什么，又牺牲了什么

### 4.1 数据量不会因为合批减少

固定模型的每层每 token KV 大小为 $\kappa_\ell$，则

$$
v_{i\ell}=H_i\kappa_\ell,\qquad
V_{\mathcal B\ell}=\sum_{i\in\mathcal B}v_{i\ell}.
$$

在不去重、不压缩、不重算的边界下，混合组批不会降低短请求的 $v_{i\ell}$。它可能改变的是读取需要在多长时间内完成。

短请求 S 单独计算时，下一层无等待需求约为 $v_{S\ell}/c_{S,\ell-1}$。放入混合批后，可用计算窗口变为 $c_{\mathcal B,\ell-1}$，将其读取量摊到这个窗口的需求为

$$
q^{\mathrm{need}}_{S\mid\mathcal B,\ell}
=\frac{v_{S\ell}}{c_{\mathcal B,\ell-1}}.
$$

只有当混合批计算窗口更长时，这个值才降低。它是对短请求的归因，存储实际服务的是整批读取流，其申请值取决于 $V_{\mathcal B\ell}$。不能把短请求的归因速率降低，直接称为全系统带宽需求降低。

例如 S 每层读 1 GB、算 1 s，L 每层读 4 GB、算 2 s，混合批每层算 2.25 s。短请求的窗口需求由 1 GB/s 降为约 0.444 GB/s；整批窗口需求却为 $5/2.25\approx2.222$ GB/s。它比 S 独占时大，比两个单请求在各自计算窗口同时读时的需求之和小。比较对象与时间窗口必须明确。

还有一个方向相反的作用。若计算优化使相同批的 $c_{\mathcal B}$ 更短，而读量不变，则下一层无等待需求反而变大。**更快的计算可能暴露更多 I/O 等待，同时仍使端到端完成更快。**

### 4.2 短请求的 SLO 可能下降，但不必然下降

完整批中，短请求必须等共同的读取依赖和批计算完成。比较两种完整调度下的短请求完成时间

$$
\Delta F_S=(u_S^{\mathrm{mix}}-u_S^{\mathrm{sep}})
+(T_S^{\mathrm{mix}}-T_S^{\mathrm{sep}}).
$$

合批可能增加执行阶段时间，同时减少在统一队列中的等待，也可能获得足够大的计算加速。只有这些效应相加后为正，短请求才真正变慢。

对于绝对截止时间 $d_S$，满足率下降要求

$$
F_S^{\mathrm{sep}}\le d_S<F_S^{\mathrm{mix}}.
$$

如果两个结果都在截止时间内，SLO 满足与否不变；如果合批让它更早离开长队列，也可能改善 SLO。

两层、独占 4 GB/s 的上述例子中，S 单独执行需要 $0.25+1+1=2.25$ s，LS 混合批需要 $1.25+2.25+2.25=5.75$ s。4 s 的 SLO 会由满足变为不满足，6 s 的 SLO 则仍满足。这是执行阶段对照；在线调度还要加入两者不同的等待时间。

## 5. 一个完整的形式化问题

### 5.1 输入与调度变量

输入包括 $N$ 个请求、$W$ 个实例、$L$ 层模型，以及已定义的容量、profile 和 FCFS 规则。

| 输入 | 内容 |
|---|---|
| 请求 $i$ | 到达 $a_i$、命中前缀 $H_i$、后缀 $U_i$、SLO 时限 $s_i$ |
| 批能力 | $n_{\max}$、$T_{\max}$、$\operatorname{Fit}(\mathcal B)$ |
| 计算模型 | 每个合法批每层耗时 $c_{\mathcal B\ell}$ |
| 存储模型 | 每层读量、容量 $\beta(t)$、入口上限、共同申请函数与同刻事件规则 |
| 参考 TTFT | 固定的 $T_i^0>0$，所有策略使用同一分母 |

离线调度 $\sigma$ 选择请求集合的一个合法分批 $\{\mathcal B_b\}$，每批执行实例 $w_b$，以及领取并开始执行时间 $u_b$。不再包含实例本地排队次序或存储优先级变量。

$$
\bigcup_b\mathcal B_b=\{1,\ldots,N\},\qquad
\mathcal B_b\cap\mathcal B_{b'}=\varnothing\quad(b\ne b'),
$$

$$
|\mathcal B_b|\le n_{\max},\quad
\sum_{i\in\mathcal B_b}U_i\le T_{\max},\quad
\operatorname{Fit}(\mathcal B_b)=1,\quad
u_b\ge\max_{i\in\mathcal B_b}a_i.
$$

每个实例上的活动批区间 $[u_b,F_b)$ 互不重叠。请求直到 $u_b$ 才离开调度器队列，元数据领取成功后恰好由一个实例执行。

在线时，调度器只能从已到达且未领取的请求集合 $\mathcal Q(t)$ 中选批。离线解中的未来分配只是求解计划，不代表提前把请求放入某个实例队列。

### 5.2 从调度决定计算出全局时间线

对批 $b$ 的第 $\ell$ 层，定义读取提交时间 $A_{b\ell}$、就绪时间 $R_{b\ell}$、计算开始时间 $C_{b\ell}$ 和结束时间 $Z_{b\ell}$。

$$
A_{b1}=u_b,\qquad Z_{b0}=u_b,
$$

$$
R_{b\ell}=\inf\left\{t\ge A_{b\ell}\ \middle|\
\int_{A_{b\ell}}^t b_{b\ell}(x)\,dx\ge V_{b\ell}\right\},
$$

$$
C_{b\ell}=\max(R_{b\ell},Z_{b,\ell-1}),\qquad
Z_{b\ell}=C_{b\ell}+c_{b\ell},\qquad
A_{b,\ell+1}=C_{b\ell}.
$$

最后 $F_b=Z_{bL}$，批内请求 $F_i=F_b$，$TTFT_i=F_i-a_i$。实际速率 $b_{b\ell}(t)$ 由第 3 节 FCFS 递推确定。因而 $F_i$ 是整个调度 $\sigma$ 的函数。

若记 $x_{b\ell}=R_{b\ell}-A_{b\ell}$，则单批执行耗时仍有

$$
F_b-u_b=x_{b1}+\sum_{\ell=2}^L
\max(x_{b\ell},c_{b,\ell-1})+c_{bL}.
$$

这里的 $x$ 已包含共享竞争，不能在换批或错峰后继续沿用旧值。对主模型的单活动批实例，全部 I/O STALL 可按

$$
S(\sigma)=\sum_b\sum_{\ell=1}^L
\left(C_{b\ell}-Z_{b,\ell-1}\right)
$$

计算。首层启动读取也在其中。若将来允许其他批计算填补等待，上式只能表示批等待，必须重新按设备时间统计 STALL。

### 5.3 分别定义优化目标

设共同观测起点为 $t_0$，全部请求均需完成，$d_i=a_i+s_i$。

| 目标 | 形式化定义 |
|---|---|
| 最小全部完成时间 | $\min_\sigma M(\sigma)=\max_iF_i(\sigma)-t_0$ |
| 最大 SLO 满足率 | $\max_\sigma A(\sigma)=\frac1N\sum_i\mathbf1[F_i(\sigma)\le d_i]$ |
| 最小平均 TTFT | $\min_\sigma\bar T(\sigma)=\frac1N\sum_i(F_i(\sigma)-a_i)$ |
| 最小平均归一化 TTFT | $\min_\sigma\bar R(\sigma)=\frac1N\sum_i(F_i(\sigma)-a_i)/T_i^0$ |

固定请求集时，有限工作集吞吐为 $N/M$。最小化 $M$ 与最小化完成时间之和不同。SLO 可以是共同固定阈值 $s_i=s$，也可以是 $s_i=\alpha T_i^0$，实验分别评价。

$T_i^0$ 取单请求在无竞争资源上按共同执行规则运行的参考 TTFT。batch 可能改变计算效率，因此单请求参考值并非对所有 profile 都是理论最短时间。如果必须使用理论下界，应另行计算可证明的乐观下界并更名，不动态修改分母来吸收拥塞。

归一化目标等价于固定权重 $1/T_i^0$ 的完成时间之和，不能用 $\bar T/\overline{T^0}$ 替代。它更在意短参考时间请求的相对拖慢。总 stretch 文献采用响应时间除以独占处理时间，为这个指标提供了明确的调度学对应。[Srivastav 与 Trystram，§1](https://arxiv.org/html/1404.6502)

### 5.4 全局利用率与辅助指标

令 $K(\sigma)=\sum_b\sum_\ell c_{b\ell}$ 为有效计算 NPU 秒数，忽略控制开销的完整排空窗口内

$$
U_{\mathrm{cmp}}(\sigma)=\frac{K(\sigma)}{WM(\sigma)},\qquad
P_{\mathrm{stall}}=\frac{S(\sigma)}{WM(\sigma)},\qquad
P_{\mathrm{idle}}=1-U_{\mathrm{cmp}}-P_{\mathrm{stall}}.
$$

Idle 包含实例暂缓领取和某个实例提前完成全部工作后的尾部空闲。控制开销单独记为 Other，启用时一并进入时间守恒。

存储带宽利用率定义为

$$
U_{\mathrm{io}}(\sigma)=
\frac{\int_{t_0}^{t_0+M}\sum_f b_f(t)\,dt}
{\int_{t_0}^{t_0+M}\beta(t)\,dt}.
$$

常带宽、读取总量固定时，$U_{\mathrm{io}}=V_{\mathrm{total}}/(\beta M)$，提高它与降低 $M$ 等价。长期稳定开环中则不能这样外推，固定到达率与固定每请求读量会固定长期平均存储工作量。

若 $K$ 固定，最大化 $U_{\mathrm{cmp}}$ 也等价于最小化 $M$。**允许 batch 改变计算效率后，$K$ 不再固定。** 计算更高效的方案可能更早完成，却具有更低的 Compute 时间占比。因此主实验将 Compute、STALL、Idle 用作解释指标；若单独优化 $U_{\mathrm{cmp}}$，必须同时报告吞吐与时延，防止偏好耗时更长的低效批形状。

使用固定时长 $H$ 的稳态窗口时，利用率应改为窗口内 Compute 秒数除以 $WH$，不能将不同策略各自的排空窗口与固定窗口混在一张表中。

## 6. 一个动作的全局收益如何按目标定义

这里的动作 $a$ 包含给一个或多个空闲实例选择 batch，以及是否推迟领取。设继续原策略产生结果 $F_i^0$，采取候选动作并用同一后续策略完成剩余工作产生 $F_i^a$。两者针对相同请求集合、相同资源和外部到达。

统一规定 $\Delta>0$ 表示候选更好。

| 目标 | 候选动作的全局收益 |
|---|---|
| 全部完成时间 | $\Delta_M=M^0-M^a$ |
| SLO 满足率 | $\Delta_A=\frac1N\sum_i\left(\mathbf1[F_i^a\le d_i]-\mathbf1[F_i^0\le d_i]\right)$ |
| 平均 TTFT | $\Delta_T=\frac1N\sum_i(F_i^0-F_i^a)$ |
| 平均归一化 TTFT | $\Delta_R=\frac1N\sum_i(F_i^0-F_i^a)/T_i^0$ |
| 排空窗口计算利用率 | $\Delta_U=K^a/(WM^a)-K^0/(WM^0)$ |

固定窗口下最后一行改为 $(K_H^a-K_H^0)/(WH)$。不能在比较 batch 变化时把计算秒数当作不变量。

这些和式必须包括受到影响的其他请求，不能只算被选入当前批的成员。一次动作救回一个短请求但导致两个其他请求超时，其 SLO 净收益是 $-1/N$；降低某个实例 STALL 也可能只把等待转移成调度器队列等待。

SLO 是阈值目标。某请求从 20 s 降到 18 s，而截止时间为 10 s，对当次满足率贡献为零。在线预测存在误差时，可以采用

$$
\widehat A(a)=\frac1N\sum_i
\Pr(F_i^a\le d_i\mid\text{当前可观测信息})
$$

排序，并用平均 TTFT 或老化规则处理平局。但概率估计是替代目标，需要校准；不能把 EDF、最小余量或某个平滑打分直接称为最大满足率算法。

在线实现只预测已到达请求和声明的统计负载。若只展开部分队列，必须为剩余请求设置共同的后续完成规则或尾部估计。知道未来全部 trace 的离线比较单列，不能作为普通在线策略的信息输入。
