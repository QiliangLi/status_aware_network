MPC 方案图解

MPC（滚动预测控制，cq_mpc）是我们提出的共享 KV 存储调度方案。 它的核心想法一句话：每次要做决定时，把每个候选动作在"系统副本"里推演到所有请求完成， 比较结局，选结局最好的那个动作的第一步来执行——像下棋先在脑子里推演再落子。 本页用一个可以手算的小例子，一步步展示它怎么想、怎么算、依据什么公式。
本页自足。看懂例子需要的全部背景在 §1 预备知识（90 秒读完）； 所有数字都可以用 §1.4 的"手算钥匙"自己验算；动画在 §4； 公式汇总在 §7。不需要先读任何其他文档。

①预备知识：看懂例子需要的四个事实

1.1 一个请求 = "已缓存的前缀 + 要新算的部分"，计算逐层进行

大模型推理时，用户的问题往往有前人问过的部分——这部分 KV（注意力缓存）在共享存储上已经有了， 不用重算，但要读回来；只有新添的部分需要真算。我们记：

命中前缀 h
这些 token 的 KV 在共享存储上
→ 每层都要读 κ·h 字节
新 token u
这部分要真算
→ 计算量随 u 增长

模型有 L 层（本例 L=2）。一批请求被实例领取后，逐层执行下面的循环； 整批同进同出（"批屏障"：批里最后一个成员算完，大家才一起得到首 token）：

读第 ℓ 层的 KV→ 算第 ℓ 层→ 算的同时预读第 ℓ+1 层 → … 末层算完 → 整批完成，时刻记为 F

1.2 多个实例共用一条带宽，规则只有两条

所有实例的读取挤同一条总带宽 B（本例 B = 4 GB/s）。存储按提交顺序服务（FCFS），规则：

规则一（排队）：先提交的读取流先用带宽；排在前面的流拿满它申请的速率后，剩余带宽才给后面的。
规则二（申请率）：一个流最多申请"自己需要的速率"——下层读取的申请率 = 下层字节数 ÷ 本层计算时长 （刚好藏进计算窗口）；到本层算完还没读完，才提速到上限补读。

1.3 批：读字节相加、计算时间相加（本例无合批加速）

两条请求拼成一批后，每层的读取字节 = 两条相加，每层的计算时长 = 两条相加（我们例子里故意用 "无合批加速"的设定，让数字可手算）。所以"拼批"改变的是读的节奏和等待结构，不省计算。

1.4 手算钥匙（本例的全部数字都能这样验算）

对象每层读取每层计算算一遍
短请求 S（共 2 条：S0、S1）1 GB1 s读 1GB ÷ 4GB/s = 0.25s/层
长请求 L（共 2 条：L0、L1）4 GB2 s读 4GB ÷ 4GB/s = 1s/层
短批 SS（S0+S1）2 GB2 s读 2GB ÷ 4GB/s = 0.5s/层
长批 LL（L0+L1）8 GB4 s读 8GB ÷ 4GB/s = 2s/层
混批 LS（1短+1长）5 GB3 s读 5GB ÷ 4GB/s = 1.25s/层

期限（SLO）：短请求要求 6.75 s 内完成、长请求 15 s 内。F 超过期限 = 该请求"超时"。

②为什么这个问题难：你的决定会改变别人的速度

看 §1.2 的两条规则：谁先提交读取、申请多少速率，会改变其他实例实际拿到的带宽。 举例：t=0 两个实例都想开始读——

实例1 先提交、申请 4 GB/s（全部带宽）→ 实例2 的流申请率再高也只能排队，速率 0，干等；
实例1 只申请 1 GB/s（它的下层读取恰好只需要这么快）→ 实例2 立刻拿到 3 GB/s，两边同时前进。

所以"给哪个实例发哪批、要不要晚半秒再发"不是各自独立的决定，而是通过共享带宽互相耦合的。 简单规则（先来后到 FCFS、短优先 SPT、最早截止 EDF）只用一条排序键，看不见自己这一步对别人的影响， 也看不见未来。MPC 的目标就是把这两样补上。

③MPC 的想法与五步流程

每当"有空闲实例且队列非空"，MPC 就做一轮决策。它不是发明新排序键，而是直接比较结局：

第 0 步 · 先拿保底

基础策略 π = 带老化保护的 EDF 给出一个联合动作。它是参照系：候选必须严格更好才取代它。

例子里：π 说"两个实例都立即发同类批"（就是候选 A）。

第 1 步 · 重建预测世界

MPC 不许看系统内部真值，只能用可观测信息造一个"副本"：最新带宽报价（之后当常数用）、自己提交过的读取流进展、已到达请求的参数。

例子里：带宽恒为 4 GB/s，4 条请求全部已知，无未来到达——预测世界 = 真实世界（教学例的理想化）。

第 2 步 · 生成候选动作

从队列挑候选请求（四池轮询，最老必入），按同形/互补/紧迫三种顺序贪心填批；再逐空闲实例组合，并加入"等待"候选：

等待时长 ∈ {0.05, 0.1, 0.2} × C_ref
（C_ref=已到请求 T0 的中位数）

例子里：候选 A=同类批同发；B=两个混批；C=SS 立即发 + 实例2 等 0.5 s 再领 LL。

第 3 步 · 推演到排空并打分

每个候选在副本上落实，之后统一由 π 接管，直到当前所有请求完成，得到每条的完成时刻 F̂。按优化目标 θ 的词典序打分（§5）。

例子里：就是 §4 动画推演出的三张时间线。

第 4 步 · 门槛校验，只落第一步

最优候选的主目标必须严格小于保底动作，否则回落 π；无论推演多深，只执行第一个动作，下一个事件到来全部重来。预算 2 ms / 2 万事件。

例子里：若 θ=T，候选 C 严格更好 → 落子"实例1 发 SS，实例2 设 0.5 s 后领取"。

两个易误解点：① 推演用的排队/分层规则与真实引擎完全相同，但跑在预测世界上，估值可能错——所以要有第 4 步的门槛兜底； ② "等待"不是预订：请求始终留在中央队列，等待只是一个闹钟，任何新事件都能提前叫醒重评。

⑥为什么实验里 MPC 常常和 EDF 一模一样

我们的全量实验（7080 次运行）里，MPC 相对 EDF 的差别在四个目标、全部场景上都是 0.000。四个原因，每个都能在上面的例子里找到影子：

原因解释（对照本页例子）
保底太强π（EDF）在排队很深的系统里已接近时延最优。本页例子里 π 恰好就是候选 A——而 θ=T 时 A 与 C 只差 0.5s；真实负载里这种差距常为 0，"严格更好"不成立，MPC 就回落 π。
换批成员无利可图真实负载的批内新 token 远超计算饱和点，怎么拼都不省计算（本页例子干脆设为不省）——候选 B 那种"均衡"打法失去了计算收益的支撑，只剩同步损失。
等待等不来东西候选 C 的 0.5s 等待之所以值，是因为 SS 的下层流能插队保护。真实负载里带宽常不紧张（无流可保护）、或请求成批同刻到达（等一会儿不会来新请求）——等待就没有收益。
预算有限2 ms / 2 万事件只够浅推演，多数候选与保底打平，平局不切换。

反过来这四条也指明了 MPC 什么时候会有增量：带宽紧张且峰值打满（有旧流可保护）、突发之间有空隙（等得来请求）、短 token 负载（拼批有计算收益）、更松的门槛与更深的推演。

⑦公式速查（与代码实现一一对应）

打分：θ 的词典序元组（首项是主目标，其余只用来破平局）
θ=M: ( maxi F̂i , Σ TTFT )    θ=S: ( 超时条数 , Σ TTFT )
θ=T: ( Σ TTFT , 超时条数 )    θ=R: ( Σ TTFTi/T0i , Σ TTFT )   越小越好

对应 sim/cq/search.py: score_of()。F̂ 是推演到排空的预测完成时刻；TTFT = F̂ − 到达时刻；T0 = 该请求独占系统时的参考完成时间。

候选批的三种排序（对每个锚请求贪心填批，保留每个中间不满批）
同形: |log1p hi − log1p ha| + |log1p ui − log1p ua
互补: |log ri + log ra − 2·log rref| ，r = 读取量/计算量（读算比）
紧迫: ( 截止时刻, 到达时刻, 编号 )

排序后逐项尝试加入，第一项违反硬约束（≤8 请求 / ≤token 上限 / ≤内存）即停批。

等待候选与唤醒
wait ∈ now + {0.05, 0.1, 0.2}·C_ref ∪ {预测的读取完成时刻}，C_ref = median(T0)

纯等待必须有严格未来的唤醒时刻；请求留在中央队列，新事件可提前重评。

门槛、预算与回退
切换条件: 最优主目标 < 保底主目标 − gate（gate=0 ⇒ 必须严格改善）
预算: 2 ms CPU（软）· 20000 事件（硬）· 推演深度 H=1
超预算 / 推演不可排空 / 状态已失效 ⇒ 回落 π 并记账 fallback
