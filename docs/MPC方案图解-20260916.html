MPC 方案图解

MPC（滚动预测控制，cq_mpc）是我们提出的共享 KV 存储调度方案。 它的核心想法一句话：每次要做决定时，把每个候选动作在"系统副本"里推演到所有请求完成， 比较结局，选结局最好的那个动作的第一步来执行——像下棋先在脑子里推演再落子。 本页用一个可以手算的小例子，一步步展示它怎么想、怎么算、依据什么公式。
本页自足。看懂例子需要的全部背景在 §1 预备知识（90 秒读完）； 所有数字都可以用 §1.4 的"手算钥匙"自己验算；候选枚举在 §4；动画在 §5； 公式汇总在 §8。不需要先读任何其他文档。

①预备知识：看懂例子需要的四个事实

1.1 一个请求 = "已缓存的前缀 + 要新算的部分"，计算逐层进行

大模型推理时，用户的问题往往有前人问过的部分——这部分 KV（注意力缓存）在共享存储上已经有了， 不用重算，但要读回来；只有新添的部分需要真算。我们记：

命中前缀 h
这些 token 的 KV 在共享存储上
→ 每层都要读 κ·h 字节
新 token u
这部分要真算
→ 计算量随 u 增长

模型有 L 层（本例 L=2）。一批请求被实例领取后，逐层执行下面的循环； 整批同进同出（"批屏障"：批里最后一个成员算完，大家才一起得到首 token）：

读第 ℓ 层的 KV→ 算第 ℓ 层→ 算的同时预读第 ℓ+1 层 → … 末层算完 → 整批完成，时刻记为 F

1.2 多个实例共用一条带宽，规则只有两条

所有实例的读取挤同一条总带宽 B（本例 B = 4 GB/s）。存储按提交顺序服务（FCFS），规则：

规则一（排队）：先提交的读取流先用带宽；排在前面的流拿满它申请的速率后，剩余带宽才给后面的。
规则二（申请率）：一个流最多申请"自己需要的速率"——下层读取的申请率 = 下层字节数 ÷ 本层计算时长 （刚好藏进计算窗口）；到本层算完还没读完，才提速到上限补读。

1.3 批：读字节相加、计算时间相加（本例无合批加速）

两条请求拼成一批后，每层的读取字节 = 两条相加，每层的计算时长 = 两条相加（我们例子里故意用 "无合批加速"的设定，让数字可手算）。所以"拼批"改变的是读的节奏和等待结构，不省计算。

1.4 手算钥匙（本例的全部数字都能这样验算）

对象每层读取每层计算算一遍
短请求 S（共 2 条：S0、S1）1 GB1 s读 1GB ÷ 4GB/s = 0.25s/层
长请求 L（共 2 条：L0、L1）4 GB2 s读 4GB ÷ 4GB/s = 1s/层
短批 SS（S0+S1）2 GB2 s读 2GB ÷ 4GB/s = 0.5s/层
长批 LL（L0+L1）8 GB4 s读 8GB ÷ 4GB/s = 2s/层
混批 LS（1短+1长）5 GB3 s读 5GB ÷ 4GB/s = 1.25s/层

批的大小（batch size）有硬上限：本例每批最多 2 条请求（真实实验里是 8 条）。 所以 4 条请求无论怎么拼，最多同时组成 2 个"2 条批"，分给 2 个实例。

期限（SLO）：短请求要求 6.75 s 内完成、长请求 15 s 内。F 超过期限 = 该请求"超时"。

②为什么这个问题难：你的决定会改变别人的速度

看 §1.2 的两条规则：谁先提交读取、申请多少速率，会改变其他实例实际拿到的带宽。 举例：t=0 两个实例都想开始读——

实例1 先提交、申请 4 GB/s（全部带宽）→ 实例2 的流申请率再高也只能排队，速率 0，干等；
实例1 只申请 1 GB/s（它的下层读取恰好只需要这么快）→ 实例2 立刻拿到 3 GB/s，两边同时前进。

所以"给哪个实例发哪批、要不要晚半秒再发"不是各自独立的决定，而是通过共享带宽互相耦合的。 简单规则（先来后到 FCFS、短优先 SPT、最早截止 EDF）只用一条排序键，看不见自己这一步对别人的影响， 也看不见未来。MPC 的目标就是把这两样补上。

③MPC 的想法与五步流程

每当"有空闲实例且队列非空"，MPC 就做一轮决策。它不是发明新排序键，而是直接比较结局：

第 0 步 · 先拿保底

基础策略 π = 带老化保护的 EDF 给出一个联合动作。它是参照系：候选必须严格更好才取代它。

例子里：π 说"两个实例都立即发同类批"（就是候选 A）。

第 1 步 · 重建预测世界

MPC 不许看系统内部真值，只能用可观测信息造一个"副本"：最新带宽报价（之后当常数用）、自己提交过的读取流进展、已到达请求的参数。

例子里：带宽恒为 4 GB/s，4 条请求全部已知，无未来到达——预测世界 = 真实世界（教学例的理想化）。

第 2 步 · 生成候选动作

从队列挑候选请求（四池轮询，最老必入），按同形/互补/紧迫三种顺序贪心填批；再逐空闲实例组合，并加入"等待"候选：

等待时长 ∈ {0.05, 0.1, 0.2} × C_ref
（C_ref=已到请求 T0 的中位数）

例子里：候选 A=同类批同发；B=两个混批；C=SS 立即发 + 实例2 等 0.5 s 再领 LL。

第 3 步 · 推演到排空并打分

每个候选在副本上落实，之后统一由 π 接管，直到当前所有请求完成，得到每条的完成时刻 F̂。按优化目标 θ 的词典序打分（§6）。

例子里：就是 §5 动画推演出的三张时间线。

第 4 步 · 门槛校验，只落第一步

最优候选的主目标必须严格小于保底动作，否则回落 π；无论推演多深，只执行第一个动作，下一个事件到来全部重来。预算 2 ms / 2 万事件。

例子里：若 θ=T，候选 C 严格更好 → 落子"实例1 发 SS，实例2 设 0.5 s 后领取"。

两个易误解点：① 推演用的排队/分层规则与真实引擎完全相同，但跑在预测世界上，估值可能错——所以要有第 4 步的门槛兜底； ② "等待"不是预订：请求始终留在中央队列，等待只是一个闹钟，任何新事件都能提前叫醒重评。

④候选从哪来？——动画前的最后一块拼图

"候选"就是 MPC 此刻可以考虑采取的动作。它由两个维度组合出来： 怎么分批（哪些请求拼一批给哪个实例）× 什么时候发（立即，还是让某个实例等一会儿）。 本例只有 4 条请求、2 个实例、每批最多 2 条，所以可以把候选完整枚举出来：

维度一：分批方式（本质不同的只有两种）

分法内容谁会想到它
同类分批[S0,S1] 给实例1，[L0,L1] 给实例2（短归短、长归长）"同形"排序：把形状相近的请求排在一起逐个装批
混合分批[S0,L0] 给实例1，[S1,L1] 给实例2（每批一短一长）"互补"排序：倾向把读取重的和计算重的配对；另一配法 [S0,L1]+[S1,L0] 在本例数值完全等价（两条 S 相同、两条 L 相同），不再单列

（也有"先只发一批、剩两条留队列"的做法——它其实就是维度二里"另一个实例等一会儿"的变形，被下面覆盖了。）

维度二：发送时机（两种）

时机含义
同时发两个实例都在 t=0 领批（谁先提交读取流按实例编号排）
错峰发一个实例先发，另一个等 δ 再领。δ 的候选值：{0.05, 0.1, 0.2}×C_ref（C_ref=已到请求参考时长的中位数），以及"预测某条读取完成的时刻"——本例取 δ=0.5，正好是 SS 首层读完的时刻（§1.4：0.5s）

两个维度一组合 → 本页的三个候选

候选= 分批 × 时机一句话
A（同类）同类分批 × 同时发先来后到的直观做法；恰好也是保底策略 π（EDF）此刻的选择，所以它是"参照系"
B（混批）混合分批 × 同时发两批负载均衡，看谁能最快全部做完
C（错峰）同类分批 × 等 0.5 sMPC 的"等待"类候选：只晚半步，让 SS 的下层读流插到 LL 前面
真实系统里候选远不止三个：每轮从队列选最多 32 个候选请求、按三种排序生成最多 24 个候选批， 再逐空闲实例组合、附加等待候选，在 2 ms 预算内能推演几十个联合动作。本例只有 4 条请求， 恰好枚举得完，我们就挑这三个最有代表性的来展示机制：一个保底、一个换分法、一个换时机。

⑦为什么实验里 MPC 曾与 EDF 一模一样（20260917 审计更新）

全量实验（7080 次运行）中 MPC 相对 EDF 的差别一度在四个目标、全部场景上都是 0.000。 事后审计发现这不是"方案没用"，而是两个实现缺陷 + 一个预算设定叠加的结果——前两者已于 20260917 修复：

根因（按审计结论排序）解释与证据
R1 · 预算耗尽（真实 trace 主因）2 ms CPU 软预算低于单次基础排空推演的成本（审计实测：真实负载上单次 decide P50≈23 ms、P95≈45 ms）——候选循环在评分第一个候选前就被打断，n_scored=0。规格当年自己预警过"synthetic 服务很快、2 ms 可能明显超预算"。
R2 · 候选从排空态分支（实现缺陷，已修复）基础动作的推演把副本一路跑到全部完成，候选再从这个"已终结的世界"克隆——DISPATCH 验证必然失败，全体候选得分==基础动作，搜索从未真正分支。修复：候选一律从决策点原始状态克隆。
R3 · WAIT 被推演丢弃（实现缺陷，已修复）推演落实首动作时只处理 DISPATCH、跳过 WAIT，闭环 π 又会在同一时刻向等待的 worker 派批——等待候选的推演退化为立即派发，MPC 永远选不出等待。修复：_HoldPi 在唤醒时刻前保持该 worker 空闲（单测：WAIT@0.725 的推演 F=0.725+2.25，精确）。
R4 · cq_local 曾是占位（已实现）"独立带宽"评分消融曾与普通观察者行为完全相同——local≡mpc 是构造使然。现已实现独立带宽推演（每流各得 min(申请率, B̂)）：B=80 下与 MPC 差异 <0.1%（无竞争则建模无价值），B=20 竞争下 local 比 MPC 差 0.6pp——干扰建模的价值随竞争强度增长。
保底本身很强π（EDF）在 deadline∝T0 的负载里等价于 SPT，已接近时延最优；θ=S 的平局回退（本页落子步演示过）在真实负载里高频发生。

修复 + 放开预算后的验证（金标小世界与真实 trace 面板）：给足搜索预算时，MPC 确实产生增量——小世界 θ=T 找到 ΣTTFT −15.4%（26.63 vs 保底 31.5）、θ=M 找到比四计划最优 P3 还好的 M=8.51；真实 trace 上相对 EDF 的平均 TTFT 最高再降约 7%（相对 FCFS 合计 −34~−37%），代价是单次决策 P50≈23 ms / P95≈45 ms 的 CPU。也就是说：此前"MPC 没用"的结论主要是实现与预算问题，不是方案思想问题；剩余的边界条件（深队列耗尽 2 万事件预算、保底平局不切换、G≈1 无组批收益）才是方案层面真实的适用限制。

⑧公式速查（与代码实现一一对应）

打分：θ 的词典序元组（首项是主目标，其余只用来破平局）
θ=M: ( maxi F̂i , Σ TTFT )    θ=S: ( 超时条数 , Σ TTFT )
θ=T: ( Σ TTFT , 超时条数 )    θ=R: ( Σ TTFTi/T0i , Σ TTFT )   越小越好

对应 sim/cq/search.py: score_of()。F̂ 是推演到排空的预测完成时刻；TTFT = F̂ − 到达时刻；T0 = 该请求独占系统时的参考完成时间。

候选批的三种排序（对每个锚请求贪心填批，保留每个中间不满批）
同形: |log1p hi − log1p ha| + |log1p ui − log1p ua
互补: |log ri + log ra − 2·log rref| ，r = 读取量/计算量（读算比）
紧迫: ( 截止时刻, 到达时刻, 编号 )

排序后逐项尝试加入，第一项违反硬约束（≤8 请求 / ≤token 上限 / ≤内存）即停批。

等待候选与唤醒
wait ∈ now + {0.05, 0.1, 0.2}·C_ref ∪ {预测的读取完成时刻}，C_ref = median(T0)

纯等待必须有严格未来的唤醒时刻；请求留在中央队列，新事件可提前重评。

门槛、预算与回退
切换条件: 最优主目标 < 保底主目标 − gate（gate=0 ⇒ 必须严格改善）
预算: 2 ms CPU（软）· 20000 事件（硬）· 推演深度 H=1
超预算 / 推演不可排空 / 状态已失效 ⇒ 回落 π 并记账 fallback
