## 1. 工况定义（用户给定，不得更改）

| 参数 | 值 |
|---|---|
| NPU 数 m | **32**，同构，全局中央队列（任意卡领任意请求） |
| 模型层数 L | **8** |
| A 类请求 | 输入 128K token（命中前缀），重计算 256 token；**每层读取 175.65 MB，每层计算 6.02 ms** |
| B 类请求 | 输入 32K token，重计算 4096 token；**每层读取 38.5 MB，每层计算 28.59 ms** |
| 存储总带宽 B | **120 GB/s**（所有卡的读取挤这一条，FCFS 分配） |
| batch size | **1**（每批恰一条请求；`HardLimits.n_max=1`） |
| 请求配比 | A:B = **1:2**；总量 **1280 A + 2560 B = 3840 条**（"每卡 40A+80B"仅为比例示例，不绑定卡） |
| 用户给的带宽需求 | A 28.48 GB/s、B 1.31 GB/s（=V/c 口径；按给定 c、V 精确反推为 29.18/1.347，差 ~2.5%，判定为用户侧四舍五入——**本实验以 c、V 为准**，"带宽需求"作为派生校验量） |

**派生量（执行前先核对，见 §5 单测 U1）**：T0_A=49.62ms、T0_B=229.04ms（比值 0.217——SPT/EDF 会强烈偏向 A）；总读取 2587 GB → 排空下限 21.56s（纯传输）；每卡计算总量 20.22s → 计算利用率上限 93.8%；**4.1 条并发 A 流即打满 120**；32 卡同时跑 A 的需求 934 GB/s。

## 2. 为什么这个工况对目标有利（先验机制，写给执行者）

1. **存储是第一瓶颈且与计算几乎打平**：传输下限 21.56s vs 每卡计算 20.22s（93.8%）——任何"多张卡同时跑 A"的时刻带宽严重超订（需求最高 934 GB/s = 7.8×容量），FCFS 的 boost 洪水与 IO 等待将大面积出现。
2. **EDF/SPT 会主动加剧争抢**：T0_A 只有 T0_B 的 1/4.6，排序类把 A 全排前面 → 并发 A 数暴增 → 带宽互拖。**这是本工况里顺序类反而可能比 FCFS 更差的机制点**（甘特图上会非常直观）。
3. **local 的"独享带宽"想象错得极大**：它以为每条 A 流独享 120，而真实世界 4.1 条 A 就满——预测失真远大于 E25（E25 甜带里单流需求 ≈B/4，本工况 ≈B/4.1 且 A 占比 1/3，撞车频率高一个量级）。
4. **最优策略形态明确（可对照）**：控制"同时在跑的 A"≈3~4 条、其余卡跑 B，让带宽贴 120 不溢出、计算不空转——这是 MPC 推演能"看见"而 local/顺序类看不见的形状。

## 3. 计算画像标定（零引擎改动方案，精确复现两类数值）

现有引擎（`sim/cq/profile.py`）用 `c = t_launch + a·N/η(N) + b·A` 计算每层时长、`V = κ·h` 计算每层读取。**batch=1 时批计算=单请求计算**，因此可用"虚拟 h + 重标定 (a,b)"精确命中用户给定的 (c, V)，不需要改引擎：

```python
from fractions import Fraction as F
from sim.cq.config import ProfileConfig
# L=8；κ、t_launch、N_sat、eta_floor 全部用默认值
# A 类：h=42883, u=256   → V_A=0.175649 GB/层, c_A=6.0200 ms（精确）
# B 类：h=9399,  u=4096 → V_B=0.038498 GB/层, c_B=28.5900 ms（精确）
E26_PROFILE = ProfileConfig(
    L=8,
    a_s_per_token=F("1.627277e-6"),    # 标定解（s/token/层）
    b_s_per_pair=F("4.665208e-10"),    # 标定解（s/配对）
)   # 其余字段默认：κ=4.096e-6, t_launch=50e-6, N_sat=512, eta_floor=1/16
```

标定方程与验算（新会话执行 U1 单测时逐项对拍，容差 1e-9）：

```text
η_A = 256/512 = 0.5；A_A = 256×42883 + 256×257/2 = 11,011,344
η_B = 1（4096>512）；  A_B = 4096×9399 + 4096×4097/2 = 46,890,460
512·a + 11,011,344·b = 6.02ms − 50μs ； 4096·a + 46,890,460·b = 28.59ms − 50μs
→ a = 1.627277e-6 s/token/层， b = 4.665208e-10 s/pair
验算：c_A = 50μs + 512a + A_A·b = 6.0200 ms ✓   c_B = 50μs + 4096a + A_B·b = 28.5900 ms ✓
```

**语义说明（写进结果文档，不得隐瞒）**：虚拟 h 使注意力项吸收了一部分本属线性投影的计算——语义故事变了，但**对调度有意义的全部量（每层 c、每层 V、T0、deadline、读取协议行为）精确匹配**用户给定值；batch=1 保证了批内无混合。备选方案（实现 per-class 常数画像，改 `profile.py`）仅在标定方案出问题时启用，需另写单测。

**场景配置**：

```python
scn = CqScenario(
    scenario_name="e26_ab", profile=E26_PROFILE,
    storage=StorageConfig(b_schedule=((F(0), F(120)),), q_max_gbps=F(200),
                          b_ref_gbps=F(120)),   # T0 参考带宽=本场景带宽（单带宽实验，无需固定参考锚）
    limits=HardLimits(n_max=1, token_max=F(8192), workspace_gb=F(8)),
    m_workers=32, alpha_slo=F(α), source_kind="synthetic", trace_key="e26_ab")
```

q_max=200 说明：首层读取申请 q_max（引擎协议），预取申请=V/c（A 29.18 / B 1.347 GB/s，与用户"带宽需求"口径一致）；到期未读完 boost 到 200——这是引擎既定读取协议，对全部策略一致。

## 4. 负载与到达模式（D1、D2 两种都跑；CRN）

总量恒定 1280A+2560B。生成器放 `sim/experiments/e26_ab.py`，`RequestSpec(rid, arrival_s, h_tokens, u_tokens, class_id="A"/"B", ...)`，T0/deadline 由引擎管线生成（α×T0）。

**D1 分批持续到达（泊松）**：全局泊松到达，每条按 1/3 概率为 A、2/3 为 B（固定 seed=格点号，所有策略同一份流——CRN）。到达率按**存储饱和度**定标：E[每条总读取]=0.6737 GB → λ_sat=178 req/s（此时计算利用率 94%——双瓶颈同时逼近）。扫描：

| ρ_storage | 0.5 | 0.7 | 0.9 | 1.0 | 1.1 |
|---|---|---|---|---|---|
| λ (req/s) | 89 | 125 | 160 | 178 | 196 |

（到达期时长=3840/λ ≈ 43~20s；跑至排空。）

**D2 突发轮次**：每轮同时到达 96 条（32A+64B，恰为"每卡 3 条"的量），共 40 轮=3840 条；轮间隔 T_burst ∈ **{0.75, 1.0, 1.5}s**（每轮传输下限 0.54s：0.75≈准连续、1.0=轻间歇、1.5=明显间歇——覆盖"队列深浅交替"的甜带形态）。轮内次序固定（A、B 交错），CRN 同上。

可选扩展（首轮不跑，登记即可）：D3 背景 B 泊松 + 突发 A 轮次。

## 7. 验收标准（实验成功的定义）

1. **大幅提升之一（vs 基线）**：最优格点上 mpc 与 local 相对 FCFS 和 EDF，平均 TTFT 降幅 ≥20% 或 SLO 提升 ≥10pp（量级参照 E25 甜区 +6.5~31.8%；本工况带宽超订更狠，预期更高——达不到就按 §8 排查）。
2. **大幅提升之二（mpc vs local）**：θ=S 下 mpc 相对 local SLO ≥ +5pp 且 TTFT 不为负（"双赢"口径，参照 `实验结果-E25Q-…` §4 的判据与反例清单）；本工况 local 的失真应显著大于 E25（§2.3）。
3. **机制证据**：图 1/图 2 能用肉眼讲出故事（基线的红海与需求线冲天 vs mpc 的规整），且并发 A 数分布显示 mpc 把 p90 并发 A 压到 ≤5（4.1 条打满的工程含义）。
4. 若 1/2 未达标：按 §8 的排查树执行并如实记录（负结果也是结果，写进结果文档）。

## 8. 实施步骤、冒烟门槛与风险排查

**步骤**：①写 `sim/experiments/e26_ab.py`（场景/负载/策略循环/记录，注册 `sim/run.py` CLI `--exp e26`，参考 `sim/experiments/e25_factor.py` 的结构与 `sim/experiments/cq_common.py` 的工具）；②写 5 项单测；③图工具 `tools/e26_gantt.py`、`tools/e26_bw.py`；④冒烟；⑤全量 96 runs；⑥结果文档（仓库根 `实验结果-E26-AB双类带宽争抢-YYYYMMDD.md`，嵌两图+读法+分 A/B 指标+与前序衔接+局限+通俗版）。

**冒烟（必做，1 格点 D1/λ=160/α=8 ×6 策略）门槛**：a) 字节守恒零失败；b) 带宽饱和占比>0 且 IO 等待>0（瓶颈确实落在存储上——区分度检查）；c) **mpc n_scored>0**（未退化为 EDF）；d) FCFS 单 run <10 分钟、mpc 单 run <60 分钟（超了先降事件预算外的成本：D1 λ 降档/D2 减轮数，并记录）。

**风险与排查树**：
- **mpc≡edf（n_scored=0）**：队列过深把 2 万事件预算吃光 → 看 D1 高 λ 档与 D2 短间隔档；缓解=加大 `max_forecast_events`（如 20 万）并在结果文档注明口径；仍不行=降到浅队列格点（D2 间隔 1.5s）。
- **mpc 决策太慢**：32 卡触发决策频繁（每 run ~3840 次派发），D2 轮初队列 96 → 每决策 (1+候选)×~1500 事件；实测冒烟超门槛就减候选或预算。
- **EDF 反而比 FCFS 好（不加剧争抢）**：检查并发 A 分布——若 EDF 的 A 并发没有暴增，说明首层读取掩盖了 paced 差异，转向看 boost 行为；如实记录，机制解释放结果文档。
- **local≈mpc（差距<1pp）**：带宽超订是否真的发生（图 2 需求线是否长时间 >120）？若需求线不超，说明到达率太低——升 λ 或缩 D2 间隔；仍不行则 α 降 4（临界区变化）并报告。

**规范遵循**：CRN（同格点全策略同流）；信息边界不变（local/mpc 各用推演存储，普通策略只读可观测接口）；`results/` 不入库、`docs/figures/` 入库、图不覆盖既有正式图；每完成一个逻辑单元即提交推送（中文 conventional commit）；全量 pytest 绿再提交。
