## 一、先说结论

三句话：

1. **纲领可以照着干。** 它把"要证明什么、怎么证明、什么算成功、什么算失败"都提前写死了，而且把上一轮几个想当然的判断都纠正了。是仓库里迄今最完整的一份设计文档。
2. **但写第一行代码之前，有三个坑要先填**：新旧实验的关系没有盘点；纲领里最重要的"对手策略"在代码里还不存在；新仿真引擎（带 decode）工程量最大，边界没划清。这三件事分别见第五节。
3. **第一个里程碑建议**：补完三件事后，从纲领 §12.1 的最小闭环（R0→R2）做起，第一份"存储反馈到底值不值"的判决不晚于 R2 出来。

## 二、纲领到底在研究什么（两分钟版）

借用纲领第 14 节的厨房类比：

- 几间厨房（GPU 推理实例）共用一个半成品仓库（共享 KV 存储）。
- 来了一张订单（一个推理请求）：一部分备菜工作仓库里已经有现成的半成品（KV 命中）。这部分可以**去取**（fetch），也可以**自己做**（recompute）。
- 取要占货梯和走廊（存储带宽、共享网络），做要占厨师（GPU 计算）。
- **关键问题：货梯现在堵不堵，厨房隔着墙看不清。**

现状的默认做法是：仓库目录说"有货"，厨房就去取——哪怕货梯此刻被别人占死，所有订单一起排队。

纲领研究的就是：**把仓库的真实拥堵状态告诉厨房，能不能让整个系统接更多订单，或者让每桌客人等得更短？** 以及纲领比以前更严格的地方——**这个消息值不值得传、能旧到什么程度、应该交给谁用**。

特别注意：纲领要求先打赢"会记笔记的对手"。厨房自己记送货笔记（每次去仓库取货花了多久、走哪条路），时间长了也能估个八九不离十。如果光靠笔记就够了，那就不值得装实时看板。所以实验里必须有这个"会记笔记的厨房"当对手，而不是找一个永远相信货梯空闲的傻子对手。

### 类比 ↔ 术语对照表

| 厨房里的东西 | 术语 | 一句话解释 |
|---|---|---|
| 厨房 | worker | 跑模型的 GPU 推理实例 |
| 半成品仓库 | 共享 KV 存储 | 存放历史计算的中间结果 |
| 现成的半成品 | KV 命中（H） | 可以直接复用、不必重算的部分 |
| 去取 | fetch | 把 KV 从远端搬过来 |
| 自己做 | recompute | 重新计算生成这份 KV |

| 开席后连续上菜 | decode | 逐个生成输出 token |
| 多久上第一道菜 | TTFT | 首 token 延迟，用户感知的响应速度 |
| 后面每道菜的间隔 | ITL / TPOT | 生成阶段的流畅程度 |

| 实时看板 | 存储状态反馈 | 存储侧主动报告当前拥堵 |

## 三、纲领比之前想得更对的四个地方

这一节把纲领 §1.3 的修正表展开讲。每条按"以前怎么想 → 现在怎么想 → 为什么改"。

### 修正一：先看服务，再看机器忙不忙

以前的结果文档第一层看资源利用率（GPU 忙不忙、仓库忙不忙），第二层才看用户指标。纲领改成：**用户请求有没有按时完成，才是最终裁判**；利用率只用来解释收益和损失从哪来。

为什么改：重算会让 GPU 更忙。按旧口径，"重算多了 → 机器利用率高了 → 看起来不错"；但用户看到的可能是更多请求排队、更多超时。"机器很忙"不等于"用户更满意"。这个顺序不颠倒过来，后面所有实验都会朝错误方向解读。

### 修正二："100–500 毫秒反馈够用"降级为待验证假设

以前的结论是存储状态每 100–500 毫秒更新一次就够了。纲领改为：**这只是待验证的假设**，改用相对时间研究——看板数据的有效年龄，除以压力变化的快慢（纲领记作 d/τ）。

为什么改：看板半小时不更新，如果货梯拥堵是按天变化的，没关系；如果拥堵按秒抖动，同样半小时的看板就是废纸。答案取决于请求多大、压力变化多快，不是一个固定毫秒数能概括的。

### 修正三："协同只改善稳定性"也要重新验证

以前的结论：几间厨房同时冲向最空的货梯时，互相协调主要让系统更稳（少振荡、少羊群），不会让系统接更多订单。纲领改为**吞吐、稳定性、尾延迟分开检验**。旧结论只来自单一场景，不能排除其他负载组合下协调也能提高容量。

### 修正四：预取浪费要拆开查原因

以前认为预取浪费主要是"缓存留不住"——预测对了，但数据在用之前被挤掉了。纲领要求把四种原因分开统计：**预测错了 / 做完了但没用上 / 预测对但留不住 / 命中了但其实不省时间**。四种原因对应四种完全不同的改进动作，混在一个"浪费率"里就没法改进。

另外，纲领对两篇相关论文（Cascade、CacheFlow）的边界做了收紧：不再说人家"只处理本地存储"或"只是静态优化"，改为"机制归属保留，是否覆盖我们的反馈边需要进一步核查原文"。这个口径更安全，避免创新性声明被打脸。

## 四、纲领里最容易忽略、也最重要的一个洞察

纲领 §3.1 有一个反例，值得单独讲，因为它直接决定以后的负载怎么设计：

> 如果"要搬运的字节数"和"能省下的计算时间"都跟命中长度成正比，那么"取回还是重算"的结论**跟长短完全无关**。

打个比方：外面买半成品 10 元/斤，自己做成本 20 元/斤。买 1 斤划算，买 10 斤同样划算——比例没变。把同一个请求放大十倍（输入长十倍、命中长十倍、省的计算也长十倍），调度器该做的选择一模一样。

这意味着：**想在实验里看到"长命中更值得取回"（或反过来），差异必须来自别的东西**——比如固定的启动开销（再小的搬运也要握手）、GPU 上的排队竞争、deadline 约束。反过来，如果实验跑完发现长短命中的行为没差别，那不一定是 bug，可能只是负载里只有线性成分。

以后设计负载按纲领 §7 的正交设计来：输入长度、命中长度、输出长度三个维度独立变化，就能避开这个坑。

## 五、开工前必须先补的三件事

以下三件事都不改纲领的结论，但都影响实施效率和结论可信度。按优先级排。

### 5.1 第一件事：盘点旧实验，列一张"留 / 重跑 / 作废"表

**现状**：仓库里已有 E1–E18 十八组旧实验（E1–E4 是第一代仿真，E5–E18 是第二代）。新纲领把实验重新编号为 R0–R9。两边大量重叠，对应关系大致是：

| 新纲领实验包 | 研究的问题 | 最接近的旧实验 |
|---|---|---|
| R1 | 存储反馈比静态信息好在哪 | E1a / E1b / E3 |
| R2 | 长短混合 + 完整服务约束 | 无直接对应（旧世界没有 decode） |
| R3 | 状态该给路由器还是引擎 | E2 / E5 / E6 |
| R4 | 接口字段、时效与成本 | E3（时效部分） |
| R5 | 会不会羊群、要不要协调 | E4 / E9 |
| R6 | 部分恢复 | E7 |
| R7 | 缓存演化后结论还在吗 | E11 / E17 |
| R8 | 主动复制 / 预取 | E8 / E10 / E13 / E15 |
| R9 | 标定与迁移验证 | E16（参数敏感性部分） |

（这是帮助定位的粗对照，不是等价关系。）

**问题**：没有一张表说清楚，每条旧结论在"带 decode 的新世界"里是什么地位——可以直接继承？必须在 decode 下重跑？还是作废？

**风险**：两头浪费。要么把 decode 下可能不成立的旧结论直接搬过来用（纲领 §3.6 明确禁止这种做法），要么把已经证明过的机制在新世界重跑一遍，白白花掉机时。

**怎么补**：花半天写一页对照表，每条旧结论标三档之一——

- **继承**：结论在机制层面与 decode 无关（例如"陈旧反馈导致羊群"），可作为先验；
- **重跑**：结论可能被 decode 改变（例如所有"TTFT 收益"都要补问一句"是否以生成流畅度恶化为代价"）；
- **作废**：前提已经不成立。

### 5.2 第二件事：先把"会记笔记的对手"做扎实

**为什么这是第一优先级**：整个研究的第一份判决押在一个对比上——新的存储状态接口（实时看板）必须赢过"调度器自己记历史笔记"（纲领里的 History-Cost，也叫 I1 基线），才算有信息增量。

**现状**：我核实过 `sim/policies2.py` 和 `sim/quote.py`。现有策略里最强的是"读当前状态快照"的 joint2；协调策略 coord2 会记录自己已承诺的在途流量，算是有了半本笔记。但**按路径、按对象大小，从过去的传输结果里学习成本估计的"笔记本"完全没有**——没有滑动平均，没有超时处理，没有对没走过的路的兜底估计。

**风险**：如果这个对手做得很弱（比如只拿最近一次的耗时当估计），赢了也不算数。纲领自己反复警告"不能只胜过弱基线"，到时候整个 headline 都立不住。

**怎么补**：

1. 把 I1 基线当一个正式机制交付，不是随手写的对照组。至少包含：按"路径 × 对象大小"分开记账、指数滑动平均、超时样本的处理、对没用过的路径的保守兜底、自己已承诺的工作量。
2. 给它配验收测试：在带宽平稳的场景里，它的估计应能收敛到真实成本。建议把这条补进纲领 §11.1 的不变量测试表。
3. 用独立的开发集调参，不许在正式评估 trace 上调。

### 5.3 第三件事：说清楚新引擎怎么搭、旧代码留多少

**现状**：纲领要求的 M1 世界——逐迭代 decode、请求一边生成一边占内存、影响别人速度——在现有代码里是零。我核实过 `sim/engine2.py`、`sim/gpu.py`、`sim/metrics.py`，里面没有任何 decode。现有仿真只模拟"第一道菜"（prefill 和 TTFT）。

**这意味着**：这是整个纲领最大的一块工程，很可能比现有仿真核心还大。开工前要先把两件事想清楚：

1. **复用边界**。初步判断：`storage.py`（存储资源）、`topology.py`（拓扑与目录）、`quote.py`（可观测视图）、`workload.py`（负载生成）大概率可以留用；`engine2.py`、`gpu.py`、`metrics.py` 基本要重写或大改。开工前把这个清单写下来，避免边写边纠结。
2. **回归责任**。按仓库规范，改动共享代码必须跑全量 v1 回归。如果走"新包并行"路线，要在文档里写明 v1/v2 冻结不再演进；如果走"原地改造"路线，就要接受每一步都跑全量回归的成本。

另外补一个小的操作性定义：纲领 R4 用"状态年龄 / 压力变化时间"（d/τ）当横轴，但 τ 怎么算没有说。建议在冻结定义时明确，比如"τ 取背景负载 schedule 的最短段长或主周期"，否则后面的扫描没有锚点。

## 六、我替你核对过的事实

写这份补充时逐项验算核实过，可以放心引用。

**数字（全部正确）**：

- KV 字节算例：32 层 × 8 个 KV 头 × 128 维 × 2 字节 × 2（K 和 V）= 每 token 131072 字节；4096 token 约 0.537 GB。✓
- 取回带宽阈值 b* = B/(ΔC−ℓ)，以及"固定开销超过省下的计算时，光提带宽没用"。✓
- 两请求算例的四种分配结果：都取 2 秒、都算 2.2 秒、贵的取便宜的算 1 秒、便宜的取贵的算 2 秒。✓
- 两组 8 类负载的减法（后缀 = 输入 − 命中）和命中不超过输入的约束。✓

**代码现状（决定工程量在哪）**：

| 纲领要求的构件 | 代码现状 |
|---|---|
| I1 历史学习基线（核心对手） | **不存在**，需要从零写 |
| decode / ITL / TPOT 指标 | **不存在**，引擎和指标都要加 |
| 逐迭代混合批引擎（M1 核心） | **不存在**，现有引擎只做 prefill |
| 存储快照 / quote / oracle 诊断 | 已有，纲领在此之上扩展 |
| 静态成本 / 预算化 / 协调策略 | 已有雏形（static2 / cascade2 / coord2） |

一句话：**信息层和策略层的骨架已经有了，最缺的是"会记笔记的对手"和"完整的计算世界"这两块。**

## 七、建议的行动顺序

按依赖关系排，前一步没完成不进后一步，与仓库总工作流一致：

1. **补映射表**（半天）：R0–R9 与 E1–E18 的"继承 / 重跑 / 作废"对照，可并入纲领或单独成文。
2. **S0 定义冻结**（纲领 §12.2 第一阶段）：把 τ 的算法、M1 代码复用边界、I1 基线的验收标准一起冻结进去。
3. **实现 I1 基线 + 收敛性测试**：这是 R1 的前置条件。
4. **搭 M1 引擎（带 decode）+ R0 正确性验证**：纲领 §11.1 的 11 条不变量可以直接转成 `tests/` 的测试计划；R0 不通过不进入任何机制跑分。
5. **R1→R2 最小闭环**：出第一份"存储反馈到底值不值"的判决。第一个 go/no-go 不晚于 R2。

## 八、纲领十分钟读法

纲领 14 节不用都精读，按目的选：

| 你要做什么 | 读哪些 | 为什么 |
|---|---|---|
| 只想了解研究什么 | §1、§14 | 一节讲证明什么，一节是厨房类比 |
| 设计实验 | 精读 §3、§7、§8 | 从单请求推到多请求、负载怎么造、对手怎么设，是操作核心 |
| 写代码 | 精读 §5、§6、§11.1 | 仿真世界、信息接口、不变量测试表 |
| 判断结果 | §4、§10、§11.2–11.3 | 成功怎么定义、统计怎么做、没赢怎么办 |
| 管进度 | §9、§12 | 实验包依赖顺序、阶段停止条件 |

每节开头一段就是它回答的问题，跳读是安全的。
