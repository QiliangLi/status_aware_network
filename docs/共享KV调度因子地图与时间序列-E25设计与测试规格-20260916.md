## 1. 为什么做 E25：一页背景

### 1.1 当前结果缺什么

测试报告（20260915）已通过全部正确性硬门槛，但它的**呈现层**与研究问题之间有四层差距：

1. **时间序列图从未进入交付清单。** 文档1 §12.9 设想的正式汇总图明确包含"NPU 三状态和存储时间线"、"队列随时间变化"；规格 §12.3 收敛最低交付时把时间线只留给了 E22 的 4 请求解析算例，E23 的 `backlog` 图在实际实现中被 TTFT 分布散点占位。因此现存全部产出图的时间轴都不是仿真时间。
2. **数据层只有全程累计标量。** 引擎内存里本有完整的 worker 区段（`WorkerState.segments`，每段 `(start,end,state,batch_id,layer)`）与流速率区段，但 `run_one` 取完 `summarize()` 标量即丢弃 engine；存储侧只有累计积分 `actual_integral_gb / integrated_capacity_gb`。时间序列既没聚合也没落盘，事后无法从 `results/` 重建。
3. **四目标从未在 Mooncake 输入上跑齐。** E23 在线流只跑 θ∈{S,T,R}；E21 有限工作集（唯一能干净定义 makespan M 的模式）只跑了 θ=T。四目标 × 全策略的绝对值对比表不存在，报告主叙事只剩"相对 FCFS 的配对收益"一个数字家族。
4. **影响因子覆盖窄且割裂。** eval 实际格点为 B∈{20,80}、ρ∈{0.6,0.9}、α=4、zero 成本；B=320、ρ∈{0.3,1.1}、α∈{2,8}、profile 扫描、能力块、E22 相位策略均未跑。同时三个真实机制发现使默认配置下若干因子维度平坦：真实 trace 的 u 太大导致 **G≈1**（组批不省计算，能力块/no_speedup 线是平的）；**MPC≡EDF 且 fallback=0**（搜索线是平的）；**θ=S 无策略稳定胜 FCFS**。

### 1.2 E25 交付什么

一句话：**一张地图 + 三条时间线 + 配套测试。**

- **因子地图**：以"有限工作集 + 在线流"两种模式，按基线格点 + 单因子扫描线组织，产出四目标（M / SLO 满足率 / 平均 TTFT / 平均归一化 TTFT）× 8 策略的**绝对值对比**与因子响应曲线；
- **时间序列**：每个 run 按**锚定桶网格**聚合 Compute/STALL/Idle、存储 served/capacity/requested、队列长度，产出随仿真时间变化的三类图；
- **敏感性通道**：通过 `N_sat=128`、能力块、（可选）固定相位策略把"组批 / 时机"两条在默认配置下塌缩的通道显式打开，让因子地图不平。

### 1.3 E25 不做什么

- 不重新验证物理内核正确性（E19–E24 已完成，四计划金标与守恒测试继续有效）；
- 不修改任何策略决策规则、存储协议、观测接口；
- 不推翻测试报告结论；E25 的在线流结果预期会复现"时延改善与 SLO 改善分裂"的结论，新增的是**四目标齐全的视角、因子响应与时间结构**。

## 2. 两种运行模式与既有实验的关系

### 2.1 模式定义

| 模式 | 全称 | 请求构造 | 可用目标 | M 的定义 |
|---|---|---|---|---|
| **FW** | 有限工作集（finite workload） | 每窗口前 128 条请求（不足则全取），`arrival=0`、`deadline=α·T0`，h/u 与目录不变（复用 E21 `finite_workload`） | **M、S、T、R 全部** | 真实 makespan：全体请求完成时刻的最大值（有未完成时为 null 并记下界） |
| **OL** | 在线流（online trace replay） | E23 的窗口缩放回放：first_seen 命中、统一 20 窗口、`scale=λ_raw/λ`（v1.4 口径） | S、T、R | **drain_M**（描述性）：停止到达后固定 cohort 排空的 max F 下界，单独标注口径，不与 FW 的 M 混排在同一坐标 |

两模式共用：synthetic-v1 画像、`HardLimits`（trace 能力组 8 请求 / 262144 token / 128 GB）、FCFS 存储协议、同刻五阶段顺序、zero 控制成本（measured 列为扩展）。

### 2.2 复用关系

| 复用对象 | 来源 | E25 中的用法 |
|---|---|---|
| `finite_workload` | `sim/experiments/e21_batch.py` | FW 模式的请求构造（θ 从写死 T 扩为四目标，属 e25 内部传参，不改 e21 代码） |
| `MooncakeSource.window_specs` | `sim/experiments/cq_common.py` | OL 模式的窗口装载与缩放 |
| 能力块 A/B/C | 规格 §9.4、e21 | FW 的 cap 因子线（A：n_max=1；B：同象限；C：自由） |
| 简单策略跨 θ 复用缓存 | `e23_trace.run_matrix` | 同一物理 run 供全部 θ 复用（见 §3.4） |
| 固定批目录与相位策略 | `e22_stagger` | 可选 timing 线（§7.4），默认不跑 |

**铁律**：E25 只**调用**上述模块，不修改它们的函数签名与行为；e19–e24 的输出目录与图不受影响。

## 3. 实验矩阵

### 3.1 基线格点（全策略 × 全目标，先跑）

| 维度 | 取值 |
|---|---|
| 模式 | FW 与 OL 各一套 |
| 文件 | conversation / toolagent / synthetic 三份 |
| 窗口 | {0, 4, 9, 14, 19}（跨冷启动到尾部，与 E23 eval 一致） |
| 策略 | `ALL_POLICIES` 8 个 |
| 目标 | FW：θ∈{M,S,T,R}；OL：θ∈{S,T,R}（另记 drain_M） |
| 固定因子 | B=80、α=4、能力块 C（自由）、profile=default（synthetic-v1）、zero 成本 |
| 负载（仅 OL） | ρ=0.6 |

### 3.2 因子扫描线（每条线只动一个因子，其余钉在基线）

| 线名 | 水平（基线水平不重跑） | 模式 | 回答的问题 | 预期（默认配置下的先验） |
|---|---|---|---|---|
| `line_B` | B∈{20, 320} | FW+OL | 带宽压力怎样改变策略排序与四目标 | B=20 读取竞争加剧，STALL 结构差异显现 |
| `line_alpha` | α∈{2, 8} | FW+OL | SLO 紧度怎样改变 S/T/R 结论 | α=2 时 S 曲线整体下移，排序类惩罚或放大 |
| `line_rho` | ρ∈{0.3, 0.9, 1.1} | 仅 OL | 负载—容量边界附近谁受益 | ρ=1.1 过载，积压主导，策略差异收窄 |
| `line_cap` | 能力块∈{A, B} | 仅 FW | 组批能力（禁止/限制混批）的价值 | default 画像下预期平（G≈1），如实报告 |
| `line_profile` | profile∈{no_speedup, N_sat=128} | 仅 FW | 计算收益通道打开后组批是否转化为请求收益 | **N_sat=128 使短 u 批 η<1、G>1，此线预期有真实分化** |

每条线在每个窗口 × 每文件 × 8 策略 × 该模式全目标上运行；线与线之间不做笛卡尔积。

### 3.3 运行规模与预算

仿真数估算（简单策略 6 个跨 θ 复用为 1 次仿真；MPC/local 按 θ 各一次）：

| 部分 | 格点数 | 每格点仿真数 | 小计 |
|---|---:|---:|---:|
| FW 基线 | 3 文件×5 窗 = 15 | 6 + 2×4θ = 14 | 210 |
| FW 四条线 | 4 线×2 水平×15 = 120 | 14 | 1,680 |
| OL 基线 | 15 | 6 + 2×3θ = 12 | 180 |
| OL 三条线 | (2+3+2) 水平×15 = 105 | 12 | 1,260 |
| **合计** | | | **≈3,330 次仿真，≈7,200 条记录** |

对照：E21 eval（720 runs）与 E23 eval（600 次仿真）单机各一天内完成；E25 约为其总和的 2.5 倍。因此：

- **可续跑**：每完成一个格点即写盘（目录见 §8），重跑时校验哈希一致后跳过已完成格点；
- **分线执行**：内部按 基线 → line_B → line_alpha → line_rho → line_cap → line_profile 顺序推进，中断可从断点继续；
- 时间序列数据量约 3,300 份 × 201 桶 ≈ 66 万行，gzip jsonl 约 100 MB，全部留在 `results/`（不入库）。

### 3.4 CRN 与配对

同格点内所有策略共享同一份 `specs`（相同 trace_hash）、同一带宽 schedule、同一 T0/deadline；配对统计沿用规格 §10.3（同窗口配对差值、moving-block bootstrap）。简单策略的物理轨迹不随 θ 变化，跨 θ 复用同一次仿真与同一份时间序列文件；`cq_mpc`/`cq_local` 的决策依赖 θ，按 θ 分别仿真并分别存时间序列。

## 4. 指标口径

### 4.1 四目标

沿用规格 §2.1/§10.2 定义，不重新定义：

| 目标 | FW 模式字段 | OL 模式字段 |
|---|---|---|
| M | `makespan_M`（全体完成；有未完成为 null + `makespan_M_lower`） | `drain_M`（= `makespan_M_lower`，描述性下界，单列不与 FW 混坐标） |
| S | `slo_success / n_cohort` | 同左 |
| T | `ttft_mean_lower` | 同左 |
| R | `ttft_norm_mean_lower` | 同左 |

### 4.2 设备与带宽指标的窗口拆分（OL 模式新增字段，不改旧字段）

现有 `device_compute_s` 等为**全程**积分（含排空期）。E25 为 OL 模式新增主窗/排空拆分，旧字段语义保持不变（避免破坏既有测试）：

- `device_*_main`：`[0, arrival_stop)` 内的 Compute/STALL/Idle 设备秒；
- `device_*_drain`：`[arrival_stop, T_end)` 内同项；
- `storage_util_main` / `storage_util_drain`：对应窗口的 served / ∫B。

FW 模式 arrival_stop=0，全部计 drain，沿用全程字段即可。

### 4.3 时间序列与 θ 的关系

时间序列属于**物理轨迹**：简单策略一份（θ 无关），`cq_mpc`/`cq_local` 每目标一份。记录行通过 `ts_path` 指向实际使用的时间序列文件。

## 5. 锚定桶网格与时间序列聚合（核心新增）

### 5.1 设计动机与锚定规则

时间序列要能**跨策略逐桶对比**，桶边界必须一致；但各策略完成时刻不同，若各自按自身 T_end 分桶则时间轴错位。解决：以格点内先跑的 `cq_fcfs` 为锚。

> **T_anchor 规则**：格点内先运行 `cq_fcfs`，取其仿真终止时刻 `T_end(FCFS)`，令
> `T_anchor = ceil(0.1s 网格上取整( 1.1 × T_end(FCFS) ))`。
> 该格点内所有策略共用此 T_anchor。锚定 run 复用简单策略跨 θ 缓存，不额外消耗仿真。

- 若 FCFS 无法排空（undrainable），`T_end` 即排空预算截止时刻，规则同样适用；
- 1.1 倍余量覆盖多数策略慢于 FCFS 的尾部；仍超出者进入**溢出桶**（§5.2），不截断、不丢弃。

### 5.2 桶网格

- 固定桶数 **K=200**，桶宽 `Δ = T_anchor / 200`；
- 桶 `i`（0 ≤ i ≤ 199）：`[iΔ, (i+1)Δ)`；
- **溢出桶** `i=200`：`[T_anchor, ∞)`，实际宽度 = `T_end − T_anchor`（策略快于锚时不产生数据）。

### 5.3 采集实现（挂钩点与算法）

聚合器作为 engine 的**只读观察者**接入，默认关闭，仅 e25 开启——保证 e19–e24 轨迹零影响（测试断言见 §11.2 BU11）。三个挂钩点：

1. **worker 区段结算**（`WorkerState.set_state` 结算处或 run 结束统一遍历 `segments`）：把每段 `(start, end, state)` 与各桶区间求交，按 state 累入 `compute_s / stall_s / idle_s`；run 结束时若存在未结算的开区间，先结算到 `T_end`。
2. **存储速率区段**（engine 推进循环的每个积分区间 `[t, t_next)`，此区间内各流速率恒定）：对每段求 `served_gb += Σ_f rate_f × dt`、`requested_gb += Σ_f q_f × dt`（含未被服务的申请流），与桶求交累入。
3. **队列长度**：维护 `backlog = |QUEUED| + |ACTIVE|` 及其最近变更时刻，每次变更把 `长度 × 时长` 时间加权累入桶；桶内记 `queue_mean`（时间加权均值）与 `queue_max`。

```text
算法 TS：AGGREGATE(engine, T_anchor, K=200)
    Δ ← T_anchor / K
    对每个 worker 的每段 (s, e, state)：按 §5.5 区间求交法累入对应桶字段
    对每个存储速率区段 (s, e, rates)：served/requested 同法累入
    对每个队列区间 (s, e, len)：len×时长 累入 queue_sum，max 更新 queue_max
    每桶 capacity_gb ← 从 B(t) schedule 解析积分 ∫B（与引擎无关，闭式计算）
    溢出桶宽度用 T_end − T_anchor；关闭 run 前结算所有开区间
    校验 §5.6 三条守恒恒等式，失败则该 run 状态 invalid
    写 <policy>[_<theta>].json.gz
```

### 5.4 桶数据 schema

每份文件 = 元信息 + 行数组：

```json
{
  "meta": {"cell": "conversation_trace|FW|B80|rho-|a4|C|synthetic-v1|w9",
            "policy": "cq_fcfs", "theta": null,
            "T_anchor_s": 12.3, "delta_s": 0.0615, "K": 200,
            "T_end_s": 11.82, "mode": "FW",
            "b_schedule": [[0.0, 80.0]], "overflow_used": false},
  "rows": [
    {"i": 0, "t_start_s": 0.0, "width_s": 0.0615,
     "compute_s": 0.24, "stall_s": 0.02, "idle_s": 0.00,
     "served_gb": 0.019, "capacity_gb": 4.92, "requested_gb": 0.020,
     "queue_mean": 5.5, "queue_max": 9,
     "cum_arrived": 7, "cum_done": 0},
    ...
  ]
}
```

`cum_arrived / cum_done` 为到达该桶末尾的累计到达/完成请求数（供 cohort 流动背景）。数值模式 float64，字段禁止 NaN/Infinity（转 null + reason）。

### 5.5 手算示例（实现与测试共用，勿改）

**例 1｜worker 区间跨桶。** Δ=0.5，worker 处于 STALL 的区间 `[1.4, 3.1)`。逐桶相交：

| 桶 | 相交长度 |
|---|---:|
| [1.0, 1.5) | 0.1 |
| [1.5, 2.0) | 0.5 |
| [2.0, 2.5) | 0.5 |
| [2.5, 3.0) | 0.5 |
| [3.0, 3.5) | 0.1 |

合计 1.7 = 区间长度，无丢失无重复。端点重合按左闭右开归属（`[1.5,2.0)` 的左端点属本桶）。

**例 2｜队列时间加权。** Δ=0.5；t∈[0, 0.2) 队列 0，t∈[0.2, 1.1) 队列 3，t≥1.1 队列 1。桶 0 `[0,0.5)`：均值 = (0×0.2 + 3×0.3)/0.5 = **1.8**，max=3；桶 1 `[0.5,1.0)`：均值 = 3，max=3。注意事件数平均（(0+3)/2=1.5）不是时间加权均值，禁止混用。

### 5.6 守恒恒等式（每 run 落盘前强制校验）

1. `Σ桶(compute_s + stall_s + idle_s) = m × T_end`（float64 容差 1e-9，下同）；
2. `Σ桶 served_gb = storage.actual_integral_gb`（总读取字节）；
3. `Σ桶 capacity_gb = ∫_{0}^{T_end} B(t)dt`（由 schedule 闭式积分，独立于引擎累计值）。

任一失败该 run 标 `invalid`，不得进入图表。

## 7. 敏感性通道与预期判断

因子地图的价值取决于通道是否打开。各线与机制通道的对应及先验预期：

| 通道 | 打开它的线 | 默认配置下为什么平 | 打开后的预期现象 |
|---|---|---|---|
| 组批计算收益 | `line_profile`（N_sat=128）、`line_cap` | 真实 u 大 → N≫512 → η≡1 → G≈1（测试报告三次确认） | N_sat=128 使短 u 批 G>1，cap 线 A/B/C 分化，E21 的"胜负边界"问题重新有内容 |
| 顺序/优先级 | 基线 + `line_alpha` | 已有分化（SPT/EDF 时延 −28~−30%） | α=2 收紧后长请求惩罚的形态变化 |
| 时机/错峰 | （可选）timing 线：e22 的 `fixed_phase`/`fixed_wait_mpc` 在 Mooncake 固定批目录上 | 未展开 | 相位错开对 STALL/带宽时间结构的影响，直接在图 D/E 呈现 |
| 搜索/信息 | 无（MPC≡EDF 已三处复现） | gate=0 + 2ms/20k 预算下无增量 | 不强求；如 timing/突发窗口下仍无增量，作为稳定负面结论报告 |
| 带宽/负载 | `line_B`、`line_rho` | eval 只覆盖了 2×2 角 | B=20 与 ρ=1.1 的 STALL/队列时间结构 |

`line_profile` 与 timing 线属于**机制打开装置**：N_sat=128 不是对真实硬件的断言，图注必须写明"该面板用于隔离组批通道，非实测画像"。

### 11.2 桶聚合测试（BU01–BU12）

夹具构造器：`make_tiny_engine(specs, B, ...)` 直接组装 `CqEngine` 跑小规模请求（n≤3、L≤2、小有理数 V/c），不经 e25 矩阵。区段求交函数单独可测（纯函数）。

| ID | 输入 / 夹具 | 硬断言 |
|---|---|---|
| BU01 区间切分 | 纯函数：区间 `[1.4, 3.1)`，Δ=0.5（§5.5 例 1） | 各桶分账恰为 0.1/0.5/0.5/0.5/0.1，合计 1.7；端点重合按左闭右开（`[1.5,2.0)` 的左端点 1.5 属该桶） |
| BU02 端点与零长 | 区间 `[0.5, 0.5)`（零长）、区间恰为一整桶 `[0.5, 1.0)`、区间跨溢出边界 `[T_anchor−0.1, T_anchor+0.2)` | 零长区间贡献为 0 不产生行；整桶区间恰好一个桶得全长；跨界段在桶 199 与溢出桶各得 0.1/0.2 |
| BU03 三态守恒 | 任意 tiny run（含排空） | `Σ桶(compute_s+stall_s+idle_s) == m × T_end`（1e-9）；与 `WorkerState.compute_s/stall_s/idle_s` 之和逐项相等 |
| BU04 字节守恒 | 同上 | `Σ桶 served_gb == storage.actual_integral_gb`；`Σ桶 requested_gb == storage.requested_integral_gb` |
| BU05 容量闭式 | B(t)=`((0,4),(1,2))`，T_end=3 | 逐桶 capacity 为解析值：桶含 [0,1) 段按 4、其后按 2 积分；总计 `4×1+2×2=8`；该计算**不读** storage 累计器（独立复算） |
| BU06 溢出桶 | 人造 T_end = 1.3×T_anchor 的 run（如放慢策略或缩短锚） | 溢出桶宽度 = T_end−T_anchor；三态守恒含溢出桶后仍成立；`meta.overflow_used=true`；`width_s` 用实际宽度而非 Δ |
| BU07 锚定一致 | 同格点跑 fcfs 与另一策略 | 两份 ts 的 `meta.T_anchor_s / delta_s / K` 完全相等；`T_anchor == ceil_0.1s(1.1 × T_end(fcfs))`（重算核对）；fcfs 两次运行 T_end 一致（确定性前提，复用 U29 机制） |
| BU08 队列时间加权 | 1 请求 t=0 到达、t=0.5 派发、t=1 完成；Δ=0.25（§5.5 例 2 的变体） | `queue_mean` 逐桶为时间加权值（手算金标）；断言 `mean(queue_mean) ≠ 事件数平均`（防口径退化）；`queue_max` 为桶内峰值 |
| BU09 累计口径 | tiny run | 最后一桶 `cum_arrived == n_requests`、`cum_done == n_done`；两累计序列单调不减 |
| BU10 空与零值 | 全 h=0（无读取流）请求；空 specs | 无流 run：`served_gb` 全 0、`capacity_gb` 按 B 正常积分、util=0.0（非 null）；空 specs 不产生 ts 文件且不抛异常 |
| BU11 零影响开关 | 同一 tiny run，聚合器开/关各跑一次 | 两次运行的请求/批/事件规范日志哈希相同（聚合是纯观察者）；关闭时 e19–e24 路径行为与现状逐位一致 |
| BU12 ts 落盘格式 | 任一 tiny run 落盘后回读 | JSON 合法、无 NaN/Infinity（出现即解析失败）；行数 = K +（溢出桶被使用?1:0）；字段名与 §5.4 逐一对应；gzip 可回读 |

## 13. 局限与不声称

1. synthetic-v1 画像依旧，非实测 NPU；`N_sat=128` 面板是机制隔离装置，不外推为硬件结论。
2. OL 模式时间为缩放后仿真秒（`scale=λ_raw/λ`），图注必须写明缩放比；native_time 不在 E25 范围。
3. T_anchor 以 FCFS 为锚，个别远慢于 1.1×FCFS 的策略尾部进溢出桶，占比逐 run 报告；逐桶对比在溢出段不成立（宽度不同）。
4. 线扫描而非全笛卡尔积，因子交互作用（如 B×α）不可从 E25 直接得出。
5. MPC 无增量若在全部线上复现，作为稳定负面结论报告，不代表搜索方法本身无效（预算与 gate 固定为规格默认值）。

## 15. 通俗版解读

前面的实验像是一场只公布"平均分差"的考试——我们知道了每个学生比先来后到规则快了多少，但看不到单科成绩单，也看不到考试过程中谁在奋笔疾书、谁在等草稿纸。

E25 补两样东西。**第一张是全科成绩单**：四种评分标准（最快全部做完、按时交卷率、平均等待、小单相对等待）下八个策略的直接对拼，而且把考题难度（带宽、负载、交卷期限、合盘能力、合盘收益）一项一项拧动，画出"难度—成绩"曲线；其中"合盘收益"这根旋钮在真实考题下原来是锁死的（合盘不省工），我们特意造一把钥匙把它拧开，看合盘到底值不值。**第二样是考场录像**：把整场考试切成两百个小片段，每个片段记下四张桌子分别在"算题、等料、闲着"的比例，以及传送带送了多少料、还压着多少单——于是"错峰到底有没有用"不再是一个平均数，而是一段看得见的时间线。

这套交付同时配三道质检：**BU 组**查录像机本身——一段 1.7 秒的等待切成五份，加起来必须还是 1.7 秒，一分不能丢、一分不能多，录像开机与否不能改变考试过程；**FM 组**查成绩单的登记——四个科目的分都要有，只拧一根难度旋钮时其他旋钮的读数不许悄悄变，同一份考卷所有学生的用纸量必须一样；**FG 组**查成绩单印刷——图上画的每一笔都得能从登记簿里原样查出来，新发的图表不许弄脏以前任何一张旧图。
