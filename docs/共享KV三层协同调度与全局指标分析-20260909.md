# 共享 KV 存储下的三层协同调度与全局指标分析

| 项目 | 约定 |
|---|---|
| 研究对象 | 多个推理实例共享分布式 KV 存储时的 prefill 调度 |
| 三层决策 | 请求路由与改派、实例内排序与组 batch、存储服务分配 |
| 数据来源 | 已有可复用 KV 默认从共享存储读取，所有实例可见全局 KV |
| 执行边界 | 请求获准开始执行后才发起读取，执行中允许下一层加载与当前层计算重叠 |
| 计量单位 | 时间为秒，数据量为十进制 GB，带宽为 GB/s |
| 文档性质 | 独立的研究模型与实验设计，八请求部分为假设参数下的精确算例 |
| 文献核验日期 | 2026-09-09 |

## 1. 研究问题究竟是什么

**一个实例决定下一批执行哪些请求，也决定了它将在什么时候占用多少共享存储带宽。其他实例的读取完成时间会随之改变，进而改变整个集群的计算节奏。**

因此，请求的服务时间随全局执行过程变化。先给每个请求算出一个固定的“存储时间”，再分别优化每个实例的队列，会漏掉这个研究问题最关键的因果关系。

需要研究的完整链条是

```text
请求分到哪个实例
    ↓
实例选择何时开始、先执行谁、哪些请求组成同一批
    ↓
各批逐层产生读取，竞争共享存储和链路
    ↓
存储分配服务，使各批在不同时间完成当前层读取
    ↓
各实例开始计算，并在计算中发起下一层读取
    ↓
新的读取竞争、计算空档、请求完成和下一轮调度
```

三层可以分开实现，但应评价同一个全局目标。让每个实例各自追求最快完成当前请求，不保证平均 TTFT 最小；让所有实例尽快开始，也不保证全局计算等待最少。

### 1.1 保持分析可控的边界

本文只调度 prefill。请求完成表示完成 prefill 并产出首 token，末端采样等固定开销可并入最后一层计算。这里的完成吞吐是 **prefill 请求吞吐**。如果要声称完整生成吞吐提升，需要另行验证后续阶段的瓶颈。

等待队列只保留请求及元数据，不读取该请求的 KV。实例正式准入一个执行批后，开始加载第一层 KV；计算第 $\ell$ 层时，最多提前加载第 $\ell+1$ 层。不能把“准入”仅作为后台预取的名称，再让任意多的批次等着计算。

基础模型规定每个实例同一时刻只有一个活动 prefill 批，其余请求排队。批内请求完成当前轮 prefill 前不被迁走。所有策略使用相同的批大小、token 预算和经过容量验证的执行缓冲上限。这些是固定可行性约束，不展开为 HBM 生命周期优化。若扩展到多活动批，必须明确允许的并发数及计算切换规则，所有对照一同开放。

全局 KV 可见性只表示所有实例都能取到数据。共享存储内部可以存在不同分片、出口和路径，实际成本仍可能不同。基础实验先用一个共享带宽瓶颈隔离全局竞争，再加入分片和路径差异。基础模型也不做请求间读取去重、缓存写回策略或取数与重算选择，固定这些能力才能判断调度本身的贡献。

按层等待本层 KV、触发下一层异步加载具有已有系统机制依据。Mooncake 的 Layer-wise Prefill 描述了这一执行关系。本文额外施加的“排队时不预取”和单活动批限制是本研究的建模边界，不据此断言 Mooncake 的全部实现行为。[Mooncake，§5.2](https://arxiv.org/html/2407.00079v4#S5.SS2)

## 2. 先定义指标，再决定三层要优化什么

### 2.1 与论文口径的对应关系

| 文献 | 可借鉴的指标或方法 | 本文的使用范围 |
|---|---|---|
| DistServe | 在给定 TTFT、TPOT 约束及 SLO 满足率目标下，最大化每 GPU 可承载请求率 | 保留“满足时延目标时的容量”定义，本文只施加 TTFT 约束 |
| Sarathi-Serve | Capacity 是满足时延目标的最大持续请求负载；同时报告 TTFT 与尾部时延 | 用于区分持续容量与一次有限请求集合的吞吐 |
| FastServe | 同时关注平均、尾部响应时延及相应时延要求下的吞吐 | 支持同时评价均值与尾部，但不能把全文响应时延直接当作 TTFT |

来源分别为 [DistServe，§1](https://arxiv.org/html/2401.09670v3#S1)、[Sarathi-Serve，§2.3 与 §5.1](https://arxiv.org/html/2403.02310v1#S2.SS3)、[FastServe](https://arxiv.org/html/2305.05920v3)。

Sarathi-Serve 还用无争用执行时间的倍数构造部分时延 SLO，但其相应定义针对 TBT。本文采用“每个请求参考 TTFT 的倍数”时，应明确这是适配本研究的定义。类似地，本文的归一化 TTFT 有独立公式，不能与其他论文里按输出长度、某个系统结果归一化的 latency 混用。

### 2.2 请求级定义

设请求 $i$ 的到达时间为 $a_i$，进入活动执行批的时间为 $u_i$，首 token 完成时间为 $F_i$。

$$
T_i=F_i-a_i=(u_i-a_i)+(F_i-u_i)
$$

前一项包含全局队列、实例队列和等待组批。后一项包含启动读取、逐层计算、未被计算掩盖的 I/O 等待。改派不重置 $a_i$，组 batch 不重置 SLO。

为每个请求预先固定无竞争参考时间 $T_i^0$。一个易于复现的定义是该请求独占同类实例与完整基准存储带宽，按相同层间流水规则执行时的单请求 TTFT。所有被比较的策略使用同一组参考值，背景拥塞也不能把分母动态调大。

**一般组批模型中，这个单请求参考值未必是数学上的最优下界。** 如果 batch 能显著提升计算效率，请求可能比单独执行更快，此时 $T_i/T_i^0<1$ 合理。若研究必须使用“理论最优 TTFT”，应在统一动作空间中求该请求的合法最快完成时间，或明确采用乐观下界并更名为“相对下界比值”。不能把不可证明的参考值称为最优值。第 7 节采用线性批计算模型，单请求参考值同时也是该算例的理想最短时间。

### 2.3 五种目标的精确定义

| 研究目标 | 指标 | 需要回答的问题 |
|---|---|---|
| 有限工作集吞吐 | $M=\max_i F_i-t_0$，$X_{\mathrm{finite}}=n/M$ | 固定同一批请求，全部做完需要多久 |
| 持续服务容量 | $\lambda^*(\eta)=\sup\{\lambda\mid A(\lambda)\ge\eta,\ \text{队列稳定}\}$ | 给定满足率目标 $\eta$，系统最多持续接收多少请求 |
| SLO 满足率 | $A=\frac1n\sum_i\mathbf1[T_i\le s_i]$ | 同样的输入负载下，有多少请求按时完成 |
| 平均 TTFT | $\bar T=\frac1n\sum_i T_i$ | 每个请求权重相同，平均等待多少秒 |
| 平均归一化 TTFT | $\bar R=\frac1n\sum_i T_i/T_i^0$ | 每个请求相对自身参考速度平均慢多少倍 |

$t_0$ 是有限工作集的共同观测起点。所有请求同时到达时，最小化 $M$ 等价于最大化该工作集吞吐。最小化 $\sum_i F_i$ 则对应平均完成时间，二者应分别报告。长短请求比例必须固定，否则 requests/s 的变化可能来自工作量变化；处理的输入 token/s 可作为辅助工作量指标。

SLO 可采用固定阈值 $s_i=s$，也可采用相对阈值 $s_i=\alpha T_i^0$。绝对截止时间为 $d_i=a_i+s_i$。两个模型都应实验，因为固定阈值与按长度放宽阈值可能改变策略排序。

实际成功请求率也可以报告为 $G=N_{\mathrm{on\ time}}/H$，其中 $H$ 为统一统计窗口。这个实现层面的成功吞吐，与 $\lambda^*(\eta)$ 所表示的“给定满足率下的最大可承载负载”是两个量，表头应写清。拒绝或超时的请求计入到达分母并视为 SLO 失败，不能通过删除困难请求提高满足率。

$\bar R$ 按每个请求的 $1/T_i^0$ 加权实际时延。它会更重视短请求遭受的相对延迟，并不等于 $\bar T/\overline{T^0}$。均值之外，报告 TTFT 与归一化 TTFT 的 P50、P95、P99，以及长短请求各自的结果，避免均值掩盖饥饿。

### 2.4 全局 NPU 利用率与 STALL

在统一窗口 $[t_0,t_0+H]$ 内，每个 NPU 的时间分成互斥状态。

| 状态 | 定义 |
|---|---|
| Compute | 正在进行有效 prefill 计算 |
| I/O stall | 已有活动批需要计算，但依赖读取未完成，且没有其他可运行计算 |
| Idle | 没有活动批，包括无请求、等待准入或等待组批 |
| Other | 调度、通信控制等未计入上述状态的开销 |

若有 $W$ 个同构单 NPU 实例，则

$$
U=\frac{\sum_w C_w}{WH},\qquad
P_{\mathrm{stall}}=\frac{\sum_w S_w}{WH},\qquad
U+P_{\mathrm{stall}}+P_{\mathrm{idle}}+P_{\mathrm{other}}=1
$$

多 NPU 实例按设备时间加权。这里的 $U$ 是有效计算的时间占比，无法代替硬件 FLOPS 利用率。batch 增大可能缩短总计算时间并提高吞吐，即便忙碌时间占比下降，也未必是性能退化。

必须同时报告 STALL 的绝对 NPU 秒数及占比。若策略把等待从“活动批等 I/O”搬到“队列等准入”，STALL 会降低，却可能没有任何请求更早完成。单个请求等 I/O 时，如果 NPU 正在计算其他请求，也不能计为设备 STALL。

### 2.5 优化目标怎样选择

建议建立三条独立的评价线，每条只设一个主目标。

| 评价线 | 主目标 | 配套观察 |
|---|---|---|
| 容量线 | 最小有限工作集 $M$，或最大稳定容量 $\lambda^*(\eta)$ | 全局 Compute、STALL、Idle 与存储利用率 |
| SLO 线 | 固定到达负载和阈值时最大化 $A$ | 失败请求、各长度组满足率、成功请求率 |
| 时延线 | 分别最小化 $\bar T$ 与 $\bar R$ | 尾部时延、最长等待及吞吐损失 |

NPU 利用率主要解释性能变化的原因。除非实际目标就是最小设备等待，否则不把它与 TTFT、SLO 用任意权重相加。一个方案是否值得采用，应给出它在目标之间的取舍。

## 3. 全局模型如何把三层连起来

### 3.1 批次、层和带宽

用 $\mathcal B$ 表示一个活动批，$i$ 表示请求，$\ell$ 表示模型层，$w$ 表示实例。请求在第 $\ell$ 层需要读取 $v_{i\ell}$ GB。无去重时，该批本层读取总量为

$$
V_{\mathcal B\ell}=\sum_{i\in\mathcal B}v_{i\ell}
$$

本层计算耗时记为 $c_{\mathcal B\ell}=g_w(\mathcal B,\ell)$。$g_w$ 由模型与硬件上的测量表提供，可以反映 token 数、上下文长度和 batch 形状。不能默认用 batch 中最长请求、请求数或 token 数之一完全代替它。

读取流 $f$ 的带宽为 $b_f(t)$。在基础单瓶颈模型中

$$
\sum_{f\in\mathcal F(t)}b_f(t)\le B(t),\qquad b_f(t)\ge0
$$

$\mathcal F(t)$ 只包含已经合法发起、尚未完成的读取。$B(t)$ 是共享系统当时可供本业务使用的容量。多分片、多链路模型应对每个资源 $e$ 分别约束

$$
\sum_{f\mid e\in\operatorname{path}(f)}b_f(t)\le B_e(t)
$$

第一阶段可将资源视为流体带宽约束。若启动时延或存储 IOPS 成为瓶颈，再增加对应服务阶段，不能把它们虚构成随意变化的带宽。

### 3.2 层间流水与批内同步

设某批第 $\ell$ 层读取发起、读取完成、计算开始和计算结束时间依次为 $A_{\mathcal B\ell}$、$R_{\mathcal B\ell}$、$C_{\mathcal B\ell}$、$Z_{\mathcal B\ell}$。第一层 $A_{\mathcal B1}=u_{\mathcal B}$。每个请求本层读取完成需满足

$$
\int_{A_{\mathcal B\ell}}^{R_{i\ell}}b_{i\ell}(t)\,dt=v_{i\ell}
$$

基础模型采用整批本层 KV 齐备后启动一个批计算的同步边界。

$$
R_{\mathcal B\ell}=\max_{i\in\mathcal B}R_{i\ell},\qquad
C_{\mathcal B\ell}=\max(R_{\mathcal B\ell},Z_{\mathcal B,\ell-1}),\qquad
Z_{\mathcal B\ell}=C_{\mathcal B\ell}+c_{\mathcal B\ell}
$$

其中 $Z_{\mathcal B0}=u_{\mathcal B}$。下一层加载在当前层计算开始时发起

$$
A_{\mathcal B,\ell+1}=C_{\mathcal B\ell}
$$

完整 prefill 的固定 batch 中，$F_i=Z_{\mathcal B L}$。若采用 chunked prefill，则上述批是一个执行 chunk 的批次，请求只有最后一个 chunk 完成才产生 $F_i$。跨 chunk 的 KV 保留或重读规则须固定，不能既不留存又假设后续读取免费。

当 batch 本层读取可以作为一个聚合流处理时，直接对 $V_{\mathcal B\ell}$ 积分即可。真实按请求、对象或连接公平的系统不一定等价于按 batch 公平，仿真必须固定第三层的服务粒度。

令 $x_{\mathcal B\ell}=R_{\mathcal B\ell}-A_{\mathcal B\ell}$，该批执行时间可写成

$$
T_{\mathcal B}^{\mathrm{exec}}
=x_{\mathcal B1}
+\sum_{\ell=2}^{L}\max(x_{\mathcal B\ell},c_{\mathcal B,\ell-1})
+c_{\mathcal B L}
$$

这个式子便于解释 overlap，但 **$x_{\mathcal B\ell}$ 必须由全局带宽分配积分得到**。改派、重排或组批会改变读取发起时间和竞争者，不能继续沿用动作发生前的固定 $x$。

### 3.3 一个局部动作的全局代价

若某个动作让请求 $i$ 提前执行，它可能同时推迟其他实例的请求。以平均 TTFT 为例，应比较

$$
\Delta J=\frac1n\sum_{i\in\mathcal I}
\bigl(\widehat F_i^{\mathrm{action}}-\widehat F_i^{\mathrm{keep}}\bigr)
$$

$\mathcal I$ 至少覆盖预测窗口内受到影响的已到达请求。两条预测都要重新计算共享资源竞争，不能只更新目标实例。容量目标则比较预测尾部完成时间，SLO 目标比较预计按时完成的请求数。在线实现只使用已知请求和声明的统计预测，不借用未来 trace。

这种全局评估可以作为小规模参考策略。实际策略可以用短预测窗口、候选 batch 筛选和存储服务报价近似，实验要量化近似损失，而非先假设精确预测永远可用。

## 4. 三层各自需要什么状态、执行什么动作

| 层 | 需要的状态 | 可用动作 | 应交给下一层的信息 |
|---|---|---|---|
| 请求调度器 | 各实例活动批进度、待执行工作量、候选批、共享存储报价及路径差异 | 首次派发、保留全局队列、未执行请求改派 | 请求到达时间、SLO、读取量和计算画像 |
| 推理实例 | 本地队列、截止时间、每层读量和计算时间、其他实例造成的可观测带宽压力 | 排序、组批、确定开始时间与合法 chunk 大小 | 本层剩余读取量、下一层消费时刻、批依赖关系 |
| 存储服务 | 已提交读取、资源容量与服务进展，以及实例传来的依赖和紧迫性 | 公平共享、加权共享、优先服务、在可行范围内承诺速率 | 可观测服务率、预计完成时间、报价有效期与误差范围 |

### 4.1 第一层应均衡可执行工作

按请求数均匀分发是必要的弱基线。长短请求、命中 KV 量和剩余计算不同，仅靠数量不能保证算力均衡。更强的基线是按预计计算工作量或排空时间分配。

存储感知路由还要看派发后的读取时间分布。两个实例都排了等量计算，也可能恰好同时开始大读取，随后同时陷入等待。路由的意义包括形成适合组批、错开竞争的本地候选集。

在实例完全同构、所有读取路径完全相同、所有实例还处于对称状态时，单独换一个 worker 标签不会产生存储收益。收益必须来自后续的排队、组批、执行时刻或实际路径差异。这个对称场景应成为正确性对照。

### 4.2 未执行请求应允许改派，但收益要全局计算

请求在 $u_i$ 前未读 KV，改派主要转移元数据，可避免运行态 KV 搬运。在实例空闲、等待时间明显失衡或存储状态变化时，允许撤销原队列中的待执行请求，重新分配给其他实例。

改派需要保证请求只有一个所有者。撤队与开始执行发生竞争时，只允许一个动作成功；已经进入活动批的请求不再属于本机制。候选改派还应计入控制时延、目标队列影响，以及拆掉原有 batch 的计算效率损失。

如果空闲实例提前启动了大读取，其他实例本来可以隐藏的下一层 I/O 可能开始暴露。此时“被迁请求变快”不足以证明改派有益。应按第 3.3 节比较全局目标，并设置收益门槛、冷却期和最大改派次数。

Llumnix 已研究跨实例运行时重调度及请求状态的 live migration。本文的未执行请求改派范围更窄，用它检验在没有 KV 搬迁成本时，纠正早期派发是否仍有足够价值。[Llumnix，OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/sun-biao)

必须加入两个强对照。一个是空闲实例从其他队列偷取未开始请求；另一个是全局排队、实例准备执行时才派发。若后者已消除大部分早期分配错误，复杂改派机制的额外价值可能很小。

### 4.3 第二层决定进入共享带宽竞争的形状

实例内排序除了改变队列等待，还改变下一次读取的大小与时机。组批进一步改变本层计算持续多久，以及下一层读取需要在多长时间内完成。

因此，第二层的候选方案至少包含“候选 batch + 计划开始时刻”。对候选批，预测本层启动读取、后续层可隐藏的读取、批内同步等待，以及对其他活动批的影响。

延迟准入可能帮助已经执行的批保持计算连续，也会直接增加本队列的 TTFT。策略应比较这两项，不以降低活动读取数为目标，更不能通过长期不给请求准入制造很低的 STALL。

### 4.4 第三层应关注计算何时需要数据

对于已经发起的下一层读取，设当前剩余数据为 $r_f(t)$，希望在 $\tau_f$ 前就绪，则一个局部的无等待需求率是

$$
q_f(t)=\frac{r_f(t)}{\tau_f-t},\qquad \tau_f>t
$$

$\tau_f$ 可以取该批当前层预计计算结束时刻。若所有已释放读取的速率需求在每条路径上都可满足，及时完成它们可避免对应层间等待。$\sum q_f>B$ 是这组局部速率目标无法同时维持的信号，但仅凭这一时刻的比值，不能判定未来整个调度必然不可行。

更强的可行性检查要看时间窗内必须完成的总数据与可提供服务量，并考虑读取释放时间、路径和批依赖。尚未发起的下一层不能提前获得真实服务。

第一层读取没有前一层计算可供掩盖。它需要结合请求截止时间或启动一个新计算批的价值安排，不能把“希望立即开始”的零时限代入上述除法。

当所有需求无法同时满足时，按需分配还缺少一项决策，即放弃保护哪些层的就绪时限。可以分别研究保护最多 NPU 计算时间、保住最多可完成 SLO、或降低平均完成时间的服务规则。这些规则未必选中同一批。

批内同步也影响分配价值。给已提前就绪的成员增加服务没有收益；给阻塞全批的最后一段读取带宽，可能马上释放一个 NPU。若一个批还缺好几份数据，则需要把它们视为有共同完成条件的一组需求。单纯最短读取优先或最早截止时间优先，都不保证全局最优。

### 4.5 一套可以直接实现的决策过程

先实现一个小规模的全局预测参考策略，用它判断简单规则漏掉多少收益。每逢请求到达、批完成、读取完成或报价更新，按以下过程决策。

1. 从 FCFS、短服务优先和剩余预算优先各取有限个候选，构成合法的单请求批、同类批和混合批。路由候选包含几个低负载实例；只有未执行请求进入改派候选。
2. 对每个候选分别尝试立即开始，以及等待下一个已知计算或读取完成事件后再开始。等待期间维持当前活动批，不读取候选批的 KV。
3. 第三层尝试公平分配、消费时限需求分配和截止时间优先。需求分配若可行，先保护各下一层所需的速率，余量给合法启动读取；需求不可行时，枚举少量待保护批集合，剩余服务按固定公平规则分配。第一层读取不伪造零时限需求。
4. 使用同一份可观测容量预测，把所有活动批及受影响队列推进到共同预测终点。容量线比较预测尾部完成时间，SLO 线比较按时完成数，时延线比较完成时间之和或归一化之和。预测窗口外的剩余工作采用统一尾部估计，不能把它直接忽略。
5. 执行选中方案的当前动作，未来动作仅作预测，等新事件发生后重算。平局按原到达顺序处理；改派还需通过收益门槛。

这定义了一个有限候选、滚动执行的参考控制器，没有保证求得连续动作空间的全局最优。候选数、预测窗口、状态更新成本和公平保底应明确记录。后续若简单的局部规则能接近它，就优先保留简单实现。

## 5. 如何理解“过载、SLO、开环与闭环”的关系

“过载后按需分配、空闲时尽量用满带宽”是合理的服务方向，但需要将负载状态与优化目标分开判断。

| 当前情形 | 合理动作 | 不能据此承诺的结果 |
|---|---|---|
| 已发起读取可在对应消费时限前全部完成 | 保证及时就绪，有剩余带宽时继续服务合法待传数据 | 链路必须达到 100% 利用率 |
| 部分层间需求无法同时满足 | 选择保护对象，分配带宽，必要时限制新批开始 | 按请求均分或越紧急越优先必然减少总 STALL |
| 所有请求 SLO 都有余量 | 选择容量或平均时延目标，同时保持 SLO | SLO 不构成约束后就没有调度价值 |
| 只能使部分请求满足 SLO | 若主目标是满足率，选择联合可行的请求集合 | 每个请求单独可救就能同时救；只按最早截止时间即可 |
| 当前集合已无请求可满足 SLO | 对这部分请求避免无效抢救，按既定次目标和公平规则服务 | 后续到达请求也没有可满足的 SLO |

**存储服务应当工作保守，即存在可服务读取时不故意浪费其可用容量。** 这里的可用容量要同时满足路径和接收约束。没有已准入的合法读取时，带宽闲置合理；禁止为了填满链路预取等待请求。策略主动推迟新批准入也可能暂时减少读取供给，必须由端到端收益解释。

SLO 决策与是否带宽过载并非先后固定的两层开关。即使存储不拥塞，计算排队也可能使 SLO 只能部分满足。即使存储过载，也可能因为截止时间宽松而全部满足。

### 5.1 开环中何时利用率不变

开环指到达过程独立于系统响应。在稳定、无拒绝、无丢弃的长期运行中，如果每个请求需要的有效 NPU 计算秒数 $K_i$ 固定，则工作守恒给出

$$
U=\frac{\lambda\,\mathbb E[K_i]}{W}
$$

此时排序降低等待，却不会凭空增加长期计算工作。这个结论需要全部前提成立。有限工作集、系统不稳定、拒绝策略变化，以及 batch 改变计算效率时，都不能直接套用。第 7 节是有限工作集，利用率分母随最后完成时间变化。

### 5.2 闭环中何时利用率可能提高

闭环指固定 $N_c$ 个客户端完成一轮后才发下一轮。若平均思考时间为 $Z$，每轮平均响应时间为 $\bar T_{\mathrm{cycle}}$，稳态流量满足

$$
X=\frac{N_c}{\bar T_{\mathrm{cycle}}+Z}
$$

对于只请求一个首 token 的 prefill 基准，$\bar T_{\mathrm{cycle}}=\bar T$。如果客户端等待完整回答，周期必须使用完整响应时间，不能用 TTFT 替换。

降低周期时间可能提高请求到达率和 NPU 利用率，直到其他瓶颈限制流量。闭环也可能掩盖拥塞，因为系统变慢时客户端自动降速，所以应与相同请求类型分布的开环实验分别报告。

## 6. 组 batch 会怎样改变结论

### 6.1 四种需要分别测量的影响

| 影响 | 进入模型的位置 | 可能带来的取舍 |
|---|---|---|
| 等待组批 | $u_i-a_i$ | 获得计算效率前，先付出等待成本 |
| 计算效率 | $g_w(\mathcal B,\ell)$ | 批大可能降低每请求计算秒数，也可能因形状不合适获益很少 |
| 本层读取与计算同步 | $R_{\mathcal B\ell}=\max_i R_{i\ell}$，整批计算完成 | 短请求可能被大读取或长计算绑定 |
| 全局读取节奏 | $V_{\mathcal B\ell}$ 与 $A_{\mathcal B\ell}$ | 大批可能产生突发竞争，也可能以更长计算窗口掩盖下一层读取 |

batch 的读取时间既不天然等于所有请求读取时间之和，也不天然等于最长单请求的独占读取时间。它取决于并行度和实际带宽分配，最终由数据积分与同步边界决定。

一个“读多、算少”的请求与一个“读少、算多”的请求合批，有可能拉长计算窗口、隐藏后续层 I/O，也可能使后者等待前者的启动读取。混合组批、同类组批都需要比较，不能只凭长短分类选择。

### 6.2 区分完整 prefill 批与 chunk 批

完整 prefill 批将成员绑定到最后一层。chunk 批只绑定一个执行块，块完成后允许重新组批，可降低长请求对短请求的连续阻塞，但增加调度频率，可能损失计算效率，并改变 KV 的读取次数。

Sarathi-Serve 用 chunk 大小控制执行迭代的时延，并讨论分块开销，支持“批粒度需要按成本权衡”的研究方向。不过论文中的 stall-free 指避免正在生成的请求被新 prefill 暂停，不能用这个词证明本文的存储 I/O STALL 已被消除。[Sarathi-Serve，§4](https://arxiv.org/html/2403.02310v1#S4)

首轮仿真建议先固定完整 prefill 批，比较单请求、同类组批、混合组批和全局预测组批。确认全局竞争机制后，再加入 chunk 作为独立能力实验，避免同时改变读取生命周期与调度策略。

## 7. 四长四短请求的完整算例

### 7.1 参数和所有策略共同遵守的规则

八个请求在 $t=0$ 到达，分别为 $L_1$ 至 $L_4$、$S_1$ 至 $S_4$。两个同构单 NPU 实例共享一条 4 GB/s 的存储瓶颈。用两层模型缩短时间线。

| 请求类型 | 数量 | 每请求每层读取 | 每请求每层计算 | 单请求独占时参考 TTFT |
|---|---|---|---|---|
| 长请求 L | 4 | 4 GB | 2 s | $1+\max(1,2)+2=5$ s |
| 短请求 S | 4 | 1 GB | 1 s | $0.25+\max(0.25,1)+1=2.25$ s |

“长”在本例同时表示读取量和计算量较大。正式实验应独立改变这两个量，覆盖长前缀但剩余计算很少的请求。

最大 batch 为 2，计算时间为成员时间之和。因此 LL 每层读 8 GB、算 4 s；SS 每层读 2 GB、算 2 s；LS 每层读 5 GB、算 3 s。这里刻意没有设置 batch 计算加速，用来隔离组批同步与全局竞争，不能据此得出真实引擎应始终 batch=1。

每个活动批按层聚合为一个读取流。除单独说明的存储策略外，带宽在活跃批流之间公平共享。只有一个流时独占 4 GB/s，两个流时各得 2 GB/s；读取完成立即重分配。每个实例前一批完成后才能开始下一批，批间没有预取；本批第一层计算开始时发起第二层读取。

采用 $s_i=3T_i^0$，长请求截止时间为 15 s，短请求为 6.75 s，恰好到截止时间算满足。没有控制时延、拒绝或重算。全体读取量固定为 40 GB，全体有效计算时间固定为 24 NPU·s。

### 7.2 第一层派发与第二层执行计划

所有计划都让实例 1 接收 $L_1,L_2,S_1,S_2$，实例 2 接收 $L_3,L_4,S_3,S_4$。两边请求数、总读取量和计算工作量完全相同，因而排除了静态负载不均的解释。

| 计划 | 实例 1 的执行顺序 | 实例 2 的执行顺序 | 存储策略 |
|---|---|---|---|
| A 混合组批 | $(L_1,S_1)\to(L_2,S_2)$ | $(L_3,S_3)\to(L_4,S_4)$ | 活跃批公平共享 |
| B 同类短批优先 | $(S_1,S_2)\to(L_1,L_2)$ | $(S_3,S_4)\to(L_3,L_4)$ | 活跃批公平共享 |
| C 两实例错开长短 | $(L_1,L_2)\to(S_1,S_2)$ | $(S_3,S_4)\to(L_3,L_4)$ | 活跃批公平共享 |
| D 仅改变第三层 | 与 B 相同 | 与 B 相同 | 每次将全部带宽给每层总读量较小的活动批，平局选实例 1 |
| E 单请求短优先 | $S_1\to S_2\to L_1\to L_2$ | $S_3\to S_4\to L_3\to L_4$ | 活跃批公平共享 |

D 在每次流发起或完成时重新选择，允许暂停低优先级流，当前优先批读取完成后立即服务其他流。D 是展示第三层影响的可复现对照，没有宣称它是 SLO 最优策略。全部计划都遵守相同最大 batch 能力，E 主动选择 batch=1。

### 7.3 从 B 到 C，只改变一个实例就影响另一实例

B 中两个实例同时读 SS，每层各 2 GB，两个流各得 2 GB/s。第一层在 1 s 读完，计算为 1 至 3 s；第二层在 1 至 2 s 读完，计算为 3 至 5 s。四个短请求均在 5 s 完成。

随后两个实例同时读 LL，每层各 8 GB。第一层在 5 至 9 s 读取，计算为 9 至 13 s；第二层在 9 至 13 s 读取，计算为 13 至 17 s。四个长请求均在 17 s 完成。

C 只将实例 1 改成长批先执行。实例 2 的顺序与成员完全没变，但它的长批第一层读取从 B 中的 5 至 9 s 变为 5 至 7 s，长请求由 17 s 提前到 15 s。

|---|---|---|---|
| 0 至 1 | LL 第一层与 SS 第一层各 2 GB/s | 等 LL 第一层 | 等 SS 第一层 |
| 1 至 2 | LL 第一层与 SS 第二层各 2 GB/s | 继续等 LL 第一层 | 计算 SS 第一层，下一层读取重叠 |
| 2 至 3 | LL 第一层独占 4 GB/s，补完剩余 4 GB | 等至 3 s | 继续计算 SS 第一层 |
| 3 至 5 | LL 第二层独占 4 GB/s | 计算 LL 第一层，下一层读取重叠 | 计算 SS 第二层，5 s 完成两个 S |
| 5 至 7 | 实例 2 的 LL 第一层独占 4 GB/s | 继续计算 LL 第一层 | 新长批开始，等待第一层 |
| 7 至 9 | 实例 2 的 LL 第二层独占 4 GB/s | 计算 LL 第二层 | 计算 LL 第一层，下一层读取重叠 |
| 9 至 11 | 无合法待传数据 | 继续计算 LL 第二层，11 s 完成两个 L | 继续计算 LL 第一层 |
| 11 至 11.5 | 实例 1 的 SS 第一层独占 4 GB/s | 新短批开始，等待第一层 | 计算 LL 第二层 |
| 11.5 至 12 | 实例 1 的 SS 第二层独占 4 GB/s | 计算 SS 第一层，下一层读取重叠 | 继续计算 LL 第二层 |
| 12 至 13.5 | 无合法待传数据 | 继续计算 SS 第一层 | 继续计算 LL 第二层 |
| 13.5 至 15 | 无合法待传数据 | 计算 SS 第二层 | 继续计算 LL 第二层，15 s 完成两个 L |
| 15 至 15.5 | 无合法待传数据 | 继续计算 SS 第二层，15.5 s 完成两个 S | 无任务 |

C 中存储在有合法待传数据的时段均用满 4 GB/s，总共传输 40 GB，占用链路 10 s。9 至 11 s 的空闲符合执行规则，两个下一批都尚未开始，不能偷偷预取它们。

### 7.5 这个例子支持哪些结论

B 与 C 展示了全局竞争。一个实例调换顺序，另一个实例的服务时间也变化。C 缩短全部完成时间并增加按时请求数，同时让实例 1 的短请求等得更久，平均及归一化 TTFT 都比 B 差。

B 与 D 展示了目标冲突。D 提高满足率并降低平均 TTFT，但推迟最后完成时间，造成更长的尾部无任务时间。它的 STALL 比 B 少，计算利用率却更低，所以只看 STALL 容易误判。

A 与 E 展示了批绑定。没有计算加速时，把短请求绑进大批可能只增加等待。真实 batch 若有足够计算收益，这个结论可能反转，反转阈值正是需要测量的内容。

本例给出五个可行计划，并未穷举所有路由、组批和带宽分配。C 的 15.5 s 不能称为全局最优值，E 的平均 TTFT 也不能称为最小值。请求同时到达、层数很少、参数确定，这些限制决定了它适合验证因果与公式，不足以证明在线策略普遍有效。

本例所有计划的第二层读取都被第一层计算掩盖，表中的 I/O STALL 全部来自每个新批的第一层读取。即便层间 overlap 已经充分，启动读取与批间切换仍会影响全局利用率。正式实验还要增加“每层读量更大、计算更短”的组合，专门检验下一层数据来不及就绪时的带宽分配。

## 8. 仿真实验应得到什么未知结论

### 8.1 需要检验的研究问题

| 问题 | 关键控制变量 | 有价值的结果 | 可以否定什么 |
|---|---|---|---|
| 全局信息值多少钱 | 共享带宽、实例数、请求读算比，在相同动作空间下比较局部与全局预测 | 全局策略收益出现和消失的边界，以及局部选择损害其他实例的比例 | 若强局部策略几乎一样好，则没有必要上复杂全局控制 |
| 最值得改的是哪一层 | 路由、引擎、存储三层分别开关 | 单层收益、层间互补或重复，以及额外控制成本 | 若存储层已吸收收益，上层复杂策略可能不值得实现 |
| 何时应该同类组批或混合组批 | batch 计算加速、读量与计算量相关性、到达稀疏程度 | 计算加速何时抵消同步等待；最佳批形状如何随带宽变化 | 否定固定“短优先”或“混合一定互补”的结论 |
| 是否值得限制活动实例数 | 带宽、读取启动成本、SLO 紧度、准入并发 | 并发增加何时提高容量、何时只增加 STALL；是否存在中间最优点 | 若始终充分并发最优，可删去复杂准入控制 |
| SLO 优化与平均时延相差多大 | 固定 SLO 与倍数 SLO、紧度、长短比例 | 满足率与两种均值的取舍曲线，受益和受损请求类型 | 否定用平均 TTFT 代替 SLO 结果的做法 |
| 改派是否还有独立价值 | 初始路由误差、控制时延、状态更新周期 | 相对 work stealing 和晚绑定队列的净收益及失败条件 | 若晚绑定已足够，则改派机制可简化 |
| 观测多精确才值得用 | 报价延迟、噪声、负载变化速度 | 误差增大到何种程度后不如简单基线，是否出现同步振荡 | 否定理想真值收益可以直接落地的假设 |
| 开环结果能否解释闭环 | 固定到达率与固定客户端数分别测量 | 归因于等待缩短、计算效率变化还是反馈到达率变化 | 否定把闭环吞吐增长解释为物理带宽容量增长 |

研究结论应包含“什么时候不值得做”。如果结果显示，只要通过晚绑定和简单带宽公平就能接近全局参考策略，这同样能够明确实现方向。

### 8.2 对照策略必须具有明确语义

下面给出可独立实现的基础对照，不把它们包装成某个实际系统的完整复现。

| 位置 | 基线或对照 | 决策语义 |
|---|---|---|
| 路由 | 均匀派发 | 轮询或最少请求数，固定平局规则 |
| 路由 | 计算负载感知 | 选择剩余计算工作最少的实例 |
| 路由 | 名义服务时间感知 | 固定基准带宽与当前队列估计完成时间 |
| 路由 | 存储观测感知 | 使用可观测报价预测派发后服务，显式重算共享竞争 |
| 路由 | work stealing / 全局晚绑定 | 分别作为纠正早派发和避免早派发的强对照 |
| 引擎 | FCFS | 按原到达顺序选候选请求，固定批预算 |
| 引擎 | 前缀长度优先 | 按命中长度排序，检验大量可复用 KV 在受限带宽下是否仍值得优先 |
| 引擎 | 短服务优先 | 按固定无争用服务估计排序 |
| 引擎 | 截止时间或剩余预算优先 | 分别使用 $d_i$ 或 $d_i-t-\widehat T_i^{\mathrm{remaining}}$ |
| 引擎 | 全局候选批预测 | 对少量候选顺序、batch、开始时刻评估全局目标 |
| 存储 | 公平服务 | 在固定服务粒度上等分可用带宽 |
| 存储 | 读取大小或截止时间优先 | 分别检验纯 I/O 信息与请求时限信息 |
| 存储 | 计算依赖感知 | 使用消费时刻、批同步依赖及选定全局目标分配 |

所有 worker 命中相同的全局 KV 时，单纯的 worker 缓存命中偏好无法区分候选实例，但不同请求的命中量仍影响读量与剩余计算。不能把这两种“缓存感知”混为一谈。

普通上层策略只读存储的可观测报价与反馈。带宽真值、背景负载内部队列和假想服务结果仅供仿真资源模型或明确标注的 Oracle 对照使用。第三层服务执行器维护自身资源状态是实现职责；若研究其中的可部署决策，也须规定它能获取哪些实际可采集的状态，不能将整个仿真未来交给它。

### 8.3 先比较能力，再比较信息

固定无预取和一层 lookahead，先用路由 R、引擎 E、存储 S 的 $2^3$ 组合做三层消融。每一层“关闭”代表对应的固定基础策略，“开启”代表同一套候选能力下的感知策略。单独比较 batch=1 与允许 batch=2、禁止与允许改派时，应标注为能力消融。

在选定能力组合内，再比较固定带宽估计、历史观测、实时观测和 Oracle。普通策略与 Oracle 共享候选动作，差别仅为信息；具有未来全部 trace 的离线搜索要另列，不能混称实时 Oracle。

只更改一个实例顺序时，记录其他实例的完成时间变化。三层组合收益也不能简单相加，比较联合收益与各单层收益的差额，才能判断层间互补还是重复。

### 8.4 最小实验矩阵与运行顺序

1. **解析与小规模验证。** 复现第 7 节全部时间线。检查字节守恒、设备时间守恒、计算依赖、无排队预取及唯一所有者。对缩小后的有限状态与明确离散动作空间做穷举，得到该空间的最优值。连续带宽分配若未被求解，只能称离散参考值。
2. **稳态边界。** 固定请求分布，扫描共享带宽和到达率。既看平均负载比 $\rho_{\mathrm{io}}=\lambda\mathbb E[V_i]/B$、$\rho_{\mathrm{compute}}=\lambda\mathbb E[K_i]/W$，也看逐层需求峰值。均值小于 1 只是基础稳定条件，不能保证无突发等待或满足 SLO。$K_i$ 随组批改变时按实际批执行归因统计。
3. **批与顺序。** 用独立的读量、计算量分布构造正相关、负相关和无相关场景，扫描批计算加速与 batch 预算。找同类批、混合批、单请求执行的胜负分界。
4. **动态与信息误差。** 引入分段常数带宽变化、突发到达、报价滞后和改派开销，观察控制振荡及对其他实例的损害。再扩展到多分片和不同路径。
5. **闭环与 SLO 敏感性。** 固定客户端数扫描思考时间，同时扫描固定和倍数 SLO。分别给出容量、满足率、平均 TTFT、平均归一化 TTFT 的取舍。

同一场景共享请求 trace 和随机种子。先做少量种子的冒烟，确保存在 SLO 全满足、部分满足和几乎不满足三个区域，再做多种子正式实验。调参只使用训练场景或种子，结论用独立场景或种子验证，报告配对差值及不确定性。

长期实验选定一个到达请求 cohort，停止计入新请求后排空该 cohort，避免只统计较早完成的短请求。吞吐与设备占比另外按统一稳态时间窗统计，并记录窗口前后的积压。过载实验若无法排空，明确超时和截断请求数量，不能把幸存完成请求的均值当作全部请求的均值。

### 8.5 每组实验应交付的证据

| 结论类型 | 必须配套的证据 |
|---|---|
| 容量提高 | 相同请求分布下的稳定容量曲线，队列随时间变化，Compute/STALL/Idle 分解 |
| SLO 改善 | 随 SLO 紧度变化的满足率曲线，长短请求分组、失败或拒绝计数 |
| 平均时延改善 | TTFT 与归一化 TTFT 的分布，长短分组及尾部变化 |
| 全局协同有效 | 本地动作对其他实例的影响分布，层间三因素消融，公平服务与依赖感知服务对照 |
| 组批有效 | 实测或校准的批计算加速表、组批等待、读取同步等待和吞吐变化 |
| 策略可以落地 | 相对强简单基线的净收益、决策耗时、观测误差与更新频率的容忍边界 |

这些证据应回答，系统在哪些负载和信息条件下值得采用哪一层策略，以及为一个目标付出了多少其他目标的代价。单独观察“带宽更大所以更快”或“短请求先执行所以短请求更快”，不足以作为三层协同调度的研究结论。
