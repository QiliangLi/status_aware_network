## 0. 背景与问题定义

E26f（含 max_min 重跑）确立了三件事：① 零读类的"排队死/免费填充"二象性；② 瓶颈翻转后带宽感知调度收益不收窄；③ TFS 以 MPC 0.1% 的计算时间捕获其 91~95% 收益。但负载是**合成的三类格点**（A 簇 k=16 / B 泊松 / C 零读，形状离散、到达构成恒定）。`docs/TFS收益场景与真实trace比重-20261015.md` 已用默认画像（synthetic-v1，L=32）分析过真实 trace 的收益前提，结论"大门没开（B*≤5 GB/s ≪ 供给 80~120），但结构前提都在"，并留下五条局限：默认画像外推、AgentX 全量未做、加压回放下捕获率未验证、计算饱和未触发、到达侧上界代理不建模排队。

本实验回答四个问题：

1. **集群规模怎么定**（前置问题）：给定真实 trace 的到达节奏与 GLM5+D950PR 画像，多少张卡（m）与多少存储带宽（B）构成"有研究价值的集群"——既不落 goodput 天花板（AGENTS §5），也不是全崩塌？
2. **Mooncake 怎么接**：单文件即全集群请求流（真实全局时间戳、3s 级到达组、簇占比高），直接可用既有 `MooncakeSource`，但画像与集群口径要换代。
3. **AgentX 怎么接**：2090 个会话各自相对计时（毫秒、会话内间隔 p50=11.4s）、64 token 块、`prefix_hit_tokens` 为会话内理想命中口径——需要**会话偏移**构造全局到达节奏，这是新的负载构造机制。
4. **TFS 的收益区间在哪**：在 (m, B) 扫描面上，tfs/mpc 相对 fcfs 的收益如何随两侧资源密度变化？`tfs_trace_gain` 的"ρ≥0.7 分诊区开门"预期能否在**真排队动态**（而非到达侧上界代理）下兑现？

## 2. 计算画像：GLM5+D950PR roofline 接入（替换 synthetic-v1）

### 2.1 来源与口径

单请求每层计算时间与每层 KV 加载量全部取自 `prefill_time/prefill_time_single.py::per_request(input_length, u_tokens)`（系数与 F1–F11 修正的来源、验证见 `docs/prefill_time计算时间仿真合理性验证-20261021.md`）。要点：

- 模型 GLM5：78 层、kv_lora 512 + rope 64 + index 128 → **KV=1408 B/token/层**（FP16）；
- 语义：bs=1（每卡 1 请求、dp=ep=32）满载 32 并发口径——与 cq 引擎 `n_max=1`（E26f 同款）语义一致；
- **绝对值是 kernel 级 roofline 下界，真实生产约再乘 2~3**。定标出的集群绝对规模按下界口径给出并披露区间；调度收益为相对比较，不受该因子影响（T0、c、期限同口径缩放）。

### 2.2 宏层折叠（L_agg=8）与查表 profile

真实 78 层直接进引擎会使事件数×~10（MPC 成本不可承受），沿用 E26 系"虚拟折叠层"：

```text
c_macro(h,u) = 78 × per_layer_us(h+u, u) × 1e-6 / L_agg        # 每宏层计算
κ_macro      = 1408 B/token/层 × 78 / 8 = 13,728 B/token/宏层   # V_macro = κ_macro × h
d = V/C 折叠不变（分子分母同除 L_agg）
```

总量守恒：Σc_macro×L_agg = 78×per_layer_us（总计算）、ΣV_macro×L_agg = 1408×h×78（总读取）。T0 的 singleton 解析式（首层读 + L·c + 逐层遮蔽）在宏层口径下自洽。

**c 查表机制（最小引擎改动）**：synthetic-v1 的 c 公式 `t_launch + aN/η + bA` 是两点标定的解析形，无法在 trace 的连续 (h,u) 分布上全局命中 roofline。改为 `ProfileConfig` 增加可选 `c_table: Dict[(h,u) → c 秒]`（默认 None=现行为不变）：

- `batch_compute_s` 优先查表；`n_max=1` 下批恒为 singleton，键 `(h,u)` 必然命中（表在装载 trace 时按每请求 (h,u) 预生成）；
- 表缺失键 → `ValueError`（宁可炸也不静默回退公式）；
- η/N_sat/a/b/t_launch 在查表模式下不参与真值（L5 的"c 估计误差"研究口径留给未来：本实验 c 仍为引擎真值）；
- κ、mem 公式不动（`layer_read_gb` 继续走 κ_macro）。

### 2.3 与 E23/E26f 画像的关系

- E23 用默认 synthetic-v1（L=32、κ=4096B、a/b 默认）跑 Mooncake——E29 换 GLM5 画像后 B*、d 分布全部复算（§3 预计算表即复算结果），不与 E23 数字混用；
- E26f 的 (c_A=6.02ms, V_A=175.6MB) 是用户给定格点——E29 不再用固定格点，(h,u) 连续分布即负载。

## 3. 集群规模定标（问题一的方法与预计算）

### 3.1 定标框架：双资源密度

给定 trace（到达率 λ、每请求读取 V_total=1408B×h×78、纯计算 C_total=78×per_layer_us），集群 (m, B) 的资源密度：

```text
ρ_cal = λ · E[C_total] / m     （计算密度：NPU 需求/供给）
ρ_bw  = λ · E[V_total] / B     （带宽密度：GB/s 需求/供给）
```

λ 缩放（E23 的 `scaled_arrivals`）同时放大两个 ρ（束约束），**独立扫 (m,B) 才是在 (ρ_cal, ρ_bw) 平面扫描**——这正是"集群规模确定"的本质：trace 给定需求束，集群配置决定落点。

**基准点判据（写死）**：ρ_cal\*=ρ_bw\*=0.8。理由：① AGENTS §5 要求不落 goodput 天花板（ρ≪1 时所有策略全活，无区分度——`tfs_trace_gain` 已实测原始节奏收益≈0）；② 0.8 双资源同临界的点调度区分度最大（E26 系的 ρ=0.9 格点同哲学）；③ 深度过载区（ρ≥1.6）由扫描档覆盖。

**m 的物理锚**：m\*=32（D950PR 整机 32 卡、prefill_time 的 dp=ep=32 口径、E26 系 m=32 传统）。带宽/卡比 r=B/m 只作 sanity（D950PR 单卡 storage_bw=350 GB/s 为上界；E26 的 r=120/32=3.75，本实验 AgentX 档 r 最大 ≈21，均在界内）。

| agentx | 23.1/s | （λ_sess≈0.49/s，稳态并发会话 S≈557） | 682 GB/s | 21.3 | **A 型重读主导**（d p50 37）；零读 7.4%；会话束簇 |

（conversation 5.78×/19.7s⁻¹/12.2GB/s 备而不跑，见 §5 成本；Mooncake λ' 由 `scaled_arrivals` 时间轴压缩实现、保留同刻 burst；AgentX λ' 由会话泊松偏移实现，λ_sess 与稳态并发 S 由 Little's law：λ_req≈S×E[请求/会话]/E[净活跃时长]。）

**窗峰 sanity**：toolagent 放大 6× 后 1s 窗峰 ≈216 GB/s（B\*=27 的 8 倍瞬时限幅）——分诊区大门常开，错峰对象充足；AgentX 单请求 V p90=60GB 在 B\*=682 下首宏层（7.5GB）载 11ms，不产生"单请求吃满全带宽"的病态。

**roofline 下界的 ×2~3 不定性传导**：若真实计算时间为下界 2.4×，则同 trace 的 m\* 变为 ≈77 卡（B\* 不变——V 是精确字节量不受该因子影响，但 λ' 随定标变化）。集群绝对规模结论以区间表述：**32 卡机承载 6~14× 放大的 toolagent 流量**（6×@下界、14×@2.4× 时反解），收益区间结论不受影响。

## 4. 负载构造

### 4.1 Mooncake：放大回放（沿用 E23 骨架，三处换代）

`MooncakeSource` 骨架保留（派生导入、窗口等切），E29 侧参数化重构：

1. **画像**：`ProfileConfig(c_table=..., kappa=13728B, L=8)`（§2）；
2. **窗口**：不再固定 20 等分块，取**峰值窗**——全量 λ 缩放后，以 1s 滑窗读速率最高的时刻为中心取 N_WIN 条（默认 600，`E29_TOTAL` 兜底缩放）；避开冷启动（前 5% 时刻）与尾部（drain 段混入不完整簇）；
3. **规模**：m=32、B 按 §3.3 格点；`q_max=200`、`b_ref=B`（T0 参考带宽=场景带宽，E26 口径）沿 [0,B) 常带宽。

### 4.2 AgentX：会话偏移回放（新机制）

```python
class AgentXSource:
    # 流式读全量 jsonl；按 session_id 分组；每会话保留 (ts_ms, il, prefix_hit)
    #   逐行导入校验（64 token 块）：len(hash_ids) == ceil(il/64)；
    #   prefix_hit_tokens <= ceil(il/64)*64（尾块整块计入，可 >= il → 全命中分支）
    #   hash_ids 不加载（块内容只用于校验比例；命中判定已由转换脚本按 64 块完成）
    # 构造（CRN：seed 冻结，同格点全臂同一份偏移）：
    #   会话起点 offset_s ~ Exp(1/λ_sess)，按会话编号顺序抽（PCG64(seed)）
    #   请求全局到达 = offset_s + ts_ms/1000   （会话内相对时序原样，不压缩）
    #   u = max(1, il - prefix_hit)；h = il - u
    #   截断 [0, D_cap] 到达的请求（D_cap 由 N_WIN 反解），drain 预算同 Mooncake
```

设计决策与理由：

- **会话起点泊松**而非均匀散布：保留"多用户编程 agent 并发"的到达随机性；会话内间隔（p50 11.4s）原样保留，会话束即天然"簇"（§5 簇冲击统计的对象）；
- **不压缩会话内长空隙**（p99 26min）：压缩会虚构不存在的到达密度；代价是窗内负载低于"净活跃"口径——λ_sess 的反解用**净活跃时长**（mean 1141s）而非跨度，即稳态下 S 个会话都在活跃期（长空隙会话被 D_cap 截断自然淘汰）；
- **hit 用行内 `prefix_hit_tokens`**：会话内理想口径（无限容量、按内容寻址）是上界；LRU 有限容量下命中率更低 → 真实 u 更大、V 更小。本实验不仿真缓存（超范围），局限披露（§11）；
- **不经过 `cq_derive_hits`**：该工具的 D1~D7 是全局首现口径，AgentX 的 hash 跨会话本就无共享，会话内口径即等价于全局口径，重跑只是浪费 3GB 扫描。

### 4.3 分类口径（统计分组，不进策略）

请求保持真实连续 (h,u)；结果文档按三分组统计（着色/分类 SLO）：

- **C 类**：h=0（零读）——synthetic 55.4%、AgentX 7.4%、conv/toolagent 0.1%；
- **A 类**：d ≥ 窗口全量 d 的 P75（离线分析口径；TFS 在线门槛是策略自己的累计 P75，两者独立——L3 的"切口任意"正是要观察的对象）；
- **B 类**：其余。

E26f 的"A 簇洪水/B 泊松/C 零读"结构在真实 trace 的对应物：Mooncake 簇（同刻组）≈A 簇洪水的天然形态；AgentX 会话束 ≈ 长生命周期簇。

## 5. 实验矩阵与成本

### 5.1 主矩阵（E29b：收益区间扫描）

| 维度 | 取值 |
|---|---|
| trace | toolagent / synthetic / agentx（conversation 备而不跑） |
| 格点 (m,B) | 基准 (m\*,B\*) 的 m∈{16, 32, 64} × B∈{0.5, 1, 2}×B\* → **9 格点/trace**（即 ρ_cal∈{1.6, 0.8, 0.4} × ρ_bw∈{1.6, 0.8, 0.4}） |
| 臂 | 基准格点（m=32,B\*）全 6 臂：`fcfs / edf / localS_v2.1 / mpcS_v2.1 / mpcT_v2.1 / tfs`；非基准格点 3 臂：`fcfs / edf / tfs` |
| 引擎口径 | base=bw_edf、composer=True、budget_s=3600、max_events=40000（600 条×8 层事件≈9k，放宽保险）、H=1、MPC_PAR=6；alloc=**max_min**（20261018 后语义，E26f 重跑母本） |
| α / seed | α=4；默认 1 seed；补测规则：格点内 (tfs−fcfs) 或 (mpcS−fcfs) 总 SLO 差 <5pp 时补 2 seed 取中位 |

规模：3 trace × (1×6 + 8×3) = **90 臂位**；其中 MPC 类 6 run（3 基准格点 × mpcS/mpcT）+ local 3 run。窗口 N_WIN=600（E26f 360 的 1.7 倍；`E29_TOTAL` 兜底）。

### 5.2 成本估算

按 E26f max_min 重跑实测外推（600 条 vs 360 条、决策点 ~×1.7）：

- fcfs/edf/tfs：秒~分钟级（tfs 0.11ms/决策 × ~6k 决策 ≈ 1s 量级）；
- local：~10~60 min/run ×3；
- mpcS：~1~3h/run、mpcT ~0.5~1.5h/run（max_min 下事件塌缩红利延续）×6；
- **合计 MPC+local ≈ 10~20h（两路 MPC_PAR=6 并行过夜）**，其余臂 <1h。

### 5.3 冒烟（AGENTS §5，全量前强制）

- 规模：每 trace 基准格点 × {fcfs, tfs}，N_WIN=200；
- 检查：①FCFS 总 SLO∈[20%, 80%]（不天花板不崩塌——ρ\*=0.8 的预期落点）；②分诊区开门：带宽饱和占比 ≥30%（max_min 口径实际线贴近 B）；③簇/会话束形态在甘特可见；④AgentX 的 515s 极端长请求是否把 makespan 拖到 drain 预算外（若是 → 该请求保留但 drain_budget 放宽到 900s 并披露）；⑤**AgentX 会话多轮结构是否被短窗稀释**：600 条窗约 26s，稳态下 557 个活跃会话每会话仅贡献 ~1 条（间隔 p50=11.4s > 窗长一半）——统计窗内每会话请求数分布，若 p50=1 则 N_WIN 加倍至 1200 或 λ_sess 减半（S≈280，负载由 m=32 改 16 保持 ρ_cal，披露口径变化）。

## 6. 预注册假设

- **H1（分诊区大门）**：固定 m=32 沿 B 扫描，tfs−fcfs 总 SLO 随 ρ_bw 单调不减；ρ_bw≤0.4（B=2B\*）时 |tfs−fcfs|<2pp；ρ_bw≥1.6（B=0.5B\*）时 tfs−fcfs ≥ +8pp（toolagent 与 agentx 分别判定）。
- **H2（零读二象性在真实 trace 复现）**：含 C 类 ≥5% 的格点（synthetic 全部、agentx 全部）上，tfs 的 C-SLO ≥95% 且 FCFS 的 C-SLO <100%；两者差距 ≥20pp。
- **H3（计算侧深饱和）**：m=16（ρ_cal=1.6）格点上 tfs−fcfs 不收窄为负（E26f cB"收益不收窄"的深度版；若 FCFS 与 tfs 同入崩塌区差距→0，如实记录）。
- **H4（TFS 捕获率）**：3 个基准格点上 capture=(tfs−fcfs)/(mpcS−fcfs) ≥80%（`tfs_trace_gain` §5"未验证"项的兑现；同时记录 local——max_min 下 local 评分失配是否在真实 trace 复现 E26f 重跑的崩塌形态）。
- **H5（L3/L9 稳健性）**：连续 d 分布下 TFS 无失稳：门槛轨迹无振荡（相邻决策 P75 变化 <50%）、无饥饿（B/C 类 TTFT p99 ≤ 3×期限中位）、决策数 <30×fcfs（L8 上界口径）。
- 备用旋钮（H1 不达时先冒烟再入矩阵）：B 档加密到 {0.25,0.375,0.75,1.5}×B\*，或 N_WIN 降到 400。

## 11. 局限

1. **roofline 下界口径**：绝对集群规模（卡数/带宽）有 ×2~3 不定性（§3.3 区间表述）；相对收益与收益区间形状不受影响。
2. **宏层折叠 L_agg=8**：78 层真实读写交错粒度更细（更细交错=更多错峰机会=对 TFS 偏保守）；E26 系既有简化，粒度敏感性未扫。
3. **AgentX 全局节奏是合成的**（会话起点泊松）：真实多用户到达未知；会话内空隙未压缩 → 窗内负载低于净活跃口径的下偏；命中为无限容量理想上界（LRU 下 u 更大 V 更小，负载形态向计算侧漂移）。
4. **decode 未建模**：TTFT 口径，output_length 忽略（Mooncake 输出占比高，真实系统 decode 侧带宽/算力占用未计入——集群规模略偏小）。
5. m 档位粗（{16,32,64}），ρ_cal 轴分辨率 2×；B 轴同。
6. 单 1h Mooncake trace 的时变代表性（峰窗选择缓解但不消除）；AgentX 515s 极端长请求的 makespan 效应按 §5.3-④ 处理并披露。
7. MPC 成本仍高：非基准格点无 mpc/local 臂，捕获率（H4）只在基准格点可算——收益热图上 mpc 等值线是外推缺席的，读图时注意 tfs−fcfs 才是全平面量。
