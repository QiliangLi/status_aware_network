## 问题⑥：引擎能力 × 存储侧控制的交互未度量

### 问题定位

E10/E11 的未达标验收共同暗示：joint2 引擎的动态逃逸（重算/部分取回）"自稳"了存储压力，
压缩了存储侧控制（预取/复制/分层）的边际收益。但这是推断——引擎能力从未作为实验自变量。

### 方案（E13）

2×2 因子实验：引擎 {static2（无逃逸能力）, joint2（有逃逸）} × 控制器 {none, predictive 复制}，
场景沿用 E8（热点类单副本 + GPU 稠忙）。**假设 H6**：控制器收益在 static 引擎下显著大于
joint 引擎下（交互效应为正）；若成立，"何时需要存储侧控制"的回答是"引擎越弱越需要"。

### 验收标准

- 给出 2×2 全表（goodput / 热点类 SLO 率）与交互效应的符号及量级；
- 结论明确回答："部署存储侧控制的前置条件是引擎自稳水平低于 X"中的 X 以量化形式给出。

## 问题⑦：全局分配的价值未在容量约束下检验

### 问题定位

E9b 在 burst 场景证明先知 ≈ 逐请求贪心；但该场景资源平行、无容量/副本约束。
先知的理论优势（预知未来需求 → 预留容量）应在 E11 类"容量受限 + 热度漂移"场景复检。

### 方案（E14）

E11 场景（容量受限、6 类、漂移、无控制器），策略 {joint2, oracle2, clairvoyant2}。
**假设 H7**：容量约束下 clairvoyant > oracle（未来视线有真实价值）。

### 验收标准

- 三策略 goodput/P95 全表 + clairvoyant−oracle 差的符号与显著性（种子中位数的 IQR 不重叠）；
- 若 H7 被推翻，给出与 E9b 一致的结构性解释。

## 问题⑧：预取浪费率高，缺会话预测

### 问题定位

gated 预取只看发起时刻压力，不看"下一轮会不会来"。会话型负载中快会话（轮间隔 ~0.6s）
预取几乎必被用到，慢会话（间隔 ~8s）预取大概率被淘汰。

### 方案（E15）

1. 负载：混合速度会话（每会话以 50% 概率取快/慢轮间隔），浪费率才有区分度。
2. `PrefetchConfig.mode="predictive"`：在压力门控之上增加**类级轮间隔 EMA 条件**——
   `gap_ema(cls) < horizon`（该类最近一轮间隔短于预取 horizon）才预取。
3. 变体：none / gated / predictive（均不带回写，隔离变量）。
   **假设 H8**：predictive 的浪费率显著低于 gated，goodput 不降。

### 验收标准

- waste_frac：predictive ≤ 0.5 × gated；
- goodput：predictive ≥ gated − 1%。

## 问题⑨：参数现实性未经核查

### 问题定位（本轮已联网核查，来源见 §参数来源）

| 参数 | 我们的占位值 | 公开实测区间 | 判定 |
|---|---|---|---|
| prefill 32K (70B 级) | 0.205 s | H100 单机 0.2–0.4 s | ✅ 现实 |
| mem tier 带宽 | 40–60 GB/s | DRAM 池节点 50–100+ GB/s | ✅ 现实 |
| ssd tier 带宽 | 15–25 GB/s | LMCache 实测读峰 13–27 GB/s | ✅ 现实 |
| fabric 带宽 | 120 GB/s | Mooncake 87 GB/s（4×200Gb RoCE）/ 190 GB/s（8×400Gb） | ✅ 区间内 |
| path_lat | 2–8 ms | RDMA 机房内 RTT ~0.01–0.1 ms 量级 | ⚠️ 偏保守（高估） |

### 方案（E16）

不用等硬件：用检索到的**慢/快两个现实档位**做敏感性核查——
slow profile（ssd 13 GB/s、fabric 87 GB/s、path_lat 减半）与 fast profile（fabric 190 GB/s），
E7 式拥塞场景跑 {alwaysfetch2, static2, cascade2, joint2, oracle2}。
**假设 H9**：策略排序在两个档位下不变（结论对参数档位稳健）。

### 验收标准

- 两个档位下 joint2 相对 cascade2/static2 的优势方向与量级区间给出；
- path_lat 高估的影响单独说明（其对估计项是加性小项）。
